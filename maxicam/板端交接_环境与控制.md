# 板端交接：环境、控制方式、不能动的文件、算力瓶颈

> **给谁看**：接手这块板子做「接摄像头 + 跑去摩尔纹网络」的另一个 agent。
> **写法**：凡是有数字的都给运行点；凡是"不能动"的都给了验法；凡是没验证的都不写成结论。
> **一句话现状**：位流 v39 可用、基线 ~**6.0 s/帧**（256²，150 MHz）、摄像头**尚未接入**（USB host 未启用、无 `/dev/video*`、板子无外网）。

## 2. 控制方式（四条铁律）

### 2.1 所有板端命令必须走 `tools/boardlock.sh`
```bash
tools/boardlock.sh ssh -o BatchMode=yes xilinx@192.168.7.2 '<命令>'
```
它做三件事：**ping 前置**（不通直接 exit 7）→ **全局 flock**（跨 agent 互斥）→ **唯一 load 令牌**。
为什么需要：曾经两个 agent 同时上板 + 连续三次 `Overlay(download=True)` ⇒ 板子硬挂。

### 2.2 一个 boot 只允许一次真正的 overlay 下载
```bash
# 加载前清残留，否则 PYNQ 以为已加载
sudo rm -f /usr/local/share/pynq-venv/lib/python3.10/site-packages/pynq/pl_server/global_pl_state_.json

# 第一次：BOARD_ALLOW_LOAD=1（发令牌）
BOARD_ALLOW_LOAD=1 BOARD_TAG=<你的任务名> tools/boardlock.sh ssh ... '<跑整网>'
# 之后同 boot 内：脚本里用 download=False 接手，不要再 load
```

### 2.3 sudo 的固定形状
```bash
echo xilinx | sudo -S -p '' env XILINX_XRT=/usr /usr/local/share/pynq-venv/bin/python3 -u <脚本>
```
- **不要 `sudo -E`**：它会保留你的 `PATH`，`cc` 可能解析到别的编译器，编出错误架构的 `.so`。
- **不要 `pkill -f`**：模式会匹配到你自己那条命令行，已三次把自己的 shell 杀掉。要杀按 pid 或 `pkill -x`。
- **`ulimit -c 0`**：板子 SD 只有 28 GB，python 崩一次 core 就是几百 MB。

### 2.4 ssh 限速（踩过，症状极易误判）
`sshd` 默认 `MaxStartups 10:30:100`：未认证连接超过 10 个就开始丢。
症状是 **`:22` 能连上、但连 banner 都收不到、`rc=124`** ——看着像板子死了，其实板子好好的。
**规矩：60 s 内最多 6 次连接；失败就停手看，不许写重试循环。**（`boardlock.sh` 已内置该闸门）

### 2.5 测量协议（影响所有数字的可比性）
1. **同进程重复 N 次，取第 2 次起**的中位/最好 —— 首跑要付一次性内核装载（板端实测 3.6 s 级）。
2. **一次只开一个开关**，多臂时**奇偶换序**（否则后跑的臂白拿缓存预热）。
3. **sha1 只在同一 BLAS 线程口径内可比**：`OMP/OPENBLAS/MKL_NUM_THREADS` 不同 ⇒ 归约顺序不同 ⇒ 冻结 sha1 会变（第 72 条纪律）。
4. 只有 `[DEPS]` 全 `fast` + `deps_closure_ok=True` + `run_valid=True` 的那一跑才算数
   —— `[DEPS]` 是唯一能抓到"静默回落 numpy"的东西（数值等价，所以逐字节/拍数/资源全都会通过）。

## 3. ★ 不能动的文件（动手前必须先读这一节）

### 3.1 位流白名单（**这条最硬**）
| 位流 | md5 | 状态 |
|---|---|---|
| `design_1_150v39.bit` | `602725b86941864eeeeab3be005e1e81` | ✅ **唯一可用**（`.hwh` = `c1686bd8…`） |
| v40 `04a62581…` | — | ❌ **禁用**：跑整网 23 s 硬挂（PL 越界写 → 页缓存被改写） |
| v41 `64ac3dd1…` | — | ❌ 禁用 |

- v40 的时序**比 v39 更好**（TNS −818.7 vs −47,312），**却更危险**：
  - 违例从「准静态寄存器的 CE 引脚」变成了**真在搬数据的一级** ⇒ 违例直接变错数据。
  - **上板门槛**：WNS ≥ 0，或逐端点证明所有违例都落在准静态 CE 引脚上。

### 3.2 冻结的代码（改一个字节，所有 sha1 判据立刻失效）
- PL RTL：`pynq_specialized_code/pl/rtl_hand/modules/`（v39 资产；改前先快照 + md5）
- PS 依赖闭包：**19 个文件 / 13 个模块**，清单 `runs/board_ops/20261102/deps_closure.txt`（md5 `9de3d60c…`）
  ```bash
  # 两条判据，缺一不可（在板端 ps/pynq 下跑）
  md5sum -c <deps_closure 的清单>        # 期望 19/19 rc=0
  python3 deps_closure.py --check        # 期望 rc=0：13 模块 / 19 文件 PASS
  ```
- 冻结的 sha1 常量（256²）：`9b1940c8… / f86a7035… / 025757a8…`；64²：`bfa246d3… / 226bd39e… / 762d84b9…`
- 基线台账 `docs/baselines.md` 是**唯一权威**：任何 md5/秒数以它为准；改了代码必须同时更新它并冻结新基线。

### 3.3 运行点（可直接抄的开关）
```
BIN_PACK=e1e2 BIN_LAZY_DEQ=1 BIN_LAZY_SLOTS=24 BIN_CAT_FUSION=1 \
BIN_BILINEAR_C=1 BIN_PRECOMP=1 Q8CACHE=1 BIN_F32DIRECT=1 \
BIN_CAT_ECA_FUSE=1 BIN_EPI_NOINV=1
```
**实测为负收益、不许开**：`BIN_SAM_TILE`、`BIN_DEQ_TILE`、`BIN_CONVPF_C`（A9 上 +17%）、`BIN_MMIO_POLL`。

### 3.4 目录纪律
- 板端 `/home/xilinx/runs/` 是结果区；`/home/xilinx/demoir/` 是代码镜像（两处都有 `runs`，别搞混）。
- 宿主机跑 `tools/boardlock.sh` 的实验脚本、探针放**独立子目录**（`/tmp/probe_<任务名>/`），
  曾经两个 agent 往 `/tmp` 写同名脚本互相覆盖。

## 4. 算力瓶颈（真板实测，C 臂，256²，150 MHz / 24 槽）

| 桶 | 秒 | 占比 | 说明 |
|---|---:|---:|---|
| **PS 合计** | **3.82** | 59% | 唯一真正的墙 |
| ├ prologue（量化+视图+描述符+cfg+槽） | 1.60 | | 其中 q8 量化 ≈0.60（`Q8CACHE=0` 时） |
| ├ 非卷积 | 1.97 | | convfp **1.16** / interp 0.26 / sam 0.25 / cat 0.13 / eca 0.08 / add 0.07 |
| └ epilogue | 0.26 | | v5 已降到 0.22 |
| **PL 合计** | **2.22** | 34% | |
| ├ E1E2 pack（数据重排） | **0.97** | | 占 PL 44%，比 conv 还贵 |
| └ conv | 1.25 | | |
| wait | 0.63 | | PS 阻塞等 PL |
| overlap | 0.75 | | PL 忙时 PS 真在干活的时间 |
| **total** | **6.49 → v5 6.02** | | v5 两刀再 −0.164 |

**三条结构性结论（比任何单点优化都重要）**

- ① **PS 时间对总时间近似 1:1**，不是“藏在 PL 后面”：overlap 只有 0.75 s，而 PL 忙了 2.22 s。
  - 原因**不是调度懒**，是数据依赖：同一时刻只有 1 个 conv 在飞 ⇒ 每次 PS↔PL 交替都要同步一次。
- ② **pack（数据重排）比卷积更贵** ⇒ 减少格式搬移的收益常常大于把卷积做快。
- ③ **PL 的瓶颈是 LUT 不是 BRAM** ⇒ 任何“加并行单元”的方案先算 LUT（当前 20.5k / 46.2k）。

**剩余可打的空间（按已验证量级排序）**：帧间预计算/缓存（q8、描述符、cfg）≈1.0 s；cat/eca/epi 融合已拿到 0.16；
PS→PL 融合（去 pack、去 DDR 往返）≈0.5~0.8 s；余下是逐 op 调度开销（每 op ≈3 ms × 227 层）。

## 5. 摄像头接入：现状与三条可行路径

### 5.1 今天探测到的硬事实
| 检查 | 结果 |
|---|---|
| `/dev/video*` | **无** |
| `/sys/class/video4linux/` | 空 |
| `/sys/bus/usb/devices/` | **空**（USB 子系统在，但**没有 host controller 注册设备**） |
| 设备树根节点 | 只有 `axi`，**无 `usb` 节点** ⇒ USB host 未使能 |
| `/dev/i2c-*`、`/dev/spidev*` | **无**（`i2c-dev` 未加载/设备树未暴露） |
| `v4l2-ctl` / GStreamer / ffmpeg | **均未安装**（板子无外网，装不了） |
| Python 侧 | `cv2 4.5.4` 可用（能解码 JPEG/处理数组），`PIL 9.0.1` 可用 |
| 链路速率 | **100 Mbps**（约 $12.5\ \text{MB/s}$ 理论上限，实测 TCP ≈11 MB/s） |

### 5.2 三条路径与代价
| 路径 | 需要什么 | 代价 | 风险 |
|---|---|---|---|
| **A. 宿主机采集 → 经 192.168.7.x 送帧** | 宿主机有摄像头（USB/UVC），板端只收帧 | **零硬件改动**，今天就能做 | 带宽 12.5 MB/s：**必须在宿主机先缩到网络输入尺寸再发** |
| **B. 板端 USB 摄像头（UVC）** | 设备树使能 USB host + 内核 UVC 驱动 + `/dev/video*` | 需要重新编译/替换设备树与内核模块 | 板子无外网，工具链要在宿主机准备；**当前内核无 USB host** |
| **C. 板端 HDMI-in（ADV7611 类）** | 设备树 + I2C + 对应驱动 | 最贴近"真实相机"，工程量最大 | 当前无 `i2c-dev` 节点；需要厂商参考设计 |

**推荐先走 A**：它不改动任何冻结资产（位流/闭包/基线都不受影响），且能立刻打通
"摄像头 → 预处理 → 网络 → 输出"的整条链路，把风险留在最便宜的环节。

### 5.3 路径 A 的带宽预算（先算再写代码）
网络输入是 $256\times256$ 三通道，一帧 $256^2\times3 = 196{,}608\ \text{B} \approx 0.19\ \text{MB}$：

- 传输余量：$12.5\ \text{MB/s} \div 0.19\ \text{MB} \approx 64\ \text{fps}$ ⇒ **传输不是瓶颈**。
- **真正的瓶颈是计算**：$6.02\ \text{s}$ 一帧 ⇒ $1/6.02 \approx 0.17$ fps。

- 所以第一版的目标应是「抓一帧 → 处理 → 出结果」，而不是“实时视频”。
- 若目标 $15\ \text{fps}$ ⇒ 需要约 $90\times$ 加速 ⇒ **这不是调优问题，是架构问题**。

原始分辨率越大越要先缩：$1280\times720\ \text{RGB}$ 一帧 $2.76\ \text{MB}$ ⇒ 100 Mbps 下只有 $4.5\ \text{fps}$ ⇒ **必须在宿主机缩放/裁剪**。

### 5.4 需要用户确认的两件事
1. **摄像头的物理接口**：USB（接宿主机还是板子？）、HDMI 输出、还是网口 IP 相机？
2. **输入帧规格**：分辨率、像素格式（RGB888 / YUV420 / MJPEG）、帧率、是否要求连续流。

## 6. 故障诊断树（5 分钟分清"板子坏了"和"我错了"）

```
1) ping 192.168.7.2 不通？
     → 查供电/网线；仍不通 ⇒ 断电重启（唯一合法结论）
2) :22 能连、但拿不到 banner、rc=124？
     → 极可能 sshd MaxStartups 被自己打满 ⇒ 停手 1~2 分钟，只试一次
3) 能登录就立刻跑四项体检（不要先跑业务）：
     df -h /          ← 满则停
     df -i /          ← inode 满则停
     sudo -S -p '' true ; echo rc=$?      ← 段错误 ⇒ 走第 4 步
     python3 -c "from pynq import Overlay"  ← 失败 ⇒ 环境问题
4) sudo/find 随机段错误、或文件 md5 自己变了？
     sync; echo 3 > /proc/sys/vm/drop_caches
     再 md5 同一个文件 → 变回正常 ⇒ 【页缓存被改写】磁盘没坏
     ⇒ 停手查 PL 越界写（金丝雀报警一次都不许解释成噪声）
5) 实验按梯度，一次只加一档：
     只 load + 读 IP 基址/频率 → 单次小尺寸 → 全尺寸×1 → 全尺寸×N
     任何一档失败即停，不连试
```

**收尾**：`sync`（要写盘）。**当天还要继续跑就不要 `poweroff`**——板子每次开机要人按电源；
只有在当天收工/用户要走时才 `sync; sync; poweroff`（硬断电会让 ext4 走 journal recovery）。
