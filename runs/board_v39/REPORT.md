## 4. 频率曲线（同 bit / 同 PS 代码，只切 `Clocks.fclk0_mhz`）

| 请求 | 读回 | 总时间（min of reps） | PL | 全部采样总时间 | sha1 |
|---|---|---|---|---|---|
| 100 MHz | 100.0 | **8.508 s** | 3.573 | 8.565 / 8.508 / 8.554 / 8.557 / 8.600 | 3/3 ✓ |
| 125 MHz | 125.0 | **8.399 s** | 3.443 | 8.576 / 8.399 | 3/3 ✓ |
| 150 MHz | 150.0 | **8.096 s** | 3.061 | 8.281 / 8.198 / 8.113 / 8.096 / 8.136 | 3/3 ✓ |
| 175 MHz | **166.667** | **8.146 s** | 3.096 | 8.146 / 8.161 | 3/3 ✓ |

- 曲线**单调变好到 150 MHz**，到 166.667 MHz 反而略回升（8.096 → 8.146）。
- **150 MHz 是目前实测最快点**，与"历史上 150 MHz 曾让整网变慢（14.72 → 17.05 s）"的旧观测**不一致** —— 照实记录（见 5.3）。
- 注意 PL 时间随频率的缩放**远低于线性**：100→150 MHz 时钟 +50%，PL 只从 3.573 降到 3.061（−14.3%）。**PL 是访存受限，不是计算受限**，这正是 AXI/DDR 争用的量化证据；也解释了为什么再往上抬时钟收益迅速消失（见 5.4）。

## 5. 异常与观察（照实写，不修饰）

### 5.1 冷/热态差 1.5–1.8 s —— 不是 v39 回归

新进程里第一次跑 256² 总是 10.06–10.35 s，而同一进程内第 2 次起就稳定在 8.10–8.60 s。**三个独立进程都复现**，且三项桶同时变大：prologue 2.66 vs 1.60（+1.06）、epilogue 0.57 vs 0.26（+0.30）、非卷积 3.80–3.98 vs 3.61–3.67（+0.15）。三项同增说明这是**进程级一次性预热**（最可能是 256² 那 700 MB 级中间张量首次触碰的页错误 / C 内核 .so 首次加载），而不是某个桶的算法退化。历史日志 `lazy_ab_256_final.log` 里也专门有"复核：热内核，排除一次性 .so 加载/自检"一行，是同一现象。
**我没有证明具体机制**，只证明它可复现、与 bit 无关（三次冷态分别 10.348/10.134/10.057，抖动 0.29 s，与 v33 的抖动同量级）。

### 5.2 与 v33 基线的数值对比

| | v33（`cat_ab_256.log`，同配置同输入） | v39 本次 |
|---|---|---|
| 总时间 @100 MHz | 8.508 / 8.289 s | 8.565 / 8.508 / 8.554 / 8.557 / 8.600 s |
| PL @100 MHz | 3.586 / 3.612 s | 3.573–3.613 s |
| 总时间 @150 MHz | 无整网记录（只跑过扫掠/golden） | 8.096 s |

- **PL 时间几乎完全相同（3.573 vs 3.586，−0.4%）** ⇒ 与"v39 拍数不变"的声明自洽。
- 总时间 v39 的中位约 8.556 s，比 v33 最好的 8.289 s 高约 0.27 s（+3.2%），但 v33 那两轮自己就差 0.22 s（8.508 vs 8.289），**v39 的区间与 v33 的区间重叠**。差额落在 prologue/非卷积的 PS 侧抖动上，PL 侧没有差异。
- 严格说：**v39 没有比 v33 更快，也没有变慢到超出抖动的程度**；"8.4 s"这个说法在热态、且允许 ±0.3 s 抖动的意义下成立。

### 5.3 150 MHz 没有变慢（与历史结论相反）

`lazy_ab_256_final.log` 记录的旧观测是"150 MHz 让整网从 14.72 s 变 17.05 s"。本次在 v39 + 当前 PS 配置下，150 MHz 是**最快**的一档（8.096 s，比 100 MHz 快 4.8%）。我无法确认旧观测对应的具体配置（那份日志里没有 150 MHz 整网数据），所以不做归因，只如实并列两条事实。

### 5.4 166.667 MHz 出现"更高频更慢"的信号（PL 桶反常）

时钟 150 → 166.667 MHz（+11.1%），若拍数不变，PL 应降到 3.061×150/166.667 ≈ **2.76 s**；实测反而升到 **3.096 s（+1.1%）**，总时间也从 8.096 回到 8.146 s。也就是说 PL 侧实际耗时**不降反升**，只能由访存/争用解释。这与 5.3 的历史现象同源，只是阈值落在 150–166.667 之间。**160+ MHz 不建议当真机工作点，除非重做时序收敛并给出余量证据。**

### 5.5 175 MHz 请求 → 166.667 MHz 读回

`Clocks.fclk0_mhz = 175` 时读回 `166.666667`：PYNQ 只能给到"最接近的可达分频"。**所以本报告里没有"175 MHz"的数据点，只有 166.667 MHz 的** —— 正是任务书提醒的"约束周期 ≠ 实际频率"。凡引用该点，必须写 166.667。

### 5.6 sha1 全对 ≠ 时序收敛

166.667 MHz 下 sha1 依然 3/3 全对，但那只说明**被这组输入激励到的路径**是对的。主机侧**没有 v39 的时序报告**（`pl/scripts/` 下只有 `timing_out_v37`/`v38`，v38 的那份还显示 `Slack (VIOLATED): -2.080ns`，且其约束周期是 10 ns）。因此：
**我不认为这次结果能作为 150 MHz 或 166.667 MHz 时序收敛的证据。** 这一条是我的判断，不是实测。
