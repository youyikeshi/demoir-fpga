# M56 · 第一步：256² 整网按像素计算顺序切成「可融合线性段」— 分段地图

> 只读分析。不写 RTL、不动 PS 代码、未起 Vivado/xsim。仓库 `demoir-fpga` @ `535ee2d`。
> 数据 = `ps/pynq/bin_net.py:build_graph()`（离线建图，engine=None，无 PL）＋ `runs/board_t61/t61.json`（板端 v5 / 256²，6 跑桶中位数）。
> 机器可读全量：同目录 `segments.json`（395 op × 15 字段 + 223 段汇总）。

## 0. 摘要（七条）

1. **395 op → 223 段**（S1 严格）。段长：单 op 104、双 op 87、3–5 op 32。PS 前 10 段占非卷积 PS 的 83%。
2. **S2 从不触发**：段内 `halo ∈ {0, 2}` 行，最大片上缓冲 **64 KB**（S189），远低于 270 KB。**halo 不是约束**。
   为什么这么小：227 个卷积里 **114 个是 1×1、113 个是 3×3**，且"cat 的 fan-out"把每个 3×3 拆开 ⇒ **没有任何段出现两个 3×3 串联**。
3. **真约束是 fan-out**：**220 张**张量 `consumers>1`（84 cat、101 conv、24 interp、6 add、4 sam、1 convfp）。这些是必须物化的边界。
4. **但大多数边界很便宜**：136 张非-cat 边界张量 p50 = **64 KB**，只有 **38 张（28%）超 270 KB**，且集中在 **encoder_1（11 张）/ decoder_1（9 张）**这两级；decoder_3 一张都不超。
5. 字节账：全图读 **343.7 MB** / 写 **113.0 MB**（@480 MB/s ⇒ 0.95 s 地板）；**非卷积部分 167.6 MB ⇒ 0.37 s 地板，而 PS 实测 0.716 s ⇒ PS 是它自己字节地板的 1.96×**，这就是融合能拿的那部分。
6. 建议先做：**decoder_1 SAM 块（0.226 s）/ encoder_1 SAM 块（0.171 s）/ encoder_2 SAM 块（0.088 s）**，合计占可融 PS 的 **68%**。
7. **块级片上化在 64²/128² 上不可能**（ghost 累积 640 通道 × 硬件 11 行 ⇒ 330–880 KB > 270 KB）；M56 的融合单元只能是**段**（halo ≤ 2 行），不是 stage。

## 2. 字节账（256² · v5 一轮）

- 全图 **343.7 MB 读 / 113.0 MB 写 = 456.7 MB** ⇒ @480 MB/s **0.95 s** 地板（实测 conv PL 1.36 + pack 1.09 = 2.45 s，同量级，说明现在没贴着地板跑）。
- 非卷积 164 op：**121.8 MB 读 / 45.8 MB 写 = 167.6 MB ⇒ 0.37 s**，PS 实测 **0.716 s** ⇒ **1.96× 于字节地板**（差额 ≈ 0.35 s 就是"numpy 开销"）。
- 读量之王是 **ghost 的累积 cat**：`t_ = cat([x1,x2,t_])` × 5 层 ⇒ `p.conv` 的 cin 从 48 涨到 **528**，encoder_1 一块吃掉 97.3 MB 读。

## 3. 分段规则（逐条落法）

- **S1 线性**：`consumers==1` ⇒ 并入其唯一消费者的段；`>1` ⇒ 断段。
  落地：按 `g.ops`（建图顺序 = dfs 后序 = 拓扑序）贪心游走，`seg_id` 逐 op 可复算。
- **S2 邻域有界**：段内 `halo = Σ(k_i−1)`；`buf = Σ (k_i−1)·W_i·Cin_i ×1 B`（按级求和，比 `halo×W×C` 精确，后者可用首级 `C,W` 代入复算）。**结果：0/223 段超 270 KB。**
- **S3 形状突变**：含 `shuffle/unshuffle` 的 4 个 op 各自成段（S0、S147、S185、S222）。**26 个 interp 全部是 1-op 段**（每个都是分辨率突变点）。
- **S4 可独立验**：每段给 `out_shape` + `leak`（段内产出、段外要读的字节）⇒ 段边界即"可回比原 f32 路径"的比试点。

## 6. 必须回答的 5 个问题

### Q1 一共几段
**223 段**（S1 严格）。3 个网络输出张量 `consumers==0`（out1/out2/out3 终端）。
段长：1×104、2×87、3×12、4×19、5×1。halo：0 行 ×110 段、2 行 ×113 段（**没有 ≥4 行的段**）。
`leak` 合计 69.8 MB（= 段边界要落 DDR 的写量）。

### Q2 哪三段最值得先做（PS 秒 / 缓冲需求）

6 个 SAM 块的缓冲需求同构（都要那张 `cat3`），所以按秒排 ≈ 按性价比排：

| # | 段/块 | 收益 PS s | 缓冲需求 | 理由 |
|---|---|---:|---|---|
| 1 | **decoder_1 SAM 块**（S190/191/211/221/**S222**） | **0.226**（整块；S222 自身 0.138 非-convfp + 0.555 convfp） | `cat3` 12 MB，或"两趟 + 3 行条带" | 全网最贵；尾段 5 op 全链 `consumers==1`；两趟即可，不必真存 12 MB |
| 2 | **encoder_1 SAM 块**（S4/5/25/35/**S36**） | **0.171** | `cat3` 9 MB | 下游 `boundary` conv `consumers==1` ⇒ 可一路融进下采样读窗口 |
| 3 | **encoder_2 SAM 块**（S41/42/62/72/**S73**） | **0.088** | `cat3` 4.5 MB | 同构，规模减半 |

> 若按"能不能真装进 270 KB"排：**decoder_3 SAM 块（0.019 s，cat3 0.75 MB）** 与 **encoder_3（0.047 s，2.2 MB）** 是唯一能整块片上化的两档——**建议拿 decoder_3 当打通流程的第一个验证目标（只值 0.019 s，不图收益），收益仍靠上面三名**。

### Q3 因为 fan-out 一定不能融合的 op（220 张，逐类给理由）

| 角色 | 张量数 | 谁在读 | 为什么必须物化 |
|---|---:|---|---|
| **ghost `x1`**（primary_conv 输出） | **90** | `cheap_operation` + 该层 `cat_prev` | 一份数据两个消费者，且 cat 侧要活到本块结束 |
| **ghost `cat_prev`**（累积 cat） | **72** | 下一层 primary_conv + 下一层 cat_prev | 5 层累积 ⇒ 最后读者在 5 层之后（liveness 最长） |
| **`interp`** | **24** | 上游 `sam` + `cat3` | 同一双线性结果既进 cat3 又进 weighted_sum |
| **`rdb` 累积 cat** | **12** | 下一层 conv + 后续 cat | 同 ghost |
| **`add`（residual）** | **6** | 上游 `sam` + `interp(feat_up)` | `rdb:residual` 输出既进 sam 又进上采样分支 |
| **`sam`** | **4** | `convfp` + `interp(feat_up)` | 只有 `feat=True` 的 4 个有分支 |
| 下采样 `boundary` conv | 2 | 本 stage 输出 + decoder 侧 cat | 编码器输出既要下采样又要跳连 |
| `convfp conv_first` | 1 | `encoder_1.rdb` + 网络输出 | 网络输出张量 |
| 其他 conv | 9 | 各 2 | rdb `conv_post` / 下采样侧 |

⇒ **这就是"不可融合边界全集"**；`segments.json` 里 `consumers>1` 一键可筛。

### Q4 `sam`(0.245 s) 与 `cat`+`eca`(0.121 s) 落在哪
- **同一批 6 个段**，形态完全一样：`[cat3] → [.fusion(eca)] → [:weighted_sum(sam)]`：
  `S36`(enc1, 0.095 s)、`S73`(enc2, 0.048)、`S110`(enc3, 0.024)、`S146`(dec3, 0.008)、`S184`(dec2, 0.032)、`S222`(dec1, 0.138 = eca .033 + sam .094 + shuffle .011，段内另有 convfp 0.555)。
- `cat3` 的 `consumers==1`（只喂 eca）⇒ **链是通的**；`cat_class="blocked"` 的 6 个正是这 6 个，且 v5 下也不物化（`CAT_ECA_FUSE`）——**所以"cat 0.036 s"是 Python 记账成本，不是字节成本**。
- **邻居允许融合吗？上游不允许，下游允许。**
  - 上游 `x`（stage 输出）fan-out 5–6：被 `interp(x2)`、`interp(x4)`、`ghost b0`、`sam` 同时读 ⇒ 必须物化。
  - 下游（`boundary` conv / `convfp`）`consumers==1` ⇒ 可融进同一遍写窗口。
  - **但 `sam` 本身不是单趟算子**：要先有 `w = eca(cat[y0,y2,y4])` 才能算 `x + y0*w0 + y2*w1 + y4*w2` ⇒ **只能两趟**（趟1 边算边累积 ECA 均值，趟2 重算或重读）。这是全网唯一"结构性两趟"的地方，也是 Q2 前三名的共同形态。

### Q5 风险清单

1. **`shuffle/unshuffle`（S3，最高危）**：`pixel_shuffle(2)` 把 `(4C, H/2, W/2)` 的 4 个通道组交织成空间 2×2 块 ⇒ 输出一行要 4 个通道块全部就绪；`pixel_unshuffle` 反向同理。**条带必须按"4 通道块对齐"切，不能按行切。** 且最后一级 `out1` 是 **3 通道**（12/4），C 不是 8 的倍数 ⇒ **C8 交错在这里失效**，需要单独一条 3 通道路径。
2. **跨形状段**：26 个 `interp` 全是单 op 段；`x2/x4`(÷2/÷4) 与 `b2_up/b4_up`(×2/×4) 成对出现。双线性系数、边界 clamp、`size` 取 `round` 还是 `floor` 必须与 `bin_ref_numpy.bilinear_f32` **逐位一致** —— 这是 S4 判据最容易挂的地方。
3. **需要 halo 的段**：halo 本身便宜（≤2 行、≤64 KB），**但"整块片上化"在 64²/128² 上不是划不划算，是不可能**：

   | stage | 支路 C | ghost 累积通道 | 1 行条带 + 10 行 halo | 270 KB 能容的条带 |
   |---|---:|---:|---:|---:|
   | encoder_1 @128×128 | 32 | 432 | **594 KB** | 不可能 |
   | encoder_2 @64×64 | 32 | 480 | **330 KB** | 不可能 |
   | encoder_3 @32×32 | 32 | 640 | 220 KB | 3.5 行 ✅ |
   | decoder_3 @32×32 | 48 | 640 | 220 KB | 3.5 行 ✅ |
   | decoder_2 @64×64 | 48 | 640 | **440 KB** | 不可能 |
   | decoder_1 @128×128 | 48 | 640 | **880 KB** | 不可能 |

   ⇒ **M56 的融合单元只能是"段"（halo ≤ 2 行、≤ 64 KB），不是 stage；块级融合在 128² 上必须先物化 `cat3` 到 DDR（12 MB 往返 ≈ 50 ms @480 MB/s，比 5× 重算便宜得多）。**
4. **fp32 归约顺序**：`eca` 的 `mean(H·W)` 在 numpy 是顺序累加，PL 树形归约结果不同 ⇒ sha1 必挂。要么定死归约树，要么对 eca 输出声明容差（**会破坏 S4 的"逐字节"判据**）。
5. **带宽地板**：全图 456.7 MB ⇒ 0.95 s，现在 6.33 s。分段融合省的是"PS 开销 + 可消往返"，**不改地板**；16 lane 之前别指望从这张图里挖出 1 s。
6. **惰性 cat 的前提会被打破**：110 个惰性 cat 依赖"叶子段都在 PL 可读池里"（CATPACK）。某段一旦改成流式/片上，这个前提失效 ⇒ **必须按段重新声明段描述符（`_segments`）**，且要遵守 T-19 已记录的语义坑（mux 初始状态 / 失败停止行为）。

## 8. 按这张图，全部融合完能省多少

$$\text{可融 PS 桶} = 0.716\ \text{s}\quad(\text{sam } .246 + \text{interp } .263 + \text{eca } .085 + \text{add } .067 + \text{cat } .036 + \text{shuf } .019)$$

- **上限 0.716 s**（假设字节一次都不多走 DDR）。
- **保守 0.35 s**（= 0.716 − 该桶自己的 DDR 地板 0.366 s，即只拿"numpy 超出带宽的那部分"）。
- 扣 §Q5-3 的重算与 §Q5-4 的归约约束 ⇒ **现实区间 0.40 – 0.60 s**（取中 **≈0.5 s**）。
- **不在这张图里的大头（别记 M56 账上）**：`pack` 1.09 s（要 conv 写侧直产 E1E2，属 M3/M56 写侧改造）、`prologue` 1.17 s、`wait` 0.86 s、`conv` 残差 0.74 s、`convfp` 1.14 s（M1）。
