* `out_bytes = 12·128·128·8 = 1 572 864`，**正好等于 `max_out`** ⇒ 数据末字节 = 金丝雀首字节的前一个。
* `cout = 96` **是 8 的倍数**（`cg=12`，末组 `nvalid=8`、`WSTRB=8'hFF`）⇒ 走包装层的"整字直落"路径

  `ybase/xbase` 累加，是"行列余数"最容易出错的一层，因此单列一格仿真。
* 三层 `Hout=Wout=128`、`cin` 分别 64/160/256（cb=1/3/4）、`K=9/27/36`。

> 反向校验（题设"若 out_bytes≠1 572 864 请重新找"）：227 层里 `out_bytes ≥ 1 572 864` 的**只有这 3 层**，
> `> 1 572 864` 的**一层都没有**（表里最大即 1 572 864）。所以"唯一候选"成立。

### 3.1 读法（四档反压各自证明了什么）

| 档 | 激励做了什么 | 排除了什么 |

| `+WSLOW=1` | AW、W 各自独立随机门（约 7/8 放行）+ B 延迟 10~74 拍 | `bf_cnt` 进压力区 ⇒ `u_ce` 冻住单元 ⇒ **`pw_valid/wide_pend/wr_wide_b` 三级流水在冻结-解冻边界上的行为** |

### 3.2 为什么"三层 × 四档"就够了（覆盖面论证）

* 三层的差异只在 `cin`（cb=1/3/4）、`K`（9/27/36）、`d`（1/2/1）、`shift`（6/7/6）。
  写侧地址链只吃 `cg`、`Hout·Wout`、`cout`、`pad/d/s` → **三层已覆盖"cb 非 2 的幂(cb=3)"、
  "K 最大(36)"、"唯一空洞卷积(d=2)"、"cin 最大(256)"** 这四个极端组合。
* 四档反压覆盖"写 FIFO 压力"与"读侧饥饿"两个冻结源（`u_ce` 的两个输入端），
  外加定点刀覆盖"最后一拍"这个唯一的时间点；`+LASTHOLD` 的触发点用 `cyc` 差验证过真的打上了
  （L0：1 775 689 → 1 775 745，+56 拍 ≈ 请求的 64 拍减去重叠）。
* 单元的读数据被建模成地址相关的确定性伪随机（内容不影响地址/状态机），因此**不需要 golden 向量**。

## 4 `cout` × `Hout` 变体扫描（专找"多写一拍"）

动机（两个方向）：

1. **单元侧**：`cout` 不是 8 的倍数时（`cg=ceil(cout/8)`、末组只有 `cout-8(cg-1)` 个 lane），
   单元本应给出 `WSTRB=(1<<nvalid)-1`（`bin_conv_core8.v:648-649`）；若某种余数处理把末组的
   `nvalid` 算成 **8** 或把地址多推进一个字，就是**恰好 8 字节**越界。
   （⚠ 实测发现**前提本身不成立**：末组 `nvalid` 恒为 8，但多写的 4 个 lane 落在 `out_bytes` 之内 ⇒ 不越界。见 §5.2）
2. **包装侧**：`WSTRB≠8'hFF` 时包装层从"整字直落"切到"逐字节攒字 + 排空"路径
   （`bin_unit_axi_wrap.v:1678` `wr_byte` / `:2209` `drain_cond` / `:2356` 换字时先落上一拍），
   这条路径的**收尾**是"把半个字推出去"，理论上是唯一可能"多推一拍"的地方。

⚠ 本轮先撞出一条**结构性事实**（也是重要的正面结论）：**包装层根本不允许 `cout%8≠0` 的 conv 启动** ——
`bin_unit_axi_wrap.v:1172-1176` 在启动闸门里查 `r_cout[2:0] != 0` ⇒ `ERR_LAYOUT(4)`、**一个字节都不写**
（`AP_RETURN` 见 `ret=00000401`：bit0=done、[15:8]=4）。所以：
* 部署路径上 `nvalid` 恒 8、`wrsel_q` 恒 `8'hFF`、`base_out` 又必须 8 字节对齐（`ERR_ALIGN(5)`）
  ⇒ **conv 的写地址恒 8 字节对齐且 WSTRB 恒 FF ⇒ `be_*` 逐字节攒字路径对 conv 是死代码**，
  conv 只有一条路：单元整字 → `pw_*` → `push_beat(…,8'hFF,…)` → beat FIFO → burst ≤8 → AXI。
* 因此"层输出字节数不是 8 的倍数"这一情形**在部署路径上不存在**；它只可能在单元级单独出现，
  而单元级实测也**不是少写**：照样写满 8 个 lane，多出来的 lane 落在 `[cout, cg·8)` 之内（§5.2 / §4.1）。

* **12 个 `cout×Hout` 组合，单元级与包装级都没有出现 `oob>0` / `over>0` / `canary>0`。**

  = `ERR_LAYOUT`（`bin_unit_axi_wrap.v:1172-1176` 查 `r_cout[2:0]!=0`），**一个字节都没写**。
  ⇒ "末组只有 4 lane 的半个字被推出去"这条路径**在部署路径上根本到不了**。
* 单元级那 6 格（`cout=92/100`）能跑，结果是 **`oob = 0`、`beats = cg·HW`、`wrbytes = exp`**：

* `cout=88`（`cg=11`，末组满 8 lane）与 `cout=96` 同为整字路径，同样 0 溢出。

## 5 若仿真为 0：那 8 字节还能从哪来（逐条给证据）

先把**地址的唯一来源**钉死，这一条决定了后面所有分支：

> **包装层不做任何地址运算。** `m_axi_awaddr = ax_addr = df_addr[df_rp] = {bu_base, 3'b000}`
> （`bin_unit_axi_wrap.v:2457`、`:2396`、`:2173/2380`），而 `bu_base` 只被 `push_beat` 写成
> "刚推出去的那个 beat 的字地址"（`:2163-2182`），那个字地址来自
> `pw_word`（整字路径，`:2317` `pw_word <= u_wr_addr[31:3]`）或 `be_word`（字节路径，`:2387`
> `be_word <= w_word = p_addr[31:3]`）。`u_wr_addr` 是**单元写口**（`:1415`），
> `p_addr` 是 `u_wr_addr` 的一级寄存器（`:2294`）。
>
> ⇒ **要让某个 8 字节落在 `≥ base_out+out_bytes`，必须先是"单元把 `mem_wr_addr` 摆到那里"。**
> 包装层没有"自己造地址"的通路；它连 `base_out` 都不看（只在例化时把 `r_out` 接到单元的
> `base_out` 端口：`:1344`）。

### 5.1 `desc` 写入 —— 描述符根本不上写通道

| 问题 | 答案 | 证据 |
|---|---|---|
| 描述符会不会顺着同一条写通道写到 DDR？ | **不会**。PL 侧有两种"描述符"，两种都不走 `m_axi` 写： ① burst 描述符 `df_*` 是包装层的**片上 FIFO**（`df_addr/df_len`，`:752-755`），只喂本模块的 AX 引擎；② E1E2 的 64-bit 描述符表是**读进来**的（`desc_ram[0:7]` 由 `mem_rd_data` 装载，`bin_e1e2.v:198,736`），`base_desc` 只出现在读地址 `dbase_q = base_desc + grp*512`（`bin_catpack.v:346`、`bin_e1e2.v:491`）。 | `bin_unit_axi_wrap.v:752-755,2173,2380,2396-2397`；`bin_e1e2.v:198,736,750`；`bin_catpack.v:344-346` |
| 那描述符是谁写的？ | **PS**（`bin_net.py:3205-3207` `_v50_materialize`），写在 `need` 里额外加的 `desc_bytes` 段。 | `bin_net.py:3203-3207` |
| 有没有可能"写到 out_end 之后"？ | 若 PS 把 `r_edesc` 指到 OUT 槽里 ⇒ 会（但那是 PS 指针错，且本层 3 个 conv 启动**完全不看** `r_edesc`）。反过来，PL 侧**没有**任何"用 out 基址写控制块"的逻辑。 | `:956`（`0x208` 只由 AXI-Lite 配置写）；`:1266-1268`（`r_edesc==0` 直接报错，不启动） |
| 结论 | **desc 不可能贡献那 8 字节。** | 上面 4 行 |

### 5.2 最后一笔 burst 的 `WSTRB` —— 在本 RTL 里**恒为 `8'hFF`**，不可能多写

题设要求说明"当层输出字节数不是 8 的倍数"的一般情况。本轮把它查到底了，结论比预期更强：

| 情形 | 事实 | 证据 |
|---|---|---|
| 部署路径（`cout%8==0`，RTL 强制） | `nvalid_q = VLANES = 8` ⇒ `wrsel_q = 8'hFF` ⇒ 走"整字直落"⇒ 每拍 `WSTRB=8'hFF`、地址 8 字节对齐 | `bin_conv_core8.v:646-653`（`wrsel_q`/`mem_wr_sel`）、`bin_unit_axi_wrap.v:1658,2326` |
| **`cout%8≠0` 时呢？**（只可能在单元级出现，包装层已在启动闸门拒掉） | **仍然是 `8'hFF`**：`nvalid_q` 是在"进入下一组"时用**旧的 `o_q`** 算的（`nvalid_q <= (cout_q - o_q > VLANES) ? VLANES : (cout_q - o_q)`，`:810-811`），而 `o_q` 在这一拍才 `+VLANES` ⇒ **末组拿到的 `nvalid` 是 8**，于是照样写满 8 个 lane（多出来的 `8-cout%8` 个 lane 写的是**填充数据**，位置在 `[cout, cg·8)` 内，仍在 `out_bytes` 之内） | `:804-811`；仿真实证：`cout=92/100` 的 6 格 `wrbytes == exp`、`beats == cg·HW`、`oob = 0`（§4 表） |
| ⇒ 因此 | **本 RTL 不存在"层输出字节数不是 8 的倍数 ⇒ 末笔 burst 半字/部分 WSTRB"这种情形**；`be_strb` 只由真实到过的 lane 或上（`:1686,2359`）、`merge_done` 还要求 `be_strb_nx==8'hFF`（`:2221-2222`）——这些都成了**永不激活的死代码**（对 conv 而言） | 同左 |
| 一般性（若将来放宽 `cout%8`） | 设末组有效 lane `nvalid`，则本层最大被写字节 = `base + out_bytes - 8 + nvalid - 1 ≤ out_bytes - 1`（`nvalid=8` 时取等）。**`nvalid<8` 只会严格更小。** | 代数 |

**⇒ `WSTRB` 不是 8 字节越界的来源**：它恒为 `8'hFF`，地址又只来自单元；一个满 WSTRB 的 beat
若落在 `out_bytes` 之后，落点必然是 `base+out_bytes` 这一个**完整字**（= 金丝雀 `[0..7]`，见 §6）。

### 5.3 `drain`/收尾状态机 —— 没有"多发一笔空 beat"的分支

`push_now`（= 真的会产生一笔 beat 的唯一组合信号）只有四个来源（`:2226`）：
`merge_done`（半个字被凑满）、`merge_change && be_open`（换字时先把上一拍落掉）、
`drain_pub`（`wst==W_DR1 && be_open`，`:2224`）、`pw_valid`（整字路径落盘，`:2322-2326`）。
这四者与 `push_beat(...)` 的调用点**一一对应**（`:2326` 整字落盘、`:2348` 凑满一个字、`:2356` 换字前先落上一拍、`:2371` 排空），
且 `be_open` 只可能被"真的来过一个字节"置 1（`:2359`）。逐个检查"空 beat"的可能性：

| 怀疑点 | 结论 | 证据 |
|---|---|---|
| 排空时会不会凭空推一个 beat？ | 不会：`W_DR1` 里 `if (be_open) push_beat(...)` —— 没有 `be_open` 就什么都不推；`drain_cond` 本身还要求 `be_open || bu_len!=0`。 | `:2209`、`:2369-2376` |
| `W_DR2` 会不会多收一笔描述符？ | 只在 `bu_len != 0` 时收，且 `bu_len` 是"已经推出去但还没被收笔的 beat 数"，`push_beat` 里不 chain 时也会收（同一套记账）⇒ 描述符数 ≡ burst 数。 | `:2377-2385`、`:2163-2182`、`:2250-2252` |
| 描述符长度会不会大于 FIFO 里的真实 beat 数（⇒ 把旧 beat 当新 beat 再发一次、地址还前进）？ | 不会：`ax_can_start` 要求 `bf_cnt >= df_len[df_rp]`，且"收笔那一拍它的 L 个 beat 必然都还在 FIFO 里"（只有本笔的描述符才能弹它们）。`BU_MAX=8 ≤ bf_cnt 峰值 14`。 | `:2253-2254`、`:2476-2517` |
| 同一拍会不会推两笔？ | 不会：`p_merge` 含 `!pw_valid`（`:1690`）、`drain_pub` 含 `wst==W_DR1`（与 `wst==W_IDLE` 互斥）⇒ `push_beat` 每拍最多一次，`bf_cnt` 每拍最多 +1。 | `:1690`、`:2226`、`:2262-2277` |
| `done` 会不会在最后一笔还没落盘时就报出去（PS 提前读、第二次写？） | 不会：`wr_all_idle` 含 `!be_open && bu_len==0 && !p_valid && !pw_valid && bf_cnt==0 && df_cnt==0 && axst==IDLE`。 | `:2471-2474`、`:1019`（`run_active && unit_done_q && wr_all_idle` 才报 done） |
| **`u_ce` 冻结时会不会把同一拍吞两次？** | 不会：`wide_pend` **不含** `u_ce`（`:1676`）但 `wr_wide_b = wide_pend && u_ce`（`:1677`）；冻结期间 `pw_valid <= wr_wide_b = 0`，而单元被 `ap_ce=u_ce` 冻在同一笔上、解冻后**只**被吞一次；`p_valid` 改成"并不掉就等"（`:2292-2299`），`drain_cond` 含 `!p_valid && !wr_byte`（`:2209`）不跨过未合并的字节。**这一条是本轮 `+LASTHOLD` 定点刀专门打的**。 | `:1658-1690`、`:2290-2326`、§3.1/§3.2 |

### 5.4 两个 OUT 槽相邻会不会"跨槽写"

* 槽布局：`_PlBackend.__init__` 逐个 `arena.region(nout+4096)` 切槽（`bin_net.py:808-810`），
  槽与槽**首尾相接**，每个槽尾 4 KB 是金丝雀（`bin_engine.py:204-207` 填、`:209-214` 查）。
* **PL 完全不知道"槽"这个概念**：它只拿到一个 32 位 `r_out`（`:941` 由 AXI-Lite 写 `0xD0`），
  把它们塞进单元的 `base_out` 端口（`:1344`），地址由单元自己在 `[base_out, base_out+out_bytes)` 里生成
  （`bin_conv_core8.v:889` `oaddr_q <= ogbase_q`、`:897` `oaddr_q <= oaddr_q + VLANES`、
  `:807-810` `ogbase_q <= ogbase_q + hwout8_q`）。
  ⇒ 没有"槽偏移/槽对齐"运算，也就没有"跨槽地址算错"这一类 bug 的可能形态。
* 唯一与"相邻"有关的事实：**槽 i 的金丝雀最末 8 字节（偏移 4088..4095）就是槽 i 的最后 8 字节，
  紧贴着槽 i+1 的数据头**。所以"金丝雀**尾** 8 字节"被写坏 ⇒ 写入地址 = `槽尾-8`，
  对应"越过 `out_bytes` 正好 4088 B"或"某个写者的基址被指到 `槽尾-8`"这两种完全不同的解释；
  而"金丝雀**首** 8 字节"被写坏 ⇒ 写入地址 = `base_out+out_bytes`。**两者只差 4088 B，但嫌疑方向相反**（§6）。

## 6 判别式：那 8 字节**落在金丝雀的哪个位置**，直接决定先查哪一条

板的 `check_canary` 过去只报"坏 N/4096"、**丢掉位置**（`bin_engine.py:213` 只累加计数）。
新的守卫已加"首坏偏移 + 前 16 字节"（`runs/opt_round1/perf/T161_canary_result.md` §2/§5'）。
一条日志就能把范围劈开：

| 首坏偏移 | 物理含义 | 与"本层多写一个 beat"是否相符 | **先查哪一条（文件:行）** |
|---|---|---|---|
| **+0**（`canary[0..7]`，即 `base_out+out_bytes` 这一**个** 8 字节字） | 有人写了单元的"下一个字地址" | **完全相符**：单元的地址链在最后一个 `term_last` 之后**确实**停在 `ogbase+out_bytes`（`bin_conv_core8.v:897` `oaddr_q <= oaddr_q + VLANES`，最后一个像素也执行），只差一个 `mem_wr_en` | **`bin_conv_core8.v:225`（`pix_last` 定义）+ `:641-655`（`v1..v8` 流水线与 `mem_wr_en = v8_q`）**：查"最后一个像素的 epilogue 是否可能多出 1 个 valid"。其次是 `bin_unit_axi_wrap.v:1676-1678`（`wide_pend/wr_wide_b` 的 `u_ce` 边界）。 |
| **+4088**（`canary[4088..4095]`，写入地址 = `base_out+out_bytes+4088` = `槽尾-8`） | 写的是**槽的最后 8 字节**，紧贴下一槽数据头 | **不相符**：本层多写一个 beat 只会落在 +0，落在 +4088 需要"多写 511 个 beat" | **`bin_unit_axi_wrap.v:1371,1398`（E1E2 / catpack 的 `base_out` 直接接 `r_eout`）+ `:1414-1417`（写口 3:1 mux）+ `:1266-1268`（`r_eout==0` 才报错，非 0 就照写）**：查 `r_eout`(0x210) 的残留/误用。 |
| **4096/4096**（整块金丝雀被覆盖） | 越界 **≥4096 B** | 不是"一个 beat"，是**整行/整组/地址链错位** | 不用查写口补一拍，直接查面积公式与分组步进：`bin_conv_core8.v:149-150`（`hout_c/wout_c`）与 `:807-810`（`ogbase_q += hwout8_q`）。 |
| 一行的量级（`cg·Wout·8 = 12·128·8 = 12 288 B`）或更大 | 整行/整组多写 | 同上 | 同上（并且会连带毁掉下一个槽的数据 ⇒ 数值也会明显错） |
| 分散多点、且每次位置不同 | 多次零星写 | 与"层输出写"无关 | 查 PS 侧写者与 DMA；PL 写口一次只可能错一拍 |

**反向推理（本轮最有用的一句）**：板端报的是 **8/4096** 而不是 **4096/4096**，这说明
**越界长度被夹在 1 个 beat（8 B）以内**，不存在"地址偏了一行/一组"的结构性错误
——否则金丝雀会被整块覆盖（4096 B）。这与 §5 的逐条否定互相印证，也把"面积公式错"这一类
彻底排除（面积错必然是整行/整层级别）。

## 7 建议（按先后顺序）

0. **不要再动 FCLK0 分频**：板上真实运行点是 **50.79 MHz**（SLCR 回读 DIV0=20），
   该工作点 FCLK0 域 **WNS +7.878 ns / 0 失败端点**（`timing_at_19p6875ns.rpt:170`）⇒ 时序不是当前主嫌疑。
   ⚠ 但**任何把 `Clocks.fclk0_mhz` 调回 150 的操作都会立刻制造 756 个失败端点**（§5.5），复测期间请锁死这一项。
1. **先落金丝雀修复再复测（强烈建议，且零风险）**：把金丝雀钉到 `out_bytes`
   （而不是槽尾），并让 `check_canary` 报 `lo/hi` 偏移与首 16 字节。
   理由：① 现在 227 层里只有 3 层受保护，任何"≤512 KB 的越界"在其余 224 层都静默；
   ② 没有偏移就永远分不清"多一个 beat(+0)"和"基址指错(+4088)"（§6）。
   这一步不改数值语义、不改 RTL，只改 PS 的护栏，**可以在下一次上板时顺带验证**。
2. **复测时按 §6 表读日志**：若首坏偏移 = +0 且复现，则把 `r_run_unit`、`r_out/r_eout`、
   该次 launch 的 `arm()` 参数一起抓下来（此刻"是 conv 单元还是被误启动的单元"是唯一分叉点）。
3. **在"位置"信息没有之前，不建议动 PL**：本轮已用 4 档反压 + 12 组变体 + 256² 对照证明
   **conv 写通道在精确形状下不可能多写 8 字节**；盲目改 RTL 只会把已通过的
   `verify_all` / eqv 基线弄脏。
4. 若要继续压 PL 侧的概率空间，下一个性价比最高的实验不是"更多形状"，而是
   **"在最后一拍上做长冻结 + 复位竞态"**（本轮 `+LASTHOLD` 的加强版：冻结 64 拍 → 放开的同时
   PS 立刻读 `AP_RET`）。这一条只在怀疑"done 早报/晚报"时才有意义。
