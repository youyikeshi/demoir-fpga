# 里程碑 1：HDMI 帧缓冲扫描器「AXI 低于像素时钟 ⇒ 每行读空」仿真复现

- 工具：Vivado Simulator v2025.2.1（xsim，经 `tools/memgate.sh` 内存闸门 + `/tmp/dsh_vivado.lock`）

## 0. 一句话结论

> **丢在 AXI 域的「行缓冲写侧 / 弹像素泵」这一级**：`pops_done` 每个 `s_axi_aclk` 最多 +1
> （即 `pop_en` 每拍最多写 1 个像素进行缓冲），一行 W=1280 个像素最少要 1280 个 aclk。
> 在 50 MHz 上一行填满需要 **25 680 ns**，而一行周期只有 **22 232 ns** ⇒ 每行都填不完，
> 取数永久落后一整行，`hdr_line == in_vy - 1`，于是整行 1280 个像素全部 `pix_valid=0`、
> 每行触发一次 `uf_evt_tog` ⇒ `0x2C` 每行 +1。
> 判定门槛：**f_axi ≥ f_pix · W / H_TOTAL = 57.57 MHz**（720p60）。
> 66.67 MHz 填充 19 260 ns < 22 232 ns ⇒ 余量 13%，`0x2C` 恒 0，与板端一致。

## 1. 被测模块与数据流（先看清楚判据挂在哪）

```
          PIX 域 (74.21875 MHz)                        AXI 域 (s_axi_aclk)
  ┌──────────────────────────────┐        ┌───────────────────────────────────────┐
  │ in_vde/in_vx/in_vy           │        │  §3 取数 FSM  F_IDLE→F_BASE→F_AR→F_FIN │
  │        │                     │        │        │ arvalid/araddr/arlen(≤8拍)     │
  │        ▼                     │        │        ▼                               │
  │  rq_line + rq_tog ───toggle──┼───────►│ rtg 3FF → 受理(第2级)                  │
  │  (行请求，行号 bundled)      │        │   a_line / a_fpar / req_ack            │
  │        ▲                     │        │        │                               │
  │        └────── req_ack ◄─────┼────────┘        ▼                               │
  │                              │   pop 泵: room≥3 ⇒ pop_en 1 像素/aclk          │
  │                              │        ▼                                       │
  │  pix_valid = de && p_en      │   BRAM 写口 A (s_axi_aclk)                     │
  │            && !uf_now ◄──────┼── (hdr_line, wl_bin) ◄── gray + toggle 发布    │
  │        │                     │        ▲                                       │
  │        ▼                     │   行内写进度 pops_done (12 bit, gray)          │
  │  BRAM 读口 B (pix_clk) → rd_data → pix_rgb (延迟 1 拍)                         │
  └──────────────────────────────┘        └───────────────────────────────────────┘
```

判据（模块自己的定义，本 TB 直接采信）：

```
uf_now = in_vde && p_en && uf_en && !({hdr_line, wl_bin} > {in_vy, in_vx})
pix_valid = in_vde && p_en && !uf_now          （打一拍输出）
每行第一次 uf_now ⇒ uf_evt_tog 翻一次 ⇒ 0x2C(UNDERFLOW_CNT) +1
```

所以本报告把「一行里只要有 1 个像素 `pix_valid=0`」记为**该行读空（丢行）**，
这与 `0x2C` 的行级计数口径完全一致（一行只计一次）。

**关键结构性事实**：模块只有**一级**行缓冲，且**只在"当前行显示结束（`de_fall`）"时才请求下一行**。
于是"填充第 N+1 行"的可用窗口 = 第 N 行结束 → 第 N+1 行有效区开始（= 900 像素消隐 + 一点点），
但更重要的是：**填充本身要占满 W 个 aclk**，只要 W/f_axi > 1 个行周期，就永远追不上。

## 2. Testbench 模型

文件：`runs/opt_round1/rtl_coexist/tb/tb_fbscan_repro.v`（自包含，只例化 `hdmi_fb_scan.v`）

### (1) 视频时序发生器（PIX 域，74.21875 MHz）

与 `hdmi_timing_gen.v` 的 MODE0 **逐拍等价**（同样的寄存输出口径）：

| 量 | 值 |
|---|---|
| H_TOTAL / H_ACTIVE | 1650 / 1280 |
| V_TOTAL / V_ACTIVE | 750 / 720 |
| V_FP / V_SYNC | 5 / 5（vsync 在 vcnt ∈ [725,730)） |
| `in_vsync` | `v_vs` 上升沿拍，**1 个 pix_clk 宽**（= `hdmi_out_top.v` 里的 `vs_rise`） |
| 行周期 | 1650 / 74.21875 MHz = **22 232 ns** |

启动时把 `vcnt` 预置到 725（vsync 行），省掉 725 行的空等。

### (2) AXI4 读从机行为模型（"理想从机"是故意的）

- `arready` 常高，接受即入 16 深描述符队列；`rlast/rresp` 合规，突发内**背靠背**每拍 1 个 beat。
- **首拍延迟 `R_LAT` 可参数化**（0 / 20 / 60 …），另有 `R_LAT_MODE`：
  - `1`（默认，贴近 HP 口）：只有"数据流断开、队列空"时才付 `R_LAT`，多个 outstanding 可以掩盖延迟；
  - `0`（极端保守）：**每个突发**都付 `R_LAT`（用于证明结论不依赖延迟模型）。
- 数据按字节地址可复算（`membyte(a)=a[7:0]^a[15:8]^0x5A`），TB 逐像素比对 `pix_rgb`。

> **为什么这样建模才有说服力**：这是"无限带宽 + 零仲裁抖动"的理想从机。
> 如果连它都读空，就说明瓶颈**不在总线**，而在模块自己的取数/写缓冲吞吐。
> 主表用 `R_LAT=0`（最有利于 DUT 的假设），敏感性表用 `R_LAT=60`。

### (3) 统计与追踪

- 判据在 DUT 的**输出流**上取（`pix_de` 拍数 / `pix_valid`），坐标用输出 `pix_x/pix_y`，
  所以统计的是"下游真正看到的东西"；行结束时（`pix_de` 下降沿）定案 clean / dirty。
- 同时统计：`req_issued`（`rq_tog` 边沿）/ `req_accepted`（`req_ack` 边沿）/ `line_start`（`F_BASE` 且
  `line_cur==a_line`）/ `line_skipped`（`a_line` 跳变 > 1）/ AR 突发数 / R 拍数 /
  每行填充耗时（`LINE_START` → `pops_done` 首次等于 W）。
- 失败档按行打印时间线（`[TRC]` 前缀，见 §4）。

## 4. 失败档（50 MHz）时序分析：到底是哪一级丢的

原始时间线（`logs/repro_50.00MHz_rlat0.log`，单位 ns）：

```
t= 571654  vde_begin vy=0  hdr=0 wl=1280   ← 启动时有一段长空档，第 0 行是唯一干净的一行
t= 588914  pix_end   vy=0  inv=0           ← 整行 1280 像素全部有效
t= 588914  REQ_ISSUE next_line=1 free_before=1     ← 行 0 显示结束才请求行 1
t= 588990  AXI_ACCEPT line=1                        ← 76 ns 后受理（握手没问题）

t= 660583  vde_begin vy=4  hdr=3 wl=999  → inv=1280 ← 稳定态：每行 1280/1280 像素无效
```

### 4.1 主因：AXI 域「弹像素写 BRAM」这一级被 1 像素/aclk 钉死

`fill_ns` 与理论值 `W × T_aclk` 的对照（误差 < 0.5%，说明**每一拍都在弹、没有别的空转**）：

| f_axi | `W/f_axi` | 实测 fill | 差 |
|---|---|---|---|
| 37.125 MHz | 1280×26.94 = 34 479 ns | 34 585 ns | +106 ns ≈ 4 拍（AR 起头/收尾） |
| 50.000 MHz | 1280×20.00 = 25 600 ns | 25 680 ns | +80 ns ≈ 4 拍 |
| 66.667 MHz | 1280×15.00 = 19 200 ns | 19 260 ns | +60 ns ≈ 4 拍 |

即：**`pops_done` 严格按 1 个/aclk 增长，取数泵的吞吐上限 = f_axi 像素/s**。
要在一行周期内填完，必须 `f_axi > W × f_pix / H_TOTAL = 57.57 MHz`。
50 MHz 差 15.5%，37.11 MHz 差 55.6%，66.67 MHz 有 13.4% 余量。

为什么弹不快：`pop_en = (room>=3) && (pops_done < s_w)`，`room` 每拍最多 +8（收 1 拍）/−3（弹 1 个），
`beat_ok` 又要求 `room<=16`；稳态下"弹"是唯一的瓶颈（1 次/aclk），
**这与 AR/R 带宽无关**（实测 `outstanding` 顶到 20~24、`room` 顶到 16~21，说明 R 侧从不缺数据）。

### 4.2 次生：PIX→AXI 的行请求被**覆盖**（`rq_line/rq_tog` 只有一组寄存器）

`rq_free = (ack_s[1] == rq_tog)`，而 `req_ack` 在 `F_IDLE` 受理时就更新了，
所以在 `F_AR/F_FIN`（正在取数、长达 1.16 个行周期）期间 `rq_free` 依然是 1 ⇒ PIX 侧
**会继续发请求并改写 `rq_line`**。若一个取数窗口内落了两次 `de_fall`，只有**最后一次**被采到，
前一行被静默跳过：

- 50 MHz：1200 行只发出 1038 次请求，`line_skipped=161`；
- 37.11 MHz：1200 行只发出 772 次请求，`line_skipped=427`
  （`line_skipped` 已排除每场正常的 719→0 回卷，否则各 +1）。

这条是**果不是因**：它是由 4.1 的"填充超过一行"触发的（取数窗口跨越 >1 个 `de_fall`）。
它把"落后半行"放大成"落后整行"，所以稳态是全黑而不是半屏。

### 4.3 被排除的两级

| 环节 | 证据 | 结论 |
|---|---|---|
| ② 应答没等到就换行 | `req_issued=1038 = req_accepted=1038`，`line_start=1037`（差 1 是收尾时被打断的最后一次） | 受理链路**没丢**，每个受理的请求都产生且只产生一次行起始 |
| ③ AXI 侧采样漏了 | `AXI_ACCEPT line=N` 与随后的 `LINE_START line=N / base` 一一对应，`a_line` 连续 | toggle bundled-data 采样**正确** |
| 数据通路 | `pixels_data_mismatch = 0`（所有有效像素逐字节与期望一致，三种时钟都是 0） | 搬字节/字节序**正确**，只是"迟到" |
| 总线 | 理想从机（无限带宽、背靠背、`R_LAT=0`）仍 99.83% | 瓶颈**不在总线** |

### 4.4 66.67 MHz（对照，好的样子）

```
t= 585020  REQ_ISSUE next_line=1 ; t= 585085 LINE_START line=1
t= 589992  vde_begin vy=1 hdr=1 wl=321      ← 显示开始时写指针已在 321（且速率领先）
t= 604345  POPS_FULL line=1 fill_ns=19260   ← 在行 1 结束前 2.9 µs 就填完了
t= 607252  pix_end   vy=1 inv=0             ← 1280/1280 全部有效
```

写指针（1.0 像素/aclk = 1.49 像素/pix_clk）**始终跑在显示指针前面**，所以永不读空。
`avg_wl_at_vde_begin` 在 66.67 MHz 是 322/1280（25%）、在 50 MHz 是 644/1280（50%）——
后者看着更"高"，但它对应的是**上一行**的残余（`hdr_line < in_vy`），正是"落后一整行"的特征。

## 5. 结论

1. **根因（哪一级握手）**：丢在 **AXI 域"行缓冲写侧"的弹像素泵**——`pop_en`/`pops_done`
   的吞吐硬上限是 **1 像素 / s_axi_aclk**。PIX→AXI 的 toggle 请求握手、AXI→PIX 的
   行头 toggle + gray 写进度、BRAM 真双口、字节重排、帧号采纳**全部工作正常**（数据 0 错）。
   不是"请求发太快被覆盖"（那是次生现象）、也不是"应答没等到"、更不是"AXI 采样漏了"。
2. **量化门槛**：`f_axi ≥ f_pix · W / H_TOTAL`。720p60 ⇒ **57.57 MHz**；
   37.11/50 低于它 ⇒ 每行读空（`0x2C` 每行 +1，≈43 200 行/s）；66.67 高于它 ⇒ 0。
3. **板端 45000 行/s 的解释**：720×60×0.999 = 43 200 行/s，与板端比值 1.04，同一机制。
4. **37.11 MHz 档（板端未测，仿真是唯一信息源）**：只要它 < 57.57 MHz 就必然每行读空，
   且更早塌（请求被覆盖更严重：1200 行只发出 772 次请求、跳过 428 行）。
   结论：**37.11 MHz 必定全黑，不可用**。

## 7. 下一步建议（**只建议，未改任何 RTL**）

按"改动小 → 改动大"排序，前两条是真正解决问题的：

1. **行缓冲改 ping-pong（双行缓冲），请求提前一行**
   现在"填第 N+1 行"只能在第 N 行显示结束后开始，可用窗口 = 1 行。
   改成两行缓冲后，在第 N 行显示期间就取第 N+1 行 ⇒ 窗口变 2 行，
   门槛降到 `f_axi ≥ W·f_pix/(2·H_TOTAL) = 28.8 MHz`（720p60），
   三档里 37.11 MHz 也能用。**不动握手、不动寄存器图**，最贴合现有架构。
2. **把写侧吞吐从 1 像素/aclk 提到 ≥2 像素/aclk**（更彻底）
   BRAM 用 72/144-bit 宽口按"拍"写（一次 beat 写 8 字节 = 2⅔ 像素），
   像素化只在 PIX 侧读口做；这样写侧可达 2.67 像素/aclk，门槛降到 ~21.6 MHz。
   代价：BRAM 端口宽度 ×3、写侧需要跨拍字节拼接（现有 `room` 机制可复用）。
3. **修 toggle 握手的"请求被覆盖"**（次生问题，但会让故障形态从"半屏"变成"整屏"）
   `rq_line/rq_tog` 扩成 2~4 深小 FIFO，或让 PIX 侧只在"上一请求已被受理且 FSM 空闲"时才发
   （需要把 `fst==F_IDLE` 回传到 PIX 域，或让 `req_ack` 在 `F_FIN` 完成时才更新）。
4. **契约/PS 侧护栏（不改 RTL 也能做）**
   把 `f_axi ≥ f_pix·W/H_TOTAL` 写进 `docs/camera/05_HDMI输出_PS_PL接口契约.md`：
   720p60/1080p30 用 74.25 Mpx/s ⇒ ≥ 57.6 MHz；1080p60（148.5 Mpx/s，H_TOTAL=2200）
   ⇒ ≥ 129.6 MHz。PS 侧启动自检：读一次 `0x2C`，非 0 就报警/自动提高 FCLK。
5. **板端临时 workaround（已验证方向，非本轮范围）**
   `s_axi_aclk` 直接给 100 MHz：填充 12.8 µs，余量 74%，`0x2C` 必为 0。

## 8. 已知限制（诚实边界）

- 本 TB 只例化 `hdmi_fb_scan.v` 单体（+ 内联时序发生器），**没跑 `hdmi_out_top` 顶层**，
  也没跑 OOC 综合/时序分析；`hdmi_out_top` 里 `in_vsync = vs_rise`、`cfg_enable = ctrl_enable && !ctrl_test`
  的接线已在 TB 中按其行为对齐。
- AXI 从机是**理想从机**：无仲裁抖动、无 DDR 行冲突、无跨时钟桥。因此本报告给出的是
  **下界证明**（"最理想的从机下都不行"），板端只会更差，不会更好。
- BRAM 用行为模型（无输出寄存、无读延迟变化），未建模 BRAM 的 2 拍输出寄存器。
- 未注入 `cfg_soft_reset` / 帧号切换 / 模式切换等场景（里程碑 1 只要求复现频率现象）。
- 上次代理留下的 `runs/fbscan_cdc_fix/`（旧 TB 与日志）**未被修改**，那份 720p 日志的
  "50 MHz ⇒ 719 行/帧读空"与本报告结论方向一致，但其 `need_pops_per_aclk` 指标口径可疑
  （把 W 除以了错误的行拍数），本报告**没有引用它的任何数字**。
