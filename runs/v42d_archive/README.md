# v42d 隔离构建存档（T-48，2026-11-02）

> 运行点：`xc7z015clg485-2`、Vivado 2025.2.1、**构建约束 10.000 ns**（v39 配方逐字复刻；真实 150 MHz 由运行时 `fclk0_mhz` 设定）

## 〇、这一版为什么存在

v42c（`eecc6e80`）数据错且**非确定**：板端 64² 两次 sha1 互不相同、且都不等于冻结；**在 100 MHz 下仍然错**（同一 session 里 v39@100 MHz 两次都对、都命中冻结）⇒ **不是时序违例，是功能 bug**。
v42c 相对 v39 只动了两样：**① T-34 的 4 个只读计数器**（含 `clr_t34` 挂 `start_fire` 与写 `0x25C`）、**② `PF_AHEAD` 1→2**。
v42d 的作用就是把这两个嫌疑**拆开**：RTL 回到 v39 原文，**只**加计数器，预取参数一位不动。

## 四、W3：资源对照（同一份 report 口径）

| 资源 | v39 实测 | **v42d** | Δ(v42d−v39) | v42c（参考） |
|---|---:|---:|---:|---:|
| Slice LUTs | 20,552 | **20,408** | **−144（−0.70%）** | 20,407 |
| └ LUT as Logic | 19,744 | **19,600** | −144 | — |
| Slice Registers | 18,963 | **18,997** | **+34（+0.18%）** | 18,997 |
| Block RAM Tile | 35 | **35** | 0 | 35 |
| DSPs | 101 | **101** | 0 | 101 |
| Register as Latch | 0 | **0** | 0 | 0 |

**两个必须记账的偏差（不是"通过"就能盖掉的）**：
1. **预期 LUT +130 没有出现，实测 −144。** 网表指纹证明计数器**确实在网表里**（4×32 = **128 个触发器**、每个计数器 34 个 LUT + 8 个 CARRY4，见 `check_latch_v42d.log`），所以 −144 不是"计数器没进去"，而是 **opt/place 在控制集打包与 LUT 合并上的整体重映射**（`-control_set_opt_threshold 8` 下新增 128 个 FF 会改变打包与合并方式，LUT 总数可以反向下移）。判据按"几乎不变（Δ<1%）"过，但**方向和预期相反**，下一轮若要用资源差做归因，别拿"计数器 ≈ +130 LUT"当先验。
2. **FF 只 +34，但计数器本身是 128 个 FF。** 差出来的 ≈94 个是同一原因：QoR 抖动把一部分 FF 推进了 BRAM/DSP 的内部寄存器（Slice Registers 口径才少）。网表指纹才是"计数器在不在"的判据，报告口径的 FF 总数不是。

## 六、这个位流能不能回答"计数器是不是元凶"？

**能，而且只有它能。** 判读矩阵（与 v39 / v42c 三点对照，同一份 PS 侧脚本、同一冻结输入）：

| v39 | v42d（v39+计数器） | v42c（v39+计数器+`PF_AHEAD=2`） | 结论 |
|---|---|---|---|
| 对 | **对** | 错 | ⇒ 元凶 = **`PF_AHEAD=2` 的预取簿记**；计数器**清白**，0x250..0x25C 可以放心留用 |
| 对 | **错** | 错 | ⇒ 元凶在**计数器逻辑**（`clr_t34` / 计数器 always_ff 与读通路的耦合）——**必须先修计数器再谈任何预取改动** |
| 对 | 对 | 对 | ⇒ v42c 的错**不由这两项单独决定**（复现条件缺失/偶发），本轮隔离无效，需重设计 |

所以上板只需**一件事**：拿 `d3434a06…` 跑 v39 已经在跑的那条 64² 判据（两次 sha1 vs 冻结值）。**不必跑性能、不必跑大尺寸**——只要"两次都命中冻结"就足够落第一行结论。
（提醒：本版是**隔离件**，WNS +0.120 @10 ns 只是构建口径；真要长期用，仍须按既有门槛做 6.667 ns 审计。）
