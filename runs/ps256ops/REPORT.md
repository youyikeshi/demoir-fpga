# 256² 整网 PS 侧「非卷积 6.49 s」拆解 —— 查清 + 削减方案

**日期**：2026-10-31　**范围**：只碰 CPU 侧。**没跑 vivado、没改 RTL/比特流、没上板**
（板端实测留给主线跑，见 §7 的一条命令）。
**新增文件**：`runs/ps256ops/{prof_ops2,fit_model,ab_catpack,board_ops}.py`、
`pynq_specialized_code/ps/pynq/bin_catpack.py`（**纯新增，不改任何现有模块的现有行为**）。
**现有代码改动**：**0 行**（`bin_net.py` / `bin_engine.py` / `bin_ref_numpy.py` 一行没动）。

## 0. 一句话结论

> **6.49 s 不是一个"杂项"，它是三个算子的字节搬运：**
> **`cat` 2.44 s（37.6%）+ `interp` 1.88 s（28.9%）+ `convfp` 1.42 s（21.9%）= 5.74 s = 88.4%。**
> 剩下的 `sam 0.40 / eca 0.26 / add 0.08` 加起来 0.74 s，**其中 eca 85% 是 Python 调用开销**。
> PS 侧这 5.74 s **已经没有 numpy 层面的余地**（三项都贴着"必须搬的字节 ÷ 413 MB/s"），
> 只有两条路：**消掉 concat（−2.4 s，代码已写好并逐字节验过）** 和 **把这几个单元搬进 PL（−3.5 s）**。

三条最要紧的：

1. **上一个报告（ps256 §2）的 `convfp ≈ 3.9 s / interp ≈ 2.0 s` 是错的**，错因是
   "主机占比 × 6.49"。主机的 memcpy 比板端快 40~200×（中位 ~60×），gemm 只快 6×，
   **两个比例差一个数量级**，所以按占比缩放会把 `cat` 低估 47%、把 `interp` 高估 40%。
   本报告改用**两个独立的板端标定**（§1.3），两者互相印证到 ±3%。
2. **`eca` 不是热点**（4.0%），尽管任务里点名了它。现状 `FAST_ECA=0`（因为快速版差 16 ULP 被否掉），
   走的是参考实现的 `2×1584` 次 `np.dot`，板端 64² 实测 0.126 s ⇒ **纯 Python 调用开销，
   而且只值 0.12 s**。**不要在这里投入**。
3. **`cat` 是最大的一块，而且它是唯一"能在 PS 上直接消掉"的**：116 次里 110 次的终点是
   `binarize_pack`，而二值化逐通道独立 ⇒ **不需要把 float32 的 concat 物化**。
   已实现 `quant_pack_parts()` 并做了 **110 处 + 227 层 + 84 处嵌套 + 边界数据** 的逐字节 A/B（**0 差异**）。

## 1. 阶段 1：6.49 s 花在哪（先测量，再标定）

### 1.1 方法学：逐 op 直接计时，**没有"残差"这一步**

先纠一个容易踩的坑：`bin_net.run()` 里的 `ps_nonconv = sum(prof.values())` 是
**每个 `_exec_ps(op)` 用 `time.perf_counter()` 单独包出来再加总**，不是 `wall − Σconv`。
所以板端那个 **6.49 s 本身就是逐 op 钩子的和**（`25.80 + 6.49 + 3.28 = 35.57 ≈ PS 35.58` ✓），
没有"书签法"的误差。**剩下的唯一问题只是：这 168 个 op 各占多少？**

本报告的做法（`runs/ps256ops/prof_ops2.py`）：

| 环节 | 做法 | 为什么这样 |
|---|---|---|
| 建图 | **直接调生产代码** `bin_net.BinNet.build_graph()` | op 集合/顺序/形状不可能与线上失配（手抄镜像会失配，`runs/psops/net2.py` 就有这个风险） |
| conv | 零成本桩（按 `(cout,Ho,Wo)` 缓存常量张量） | 计时里 PL 贡献 0，PS 算子拿到形状/dtype 正确的输入 |
| 计时 | **每个非卷积 op 单独包 perf_counter** | 串行执行 ⇒ Σ = wall，没有残差 |
| 抗噪 | ①整网跑 1 遍焐热（`fp_layer`/索引缓存/分配器）②再对每个 op 就地重复 7 次取 min | **必须**：单次直测时小 op 被首次 mmap 缺页污染 **60×**（实测 `decoder_2` fp conv 12.7 → 0.19 ms） |

**交叉校验（这条决定整张表能不能信）**：
- 主机三种口径：冷启动 **0.375 s** / 整网热单遍 **0.233 s** / 逐 op 稳态 **0.118 s**。
- 板端 64² 的非卷积是 **0.60 s**（board_150v15 ⑥）/ **0.49 s**（psops §6.1 两次独立 A/B）。
  主机 64² 对应 0.110 / 0.048 / 0.031 s ⇒ 比值 **5.5~19×**，**比值本身随口径变 3.5 倍**，
  这说明"拿主机数乘一个系数"不可能对（下一节给出为什么）。
- 逐 op 稳态 Σ=0.118 s 与主机热单遍 0.233 s 差 2×（因为稳态复用了缓冲、热单遍每次新建），
  **这是口径差，不是漏项** —— 所以下面标定用的是"字节数×平台常数"，不是主机时间。

### 1.2 op 普查（平台无关，精确）

`256²` 的图有 **395 个 op = 227 个 conv + 168 个非卷积**：

| kind | 调用次数 | numpy 调用次数 | 说明 |
|---|---:|---:|---|
| `cat` | **116** | 116 | `np.concatenate`，输出 501.8 MB |
| `interp` | **26** | 312 | 14 次上采样（出 27.3 MB）+ 12 次下采样（出 3.4 MB） |
| `convfp` | **4** | 64 | 全精度卷积，0.769 GFLOP |
| `eca` | **6** | **3216** | 2×1584 个 9 元素 `np.dot`（**占全部 numpy 调用的 85%**） |
| `sam` | **6** | 42 | 三分支加权 |
| `add` | 6 | 6 | 残差 |
| `shuffle`/`unshuffle` | 3 / 1 | 12 | pixel shuffle |
| **合计** | **168** | **3768** | |

> 注意"numpy 调用次数"这一列：A9 上**一次 numpy 调用 ~19~39 µs**（板上实测），
> 而 `cat` 一次只算 0.2 M 元素。**只要 op 数×调用数大，字节少也会慢** —— eca 就是这种。

### 1.2.1 任务清单里列的算子，哪些**其实不在**这 6.49 s 里（自己核实的结果）

任务里说"非卷积算子包括 eca / sam / bilinear / add / 逐元素激活、缩放、z-score 归一 / 反量化量化的其它部分"。
按 `build_graph()` 的实际 op 集合核实，**只有前四项存在**，其余都在别处：

| 任务里列的 | 核实结果 |
|---|---|
| `eca` | ✅ 存在，6 次（`eca_attn()`，float32 sigmoid） |
| `sam`/`sam_blocks` | ✅ 存在，6 次（**只有收尾的加权 `sam` 计在这 6.49 s 里**；SAM 内部的 ghost/b0/b2/b4 全是 conv，走 PL） |
| `bilinear`/`interp` | ✅ 存在，26 次 |
| `add`/残差 | ✅ 存在，6 次 |
| **逐元素激活（RPReLU）** | ❌ **不存在独立 op**：227/227 层的 RPReLU **已融进 `bin_conv_core` 的收尾流水**（`bin_net.py` 顶部注释 + board_150v15 ①②），所以它算在 PL 的 11.28 s 里 |
| **缩放 / z-score 归一** | ❌ 本网拓扑里**没有**这两种算子（我遍历了 395 个 op 的 `kind`，只有上面 8 种） |
| **反量化/量化的其它部分** | ❌ **不在 6.49 s 里**：量化+二值打包在 **prologue（25.09 s）**，反量化在 **epilogue（3.28 s）**，两者是 `run()` 里另外两个钩子。**别把它们重复算进非卷积** |
| （额外发现） | `shuffle`×3 + `unshuffle`×1 = 0.014 s，pixel 重排，可忽略 |

⇒ 所以"6.49 s 里还藏着别的"这个担心可以排除：**它就是这 168 个 op**，
而且 88% 集中在三个算子上。

### 1.3 板端标定（两条独立路径，互相印证）

成本模型（平台无关）：`T_k = c_mem·M_k + c_flop·F_k + c_call·N_k`
其中 `M_k` 是**实现真正搬的字节**（从源码语义数出来，§1.4），`F_k` 是 FLOP（只有 convfp 非 0），
`N_k` 是 numpy 调用次数。

**路径 A：只用两个板端总量**（64²=0.60 s、256²=6.49 s）解 3 个未知数里的 2 个（c_flop 取板上实测 737 MFLOP/s）：

```
c_mem = 2.36 ns/B (= 424 MB/s)   c_call = 55 µs
自洽性：板端 memcpy 实测 190~605 MB/s ⇒ c_mem 应落在 1.65~5.26 ns/B ⇒ 实际 2.36 ✓
```

**路径 B：用 psops 的板端逐算子实测当锚点**（`interp 176.8 / convfp 108.5 / sam 27.9 / add 4.5 ms`，
同一份实现，**真跑出来的**），加两个总量做最小二乘（6 方程 3 未知数）：

```
c_mem = 2.42 ns/B (= 413 MB/s)   c_flop = 1.17 ns/FLOP (= 853 MFLOP/s)   c_call = 56 µs
残差：interp -24%  convfp -15%  sam -2%  add +19%  64²合计 +0.5%  256²合计 0.0%
```

两条路径的 `c_mem` 差 2.5%、`c_call` 差 2%，而且 **c_flop 出来的 853 MFLOP/s 与板上直接实测的
737 MFLOP/s 只差 16%** —— 这是"模型没编"的最强证据。**下面用路径 B**（它有 4 个真跑出来的锚点）。

### 1.4.1 和上一轮（`runs/psops`）的对账：**手法都用上了，但有一个等价性结论是错的**

psops 那轮做了 6 项，**当前 6.49 s 里已经全部生效**（所以我没重复）：

| psops 的手法 | 现状 | 我复核的结论 |
|---|---|---|
| `bilinear_f32`（1.42×） | ✅ 在 `bin_ref_numpy:511`，`bin_net.interpolate` 默认走它 | 生效；但**已经没有余量**（§2.2） |
| `conv2d_f32`（1.66×） | ✅ 生效 | 生效；算力已到参考 BLAS 上限 |
| `sam_mix_f32`（1.18×） | ✅ 生效 | 生效；已到 15 B/元素 |
| `tune_malloc`（cat 1.2×） | ✅ `bin_net.py:59` 导入即执行 | 生效 |
| `fp_layer` 缓存 | ✅ 生效 | 生效（eca 内的权重加载已不占时间） |
| **`eca_attn_f32`（7.2×）** | ❌ **`FAST_ECA=False`，默认关闭** | ⚠ 见下 |

⚠ **审计发现（值得记一笔）**：psops REPORT §5.3 写"验证：sha1 逐字节相同。sgemv 与 sdot 的累加顺序一致"，
但它在 §1 的可信性论证里用的是 **`net2.py --stub`** —— 桩给的是**常量张量**，
于是每个通道的值都相同，`gemv` 和 9 元素 `np.dot` 必然得到同一个数。
**那次 A/B 是空验。** 而 `bin_net.py:61-68` 的注释（后来的实测）写明：
用**真实激活**时 1584 个通道里 **614 个不同、最大 16 ULP**。

⇒ 两条教训，写在这里给后面的人：
1. **等价性 A/B 不能用常量/均匀/随机数据**，必须用**真实激活**（随机数据在 `_windowed_dot` 上也是 0 差异，
   因为随机权重/激活下 9 元素点积的差异被淹没了 —— psops 自己也在注释里写了这点）；
2. 所以 **`eca` 这 0.12 s 的优化到现在仍然是"未拿到"的状态**，而它只占 1.8% ⇒ **放过它**。

### 1.5 为什么"主机占比 × 6.49"会错（和 ps256 的数字对账）

同一份主机测量按占比缩放 vs 本报告的板端标定：

| 算子 | 主机占比×6.49 | 板端标定 | 差 |
|---|---:|---:|---:|
| `interp` | 2.56 | 1.88 | **+36%** |
| `convfp` | 2.13 | 1.42 | **+50%** |
| `cat` | 1.25 | 2.44 | **−49%** |
| `sam` | 0.28 | 0.40 | −31% |

根因：主机/板端的"减速比"**逐算子不同**（本机实测：memcpy **24~38 GB/s**、gemm **4.4 GFLOP/s**；
板端 memcpy **0.19~0.61 GB/s**、gemm **0.737 GFLOP/s**）⇒ memcpy 差 **40~200×**（中位 ~60×）、gemm 差 **6×**。
`cat` 是纯 memcpy（板端相对更吃亏），`convfp` 是纯 gemm（板端相对没那么吃亏），
**所以任何单一缩放因子都会把这两者的份额搞反。**

## 2. 阶段 2：逐算子判断（**交付 ②**）

> 门槛：占比 >5% 的只有 `cat` / `interp` / `convfp` / `sam`；`eca` 4% 也一并给结论（因为任务点名了）。

| 算子 | 占比 | 算术强度 | 内存/计算受限 | 能否硬件化 | 能否重叠 |
|---|---:|---|---|---|---|
| `cat` | 37.6% | **0 FLOP/B** | 纯内存（413 MB/s，就是板上 memcpy 速度） | **不需要单独硬件**：折叠进"打包单元"的多源描述符即可（§5 方案 A） | ❌ 消费者一定是 conv ⇒ 卡在同一条链上。只有**分支级**并行（SAM 的 b0/b2/b4）可用，而现有调度器已经吃到了（全网总重叠只有 4.58 s，且大部分被 prologue 占了 —— 见 §2.1） |
| `interp` | 28.9% | **~0 FLOP/B**（25 B/元素） | 纯内存（408 MB/s）+ gather 索引 | ✅ **RTL 里已经有 `bin_interp`**，只是 BD 无实例、PS 无驱动。搬运量可从 767.6 MB 降到 57.5 MB | ❌ 同链（`sam` 的 x2/x4/b*_up 与 `feat_up` 都是 conv 的直接前驱） |
| `convfp` | 21.9% | **5.17 FLOP/B** | **计算受限**（853 MFLOP/s 参考 BLAS；交叉点在 1.2 FLOP/B，实际 5.17） | ✅ 值得：0.769 GFLOP，200 DSP @100 MHz = 20 GMAC/s ⇒ **19 ms**；且 **K 方向串行累加可以逐位复刻**（§5 方案 C） | ❌ 是 decoder 每一级的收尾，输出直接进 `shuffle` |
| `sam` | 6.2% | 0 FLOP/B | 纯内存（15 B/元素，理论下限 11 B） | ✅ `bin_sam` RTL 已有（`sam_int8` 也已在 PS 侧验过），同样缺 BD 实例/驱动 | ❌ 是 SAM 块的收尾 |
| `eca` | 4.0% | 0（**不是带宽，是调用数**） | **调用受限**：3216 次 numpy 调用 × ~56 µs = 0.18 s | ⚠ **不建议**：全局均值 + sigmoid，PL 化要先定 Q1.14 量化点 ⇒ 非等价 | ❌ 依赖 3 个 ghost 分支全部完成（它本来就是"汇合点"，PL 此时已经没活） |
| `add`/shuffle | 1.3% | 0 | 纯内存 | 不值得 | ❌ |

### 2.1 重叠：**这三个算子基本没有重叠空间，别指望调度器**

板端对账：`42.28 = PL 11.28 + PS 35.58 − 重叠 4.58` ⇒ **全网只有 4.58 s 的 PS 工作被 PL 藏住**，
而且 ps256 §6.1 的记账显示其中 ~4.93 s 来自 **prologue**（独立分支的预打包），不是非卷积算子。
机制上也是必然的：`cat/interp/convfp/sam/eca` 的**唯一消费者都是紧邻的下一个 conv**，
它们必须等上游 conv 的 `done`，下游 conv 又必须等它们算完 ⇒ **串行**。
⇒ **想把 6.49 s 藏进 PL 是做不到的；只能让它变少或搬走。**

### 2.2 为什么 PS 侧"没有余量了"（这一节回答"还能不能抠"）

| 算子 | 现状 | numpy 可达下限 | 余量 |
|---|---|---|---|
| `cat` | 1003.6 MB（读+写各 501.8） | 就是 memcpy：1003.6 MB | **0**（`np.concatenate` 已是 memcpy；唯一出路是不搬） |
| `interp` | 25 B/输出元素 | 4 次 gather + 4 次乘 + 3 次累加，numpy 无 FMA ⇒ **≥25 B** | **0**（我已试过"把 3 次 `+=` 合并"，会改变加法顺序 ⇒ 非等价；分块/切片优化只对 12 次下采样有效，而它们只占 interp 的 11%） |
| `convfp` | 参考 BLAS 853 MFLOP/s | 参考 BLAS 就是 737~853 MFLOP/s | **0**（换 OpenBLAS 会改浮点结果 ⇒ 非等价） |
| `sam` | 15 B/元素 | 11 B/元素（3 次 `+=` 不可省，省了就改加法顺序） | 12%，且要冒等价风险 ⇒ 不值 |
| `eca` | 3216 次调用 | 逐位等价的向量化**不可能**（gemv 与 9 元素 `np.dot` 的累加顺序不同，实测差 16 ULP） | 只能靠"9 次顺序向量乘加"（≈34 次调用）换 ~0.12 s，**要板端验证**，收益 1.8% ⇒ 不建议 |

## 3. 阶段 3：已实现的优化（**交付 ③**）

### 3.1 做了什么：`quant_pack_parts()` —— 消掉 concat

**位置**：`pynq_specialized_code/ps/pynq/bin_catpack.py`（**新文件，不改任何现有模块**）

**为什么这是免费的**：`cat` 的输出 100% 流向 `_PlBackend.prepare()` 的 `pack_input()`，
而 `pack_input` 只需要 `bit[c] = (x[c] > adj[c])` —— **逐通道独立**。
所以"先 concat 再打包"与"各 part 分别打包再按通道拼位"**逐位相同**。

两个必须成立的前提，本网 100% 满足（**全量验证，不是抽样**）：

| 前提 | 检验 | 结果 |
|---|---|---|
| 每个 part 的 `C % 8 == 0`（否则一个字节会跨 part） | 116 个 cat 的 **328 个 part** | **0 例外** |
| `cin % 8 == 0` | `BinLayer._validate` 硬校验 227/227 | ✓ |
| 64 通道（8 字节）的字可能跨 part ⇒ **组字必须在拼接之后做** | 实现里各 part 只产出 `(hw, C_i/8)` 字节列，写进同一个 `bb`，最后一起 `bb.view(uint64).T` | ✓ |

### 3.2 逐字节 A/B（**0 差异**）

`python3 runs/ps256ops/ab_catpack.py --hw 256` / `--hw 64`：

| 检查 | 覆盖 | 结果 |
|---|---|---|
| **A. 8 通道闭合** | 116 个 cat × 全部 part | **0 例外** |
| **B. 嵌套 cat 结合律**：`concat(展开的叶子)` == `cat 实际输出` | **84 处嵌套**（rdb 的 `cat(y, t_)` 链） | **0 处不符** |
| **C. `quant_pack(concat)` vs `quant_pack_parts`** | **110 处 `cat→conv`**（全部会用到 part 打包的位置） | **sha1 0 处不符** |
| **C2. 逐层** | **227 层 × 2 个分辨率 = 454 次** | **0 层不符** |
| **C3. 边界数据**（元素恰等于阈值 / ±1 ULP / ±0 / ±inf） | 6 层（含最大层） | **0 层不符** |

**≥30 层的要求达成 15 倍**（454 层次，0 差异）。

### 3.3 耗时对比 + **为什么默认关闭**（这条必须说清楚）

| 分辨率 | `cat + quant_pack`（现状） | `quant_pack_parts` | 结论 |
|---|---:|---:|---|
| 64² | 0.0341 s | **0.0158 s** | **2.2× 更快** |
| 256² | 0.1275 s | 0.1326 s | **慢 4%** |

**为什么 256² 反而慢**：现状的 `quant_pack` 走 **C 内核 `bpack.c`**（0.44 ns/元素，主机），
而 `quant_pack_parts` 是 numpy（0.97 ns/元素）—— 在 256² 上"省下的 concat"抵不过
"打包慢了 2.2×"。64² 上相反，因为那里 110 次 concat 的**每次调用/分配开销**占主导。

⇒ **结论（很关键的工程判断）：`cat` 能不能消掉，不取决于算法，取决于打包内核吃不吃 part。**
板端这个差距更大（C 内核 ~7~15 ns/元素 vs numpy ~74~123 ns/元素），
所以**在板端 numpy 版 parts 会慢 10×**，必须让 **C 内核支持"多段 + 通道偏移"**。

**需要的 C 改动（~20 行，`bpack.c`）**：把 `bpack_f32` 里
`int c0 = (b * 8 + i) * 8;` 改成先加偏移 `c_off`、越界就 `continue`，
并把 `memset(out, 0, ...)` 提到"第一段之前做一次"。签名：

```c
void bpack_f32_add(const float *x, const float *adj, int c_off, int cin,
                   int hw, int cb, uint64_t *out);   /* out 由调用方零初始化一次 */
```

板端预计收益（按 §1.3 的 c_mem=2.42 ns/B）：
`E_cat 可消 = 2 × (501.8 − 33.0) = 937.4 MB ⇒ 2.27 s`。
**默认关闭的理由**：`bpack.c` 正在被"打包搬进 PL"那一路改，我不并行动它
（同一文件的并发修改风险 > 2 s 的收益）。**代码与验证都已交付，接线是 3 行：**

```python
# ① bin_engine：加一个 pack_input_parts(parts, L)（或让 C 内核吃 c_off）
# ② bin_net._PlBackend.prepare：
data = e.pack_input_parts([t.val for t in op.args["parts"]], L) if op.args.get("parts") \
       else e.pack_input(op.deps[0].val, L)
# ③ bin_net.build_graph：cat 的消费者是 conv 时，把 conv 的 deps 换成 cat 的叶子（cat 变"虚节点"）
```
（③ 是唯一有风险的一步：要重算 `g.dependents`，否则 `BV_FREE` 会在 conv 之前释放叶子张量。）

### 3.4 另外两项"做了但没启用"

| 项 | 状态 | 收益 | 不启用的理由 |
|---|---|---|---|
| `BIN_FAST_ECA`（gemv 版 eca） | **仍然默认 0**（我没动它） | 0.12 s | 差 16 ULP，**已确认非等价**；而且 0.12 s 只占 1.8% |
| `bilinear` 下采样用切片替 gather（12 次 `x2/x4`） | **没实现** | <0.1 s | 那 12 次只占 interp 的 11%，索引流量省下来不到 0.1 s，不值得引入新代码 |

## 6. 我不确定的地方（**交付 ⑥**）

1. **`interp` 的份额最不稳**：模型给 1.88 s，但 64² 锚点比模型**高 24%**
   （实测 176.8 ms vs 模型 133.7 ms）。如果把这个偏差带到 256²，interp 可能是 **2.2 s**，
   相应地 cat/convfp 各少 0.2~0.3 s。⇒ **`interp` = 1.9±0.35 s（情景表里 2.20 s 那一行就是上限）。**
2. **`convfp` 取决于 cout=12 的瘦 gemm 在 A9 上的效率**：853 MFLOP/s（标定值）⇒ 1.42 s；
   若只有 400 MFLOP/s ⇒ 2.34 s。**这是第二大不确定项。**
3. **`c_mem = 2.42 ns/B (413 MB/s) 是把 5 个算子摊平后的等效值**，不是单点实测。
   它在板上 memcpy 区间（190~605 MB/s）之内，但"gather 型访问比 memcpy 慢"这件事
   我只能从 interp 的残差间接看到。
4. **`eca` 的 0.26 s 有 0.18 s 是 c_call=56 µs 推出来的**，而板上直接实测（psops 的 64² 日志）
   是 3216 次调用 / 0.126 s ⇒ **39 µs/次**。用 39 µs 则 eca = 0.20 s。差 0.06 s，不影响排序。
5. **板端 64² 的非卷积总量本身有两个值**：0.60 s（board_150v15）与 0.49 s（psops 两次 A/B）。
   差 22% 是会话间抖动。我用 0.60 做锚点，用 0.49 做了敏感性（差异 <3%）。
6. **`quant_pack_parts` 的板端收益 2.27 s 是"字节数 × c_mem"的推算**，没在板上跑过。
   一旦 C 内核支持 part，收益应该就是可消那 110 处的全部（因为字节是精确的）。
7. **主机 vs 板端"逐算子减速比"我只验证了 4 个锚点**（interp/convfp/sam/add）。
   `cat` 的板端绝对值没有独立锚点（psops 的 137.4 ms 是 206 次 cat 的旧拓扑，字节数不可比）。
   ⇒ **`cat` 的 2.44 s 由"1003.6 MB ÷ 412 MB/s"支撑，其中 412 MB/s 是从锚点标定出来的。**
   **这条最值得花一次板端实测去钉死**（§7 的脚本 30 秒就能给出）。
8. **没考虑**：256² 的 726 MB 工作集造成的页/缓存抖动（`BV_FREE=1` 是必要条件）；
   如果 TLB/缺页成本更大，`cat`（写 501.8 MB 新缓冲）会比模型更贵。

```bash
# ── 主机（不需要板子）─────────────────────────────────────────────
cd runs/ps256ops

    xilinx@192.168.7.2:demoir/ps/pynq/
ssh xilinx@192.168.7.2 'cd demoir/ps/pynq && \
    python3 board_ops.py --hw 256 --hw2 64 --json board_ops.json | tee board_ops.log'
```

`npdot9_1152_calls_ms`（预期 20~45 ⇒ 钉死 eca）。
