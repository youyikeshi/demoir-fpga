# 非卷积算子搬进 PL —— 设计方案（**只设计，不实现**）

**日期**：2026-10-31　**配套报告**：`runs/ps256ops/REPORT.md`
**铁律遵守情况**：本文件**没有改一行 RTL、没有跑 vivado、没有动 `board/`**。
PL 侧现在有别的活在跑（打包迁移 + conv 引擎提速），所以这里只给接口/数据流/描述符/预算。

---

## 0. 先说结论：搬什么、能收回多少

按 `REPORT.md` 的两点标定，256² 的 6.49 s 非卷积里：

| 算子 | 板端（标定） | 搬 PL 之后（本节估算） | 收回 |
|---|---:|---:|---:|
| `cat` ×116（110 次可消） | **2.44 s**（可消 2.27 s） | **0.17 s**（余下 6 处喂 eca） | **2.27 s** |
| `interp` ×26 | **1.88 s** | 0.07~0.10 s（`bin_interp`） | **1.79 s** |
| `convfp` ×4 | **1.42 s**（保守 2.35） | 0.02~0.03 s（浮点卷积单元） | **1.39 s** |
| `sam` ×6 | 0.40 s | 0.05 s（`bin_sam`，RTL 已有） | 0.35 s |
| `eca` ×6 | 0.25 s | 不建议搬（见 §5） | 0 |
| `add`/`shuffle`/`unshuffle` | 0.09 s | 不值得搬 | 0 |
| **合计** | **6.49 s** | **PS 剩 ≈0.55 s / PL 多 ≈0.75 s** | **≈5.94 s** |

> ⚠ 这 5.94 s 不是"凭空消失"：它变成 **PL 侧约 0.75 s 的新增工作量**
> （DDR 搬移 + 打包）。只有 PL 的 conv 引擎和这几个单元**并发**，整网才真的掉 5.6 s。
> 目前是单引擎串行，所以**要么加一条并行的 DMA/打包通道，要么接受"PL 时间 +0.9 s"**。

---

## 1. 为什么"搬 PL"是唯一出路（而不是继续在 PS 上抠）

| 算子 | 实测/建模的算术强度 | PS 现状 | 还有没有 PS 余地 |
|---|---|---|---|
| `cat` | 0 FLOP/B（纯搬运） | 1003.6 MB @ 424 MB/s | **没有**：`np.concatenate` 就是 memcpy |
| `interp` | ~0 FLOP/B（25 B/输出元素） | 767.6 MB 实现搬移 | **没有**：25 B 已是 numpy 的下限（REPORT §3） |
| `convfp` | 5.2 FLOP/B | 参考 BLAS 0.737 GFLOP/s | 只有换 BLAS，**会改浮点结果**（非等价） |
| `sam` | 0 | 15 B/元素 | 没有（已到 11~15 B 的下限） |
| `eca` | ~0（**全是 Python 调用开销**） | 3216 次 numpy 调用 | 有，但只值 0.12 s，且需板端逐位验证 |

一句话：**PS 侧的地板是"必须搬的字节数 ÷ 424 MB/s"，6.49 s 里 96% 就是这些字节。**
真正能改的只有两件事：**少搬字节（消 cat）** 和 **换一个搬得更快的执行单元（PL）**。

---

## 2. 方案 A：PL 打包单元直接吃「未拼接的分区」（消掉 `cat`）

### 2.1 为什么可行（这是本方案的核心不变量，已逐字节验证）

`cat` 后面紧跟的一定是 `binarize_pack`（116 次里 110 次的终点是 conv 的 prologue）。
而二值化是**逐通道独立**的：

```
bit[c] = (x[c] > adj[c])            # 与同层的其它通道完全无关
```

所以「先拼接再逐通道比较」与「逐分区比较再把位拼起来」**逐位相同**。
两个必须成立的前提，本网 100% 满足（`ab_catpack.py` 全量验过）：

1. 每个 part 的 `C % 8 == 0`（116 个 cat 的 348 个 part，0 例外）⇒ **没有字节跨分区**；
2. `cin % 8 == 0` 由 `BinLayer._validate` 硬校验（227/227）⇒ 最后一个字节组不残缺。

⚠ 一个 **64 通道**（= 8 字节）的字可能跨 part ⇒ **"组 64-bit 字"这一步必须放在拼接之后**，
不能简单地把各 part 的 `quant_pack` 结果首尾相接。PS 侧参考实现见
`pynq_specialized_code/ps/pynq/bin_catpack.py:quant_pack_parts()`。

### 2.2 接口（PL 侧）

```
描述符（每层一个，放在 PS 侧的一个小数组里，64 B 对齐）：

offset  size  field
   0      4    magic / version
   4      4    n_src            ; 1..3（本网 cat 最多 3 段；允许 4 段留余量）
   8      4    H
  12      4    W
  16      4    cin              ; = Σ C_i，必须 % 8 == 0
  20      4    H*W 的字节数？    ; 保留
  24      4    src0_pa  ┐
  28      4    src1_pa  ├ 物理地址（每段必须 64 B 对齐；对齐不满足时 PS 侧先 copy）
  32      4    src2_pa  ┘
  36      4    thr_pa          ; 逐通道阈值表（float32，cin×4 B，64 B 对齐）
  40      4    dst_pa          ; 输出：ceil(cin/64) 个 64-bit 字 / 像素
  44      4    dst_stride      ; 字节/像素组（正常 = 8·ceil(cin/64)）
  48      4    flag            ; bit0 = 末组补零，bit1 = 阈值取反（保留）
  52      4    crc/guard
```

- **不再有「拼接后的 float32 张量」**：DDR 里只有各 conv 的原始输出（本来就在）。
- 每段只需要「起始通道号 + 通道数」，因为打包是逐通道的：
  `dst_byte[(c0_i + j)/8]` ← 第 i 段第 j 个通道的位。
- 逐通道阈值表由 PS 侧从容器的 `t_q` 换算（现成的 `bin_engine.pack_thresh()`）。

### 2.3 数据流

```
conv_{k-1} 完成 → OUT 缓冲（int8 C8）→ read_out 反量化成 float32 张量 T_i   ← 现状不变
                                          │
（cat 在这里被跳过）───────────────────────┼──► 打包单元按 n_src 段读 T_0..T_2
                                          │        │
                                          └────────┴──► 二值字（19 MB）→ 下一层 IN 槽
```

PS 侧只剩：**"把 3 个 part 的地址/通道号填进描述符"**（3 次 MMIO 写）+ 阈值表缓存。
这就是 `bin_catpack.quant_pack_parts()` 想做的事，只是从 CPU 换成 PL。

### 2.4 预计耗时

| 项 | 字节 | 估算 |
|---|---:|---:|
| 读 110 处 cat 的**分区原始数据** | 468.7 MB | 468.7 MB ÷ 0.8 GB/s ≈ **0.59 s** |
| 写二值字 | 12.9 MB | 忽略 |
| 相比现在 | cat 1003.6 MB + PS 打包读 468.7 MB | **省 1003.6 MB ≈ 2.44 s**；但可消的只有 110 处 ⇒ **2.27 s** |

> 注意：这 0.59 s 是**打包单元**的 DDR 读，和 conv 引擎抢同一条 DDR。
> 若打包与 conv 不能并发，净收益 = 2.27 − 0.59 = **1.68 s**；能并发则是 **2.27 s**。

## 3. 方案 B：`interp` 交给 `bin_interp`（1.83 s → ~0.08 s）

现状：**RTL 里已经有 `bin_interp`，但 BD 里没有实例、PS 也没有驱动**
（`bin_net.capabilities()` 里写明），所以 26 次插值全在 PS 上用 float32 做。

- PS 侧实现要搬 25 B/输出元素（4 次 gather + 4 次乘 + 3 次累加），共 767.6 MB；
  PL 侧只需要「读一次源 + 写一次目标」。
- 字节：输入 26.8 MB + 输出 30.7 MB = **57.5 MB** ⇒ 57.5 ÷ 0.8 GB/s ≈ **72 ms**
  + 26 次 × ~50 µs 描述符开销 ≈ 1.3 ms。
- **收回 1.75 s。**

### 3.1 接口

沿用现有 conv 单元的存取风格（IN/OUT 槽 + 描述符 + start/done）：

```
desc: mode(1=up 2=down) H W HO WO C scale_num scale_den
      src_pa dst_pa
      自动生成的 4 组索引/权重表（PS 侧算一次、按形状缓存：
      bin_ref_numpy._idx4() 已经有了，26 次插值只有 6 组不同形状）
```
- ⚠ **必须逐位等价**：PS 现实现的算式是
  `((1-ty)(1-tx)a + (1-ty)tx b) + ty(1-tx)c) + ty tx d`，**左结合顺序固定**。
  PL 定点实现要复刻这个顺序与舍入，否则 sha1 会变。
  历史教训：`BIN_FAST_ECA=1` 因为 16 ULP 被否掉过。
- 建议第一步**只在 PL 里做"取数 + 4 个乘积"**（dump 到 DDR），
  加和在 PS 上做 —— 这样不引入新的舍入点，风险最低。此时 PL 搬 4×输出 = 123 MB
  ⇒ 154 ms，PS 只剩 3 次加法（9 B/元素 = 276 MB ⇒ 0.65 s）。收回约 1.1 s。
  第二步再把加和搬进去（需要 PL 里用 float32 加法单元）。

## 4. 方案 C：4 个全精度卷积搬进 PL（1.55 s → ~0.03 s）

| 层 | 权重 | cin→cout | k | 输出 | MAC |
|---|---|---|---:|---:|---:|
| `encoder.conv_first.0` | 48×12×5×5 | 12→48 | 5 | 48×128×128 | 235.9 M |
| `decoder.decoder_1.conv` | 12×64×3×3 | 64→12 | 3 | 12×128×128 | 113.3 M |
| `decoder.decoder_2.conv` | 12×64×3×3 | 64→12 | 3 | 12×64×64 | 28.3 M |
| `decoder.decoder_3.conv` | 12×64×3×3 | 64→12 | 3 | 12×32×32 | 7.1 M |
| **合计** | | | | | **384.6 M MAC = 0.769 GFLOP** |

- 算力：Zynq-7020 有 220 个 DSP48E1。按 200 MAC/cycle @100 MHz = 20 GMAC/s
  ⇒ 384.6 M MAC ÷ 20 G = **19 ms**。
- 带宽：读 ~6.3 MB + 写 ~4.1 MB = 10.4 MB ⇒ 13 ms。
- ⇒ **20~30 ms**（受 DSP 数限制），相对 1.55 s 收回 **1.53 s**。
- ⚠ 三个 `decoder_*.conv` 是 **cout=12**（M=12 的瘦 gemm），
  PS 参考 BLAS 在这里效率极低（主机实测 1.05~4.7 GFLOP/s，差 6~26×），
  这正是 1.55 s 的主要来源。**PL 的 DSP 阵列对 cout=12 也不友好**
  （输出通道太少），建议流水按 `cout` 方向做 12 路并行 + 输入复用。
- 数值：**float32 累加顺序会变** ⇒ 与 PS 的 BLAS 结果不逐位相同。
  ⇒ 这条**不是等价优化**，必须走"改基线 sha1"的流程；或者 PL 用
  float32 顺序累加（K 方向串行）来复刻 —— 那样只能跑到 1 MAC/cycle/单元，
  220 DSP ⇒ 仍要 384.6M/(220×100M)= 17.5 ms，**顺序累加也能到 17 ms**，
  所以"逐位复刻"在这里是可行的（K=576/64 串行）。这一点很关键，建议照此设计。

## 5. 不建议搬的两类

| 算子 | 为什么 | 建议 |
|---|---|---|
| `eca`（0.25 s） | **85% 是 3216 次 numpy 调用**（2×1584 个 9 元素 `np.dot`），不是数据。板端 64² 实测 eca=0.126 s ≈ 3216×39 µs ⇒ 纯 Python 开销 | 不要搬 PL。若真要省，用"9 次向量乘加（顺序与 BLAS 一致）"把它压到 34 次调用 ⇒ 省 ~0.12 s，但**必须板端逐位验证**（历史上有 16 ULP 翻车） |
| `add`/`shuffle`/`unshuffle`（0.09 s） | 太小，描述符开销就吃掉一半 | 留在 PS |

## 6. 落地顺序建议（按"收益 ÷ 风险"）

| 顺序 | 动作 | 收回 | 风险 | 依赖 |
|---|---|---:|---|---|
| 1 | 打包单元改成 **n_src 多源描述符**（方案 A） | **2.27 s**（或 1.68 s 若不能并发） | 低（纯搬地址，判据仍是 `x>adj`，`ab_catpack.py` 已全量验过逐字节等价） | 正在做的打包迁移 |
| 2 | 4 个 fp conv 进 PL（方案 C，**K 方向顺序累加**以保逐位） | **1.53 s** | 中（要新 DSP 流水） | 新单元 |
| 3 | `interp` 分两步搬（先取数，后加和） | 1.1 → **1.79 s** | 中（舍入顺序） | `bin_interp` 加 BD 实例 + 驱动 |
| 4 | `sam` 用 `bin_sam` | 0.35 s | 低（`sam_int8` 已在 PS 侧验证过） | `bin_sam` 加 BD 实例 + 驱动 |
| | **合计** | **≈5.94 s** | | |

**做完 1+2 就能把非卷积从 6.49 s 压到 2.5 s 以内（PS 侧）；再做 3+4 到 ~0.55 s。**

## 7. 我不确定的地方

1. **PL 侧 DDR 有效带宽 0.8 GB/s 是假设值**（没有实测）。若只有 0.4 GB/s，
   方案 A 的打包读要 1.2 s、方案 B 要 0.14 s —— 收益会缩水 20~30%。
   → 需要一次 PL DMA 带宽微基准（可以和 conv 引擎的 `rd/fill` 计数一起做）。
2. **打包与 conv 能否并发**决定了方案 A 是 2.38 s 还是 1.79 s。
3. **`bin_interp` 的现有 RTL 能不能做 float32 加和**（如果只有定点，就必须先定 int16 量化点，
   那就变成"非等价"改动）。
4. **方案 C 的 DSP 预算**：220 个 DSP 是全片的，conv 引擎已经占了一部分；
   真正能分给 fp conv 的可能只有几十个 ⇒ 时间从 20 ms 变成 60~100 ms，
   但仍然远小于 1.55 s，结论不变。
5. 没有考虑 **功耗/散热**：这些单元同时开，7020 的动态功耗会明显上升。
