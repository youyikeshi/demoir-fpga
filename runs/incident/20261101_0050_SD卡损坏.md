# 事故：板端 SD 根文件系统损坏（2026-11-01 00:50 定案，证据确凿）

## 一、决定性证据（同一文件读两次 md5 相同 ⇒ 不是偶发读错，是盘上内容坏了）

```
正常 .so 的 ELF 头 : 7f 45 4c 46 01 01 01 00 00 00 00 00 00 00 00 00      ← 正确
损坏的 _lsprof.so  : fe 7f 10 00 1c 07 21 f9 fe 7f 10 00 1c 07 21 f9      ← 8 字节图案重复
```
- 文件：`/usr/lib/python3.10/lib-dynload/_lsprof.cpython-310-arm-linux-gnueabihf.so`
- import 时报 `invalid ELF header`
- `md5sum` 两次一致 ⇒ **盘上就是坏的**，不是缓存/读取抖动

## 二、连带症状（全部由它解释）
| 症状 | 机制 |
|---|---|
| `sudo -S -p "" true` → **rc=139 段错误**（每次都崩） | sudo 或其依赖的库文件被写坏 |
| `find ... .so` 类操作段错误 | 同上 |
| `ValueError: bad marshal data (invalid reference)` | `.pyc` 被写坏 |
| `pynqmetadata/.../metadata_vis.py` import 失败 | 依赖的 pyc 坏 |
| 之前判定的"金丝雀被写坏 4096/4096" | **环境坏了导致，不是 RTL 越界** |
| 之前判定的"v39 也 segfault" | 同源 |

## 三、我之前的两次错误诊断（都已作废）
1. **"SD 被 core dump 写满"** —— 错。用户实测 `df` 28%、inode 6%。
2. **"板端源码陈旧导致 segfault"** —— 部分对（源码确实旧，已同步），但不是主因。
3. 真正的连环误导：`sudo` 崩了 ⇒ 所有走 sudo 的脚本都 139/CANARY 失败 ⇒ 我一度以为 RTL 有问题。

## 四、可控与不可控
- **不可控**：换不换卡、什么时候换。
- **可控**：宿主侧资产完好 —— bit、DCP、manifest、RTL、`runs/v40_archive/` 全在，**一行没丢**。

## 五、修复路径（按优先级）
1. **换一张新 SD 卡**（A1/A2、U3、工业级），重刷 PYNQ 镜像。这块卡已被写坏到系统级，`fsck` 未必救得回。
2. 若坚持用原卡：装到 PC 上 `fsck.ext4 -f /dev/sdX2`，把 `fsck` 报出的文件从镜像里补回；至少要 `apt install --reinstall sudo python3` 与重装 pynq 包。
3. 无论哪条，恢复后**第一件事**：`df -h / && df -i / && sudo true && python3 -c "from pynq import Overlay"`，四条全过才做实验。

## 六、防复发（比修更重要的部分）
- **断电前必须 `sync; sync; poweroff`**——今晚两次硬断电都发生在系统正在写盘时。
- 上板脚本统一在结束后 `sync`。
- 板端只读验证优先（`--no-download`），减少写操作。
- **任何"板端行为异常"先查三件事**：`df -h`、`sudo true` 的 rc、`python3 -c "import ctypes"`。
  这三条能在 10 秒内区分"我的代码错"与"系统坏了"。

## 七、今晚结论有效性
- **v40 功能未验证**（"金丝雀"失败发生在系统已损坏之后，**不可作为 v40 有 bug 的证据**）。
- 00:36 之后的板端结果一律作废。
- 21:37 的"v40 bit 可安全 load、基址与 fclk 正确"那次**有效**（当时 sudo 还能用）。
