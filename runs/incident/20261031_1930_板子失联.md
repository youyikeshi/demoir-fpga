# 事故报告：板子失联（2026-10-31 19:30 发现，19:12 左右发生）

## 现象（主机侧独立复核）
- `ping 192.168.7.2`：3 包 0 收，100% loss
- `ip neigh`：`192.168.7.2 dev enp0s31f6 INCOMPLETE` ⇒ **ARP 层就不通，不是 TCP/SSH 层**
- 本机网卡 `enp0s31f6`：`UP / LOWER_UP / carrier 有` ⇒ 网线与本机 PHY 正常
- `ssh`：`No route to host`

⇒ 结论：**板子侧无响应（hang 或已重启但没起来）**。PYNQ 正常重启 60~90 s，此时已远超，偏 hang。
⇒ **需要人在板子边上断电重启**，我无法远程恢复。

## 触发过程（子代理自述 + 我的编排失误）

1. 19:12 前后，一个子代理在板端 `/tmp/psd` 跑探针，60 秒内做了 **3 次真实 `Overlay(download=True)`**：
   - #1 下载 2.49 s 成功 → 自己的探针 bug（`wrap()` AttributeError）退出
   - #2 下载 2.21 s 成功 → 同一个 bug 退出
   - #3 `p2_mmio.py` **无任何 stdout**，随即失联
2. 它把"一个 session 只 load 一次"理解成"一个 ssh 一次" ⇒ 3 个 ssh = 3 次真重载。
3. **我的编排失误（主要责任）**：我同时给**两个**子代理派了上板任务（cfg 优化 + f32 叶子审计），并各自独立判断"可以上板"。
   ⇒ 没有任何板级互斥机制 ⇒ 两个代理可能同时在板端跑，且都在重载 overlay。
4. 全程没有 kill / pkill / reboot，看门狗没被碰。

## 根因
**板子没有被"一个全局租约"保护。** 我此前只把它写成文字纪律（"一个 session 只 load 一次"），
没有做成机制 —— 而今晚刚在三个地方证明过"靠人记的规则必然被绕过"（vlock、tde、memgate）。

## 修复（必须做成机制，不是再写一条纪律）
1. **板级全局锁**：`/tmp/dsh_board.lock`（flock），所有上板命令必须包在 `boardlock.sh` 里
2. **load 计数令牌**：一次 session 只签一个 `download=True` 令牌，第二个直接拒绝
3. **单代理原则**：同一时刻只允许一个代理持有板子（租约 30 分钟，超时自动释放）
4. **失联检测前置**：任何板端脚本启动前先 ping，不通就不许跑

## 影响
- 上板实测全线阻塞（cfg 0.374 s、f32 叶子 197 MB、PF_AHEAD、融合验证）
- **本地工作不受影响**：xsim、RTL、v40 构建、设计文档都能继续
- 已冻结的 v39 基线（8.096 s / 54-54 sha1）数据完好，未受损
