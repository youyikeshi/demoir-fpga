## 6. ★ 核心发现：8.096 s / 6.485 s **今天复现不出来**，且**不是代码的锅**

### 6.1 现象

| 代码 | numpy 臂 256² | C 臂 256² |
|---|---|---|
| 冻结点（git HEAD `b58964e`） | **13.436 s** | **11.657 s** |
| 2026-11-01 跑点（`cdf4b9a9`/`f848a29c`，从板端取回） | **13.616 s** | **11.714 s** |
| 2026-11-01 **报告**里的值 | 8.058 s | 6.485 s |

### 6.2 对照实验（这是"机制"，不是猜）

`runs/board_ops/20261102/control_20261101/`：把 `bin_net.py`/`bin_engine.py` **只换这两个**
为 2026-11-01 那份（md5 `cdf4b9a9`/`f848a29c`，与 REPORT 声明**逐字符相符**），
其余 5 个文件、驱动函数、位流、频率、槽数、开关**全同**，同一 boot，`--no-download` 复用
已加载 overlay（不二次 load）。

结果：**13.616 / 11.714 s ⇒ 仍然是 13 秒级，不是 8 秒级。**
⇒ 那 5.4 s 的差**不能**归因于 `bin_net`/`bin_engine` 的代码差异。

### 6.3 桶级证据：算法相关的桶一个都没变

| 桶（numpy 臂） | 20261101 报的 | 今天·冻结点 | 今天·20261101 代码 | 判读 |
|---|---|---|---|---|
| `interp` | 1.899 | **1.921** | **1.932** | **1.00×（完全一致）** |
| `convfp` | 1.163 | 1.209 | 1.251 | 1.00–1.04× |
| `cat` | 0.128 | 0.128 | 0.151 | ≈1.0× |
| `nonconv` 合计 | 3.596 | 3.663 | 3.746 | +2~4 % |
| `prologue` | 1.580 | **5.811** | **6.006** | **≈3.7×** |
| `epilogue` | 0.257 | **1.182** | **1.188** | **≈4.6×** |
| PL 忙 | 3.054 | 4.016 | 4.051 | ≈1.3× |
| `wait` | 0.633 | 1.526 | 1.423 | ≈2.4× |
| **total** | **8.058** | **13.436** | **13.616** | **+67~69 %** |

⇒ **与内核/算法相关的桶逐项不变**（所以不是算法变了、也不是 CPU 算得慢了：
  若 CPU 变慢，`interp` 这种 gather 密集的纯 CPU 桶不可能 1.00× 不变）；
  偏差集中在 `prologue`/`epilogue`/PL/`wait` —— 即**数据搬运与 cache 维护**那一侧。

### 6.4 已证伪的假设：`BIN_F32POOL`

`bin_net.py` 自己的注释写着"池关 ⇒ 每层整块 cache 维护量 ×5.5，会把 epilogue 的收益
吃回去"，而 epilogue 正好 ×4.6 ⇒ 定向实验（同进程、同 arena、同输入，只切这个开关）：

| 跑法 | total | prologue | **epilogue** | interp |
|---|---|---|---|---|
| `BIN_F32POOL` 未设 | 12.561 | 5.927 | **1.184** | 0.994 |
| `BIN_F32POOL=1` | 13.998 | 7.081 | **1.210** | 0.744 |

**⇒ 证伪**：epilogue 没掉（1.184 → 1.210），总时间反而更慢。
（附带约束：建完 66.22 MB 的 24 槽 arena 后 `CmaFree = 0.33 MB`，而 `CmaTotal = 256 MB`
却只剩 ~64–70 MB 可用 ⇒ f32 池在这种情况下**根**本建不起来，只能静默回落。）

> 该实验里 numpy/C 臂没有显式设定（HEAD 的默认值是 `"1"`），所以它的 `interp` 桶
> （0.994 / 0.744）**不能**与 §3/§4 的 1.92 / 0.27 并列比，仅用于比"同一跑法下开关前后"。

### 6.5 结论（明确区分"已证实的"与"未查清的"）

- **已证实**：① 今天这块板、这次 boot 上，8.096/6.485 用**任何一份现存代码**都复现不出来；
  ② 差异不在算法内核（`interp/convfp/cat` 逐项 1.00×）；
  ③ 差异不在 `bin_net`/`bin_engine` 的代码差分（对照实验直接否掉）。
- **未查清**：真正的成因。**最可能**是 2026-11-01 那次会话带了**没有记录下来的环境/板状态**
  （代码里一共 consult **≥20 个** env 变量，任何开关表都只记了 6~11 个；候选：
  `BIN_FAST_ECA` / `E1E2_DESC` / `E1E2_DBG` / `BIN_CAT_THREADS` / `BIN_GEMM_THREADS` /
  `NET_TPOLL` / `BIN_LAZY_DEBUG` / `CATPACK_LAZY_MB` / `Q8CACHE_VERIFY`，以及 CPU 频率/
  热状态/CMA 碎片）。**我没有测它们，所以不下结论。**
- **对后续的要求（机制，不是纪律）**：跑点记录必须包含 `env | sort`（或至少代码实际
  consult 的全部 env 键）+ `/proc/meminfo`(CMA) + `cpufreq` 读数，否则"跑点"不闭合。

### 6.6 ★ 因此：跨代码 md5 / 跨会话的数字**一律不许直接比**

- 本次跑点引擎 `ddfe6b6f`，与 6.485 那次的 `f848a29c` **不可直接比**；
- 而且本次已证明：**即使换成 `f848a29c` 也仍然不可比**（同一 boot 上它给 11.714 s，
  而报告里是 6.485 s）⇒ 差异里还含"未记录的会话状态"这一项；
- **唯一可用的跨跑点量**是同一进程内、同一跑法下的**臂间差**与 **`interp` 桶**。
  本报告 §2/§3/§4 的所有结论都只用这两类量，没有一处依赖跨会话绝对时间。

## 10. 结论摘要（给主代理）

1. **⑤ 64²@150**：numpy 3.3155（中位）/ C 3.2015 中位，best-best **−3.99 %**，
   `interp` **−69.9 %**（0.157→0.047）；sha1 **10/10 全中**。与 brief 的 −4 % 预期吻合。
2. **⑥ seed=2 的 256²**：两臂输出**逐位相同**（两轮皆 ✓）⇒ 收益不是"对单一输入碰巧成立"；
   `selftest("full")` **36 形状全过**。
3. **⑦ `16efab60` 已找回并入库**，"永久丢失"的旧结论**作废**；它与 HEAD 只差 C 内核挂钩，
   numpy 内核体逐字节相同。
4. **★ 最重要的一条**：**8.096 s / 6.485 s 今天用任何现存代码都复现不出来**
   （冻结点 13.44 / 换回 20261101 代码 13.62），且**已证伪**"是 bin_engine/bin_net 的锅"
   与"是 BIN_F32POOL 的锅"。差异全部落在 prologue/epilogue/PL/wait 这些**搬运侧**桶。
   ⇒ 结论只能写到"**极端可疑：2026-11-01 会话带了未记录的环境/板状态**"，
     **不准写成"已定位"**。后续任何"跑点"记录必须补 `env` + CMA + cpufreq。
5. **跨代码 md5 / 跨会话的数字不许直接比**——本报告只用"同进程臂间差"与 `interp` 桶下结论。
