## 1. 两个尺寸下的全部关键量（算数，逐条给出位宽需求）

`VLANES=16`；256² 的 unshuffle(2)×2 在 **PS/numpy** 侧完成（`bin_net.py:170` 明确写 "pixel_unshuffle **无 RTL**"），
所以 **PL 见到的最大的 H、W 是 128、128**，最大像素数就是 16384。

| 量 | 公式（文件:行号） | 64²（32²） | 256²（128²） | 最小位宽 |
|---|---|---|---|---|
| `npix`（组内像素） | `w21:1677-1680` | 1024 = 2^10 | **16384 = 2^14** | 15 |
| `plane_delta`（C8 平面步长） | `w21:1681` `npix<<3` | 8192 = 2^13 | **131072 = 2^17** | 18 |
| `plane_stride`（核侧组步长） | `c50:696` `hout*wout*VLANES` | 16384 = 2^14 | **262144 = 2^18** | 19 |
| `hw8` | `c50:163` `(H*W)<<3` | 32768 | 131072 | 18 |
| 每层写拍 `npix*cout/8` | `w21:1677-1681` | 8192 = 2^13 | **131072 = 2^17** | 18 |
| 行内线数 `W/16` | `w21:2436` | 2 | 8 | 4 |
| 整层激活线数 `cb*H*W*8/128` | `w21:330 LC_N=512` | 256（**全驻留**） | **4096（8× 超容）** | — |
| 单个 C8 平面字节 | `w21:1681` | 8192 | **131072** | 18 |

**位宽结论（复核 T-113，且加了新的两条）：**
- `pix_q/pix8/pbase_q/plane_delta/plane_stride/oaddr_q/hw8_q` **全部 ≥17 bit 且都在 32 位上下文**（我逐个看了声明：`w21:1672-1684`、`c50:180-200`、`c50:221-222`）⇒ **没有 16 位截断**。
- 「`H·W = 65536 = 2^16` 恰好」**只存在于 PS 侧**（`pixel_unshuffle`、`cat` 的 `hw=H*W` 偏移 `bin_engine.py:3919`，都是 Python int）⇒ **它不可能撑爆任何 PL 字段**。任务书线索①在 RTL 里**不成立**，在 PS 里也不成立（无固定宽度）。
- **唯一真正卡在 2^17 的是 `cnt_wbeat`：它是 16 位**（`w21:828` `logic [15:0] cnt_rdreq, cnt_fill, cnt_burst, cnt_wbeat;`）。**131072 mod 65536 = 0** ⇒ 256² 下这个 DBG 计数器**恰好回绕到 0**。这条见 §2（它已经误导了一次结论）。

## 2. 两条**必须撤回**的"证据"（比找 bug 更要紧）

### 2.1 `dbg_wbeats` 不能当"丢写拍"的判据 —— 16 位回绕 + 64² 上已有 53/227 不符

`runs/board_t115/ops_timing_{64,256}.csv` 逐 op 对账（我用 out_bytes/8 作期望值，`cout` 全为 16 的倍数时该式与
`npix*ceil(cout/16)*2` 逐值相等）：

| | 相符 | 不符 |
|---|---|---|
| 64²（**输出全对**） | 174/227 | **53/227** |
| 256² | 117/206（≤64 K 者） | 101（含 9 个 >64 K 的对上了回绕） |

⇒ 64² 输出正确却有 53 个 op 对不上 ⇒ **这个指标本身就不是"落盘拍数"**（它把 `be_open` 收笔、W_DR2 收笔、
`d=2/s=2` 的额外描述符都算进去），再叠 16 位回绕 ⇒ **256² 的 wbeats 差异不能作为"PL 丢了一半写"的证据**。

### 2.2 「PL 只干了约一半」是**模型口径伪影**，不是"少干活"

`estimate_cycles`（`bin_engine.py:319-323`）是**逐 oc 串行**模型：

```
per_oc = 10 + 2K + Hout*Wout*K + 10 ;   cyc = cout * per_oc
```

而核一拍算 **VLANES=16 个 oc**（`c50:700-760`，一拍一个 term，16 lane 并行）。
⇒ 该模型先天就是"纯算拍数"的 **≈16 倍**。用 T-115 的逐 op CSV 反算（50 MHz）：

| | Σcyc_meas | 纯算拍（`ceil(cout/16)*npix*K`） | **stall 因子 = 实测/纯算** |
|---|---|---|---|
| 64²（32²） | 69.9 M | — | **17～45**（按形状中位数） |
| 256²（128²） | 219 M | — | **9～20** |

⇒ 两个尺寸都远比"纯算"慢（访存受限），256² 的 stall 因子只是**掉到约一半**——因为它一行 128 像素、
一条 128 B 线覆盖 16 像素的复用率是 64² 的 4 倍。**逐像素拍数 180（64²）vs 135（256²）**，
总拍数 3.13× 对应 16× 像素，与"每像素访存成本下降"完全自洽。
⇒ **"PL 少做了约一半"没有被数据支持**；`ratio=0.48` 与 64² 的 `1.15~1.62` 是同一个模型的两个取样点，不是故障指纹。
（这也意味着 T-115 若按"数 seconds≈0 的 op"去找，很可能数出的是**短层**而不是**没跑**的层。）

## 3. 最可能的根因（按"能否解释 256² 必错 + 同跑不相同"排序）

我必须先说实话：**我把 `bin_conv_core_v50.v` 与 `bin_unit_axi_wrap_v50.v` 的地址/位宽/握手全部走完，
没有找到一条"1024 对、16384 必错"的确定性算错。** 逐条否证的记录在 §4。
所以下面是"**唯二能把 1024 与 16384 分开的结构性边界**"，而不是已定罪的算式。

### ① ★最可能：直接映射线缓存 —— 64² 的工作集**整个装得下**（256 条 < LC_N=512），256² 永远装不下（4096 条，8×）

**位置**：`bin_unit_axi_wrap_v50.v:330`（`LC_N=512`）、`:436-437`（`IDX_W=4, TAG_W=25`）、
`:2377-2404`（`lc_hash`）、`:2425-2436`（`fill_rd` 闸门与 `rd_hit`）。

**算两个尺寸的值**：

```
一条线 = RD_WIN_WORDS(16) × 8 B = 128 B            (w21:310, 440)
整层激活线数 = cb·H·W·8 / 128
   64² :  cb·32·32·8/128  =  64·cb   = 64…256 条   ≪ 512   ⇒ 整层驻留，暖机后几乎不再填线
   256²:  cb·128·128·8/128= 1024·cb  = 1024…4096 条 = 2…8× 超容 ⇒ 每一拍都在 miss/fill/evict
```

**为什么只有 256² 失效**：这不是"算错"，是**状态覆盖**。64² 下 `alloc/fs_*/pf_*/fill_rd` 这套机器只在
暖机时跑几十拍；256² 下它**每一层每一拍都在跑**。任何隐藏在这套机器里的窗口（fill 槽复用、
`fill_rd` 与 `lc_tag` 的同拍先后、预取 `pf_issue` 与需求 miss 抢同一槽）在 64² 上是**不可达状态**，
在 256² 上是**常态**。

**能否解释"同跑不相同"**：能，且是天然的解释 —— 哪一条线被谁挤掉、fill 与 demand 谁先到，
取决于 DDR/AXI 回程时序，两次跑不同 ⇒ 落点不同。

**修它改哪几行（不追求性能的最小改动，用来定罪而不是提速）**：
1. `w21:3319` 打印的 `LC_N` 参数由 512 → **4096**（128 B × 4096 = 512 KB = 56.8 个 BRAM36，板端 BRAM 只用 15/95，
   装得下）；一行改动、零逻辑改动，若 256² 变对/变稳定 ⇒ ①成立。
2. 若 BRAM 不够，退而求其次把 `RD_WIN_WORDS` 从 16 降到 8（线 64 B ⇒ 2× 条目数），或
   `w21:3319` 同处把 `PF_EN` 关掉（预取是纯性能特性，关掉只会变慢）。
3. 定罪断言（xsim 一层 128² 即可）：`store && (fill_rd && rd_hit)` 同拍 ⇒ `$error`。

### ② 次可能：16-lane 写串行化与写引擎的"吞拍许可"（T-113 的头号怀疑），我把它**降级**了

**位置**：`w21:1704-1713`（`beat_go` 分支）、`:1722-1734`（promote 分支）、`:1742` `wr_split_busy_i = p1_v`、
`:1576`（`u_wr_en_i = … cw_beat_en`）、`:2288-2295`（`u_ce_ns`/`wr_accept_ok`/`wide_pend`/`wr_wide_b`）。

**我把这条时序逐拍追完了，结论是它在本网络形状下是自洽的**（这是与 T-113 不同的结论，请据此销账）：
- 引擎的写源是 `u_wr_en_i`（`w21:1576`），它取的是 **`cw_beat_en` 这个寄存器**，核的输出 `c_wr_en` 从不直连引擎
  ⇒ 在第 T 拍 `beat_go=1` 覆盖 `cw_beat_en` 的同时，引擎读到的仍是**旧** `cw_beat_en`（beat0）⇒ **不覆盖、不丢拍**。
- `beat_go=1 ⇒ u_ce=1 ⇒ u_ce_ns=1 ⇒ wr_accept_ok=1 ⇒ wr_wide_b=1 ⇒ pw_* <= 旧 beat0`（`w21:2293-2295, 2932`）⇒ 那一拍必被吞。
- `pw_valid` 背靠背覆盖的担心不成立：`push_now` 含 `pw_valid`（`w21:2843`），所以"本拍推 W1、同拍装 W2"是允许的（1 beat/拍）。
- W_DR1 与 pw_valid 同拍双推 `push_beat`（`w21:2943` vs `:2987`）不可达：`drain_cond` 带 `!pw_valid && !wr_wide_b`
  （`w21:2826-2828`）⇒ 进 W_DR1 的那一拍 `pw_valid` 必为 0，W_DR1 那拍 `pw_valid` 仍为 0。
- **残留的唯一前提**：`c_wr_sel` 必须是 `8'hFF`（否则 `u_wr_wide_w=0`，一拍 128 位会被当**单字节**走
  `wr_byte` 逐字节路，`w21:2296-2297`，而串行化器只当它"拍已吞"）。本网 `cout ∈ {32,48,64,96,192}` 全是 16 的倍数
  ⇒ 每拍全 16 lane 有效 ⇒ `sel=8'hFF` 恒成立 ⇒ **本网不触发**。但这是一个真雷：**任何 `cout%16≠0` 的层会静默错**。

⇒ 排第 2 的理由：它能解释"丢 8 B"，但**解释不了 16× 的规模依赖**（每层的丢失概率与像素数无关，只是机会数 ×16）；
且 50 MHz 下仍错，而它的窗口是按拍的、与频率关系不大。

### ③ 第三条：`idx[3:0] = tag[3:0]` 在两尺寸下含义不同 —— 3 行窗口可用的索引位从 3 位掉到 1 位（已文档化）

**位置**：`w21:2388-2396`（作者自己写的实测记录）、`:2377-2404`（`lc_hash`，`idx[IDX_W-1:0] = tg[IDX_W-1:0]`）。

```
line 号低 4 位 = { 行内线号, 行号低位 }
  64² : W/16 = 2 ⇒ 行内线号 1 位 ⇒ idx[3:1] = iy[2:0]  ← 3 个 ky 抽头天然分开（d=1 时 9 条活线占 9 个 set）
  256²: W/16 = 8 ⇒ 行内线号 3 位 ⇒ idx[3]   = iy[0]    ← 3 行只剩 1 位可分，另 5 位全靠 idx[8:4] 的异或折叠加左旋去分
```
作者为 128² 加了奇数段左旋（`w21:2396-2404`）把别名从 180/240 降到 0/240（单点实测）。
**这只是性能（tag 是全 21 位精确比较，`:2431-2435`，别名不会错数）** ⇒ 我把排第 3，因为**它不能产生错数据**。

## 5. 必须先做的一件"销账"实验（我不许做，但它是唯一能定性的）

T-113 §0.1 的整条推理建立在一个**未经本轮复核**的前提上：
「v39 位流在 256² 是正确的参照（`9b1940c8/f86a7035/025757a8`）」。

- 那三个 sha1 是 **11-01 的旧 PS** 跑出来的；现在的 PS 多了 `Q8CACHE/BIN_PRECOMP/BIN_F32DIRECT/
  BIN_CAT_ECA_FUSE/BIN_EPI_NOINV` 一堆图级融合（`runs/board_t112/REPORT.md` §3 "下一步 3" 自己列了这条）。
- ⇒ 若 **v39 位流 + 当前 PS + 256²** 也不中冻结值，则根因**不在 lane16**，而在 PS 的尺寸相关路径，
  §3 的 ①②③ 全部作废。这一步比任何 RTL 断言都便宜（换 bit 不换 PS）。

若 v39 仍命中，则按 §3① 的两行改动（`LC_N 512→4096`）做一次 A/B：那是唯一能把
「1024 安全 / 16384 不安全」这条结构性边界从假设变成判据的实验。

## 6. 一句话结论

**没有找到"16384 处算术出错"的算式**（所有像素/偏移量最小需 17 bit，全在 32 位上下文；`65536` 只活在 PS 的 Python 里）。
**唯一能把 1024 与 16384 严格分开的结构性边界是线缓存容量**：64² 整层激活 64–256 条 < `LC_N=512`（全驻留），
256² 是 1024–4096 条（超容 2–8×）⇒ 填充/分配/预取这台机器在 64² 是**不可达状态**、在 256² 是**常态**，
与"必错 + 同跑不相同"的形状完全吻合，但**读代码无法定罪**（tag 是 21 位精确比较，容量不足本身只会变慢）。
"PL 只干一半"与 "wbeats 不符" 两条现成证据都**不成立**（模型口径伪影 + 16 位计数器回绕），请勿据其继续推断。
