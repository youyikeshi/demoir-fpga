# T-114：256² 整网错的根因 = 「槽数」还是「真逻辑错」？（实验 A + B）

**一句话**：**两个都不是槽数/CMA**。
**实验 A**：64² @50 MHz，槽数 2/4/8/24 各跑 2 次 ⇒ **8 跑全部命中冻结三 sha1、两次全同**（槽数无辜）。
**实验 B**：256² @50 MHz，**真的拿到了冻结尺寸的 24 槽 arena（66,224,128 B，逐字节等于 `boardops2_frozen.json`）** ⇒
**仍然错，而且两次互不相同**（`e1f6988c…` / `b7c1a957…`）。
$\Rightarrow$ **根因 = 只在 256² 出现的时间相关逻辑/调度错**（与槽数、CMA、频率、热无关）。

$\Rightarrow$ **B_MISS**：即便 24 槽、即便 arena 字节数与冻结基线**完全相同**，256² 仍错、两次仍不同。
（且两次的值与 T-112 那 7 个都不同 ⇒ 共 9 跑 9 个不同 sha1。）

### 2.1 顺带推翻一条旧前提：**CMA 从来不是墙，`CmaFree` 是误导性读数**

24 槽的 66.22 MB 是在 **`CmaFree` 只有 5.34 MB** 时**分配成功**的；分配后 `CmaFree` 只降了约 5 MB
（5.60→0.53 MB）。机理：本机 CMA 区是**可迁移区**，page cache 会驻留在里面对外表现为"已占用"，
真正要拿大块时内核把它们迁出去（同一 session 里 `drop_caches` 把 `CmaFree` 从 104→146 MB 也印证了这点）。
$\Rightarrow$ T-112 的"`CmaFree` 33 MB ⇒ 拿不到 24 槽（66 MB）⇒ 探针自动降到 8 槽"这条**混淆变量根本不存在**：
`pick_slots()` 的 `need ≤ 0.80×CmaFree` 只是**探针自己的保守闸门**，不是硬件限制。

## 3. 结论（一句话根因判定）

$$\boxed{\textbf{根因 = 真逻辑错（时间相关），不是槽数/CMA}}$$

- 槽数（在 `BIN_LAZY_DEQ=0` 下甚至结构上就**不是**变量：`bin_net.py` 第 2988-2998 行与第 3019 行里 `nbuf` 恒为 2，
  arena 的"槽数"只是一个尺寸旋钮，引擎永远只切 2 IN + 2 OUT）⇒ A 四档 + B 的 24 槽 三方互证。
- 留下两条**可直接用**的定量指纹，供下一轮定位：
  1. **PL 只干了约一半活**：64² 稳态 PL/公式 = 1.15–1.21（模型准），256² = **0.48–0.50**；
     PS 侧同样缩水（64² 2.5 s/227 op = 11 ms/op，256² 14.3 s/227 op = 63 ms/op，16× 数据只有 5.7× 时间）。
     ⇒ 有相当一部分 conv **PS 认为 done 了、PL 其实没做**（`0x310=0`、金丝雀、`err_code` 全干净 ⇒ 不是超时也不是越界）。
  2. **9 跑 9 个不同 sha1**（含本轮 2 个）⇒ 纯时间相关，非确定性。
  两者合起来最指向 **"sticky done / start 握手竞态"**：`bin_engine.wait()` 在 start 写下去之后立刻轮询
  `AP_RET.bit0`，而 RTL 的 done 是 sticky、只有下一次 start 才清 —— 若 PS 的第一次读早于 start 生效，
  就会读到**上一层的 done**，直接 `read_out` 未写完的 OUT（PS 记的 PL 时间≈0，结果每次不同，无任何错误位）。
  验证成本极低：给 `reap()` 记**每 op** 的 `(t0, t_done, seconds, est_s)`，数出 `seconds ≈ 0`/`≪est` 的 op 个数
  与位置（若集中在 256² 的长层/大 band 上即为命中）。
