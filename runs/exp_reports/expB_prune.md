# 实验 B：结构化通道剪枝 48/32/64/32 → 48/16/64/16（0.697× MAC）+ 微调

日期 2026-10-23 18:20–20:16（剪枝 + 零样本 + 60 ep 无蒸馏 + 30 ep 蒸馏，GPU 全程串行）｜`/data/work/ft_probe/`

## 0. 一句话结论

**知识保留式剪枝把 0.697× MAC 的代价压到"中位 −0.21 dB（vs 发布基线）"，但崩坏块 10 个（红线是 ≤5）⇒ 不建议直接上板。**
中位口径达标（≥−0.3），**红线不过**。详见 §4 判据、§6 归因、§8 上板时间。

代价口径要说清（很容易说错）：
- **等训练量对比（5.45 遍，都是 30 ep）**：B 中位 18.7843 vs CONTROL 19.5232 ⇒ **剪枝本身值 −0.74 dB**；
- 再训 5.45 遍（到 10.9 遍）只收回 **+0.195 dB**，所以**现在**B 落后 CONTROL 的 5.45 遍点 **−0.54 dB**；
- 稠密模型没有训到 10.9 遍，所以"CONTROL 的 10.9 遍上限"未知，−0.54 是**偏保守**的读法。

## 1. 剪枝方案（为什么必须这样剪）

### 1.1 先纠正一个结构误解（这是本实验最容易做错的地方）

`en_i / de_i = 32` **不是"一层 32 通道卷积"**，而是 `GhostModule` 里每个 `GhostBlock` 的**输出宽度**：

```
GhostBlock(inp, oup=32, ratio=2)
    init_channels = ceil(32/2) = 16   → primary_conv : Conv(inp, 16, 1×1, bias=False)
    new_channels  = 16                → cheap_operation: Conv(16, 16, 3×3, dense, bias=False)
    out = cat([x1(16), x2(16)], 1)[:, :32]        # 32 个输出槽 = 16 primary + 16 cheap
```

目标宽度 16 时**同一套代码**给出的是 `cat([x1(8), x2(8)])[:, :16]` = **8 primary + 8 cheap**。
⇒ "留 top-16"**不能任意挑 16 个通道**，必须**按槽位分组各留 8 个**（`ratio=2` 把 16 个槽焊死成 8+8）。
（另一个"留 16 个 primary、丢掉整个 cheap 分支"的方案不是 0.697× 的目标结构，会改 HLS 层表，不在本次范围。）

### 1.2 同步裁剪的三处（缺一处权重就对不上）

| # | 张量 | 变化 | 说明 |
|---|---|---|---|
| 1 | `primary_conv.weight` | `[16, inp, 1, 1] → [8, inp, 1, 1]` | 保留 out 槽 |
| 2 | `cheap_operation.weight` | `[16, 16, 3, 3] → [8, 8, 3, 3]` | 保留 out 槽 **+ 对应 in 槽**（cheap 的输入就是本 block 的 8 个 primary 槽） |
| 3 | `<GhostModule>.conv.weight` | `[inp, inp+B·32, 1, 1] → [inp, inp+B·16, 1, 1]` | 按列挑 |
| 3' | **`primary_conv` 的 in 维**（block b≥1） | `inp+B·32 → inp+B·16` | block b 的输入是前面所有 block 输出的 concat，也要跟着收 |

其余**全部逐元素不变**：`feature_num` 48/64 不动 ⇒ preconv / down / ECA / residual / decoder 的 concat 维全不变；
`primary_conv` 与 `cheap_operation` 都 `bias=False` ⇒ 丢输入通道不需要补偿 bias；
`GhostModule.conv` 输出通道数不变 ⇒ 它自己的 bias 也不动。

### 1.3 cat 布局（踩过的坑，见 §9-1）

`GhostModule.forward` 是 `t = torch.cat([_t, t], dim=1)` —— **新 block 的输出放在前面、x 在最后**。
所以 n 个 block 的最终顺序是 `[blk(n−1), blk(n−2), …, blk0, x]`，不是 `[x, blk0, …]`。
第一版按后者写，**零样本直接 −13.2 dB**（权重排列全错）。

### 1.4 重要性准则：激活幅值

- 网络上**没有任何 BatchNorm**（实测 0 层）⇒ 任务里说的"BN 缩放因子"这条路**不存在**。
- 采用：在 12 个随机训练块（512²）上前向，统计每个 `primary_conv` / `cheap_operation` 输出的
  **逐通道 mean|act|**，在各自 16 槽内取 top-8。
- 交叉验证（outgoing 1×1 列 L1 口径）：与激活口径的 top-8 重合率 primary 63.3% / cheap 56.7%（随机期望 50%），
  逐 block 相关系数 r=+0.12 ⇒ 两者只是**弱一致**。
- **决定性对比（保留的激活质量，8/16 槽）**：

| 准则 | 保留的激活质量 |
|---|---|
| **按激活选（本次）** | **0.684** |
| 按 outgoing L1 选 | 0.575 |
| 随机选 8 个 | 0.502 |

⇒ 激活幅值口径明显更优（L1 只比随机好一点，因为 1×1 列范数本身很平：max/min 中位仅 3.37，而激活是 10.33）。

### 1.5 加载与断言

- `load_state_dict(strict=False)`：`missing=0 unexpected=0`（所有 294 个 key 都能对上，240 个形状变化）；
- **逐元素断言**：240 个被裁剪层 = 发布权重对应切片（`torch.equal`），其余 54 个参数**逐元素相同**；
- **布局不变量自检**（关键）：把 `keep_primary=keep_cheap=16`（全留，inter 仍是 32）跑一遍流水线，
  要求**权重逐元素还原 + 输出最大绝对误差 0.000e+00**。
  ⚠️ 这个测试才是抓 §1.3 那类错误的唯一手段——"断言切片等于原张量"是抓不到的（切片本身没错，错的是顺序）。

参数：**1.5616 M → 1.0709 M（0.686×）**，与 exp3 的宽度实验完全一致。

10 个崩坏块（无蒸馏 e60）：`0005_2, 0023_1, 0035_2, 0036_2, 0054_1, 0060_2, 0063_0, 0063_2, 0063_3, 0094_1`

| 统计量 | 崩坏块 | 全体 400 块 |
|---|---|---|
| **gt_std（GT 亮度 std）中位** | **0.0129**（蒸馏 e90 上是 **0.0000**） | 0.1112 |
| moire_p90（摩尔纹强度）中位 | 90.8 | 56.0 |
| gt_std 落在全体 p25 以下的比例 | **80%**（e90 是 86%） | — |

⇒ **和 depthwise 那批是同一个机理：GT 极平坦（甚至完全纯色）+ 摩尔纹强。**
平坦块的 PSNR 几乎只反映"输出这一块的 DC/颜色准不准"，所以"少 16 个通道"的容量损失在平坦块上被放大成 −10 dB 以上。

反证：在这同样的 10 块上，**A（稠密同配方）的 Δ 中位也有 −4.41 dB**——这些块本来就脆；
而 A 只有 2 块跌破 −10，B 有 10 块。**非崩坏块的 Δ 中位是 −0.13（e60）/ −0.09（e90）**，主体是健康的，问题集中在尾巴。

### 6.1 崩坏块是不是"PSNR 太敏感、其实看不出来"？——不是，是真坏了

在这些块上直接量**平均绝对误差（MAE，/255）**：

| 模型 | 崩坏块 MAE 中位 | 最小 / 最大 |
|---|---|---|
| 发布基线 | **1.42 / 255** | 0.05 / 8.85 |
| B 无蒸馏 e60 | **30.18 / 255** | 0.50 / 70.55 |
| B 蒸馏 e90 | 19.20 / 255 | 0.90 / 56.25 |

发布版在这些纯色块上几乎完美（MAE 1.4/255），剪枝版输出**偏色 30/255 ≈ 12%**——这是**肉眼明显可见的颜色/亮度错误**，
不是"数值敏感"。⇒ **红线（崩坏块 ≤5）是真问题，不能当口径瑕疵放过。**

## 8. 上板时间推算（⚠️ 不是 0.699×43.55）

板端实测（`docs/部署/交付_20261023_整网52s.md`）：整网 **43.55 s**，其中 **conv 35.43 s（81.3%）**，
非 conv（sam_sum / cat / interp / eca / add / pixel_shuffle）**8.1 s**——**这部分剪枝完全不影响**。

> ⚠️ 该文档 §2.1 写的 "conv 44.21 s（84.4%）" 是**旧的 52 s 配置**的数（44.21/0.844 = 52.4 s，
> 也和文档标题"整网52s"对得上），不是 43.55 s 这一版。§2.2 的逐算子表才属于 43.55 s 版：
> 35.43+3.6+1.8+1.0+0.66+0.37+0.49 = 43.35 ≈ 43.55 ✓。**引用时不要拿 44.21 s 去乘比例。**

| 估法 | 假设 | 预计整网 |
|---|---|---|
| 朴素 MAC 线性 | 43.55 × 0.697 | **30.4 s**（偏乐观，忽略了非 conv 地板） |
| conv MAC 线性 + 非 conv 不变 | 35.43×0.697 + 8.1 | **32.8 s** |
| **按板端分层效率**（k1 8.34 GMAC↔28 s、k3 11.93↔13 s、k5 0.94↔3.6 s） | 只有 k1 与稠密 k3 缩小 | **≈37.5 s** |

⇒ **现实预期 33–38 s（约 −13% ~ −24%），不是任务里写的 ~35 s 以下**。
原因：节省的 MAC 集中在 k=1（8.34→4.74，−3.6 GMAC）和稠密 k=3（−2.84 GMAC），
而 k=5（3.6 s）与 8 个"其它 k=3"层（8.14 GMAC）一点没动，**它们占了 conv 时间的 40%**。
上板前必须实测；另外 k=1 单元是 16 车道，剪枝后大量层退到 8 通道，**车道利用率可能只有 50%**，
实际 conv 时间可能比 35.43×0.697 更难降。

## 9. 坑（按踩到的顺序）

1. **`cat([_t, t])` 的顺序**：新 block 输出在前、`x` 在最后（`[blk(n−1)…blk0, x]`）。
   我第一版按 `[x, blk0, …]` 写，零样本 **−13.2 dB**。
   ⇒ 结构化剪枝**必须**有一个"全留 ⇒ 输出逐元素相同"的不变量测试；"断言切片等于原张量"抓不到顺序错误。
2. **`primary_conv` 的 in 维也要裁**（block b≥1 的输入含前面所有 block 的输出）。漏了会 size mismatch。
3. **`en_i=32` 不是一层卷积**，而是 GhostBlock 输出宽度；`ratio=2` ⇒ 目标 16 必须是 **8+8**，不能任意挑 16 个。
4. **没有 BatchNorm** ⇒ "BN 缩放因子"准则不存在；只能用激活统计。而 outgoing 列 L1 在本网络是很弱的代理
   （保留激活质量 0.575 vs 激活口径 0.684）。
5. **`conv.weight` 是 1×1**（`[out,in,1,1]`），算列范数要 `sum(dim=(0,2,3))`。
   只写 `.sum(0)` 会得到 `(C,1,1)`，`argsort` 静默返回全 0 —— 我因此一度得到"L1 与激活重合 6.6%（低于随机）"的假结论。
6. **只看"退火到底"的 checkpoint**：中间点中位能差 0.5–1.2 dB（e40 17.73 / e50 17.80）。选错点会得出完全相反的结论。
7. **中位数在 400 块上也会抖**：同一配方 A vs CONTROL 差 0.098 dB、崩坏块 2 vs 0 ⇒ **±0.1 dB 是噪声底**，
   小于它的差异不要解读。
8. **曲线噪声与 LR 强相关**：高 LR 时平坦块出现系统性 DC 偏差，中位被拉低最多；这也是"中位"与"崩坏块"同源的原因。
9. 所有 checkpoint 写 `/data/work/`（`/media/felix/Data` 是 NTFS-3G，刚坏过）；每次启动前跑 20 MB 写探针。
10. **蒸馏能装下**（teacher 1.56 M + student 1.07 M，峰值 3528 MiB，12 GB 卡没问题），
    因为 teacher 参数 `requires_grad=False`、图不追踪反向，只多付一份前向激活。
11. `runs/dw_probe/train_dw.py` **没有给 DataLoader 传 generator** ⇒ batch 序不可复现；
    `runs/ft_probe/train_B.py` 用独立 `gen_seed=2024`。

## 10. 最终推荐

**不值得直接上板。** 理由按优先级：

1. **红线未过**：崩坏块 10（e60）/ 7（e90），红线是 ≤5；且崩坏块的 MAE 达 30/255，是**肉眼可见的偏色**，不是口径问题。
2. **收益也不够**：上板时间从 43.55 s 只能降到 **33–38 s**（§8），而不是 0.699×43.55 = 30.4 s；
   为此付的是中位 −0.21（vs 发布）/ **−0.54~−0.74（vs CONTROL）**。
3. **性价比结论**：B（0.697× MAC，中位 −0.21）与已放弃的 dwA（0.833× MAC，中位 −0.19）**中位打平**，
   但 B 用一半的 MAC 换到同样的质量 ⇒ **如果将来一定要接受一份质量损失，B 明确优于 depthwise**。

**要继续做的话，唯一值得投入的方向是"压崩坏块"，而且已经有可行信号**：
蒸馏把崩坏块按 16→10→7 单调压下来（每段 −3 个左右），再接 1–2 段蒸馏微调（每段 33 min）
有机会降到 ≤5；代价是中位会往"边缘"档掉（e90 已经 −0.41），
所以最终大概要在"中位 −0.3/-0.4 + 崩坏块 4–5"和"中位 −0.21 + 崩坏块 10"之间选。**这两者都不如直接放弃 0.697×。**

另一个更省的方向（未做，若时间允许）：崩坏块全部是"纯色 GT + 强摩尔纹"，
可在**训练集里对这类平坦块加权**或加一项"平坦区域的 L1"，不改结构、不加 MAC —— 比继续拉长训练更对症。
