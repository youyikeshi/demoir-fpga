## 1. 一句话结论

**§3 / §12.3 / §13 三版字段表全部作废**：RTL 里 `dw[i]` 是 64-bit **拍**不是"字"，
字 1（`out_pa`）**从来没被读过**；RTL 把 **字 2（`cfg_c`/`cin`）**当成了输出缓冲区地址。
这是 `dw` 索引的 off-by-one（4 处），不是设计分歧。

## 3. 静默后果（为什么至今没炸）

排空地址 = `cin + 带内偏移`（segq:347→462），PS 的 `out_pa` 整条丢弃。
`ARENA_LO/HI` 复位 `0/0xFFFF_FFFF`（wrap:891）且 **PS 从不写 0x318/0x31C**
⇒ `in_arena` 恒真 ⇒ **segq 一条 err 都不报，输出静默写到物理地址 `cin`**（cin=32 ⇒ 0x20 起）。
属"PL 写到不该写的地方"那一类，与 `docs/板端事故_内存踩踏_真相.md` 同族。

## 5. 新发现（需主代理裁定，⑨级）：conv 核 `cfg_h` 双用途

`hout_c=((cfg_h-1)>>s)+1`（conv:156，输出行数） **与** `hw8_c=cfg_h*cfg_w*8`（conv:163，
64-通道块步长，`cp1=(cb-1)*hw8`，conv:805）**共用 `cfg_h`**。
band 布局要求块步长 = `rows_fill·W·8`、输出行数 = `nband`；`halo≠0` 时二者不等
⇒ `cin>64`（`cb>1`）时必然错。T-88 的 `c_cfg_h=nband` 对前者对、后者错；
缺口④ 的 `base_act=HALO*W*8` 修不了它。
**建议**：本阶段融合只跑 `k=1`（`halo=0` ⇒ 双用途自洽），k=3/5 段继续走 v39。

## 5b. 另一个会立刻炸的接线错（在包装层，属我的改动范围）

`bin_unit_axi_wrap_v50.v` 给 segq 传 `.OP_MASK_SUP(16'h0001)`（segq 默认 `32'h0000_00FF`）。
PS 的 `V50_OP_BITS = {conv:0, cat:1, add:2, …}` ⇒ 融合段 `conv→cat` 的 `op_mask = 0x3`
⇒ segq:238 `(0x3 & ~0x1) != 0` ⇒ **`E_OPMASK=6`，第一条描述符就被拒**。
`conv→cat` 正是本阶段的融合形态（45 条）⇒ 现在这条链**一跑就 err**。
修法：`.OP_MASK_SUP(16'h0003)`（conv|cat），并在包装层确认 cat 在带模式下的读口
（E1E2 已接 band C 口）确实可用。**第二阶段改，本条只登记。**

## 7. 要不要改 `bin_segq.v`：**要，4 行**

```diff
240: - (dw[0][31:0]==0)||(dw[1][31:0]==0)||(dw[3][63:32]==0)
     + (dw[0][31:0]==0)||(dw[0][63:32]==0)
244: - in_arena({32'd0, dw[1][31:0]}, ...)
     + in_arena({32'd0, dw[0][63:32]}, ...)
340: - f_out    <= dw[1][31:0] & 32'hFFFF_FFFF;
     + f_out    <= dw[0][63:32];
347: - st_base <= dw[1][31:0];
     + st_base <= dw[0][63:32];
```

理由（三条，缺一不可）：
1. 字 1（`out_pa`）在整份 RTL 里零读取 ⇒ PS 的输出地址**无处可去**，只能改成读 `dw[0][63:32]`；
2. 排空基址现在 = `cin` ⇒ 输出写到 DDR 低地址，且因 arena 默认放行而**完全静默**；
3. 不改状态机/时间轴/端口/`DESC_WORDS` ⇒ 四条已验证路径（推进/链尾/出错即停/重启）语义不变，
   与 T-88 的"已验证"不冲突。
不改的后果：三边怎么对齐都没用——`out_pa` 永远落不了地。
