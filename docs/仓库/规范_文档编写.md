# 文档编写规范

> 适用范围：`docs/` 下的全部文档，以及仓库里所有 `.md`。
> 目的：**让一个完全不了解这个项目的人，能自己找到他要的东西。**
>
> 这份规范不是排版洁癖。2026-09-30 实际发生过一次事故：PYNQ 相关的说明散在
> 11 个文件里，新来的人从哪儿都进不去，只能靠问人。第 1 节就是那次事故的总结。

---

## 1. 信息架构：文档不能四处散落

**核心原则：每条线要有入口，每个入口要有指针，每个指针要写清楚"什么情况下读它"。**

散落的具体表现是：**一个意义被拆到很多地方**，读者手上没有地图。
下面五条是对应的修法。

### 1.1 每条主题线一个入口

一个主题线（部署 / 训练 / …）必须有一个 `README.md` 作为**入口**。

**入口不是文件清单，是按读者的处境指路**：

| 你的处境 | 读这份 | 为什么 |
|---|---|---|
| 第一次接触这个项目 | `对接文档_….md` | 整体计划 |
| 接手这块板子 | `交接文档_….md` | 上一任干了什么 |
| 要动手做镜像 | `流程_….md` | 照着敲 |
| 某个工具编不过 | `deploy/…/README.md` | 机理 |

**反例**（本项目原来的样子）：只有一个平铺的文件列表，
读者得自己判断"我这种情况该读哪份" —— 判断不了，就来问人。

### 1.2 每个"能跑的目录"也要一个入口

`deploy/` 这类放脚本的目录，**也要有自己的 README**。说清三件事：

1. 它和 `docs/` 的分工是什么（工具 vs 知识）
2. 里面每个文件/子目录是干什么的
3. **每个文件由哪份文档解释** —— 这一列必须有，否则工具就成了孤儿

写成表格：

| 工具 | 干什么 | 什么时候用 | 由谁解释 |
|---|---|---|---|
| `pynq/build_pynq_rootfs.sh` | 组装根文件系统 | 出镜像之前 | `流程_全链路构建.md` 第 8 节 |

### 1.3 指针要写清楚"什么情况下读它"

指针的价值在于**触发条件**，不在于链接本身。

| 写法 | 判断 |
|---|---|
| ❌ 「详见 `流程_全链路构建.md`」 | 读者不知道现在该不该点开 |
| ✅ 「**要动手做镜像时** → `流程_全链路构建.md` 第 3–9 节」 | 读者能立刻决定 |

**判断标准**：读者只看指针这一行，能不能决定"现在要不要点开"。
不能，就是指针没写清。

### 1.4 一个意义只写一处

**同一个清单、同一张表，不要出现在两个地方。** 索引只有一处。

本项目的实际教训：根 README 和 `docs/README.md` 各有一份文档清单，
结果根 README 那句"FPGA 部署尚未开始"过期了很久没人发现。

**两处重复，必然有一处过期。** 上层只放指针，不放内容副本。

### 1.5 路径要交底

**命令里出现的每个路径，第一次出现时必须说清三件事**：它是什么、哪来的、谁生成的。

本项目的实际教训：PetaLinux 工程根目录（现为 `~/SRP/qiansaiFPGA/peta_prj/ax_peta`）
在一份文档里出现 **16 次**，全文没有一处说它是怎么建出来的。读者照着敲，第一步就卡住。

**修法**：在文档开头加一张"全局地图"，把所有路径一次交底：

```text
~/SRP/qiansaiFPGA/peta_prj/ax_peta/      ← PetaLinux 工程根目录（不在 git 里）
   ├── images/linux/          ← 启动三件套产出到这
   └── build/tmp/.../zocl/    ← zocl.ko 编译输出
```

### 1.6 编号只有一个维度

**不要出现"第 2 节的第三步"。** 节号和步号必须统一，否则读者要做减法。

| 写法 | 判断 |
|---|---|
| ❌ `## 5. 第四步：准备根文件系统` | 节号 5、步号 4，正文引用"第 4 步"时读者要换算 |
| ✅ `## 5. 准备根文件系统` | 节号即步号 |

### 1.7 自检清单

新写完或重构完文档，跑这三条：

- [ ] **从仓库根 `README.md` 出发，只靠点链接，能不能走到任意一份文档？**
- [ ] 随机挑一份文档，里面出现的**每个路径**，第一次出现时交底了吗？
- [ ] 有没有同一个清单 / 表格出现在两处？

## 2. 目录怎么分

按**主题线**分目录，目录名不带编号前缀（避免插入新目录时要重排）。

| 目录 | 放什么 |
|---|---|
| `docs/部署/` | PS–PL 上板这条线：硬件对接、PYNQ、PetaLinux、板卡验收 |
| `docs/训练/` | 模型训练与推理这条线：环境、数据、训练、评估、分块推理 |
| `docs/仓库/` | 仓库自身的约定：目录结构、文档编写（本文件在这） |
| `docs/tutorial/` | 教学材料：面向新手的讲解，循序渐进 |

**一份文档只放一个目录。** 跨目录的内容用链接引用，不复制。

## 3. 文件名怎么写

```text
<类型>_<主题>.md
<类型>_<主题>_<限定>.md
```

| 部分 | 要求 |
|---|---|
| **类型** | 必须从下面的词表里选，**不许自创** |
| **主题** | 中文名词短语，说清讲的是哪件事，10 个汉字以内 |
| **限定** | 可选。日期用 `YYYYMMDD`（8 位）；或对象名（`AX7015B`、`PYNQ-M1`） |

### 类型词表

| 类型 | 用途 | 例子 |
|---|---|---|
| `规范` | 约定、规则 | `规范_目录结构.md` |
| `交接文档` | 换人 / 换机器时的交接 | `交接文档_去摩尔纹训练部署.md` |
| `对接文档` | 跨模块、跨阶段的接口约定 | `对接文档_去摩尔纹PS-PL部署.md` |
| `实施计划` | 某个阶段的执行方案 | `实施计划_<阶段>.md`（本仓库暂无；M−1 方案已并入 `流程_全链路构建.md`） |
| `说明` | 解释性文档：原理、实测记录、交付说明 | `说明_本机重训环境搭建.md` |
| `流程` | 可以照着一步步做的操作步骤 | `流程_双机协作.md` |
| `方案` | 选型、获取、决策比较 | `方案_数据集获取.md` |
| `讲解` | 教学材料 | `讲解_student模型架构_20260916.md` |

**唯一例外**：目录入口固定叫 `README.md`（GitHub 会自动渲染）。

### 为什么类型放前面

文件按字母序排列时，**同类型的文档会聚在一起**：

```text
说明_分块推理与拼接.md
说明_本机重训环境搭建.md
说明_交付_20260910.md
流程_双机协作.md
方案_数据集获取.md
交接文档_去摩尔纹训练部署.md
```

一眼就能看出"这个目录里有一份流程、一份方案、三份说明"。
反过来写（`分块推理_说明.md`）就做不到。

## 4. 符号规则

| 规则 | 正确 | 错误 |
|---|---|---|
| 字段之间用**半角下划线** `_` | `说明_分块推理与拼接.md` | `说明-分块推理.md` |
| 字段**内部**用**半角连字符** `-` | `实施计划_PYNQ-M2.md` | `实施计划_PYNQ_M2.md` |
| 不用空格 | `方案_数据集获取.md` | `方案 数据集获取.md` |
| 不用全角符号 | `说明_交付_20260910.md` | `说明＿交付.md` |
| 日期固定 8 位 | `_20260910` | `_2026-09-10`、`_260910` |
| 不写版本号后缀 | `对接文档_去摩尔纹PS-PL部署.md` | `对接文档_去摩尔纹_v3.md` |

**版本信息写在文件内容里，不写进文件名。** 文件名会变，链接就会断。

## 5. 图画成纯文本，不用 Mermaid

### 为什么

这些文档**经常是在终端里、编辑器里、`git diff` 里直接看的**，不经过渲染。
Mermaid 代码块在那种场景下就是一堆读不了的噪音：

````
```mermaid
flowchart LR
    s1["① xsa/<br/>补全 XSA"]
    s2["② pynq/zocl-kernel-6.12/<br/>装进 PetaLinux 工程"]
    s1 --> s2
```
````

渲染出来才好看，**不渲染就完全没法读**。而纯文本图两种场景都能读。

### 怎么写

用 ```` ```text ```` 代码块包一个 ASCII 图。**两个判断标准**：
- 在终端里 `cat` 出来能不能看懂
- 复制到任何地方（微信、记事本）会不会散架

**流程图** —— 竖排用 `│ ▼`，横排用 `──▶`：

```text
① deploy/xsa/
   补全 XSA
      │
      ▼
② deploy/pynq/zocl-kernel-6.12/
   装进 PetaLinux 工程
      │
      ▼
③ petalinux-build
```

**左右对照** —— 并排两列：

```text
改之前（一个分区）          改之后（两个分区）
──────────────────          ──────────────────────────
FAT32                       分区 1 · FAT32 · 512 MB
  BOOT.BIN                     BOOT.BIN
  image.ub                     image.ub
  boot.scr                     boot.scr

                            分区 2 · ext4 · 8 GB
                               Ubuntu + pynq + zocl.ko
```

**目录树** —— 用 `├──` `└──`：

```text
~/SRP/qiansaiFPGA/peta_prj/ax_peta/
   ├── images/linux/          启动三件套产出到这
   └── build/tmp/.../zocl/    zocl.ko 编译输出
```

**箭头链** —— 一行能说清就别画框：

```text
训练/  ──产出权重──▶  weights/  ──作为输入──▶  部署/
```

### 什么时候用表格代替图

**优先用表格。** 需要表达"每个东西的属性"时，表格比图好 ——
图只能表达"谁连着谁"，表格能表达"是什么、在哪、多大、谁生成的"。
只在"关系"比"属性"更重要时才画图。

## 6. 新增文档的流程

1. **先判断属于哪条线** → 决定放哪个目录
2. **再判断是什么类型** → 从词表里选（没有合适的就先讨论，不要自创）
3. **写主题**，控制在 10 个汉字以内
4. 需要区分多份同类文档时，才加限定词
5. **把链接加进该线的入口 `README.md`** —— 不是加进根 README（根只放指针）
6. 图用纯文本（见第 5 节）
7. 跑一遍第 1.7 节的三条自检

## 8. 移动 / 改名 / 新增之后要做的检查

**移动或改名文档时，必须同步更新引用。** 否则链接会断。

引用分两类，都要查：

| 类型 | 查找命令 |
|---|---|
| 仓库里其他地方提到这个文档 | `grep -rn "旧文件名" --include="*.md" --include="*.py" --include="*.yaml" .` |
| 文档**内部**的相对链接 | 见下面的自检脚本 |

自检脚本（在仓库根目录跑，检查全仓 `.md` 的相对链接能否解析）：

```bash
python3 - <<'EOF'
import os, re
link_re = re.compile(r'\[[^\]]*\]\(<?([^)>\n]+?)>?\)')
bad = 0
for root, dirs, files in os.walk('.'):
    dirs[:] = [d for d in dirs if d not in ('.git','__pycache__','.pc')]
    for fn in files:
        if not fn.endswith('.md'): continue
        p = os.path.join(root, fn); d = os.path.dirname(p)
        for m in link_re.finditer(open(p, encoding='utf-8').read()):
            t = m.group(1).strip()
            if t.startswith(('http://','https://','#','mailto:')): continue
            t = t.split('#')[0]
            if t and not os.path.exists(os.path.normpath(os.path.join(d, t))):
                print(f"  ✗ {p} :: {t}"); bad += 1
print("✅ 全部可解析" if not bad else f"仍有 {bad} 处失效")
EOF
```

**特别注意**：文档被移到子目录后，文件里**所有**相对链接都要多退一级。
仓库外部的资料（如 `../../../AX7015B_LINUX教程_2025.2版/`）也在其中。

还有一条容易漏：**改了 `docs/` 里的文件名，`deploy/` 和 `src/` 里的注释
也可能引用了它**。用上面那条 `grep` 全仓查，不要只查 `docs/`。
