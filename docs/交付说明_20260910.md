## 2. 代码变更清单

### 2.1 修复的 bug（9 处）

原始代码在 **torch 2.7 / Python 3.12 / 单卡 / 非 4K 数据** 下**无法运行**。全部为最小化修改。

| # | 文件 | 问题 | 修复 |
|---|---|---|---|
| 1 | `train.py` | 硬编码 `CUDA_VISIBLE_DEVICES="0,1"`，teacher 固定在 `cuda:1` | 按实际卡数判定；单卡时 teacher 与 student 同卡 |
| 2 | `test.py` | import 了 **3 个不存在的模块**（`model_Distillation1`/`nets_student4`/`loss_util_Distillation1`） | 指向真实文件 |
| 3 | `utils/common.py` | vendored 调度器用 `verbose` 形参，torch≥2.0 已移除 | `try/except` 回退 |
| 4 | `utils/common.py` | 调用了 `print_lr()`，torch≥2.5 已删除 | `hasattr` 保护 |
| 5 | `utils/common.py` | `thop` 依赖 `distutils`，**Python 3.12 已移除** | 延迟导入 + 优雅降级 |
| 6 | `model/model.py` | `model_fn_decorator` 的 `device1` 是必填位置参数，但 `test.py` 不传 | 给默认值 `None` |
| 7 | `config/config.py` | `open()` 用系统 locale（中文 Windows 是 GBK），含中文注释的配置报 `UnicodeDecodeError` | 强制 `encoding='utf-8'` |
| 8 | `dataset/load_data.py` | `crop` 模式把 4K 尺寸写死 `4032×3024`（官方 test 实为 `3840×2160`）→ 裁剪越界补黑边 | 改为读图片实际尺寸，并校验 `CROP_SIZE` |
| 9 | `utils/loss_util.py` | 蒸馏分支遍历 student 特征再索引 `T_feature_map[i]`，无 teacher 时 `IndexError` | 加 `if T_feature_map:` 守卫 |

**关于 #1 的额外发现（已实测证伪的猜想）**：原本以为 teacher 前向漏了 `torch.no_grad()`
会浪费显存。**实测显示显存完全相同，速度差 0.5%（噪声内）**——因为 teacher 参数冻结且输入
不参与梯度，PyTorch 不建图。**原代码此处没问题，未改。**

### 2.3 新增的可选开关：关闭蒸馏

想要**不用 teacher、单独训练 student**，在配置里加一行：

```yaml
USE_TEACHER: False
```

然后**照旧**用原来的入口，**命令完全不变**：

```bash
python train.py --config ./config/xxx.yaml
```

- 默认 `True`（保持原行为），完全向后兼容
- 关闭后损失变为 `多尺度 L1 + VGG感知`，蒸馏项自动消失
- 实测：关掉后 **loss 4.14**，开启 **13.98**（差 9.84 = `40×a×feature_loss`）
- 好处：省掉 teacher 前向，**约快 1.5 倍**；代价是通常需要更多 epoch

**实现细节**（三处配合，缺一不可）：
1. `train.py`：`USE_TEACHER` 为 `False` 时 `T_model = None`，跳过加载 teacher
2. `model/model.py`：`model_fn` 在 `T_model is None` 时，把 student 输出 `.detach()` 填入
   teacher 槽位 → 损失里 `l1_t == l1_s` → `a = 0` → 蒸馏项自动为零；同时传空特征列表
3. `utils/loss_util.py`：加 `if T_feature_map:` 守卫
   （**必须**，因为循环遍历 student 的 `feature_map` 再索引 `T_feature_map[i]`，空列表会 `IndexError`）

## 3. 已验证的结论

### 3.1 环境与显存

| 项 | 值 |
|---|---|
| GPU | RTX 4060 Laptop，8GB，**compute capability (8,9)** |
| torch | 2.7.0+cu118 / torchvision 0.22.0+cu118 |
| Python | 3.12（venv 在仓库外 `G:\qiansaiFPGA2026\.venv-pdnet`） |
| 依赖 | `tools/requirements_pdnet.txt` |

> ⚠️ 本机既有 `yolov5` 环境是 torch 1.8.1+cu111，**不支持 sm_89，不可用**。

**显存实测**（训练步含 teacher 前向+反向）：

| 分辨率 | 训练 | 推理 |
|---|---|---|
| 256 | 501 MB | 127 MB |
| 384 | 1094 MB | 255 MB |
| 512 | 1911 MB | 434 MB |

**8GB 完全够用**，交接文档里"需要把画幅砍到很小"的担心不成立。瓶颈是**速度**不是显存。

### 3.2 关键架构事实

- student **1.562M** 参数（en 48/32, de 64/32），teacher **4.396M**（48/48, 64/64）
- **两者都没有 BatchNorm / Dropout**（只有 Conv2d / ReLU / ECA 全局池化 / ChannelShuffle）
- **纯卷积 + 无尺寸相关统计量 → 任意尺寸可跑**（实测 32×32 ~ 4K）
- **teacher 4.396M 永不上 FPGA**，它只是训练期拐杖；部署的只有 student
- 蒸馏 loss = 多尺度(1×/0.5×/0.25×)[L1 + VGG感知] + `40 × a × 小波域蒸馏`，
  其中 `a` 是自适应开关：**仅当 student 比 teacher 差时才计入蒸馏项**

### 3.3 裁切尺寸 / 上下文（`context_study.py`）

**方法**：固定比较中心 256×256 的**同一批像素**，只改变网络能看到的上下文大小。

| 网络可见上下文 | 256² | 384² | **512²** | 768² |
|---|---|---|---|---|
| 输出 PSNR | 22.73 | 23.65 | **24.00** | 23.78 |

**结论**：
- 上下文**有用**，同一批像素多给周围信息可提升 **1.27 dB**
- **在 512 处饱和**，再给到 768 反而略降 → **有效感受野约 512**
- **`CROP_SIZE` 取 384~512 最划算**；低于 256 明显掉点
- **600×400 部署目标正好落在甜点区**
- 尺寸约束：必须是 **32 的倍数**；理论下限 ~224
  （最深特征图 = 输入/8，SAM 的 0.25× 分支再 /4，dilation=3 需 ≥7）

> ⚠️ **方法教训**：这个结论做错过两次。第一次用"不同尺寸裁不同位置"，看起来影响巨大
> （+0.62 → +2.36 dB），但**被内容差异污染**——大裁切覆盖更多不同区域。
> 第二次用嵌套裁切，仍受"大块含更多难内容"干扰。**只有固定同一批像素才干净。**

**teacher 侧无需任何调整**（已冻结 + 无 BN + 纯卷积）。

### 3.4 ⚠️ 四条假设的验证（重点）

这是本阶段最重要的结论，**三条已被实验证实**。

#### 假设 1：下采样会破坏摩尔纹的频率成分 ✅ 成立

`downsample_study.py`，4K 裁 1024 → 下采样 4 倍到 256：

| 处理方式 | 摩尔纹能量 | 摩尔纹峰值频率 | **gt 高频** |
|---|---|---|---|
| 原始 4K 裁块 | 基准 | 0.2167 | 基准 |
| **box 平均** | −45.0% | −0.1391 | **+102.5%** ⚠️ |
| 抗混叠（先高斯 σ=f/2） | −64.4% | −0.1809 | **−1.7%** ✅ |

**两个问题**：
1. **摩尔纹峰值频率被折叠 64%**（0.2167 → 0.0776 cyc/px）。不是平移或压缩，是**混叠折叠**
2. **gt 高频反而翻倍（+102.5%）**——box 平均**不是抗混叠滤波器**，只抑制 5×5 整周期分量，
   而摩尔纹在 2~2.5 周期。于是 gt 的超奈奎斯特高频**折返成假纹理**，把"干净目标"污染了

**根源**：问题不在"下采样"，而在"没有抗混叠"。加了低通后 gt 高频只掉 1.7%。

#### 假设 2：4K 训练的 teacher 在低分辨率数据上指导能力下降 ✅ 成立

`teacher_domain_gap.py`，同中心点同内容 40 张图：

| 条件 | 尺寸 | 输入 PSNR | 输出 PSNR | **Δ** |
|---|---|---|---|---|
| 原生 4K 裁块 | 512 | 16.00 | 22.71 | **+6.71** ← teacher 训练域 |
| 原生 4K 裁小块 | 256 | 16.31 | 22.51 | +6.20 |
| box 下采样 | 256 | 16.76 | 20.67 | **+3.90** |
| 抗混叠下采样 | 256 | 17.62 | 20.94 | **+3.31** |

**拆解**：
```
尺寸影响（256原生 vs 512原生）  : -0.51 dB   ← 换尺寸几乎没影响
频率错配影响（box vs 256原生）  : -2.30 dB   ← 假设成立
频率错配影响（aa  vs 256原生）  : -2.89 dB   ← 假设成立
```

**掉的是"频率成分不同"，不是"图变小了"。**

（反直觉细节：抗混叠的 Δ 比 box 还低，因为抗混叠去掉了更多摩尔纹，"可修的少了"。
这不说明抗混叠更差——它的 gt 更干净，训练用途上仍应选抗混叠。）

#### 假设 3：不用 teacher、单独训练 student 也可行 ✅ 成立（已实现）

见 2.3。已验证梯度正常反传、两条路径都能工作。

#### 假设 4：换一个低分辨率训练的 teacher 可解决错配 ⏳ 未验证（接口可行）

ESDNet 官方权重里有低分版本，**forward 接口与本项目 teacher 完全相同**
（同样返回 `out_1, out_2, out_3, feature_map`）：

| 权重 | 训练分辨率 | 可用作 teacher |
|---|---|---|
| `tip_checkpoint.pth` | **256×256** | ✅ |
| `aim_checkpoint.pth` | **1024×1024**（LCDMoire，真拍屏） | ✅ |

需要把 `train.py` 的 `load_teacher` 泛化（目前硬编码 `T_my_model`）。**尚未实施。**

#### 📌 由假设 1+2 推出的重要结论：下采样的摩尔纹"不物理"

摩尔纹源于相机 CFA 与屏幕亚像素的采样拍频，**任何原生采集**里它都落在
**接近奈奎斯特**处（实测 4K 原生峰值 **0.217 cyc/px**）。

而 4K 下采样后摩尔纹被折叠到 **0.078 cyc/px** —— 这个空间尺度意味着条纹有十几个像素宽，
**现实中任何低分辨率相机都不会产生这么"粗"的摩尔纹**。

| | 摩尔纹频率 | 是真实低分辨率采集的样子吗 |
|---|---|---|
| **4K 原生裁块** | 0.217 cyc/px（近奈奎斯特） | ✅ **是**——低分相机采集时摩尔纹同样在它自己栅格的奈奎斯特附近 |
| 4K 下采样 | 0.078 cyc/px（低频） | ❌ 不是，是人工折叠的 |

**所以 4K 原生裁块反而是"低分辨率原生采集"更好的物理代理**，
而下采样造出了一个现实中不存在的摩尔纹。这解释了假设 2——teacher 掉点不只是"不匹配"，
而是**那份数据本身不物理**。

### 3.5 真实数据指标

数据：官方 `test.tar.gz` → **500 对 3840×2160**（5.5GB 压缩 / 5.7GB 解压）。
按图划分为 **400 训练 / 100 评估**（`tools/make_split.py`，硬链接不占额外空间）。
评估方式：**原生分辨率裁块，不做任何重采样**（保住摩尔纹频率）。

**teacher 在 400 个块上**（100 张图 × 4 位置，512²）：

| 指标 | 输入（不处理） | teacher 输出 | Δ |
|---|---|---|---|
| PSNR 均值 | 19.12 | 23.26 | +4.14 |
| **PSNR 中位数** | 19.57 | **22.10** | **+2.53** |
| SSIM | — | 0.787（中位数 0.8345） | — |

- **中位数 22.10 dB 与 ESDNet 论文 22.12 dB 吻合** → 证明 teacher 权重真实可用 + 指标口径与论文一致
- 均值被少数平坦块拉高（平坦区可达 62 dB），**中位数更可信**
- 75% 的块有提升，25% 反而变差（网络过平滑）

**student 训练历程**：

| 阶段 | epoch | iters | train loss |
|---|---|---|---|
| 首次训练 | 1~7 | 1400 | 8.91 → 5.15 |
| → 中断（`C0000374`，见 5.3） | | | |
| 续训 | 8~30 | 1400 → 6000 | 5.15 → **4.25** |

**公平对照**（同一批 60 张图，crop 512，全部在 `split_eval` 上评估）：

| 模型 | 训练步数 | 输入 | 输出 | **Δ** | SSIM |
|---|---|---|---|---|---|
| student | 1,400 | 16.83 | 17.51 | +0.67 | 0.6428 |
| **student** | **6,000** | 16.83 | **19.33** | **+2.50** | **0.7123** |
| teacher（官方，未训练） | — | 16.83 | **22.86** | **+6.03** | 0.7760 |

**怎么读这组数**：
- student 从 1400 步到 6000 步，Δ 从 **+0.67 涨到 +2.50 dB**，SSIM 0.643 → 0.712
  → **确实在学去摩尔纹，且未收敛**（步数增 4.3 倍，提升增 3.7 倍）
- teacher 是上界参考：**Δ +6.03 dB**。我们用了论文 **1.8%** 的训练步数
  （论文 150 epoch × 2250 步 ≈ **33.7 万步**，我们 6000 步）
- 平均耗时 **0.030 s/块**，峰值显存 **270.9 MB**

产物：
- `pdnet_smoke/out/eval_real_student_c512_n60.csv`（逐样本指标）
- `pdnet_smoke/out/eval_real_student_c512_n60_grid.png`（摩尔纹 | 输出 | 真值）

> ⚠️ **局限（不要过度解读）**：
> - 训练只用了 **400 张图**（测试集划分），**不是** 4500 张官方训练集；
>   评估用的 100 张虽与训练集不同图，但**同源同分布**，绝对数值会偏乐观
> - 这是**裁块协议**，非官方整图协议，数值**不可与论文横向比**
> - 结论只对"**代码正确、能收敛、方向对、有真实提升**"有效，
>   **不代表论文指标可复现**

### 4.4 配置里的路径陷阱

| 文件 | 项 | 说明 |
|---|---|---|
| `config/real_config.yaml` | `TRAIN_DATASET` / `TEST_DATASET` | 用 `../../../uhdm_data/...`（相对 cwd） |

## 5. 已知陷阱

### 5.1 `crop` 加载器与数据分辨率

`dataset/load_data.py` 的 `crop` 分支原本把 4K 尺寸写死（`4032×3024` / `4624×3472`），
与 `CROP_SIZE` 无关。**已修复**为读实际尺寸。若非 4K 数据仍出问题，可改用 `LOADER: default`。

### 5.2 4K 整图推理不可行（决定评估方式）

8GB 显存装不下 3840×2160 整图前向：
- **fp32 全图 → 显存耗尽，溢出到系统内存，实测约 22GB 内存占用并"假死"**（GPU 100% 但几乎不前进）
- fp16 全图 → 峰值 6545 MB，勉强能跑但余量小

**因此评估必须用原生分辨率裁块**（见 `eval_real.py`），这也与最终小画幅部署目标一致。

### 5.3 ⚠️ 训练中断与恢复（操作要点）

在 A 机（本仓库的开发机）首次训练时，**Epoch 8 iter 113 中断**，
退出码 `-1073740940` = **`0xC0000374` STATUS_HEAP_CORRUPTION**（进程级堆损坏）。

**与本项目无关**：崩溃报告的故障模块是 `StackHash_4581`，即系统**无法解析到具体模块**。
这说明破坏来自 **Python 进程之外**，不是本项目的代码或依赖问题。

**已采取的对策**：

| 项 | 说明 |
|---|---|
| 存盘间隔可配 | `train.py` 新增 `SAVE_EPOCH`（默认 10，可设 5 或更小）。间隔越短，中断代价越小 |
| 续训已验证 | 从中断处续训成功，最终 30 epoch 完整跑完（`EXIT=0`）。方法见 4.3 |
| 建议 | 长时训练优先安排在 B 机；若在 A 机跑，把 `SAVE_EPOCH` 调小 |

> 📌 若 A 机频繁中断，那是**机器层面**的问题，**不在本项目范围内**，
> 因此排查记录不随本项目交付。

### 5.4 配置文件的编码

`config/config.py` 原本用 `open()` 默认编码（中文 Windows 是 GBK），任何含中文注释的
配置文件都会 `UnicodeDecodeError`。**已修复**为强制 UTF-8。

### 5.5 ⚠️ 常见概念误解：这是「知识蒸馏」，不是「对抗训练」

代码里**没有**判别器/GAN。全仓库检索 `discriminator`/`GAN`/`adversarial`/`BCELoss` 零命中。

**铁证**（`train.py`）：
```python
for p in T_net.parameters():
    p.requires_grad = False                       # teacher 梯度关闭
optimizer = optim.Adam([{'params': model.parameters(), ...}])   # 优化器只收 student
```
teacher 参数**根本不在优化器里**，物理上无法更新。

| | 对抗训练（GAN） | 知识蒸馏（本项目） |
|---|---|---|
| 谁在更新 | 两个都更新 | **只更新 student** |
| 关系 | 竞争/博弈 | 单向模仿 |
| teacher 角色 | 判别者 | **提供软标签的老师** |
| 是否需要真值 | 可以不需要 | **需要** |
| 部署时 | 两个都可能要 | **只部署 student** |

**损失结构**（`utils/loss_util.py`）：
```
loss = 多尺度(1×/0.5×/0.25×)[L1 + VGG感知]   ← 对真值，有监督
     + 40 × a × 小波域蒸馏损失                 ← a=1 仅当 student 比 teacher 差
```
- **蒸馏权重 40** 远大于 L1 的 1，是主力信号
- **`a` 是自适应开关**："只有当学生不如老师时，才让它向老师学习"

**重要澄清**：
1. **teacher 不是"原模型"**，也不是 student 的放大版。它是作者**另外独立训练**的更大模型
   （checkpoint 名 `ghost_34large`，中间通道 48 vs student 32，**架构不同**）。
   类比：老师不是"学生的原始版本"，而是**另一个人**。
2. 两者都是完整的去摩尔纹网络，接口相同，任务相同，只是容量与效果不同。
3. **teacher 是论文作者训练的**（文件名 `000150` = 第 150 epoch），不是我方产物。
