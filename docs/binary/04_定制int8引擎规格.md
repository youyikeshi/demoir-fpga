# `conv_int8_uni` —— 为二值网定制的统一 int8 卷积引擎

> 2026-10-29　|　取代 `conv_k1_engine` + `conv_k3_engine` + `conv_k5_engine`
> 动机：二值网只有 **9 个 int8 卷积形状、合计 394 MMAC**，却要占用三个引擎的
> 131 DSP / 76 BRAM / ~38k LUT。这不是"参数没调好"，是**架构错配**。

## 1. 动机：账算不过来

| 项目 | 三个老引擎 | 定制引擎 | 省 |
|---|---:|---:|---:|
| DSP | 131 | **32** | −99 |
| BRAM Tile | 76 | **~10** | −66 |
| LUT | ~38000 | **~5000** | −33k |
| 支持 k | 各管一种（1/3/5）| **一个引擎管三种** | — |
| W 上限 | 编译期写死 | **运行时 `cfg_w`** | — |

**二值网需要 int8 引擎干的活**（@256²）：

| 层 | cin | cout | k | s | Hout | MMAC |
|---|---:|---:|---:|---:|---:|---:|
| `conv_first` | 12 | 48 | 5 | 1 | 128 | 235.9 |
| `decoder_1` | 64 | 12 | 3 | 1 | 160 | 113.3 |
| `decoder_2` | 64 | 12 | 3 | 1 | 80 | 28.3 |
| `decoder_3` | 64 | 12 | 3 | 1 | 40 | 7.1 |
| `SGRA` ×5 | ≤7 | ≤4 | 1 | 1/2 | — | 9.4 |
| **合计** | | | | | | **394** |

$$\Rightarrow\ \text{按要求 } 1\ \text{fps 预算，int8 部分须 } \le 0.15\ \text{s} \Rightarrow \text{吞吐 } \ge 2.6\ \text{GMAC/s}$$

$$\text{32 lane} \times 107.1\ \text{MHz} \times 0.85\ (\text{占用率}) = \mathbf{2.91\ GMAC/s} \Rightarrow \frac{394\ \text{M}}{2.91\ \text{G}} = \mathbf{0.135\ s} \ \checkmark$$

| 参数 | 范围 | 依据 |

## 3. 与老引擎的三个关键不同

### 3.1 k 不再编译期写死

老设计里 k1/k3/k5 是三个独立引擎，每个把 k 焊死。新引擎用**统一的 tap 发生器**：

$$\text{tap}(j) = (k_y, k_x),\quad j = 0..k^2-1;\qquad \text{addr} = y\cdot s + k_y\cdot d - pad$$

$$\Rightarrow\ \text{k 只影响循环次数与地址增量，不影响数据通路}$$

### 3.2 W 不再编译期写死

老 k5 的 `LB_DEPTH = W + 2*PAD` 是编译期常量 ⇒ 换分辨率就要重新综合（这正是今天
"W 从 320 改 128 白跑三次构建"的根源）。

新引擎的行缓冲按 **`W_MAX = 256` 预留**，`W` 由 `cfg_w` 在运行时给：

$$LB_{DEPTH} = W_{MAX} + 2\cdot PAD_{MAX} = 256 + 8 = 264$$

$$\Rightarrow\ \textbf{同一份比特流支持 128×128 / 192×192 / 256×256 任意分辨率}$$

### 3.3 权重容器：TAP 改为 8·ceil(k²/8)（2026-10-30 时序优化，已改）

每个输出通道 `o` 的每个输入通道 `c` 占 **TAP** 字节，前 $k^2$ 字节是真权重
（按 `j = ky·k + kx` 排列），后面是补齐洞：

$$\text{addr} = \text{base\_wgt} + \big((o\cdot c_{in} + c)\cdot TAP + j\big),\qquad j<k^2$$

| k | k² | TAP（旧，2026-10-30 前）| TAP'（新）| 每个 (o,c) 的字节（新）|
|---:|---:|---:|---:|---|
| 1 | 1 | 4 | **8** | 1 真 + 7 补 |
| 3 | 9 | 12 | **16** | 9 真 + 7 补 |
| 5 | 25 | 28 | **32** | 25 真 + 7 补 |

$$TAP' = 8\left\lceil k^2/8 \right\rceil \in \{8,16,32\}$$

**为什么改**：旧 TAP ∈ {4,12,28} 只有 4 字节对齐 ⇒ 相邻 (o,c) 块的起点按
4/12/28 字节交错步进，引擎侧要拼"块基址 + 行内偏移"的读地址，落在
`conv_int8_uni.v` 的 `ST_WLD` 权重装载链上是一整条**三级串联 32 位加法**
（`wbase + wl_rb + wl_j0`），实测 **16 级逻辑 / 6.28 ns = 整条 35 级路径的 38%**
（见 `docs/binary/timing_2026-10-30/README.md` §7.2 段 A）。
新 TAP' 是 8 的整数倍 ⇒ 每个 (o,c) 块恰好 $TAP'/8$ 个 64-bit 字，块首地址
**低 3 位恒 0**，读地址退化成纯 `+8` 累加，这条加法链可以从关键路径上删掉。

**代价**：权重体积 +27%（本网 9 层 int8 共 44,336 B → 56,416 B，+12,080 B；
相对全网 1.79 MB 打包权重不到 0.7%）。

**两套布局的关系**：只有补齐洞宽度不同（3 → 7 字节），`j < k²` 的字节**逐字节相同**
⇒ 权重数值不用重新量化，只需按新步长 repack（或重新导出）。
验证期可以在两套之间来回切：`ps/pynq/uni_engine.py` 的 `padded=` 参数、
`pl/rtl_hand/tools/gen_uni_golden.py --tap old`。
数值等价性由 `ps/tools/test_tap_restride.py` 逐字节验证。

> ⚠ 这条改动要求 **PS 侧的 `R_TAP` 取值表与 RTL 同步改成 {8,16,32}**。
> 送错值时 `conv_uni_axi_wrap` 返回 `ERR_TAP(2)`，不会静默算错；
> 但"旧权重包 + 新比特流"（或反之）一定跑不出正确结果。

**与 `docs/rtl_hand/00_SPEC_接口契约.md` 的关系**：那份契约描述的是**旧的三引擎**
（`conv_k1/k3/k5_engine`，编译期 `K3_PAD12` / `K5_PAD28`），容器仍是 12 / 28 字节，
**没有跟着改**（那是另一个比特流）。本引擎只保证"`j < k²` 的 payload 与旧容器
逐字节一致"，步长不同。

## 4. 资源预算

| 资源 | 数量 | 说明 |
|---|---:|---|
| DSP48 | **32** | 32 lane × 1 乘加 |
| 权重缓冲 | 4–6 RAMB36 | 单 pass 最多 `cin × 32 oc × taps` ≤ 16 KB；超了报错误码 |
| 行缓冲 | 3 RAMB36 | `k_max × LB_DEPTH × 8 ch`（k≤5, W≤256）|
| 像素/输出缓冲 | 2 RAMB36 | C8 布局 |
| **合计** | **~10–12 RAMB36** | |

$$\text{加四个二值单元（0 DSP / 4–6 BRAM / ~4k LUT）} \Rightarrow \textbf{32 DSP / ~16 BRAM / ~9k LUT}$$

$$\text{对比现在光老引擎就占 } 137/76/38000 \Rightarrow \text{给时序优化和后续扩展都留出了空间}$$

## 5. 验收判据（与四个二值单元完全一致的做法）

1. 黄金向量：`tools/gen_uni_golden.py` 覆盖上表 **5 类形状 + 边界**（cin 非 8 倍数、s=2、d=3、k=1/3/5、W=128/192/256）
2. TB：`tb/tb_conv_int8_uni.v`，**单主内存口**（与四个二值单元同构）+ `ctrl_*` 握手
3. 判据：**逐字节 0 差异**，一条命令 `./tools/run_bin_unit.sh conv_int8_uni`
4. 性能判据：`cycles ≤ 1.5 × 参考拍数`，参考 = `cout·Hout·Wout·cin·k² / (32 lane)`
