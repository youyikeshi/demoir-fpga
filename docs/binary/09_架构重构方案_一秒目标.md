# 架构重构方案：整网 1 秒 + 150 MHz 时序

## 一、量化诊断（256×256 单帧）

数据来源：`ps/manifest_512.json`（521 个算子，卷积已跑在 256²）

| 项 | 数值 |
|---|---:|
| 卷积层数 | 249 |
| 总运算量 | **21.2 G** |
| int8 部分（`conv_first` + 3 个 `out_conv`）| **1.54 G MAC** |
| 二值部分（其余 245 层）| **19.7 G 位操作** |
| 单帧内存流量 | **487 MB** |
| 按 k 分布 | k=1: 39.3%，k=3: 56.3%，k=5: 4.4% |

## 二、瓶颈（实测/推算）

$$\text{当前二值引擎 } = 1\ \text{条 64-bit popcount/cycle} \Rightarrow \frac{19.7\times10^9}{64\times150\times10^6} = 2.1\ \text{s}$$

$$\text{当前 int8 引擎 } = 32\ \text{MAC/cycle} \Rightarrow \frac{1.54\times10^9}{32\times150\times10^6} = 0.32\ \text{s}$$

$$\text{内存} = 487\,\text{MB} / 2.4\,\text{GB/s} = 0.20\ \text{s}$$

$$\Rightarrow \text{合计约 } 2.6\ \text{s} \gg 1\ \text{s}$$

**三个瓶颈的权重**：二值吞吐（2.1 s）> int8 吞吐（0.32 s）> 内存（0.20 s）。

## 三、目标架构

### 3.1 二值卷积：1 lane → **8 lane 输出通道并行**

现状：每周期 1 个 popcount、1 个输出像素（`p_acc` 串行累加 term）。

目标：**8 条独立的 64-bit XNOR+popcount 通道，分别算 8 个输出通道**，
共享同一个输入字（1 次读），8 个权重字从 **BRAM 常驻**取出。

$$\text{吞吐} = 8\times64\times150\times10^6 = 76.8\ \text{G bit/s} \Rightarrow \frac{19.7\times10^9}{76.8\times10^9} = 0.26\ \text{s}$$

**为什么可行**：二值权重是 **1 bit/权重**。一层 `cout=64, cin=192` 只需
$64\times192 = 12288\ \text{bit} = 1.5\ \text{KB}$，全部能常驻 BRAM。
输入带宽只需 1 word/cycle（8 B/cycle = 1.2 GB/s），远低于 HP 口能力。

**面积反而变小**（关键）：

| 组件 | 数量 | LUT |
|---|---:|---:|
| 64-bit XNOR | 8 lane | 8 × 32 = 256（LUT6_2 一个出 2 个 XOR2）|
| popcount 加法树（16→8→4→2→1）| 8 lane | 8 × 31 = 248 |
| requant（16×16 乘 + 移位 + 饱和）| 8 lane | 约 1,600 LUT + **8 DSP** |
| 权重 BRAM 读出 | — | 0 |
| 地址/FSM | — | 约 2,000 |
| **合计** | | **约 4,100 LUT / 8 DSP** |

对比现状 `bin_unit_0`：**9,851 LUT / 21,670 FF / 18 DSP，但只有 1 lane**。
$$\Rightarrow \textbf{8 倍吞吐、面积反而减半}$$

### 3.2 int8 卷积：32 → **64 MAC/cycle**

现状：32 lane（4 oc × 8 通道）。
目标：64 lane（8 oc × 8 通道），DSP 从 32 增到 64。
$$\frac{1.54\times10^9}{64\times150\times10^6} = 0.16\ \text{s}$$

板的 DSP 预算：160 个，int8 用 64 + 二值 requant 8 + 地址 8 ≈ 80，**余量充足**。

### 3.3 内存：487 MB → 用层融合压下来

487 MB 是"每层都读写一遍 DDR"的合计。`bytes_peak_live` 只有 33 MB，
说明**理论上可以只保留 33 MB 常驻**。做法：
- 连续的同分辨率层在一段输出缓冲上原地累加（`cat` / `add` 不落 DDR）
- `pixel_unshuffle`/`pixel_shuffle` 用地址映射代替真实搬运

$$\text{目标：487 MB} \to 200\ \text{MB} \Rightarrow 0.08\ \text{s}$$

### 3.4 时间预算（目标）

| 部分 | 时间 |
|---|---:|
| 二值 8 lane | 0.26 s |
| int8 64 MAC/cycle | 0.16 s |
| 非卷积（cat/add/interp/sam）| 约 0.20 s |
| 内存 | 约 0.08 s |
| 调度开销 | 约 0.10 s |
| **合计** | **约 0.80 s ✓** |

## 四、时序策略（40 MHz → 150 MHz）

### 4.1 已修的三个时序杀手

| 问题 | 位置 | 修复 |
|---|---|---|
| 组合 16 位除法器（43 级 CARRY4，57 ns）| `conv_int8_uni.v` / `bin_conv_core.v` 的 `div16u` | stride ∈ {1,2} ⇒ 改成移位 |
| 64 级顺序 popcount 链 | `bin_conv_core.v` `pop64` | 改成 16→8→4→2→1 平衡树（深度 5）|
| 64 位数据通路（乘法器退化 LUT）| rprelu/sam/conv_core 多处 | 按真实范围收窄到 16/32/40 位 |

### 4.2 逐模块位宽审计结论

| 单元 | 变量 | 原 | 真实范围 | 现 |
|---|---|---:|---:|---:|
| `conv_int8_uni` | 累加/requant | 32 | 32 | 32 ✓ 已够 |
| `bin_conv_core` | `d_int` | 64 | 14 | **16** ✓ |
| `bin_conv_core` | `e1_q`/`dd_int`/`r_*` | 64 | ≤33 | **40** ✓ |
| `bin_rprelu` | `dd` | 64 | 10 | **16** ✓ |
| `bin_rprelu` | `prod` | 64 | 25 | **32** ✓ |
| `bin_sam` | `prod0/2` | 64 | 24 | **32** ✓ |
| `bin_sam` | `acc` | 64 | ≤47 | **48** ✓ |
| `bin_interp` | 坐标 | 40 | 21 | 待改 **24** |
| `bin_interp` | `N` | 64 | 32 | 待改 **40** |
| `bin_interp` | `rem` | 48 | 23 | 待改 **24** |

### 4.3 DSP 归位（25×18 是硬约束）

$$\text{DSP48E1 原生 } 25\times18 \Rightarrow \text{操作数超过就退化成 LUT 乘法器}$$

所有乘法必须满足：**一个操作数 ≤ 25 位、另一个 ≤ 18 位**。
收窄后：`d(16) × alpha(16)`、`dd(16) × slope(16)`、`w(16) × y(8)` 全部命中 ✓

### 4.4 流水线

- 二值引擎：S1（XNOR+popcount）→ 寄存器 → E1（requant）→ 寄存器 → E2（RPReLU）→ sat8
  每级 ≤ 6 ns 可控
- int8 引擎：MAC 累加在 DSP 内，requant 单独一拍

## 五、执行顺序

1. **二值引擎重写**（收益最大，8× 吞吐 + 面积减半）
   - 8 lane 输出通道并行，权重 BRAM 常驻
   - 位宽按上表，全程 DSP 化乘法
2. **int8 引擎 32 → 64 lane**
3. **bin_interp 除法 → 倒数乘法**（去掉 8 路 48 位长除法）
4. **层融合调度**（压内存流量）
5. 统一验证：每个单元 xsim 逐字节，再整网对拍
6. 综合 → 150 MHz 收敛 → 出 bit → 上板

## 六、验证纪律

- 每个 RTL 改动必须跑对应单元的 xsim 逐字节比对（现有 golden 齐全）
- 综合判资源**只能用** `open_checkpoint` + `report_utilization`
- 时序**必须有** `create_clock`，`WNS=NA` 表示没有约束而不是通过
- 上板前必须武装看门狗（`ps/pynq/board_safe.py`），SoC 挂死 15 秒自动复位

# 附录 A：`conv_uni_axi_wrap.v` 逐条审查结论

## A.0 三个先决事实

1. 实际 tag 是 **26 bit**（`TAG_W = 29 - IDX_W`，`IDX_W=3`），不是 29。
2. **BD 外壳没传任何参数** ⇒ 实际是 `NLINES=32`。而文件头自己写着
   "NLINES 必须 ≥ 2·NCG·k，32 时 cin=64/k=3 从 1.74× 退化到 3.11×"
   —— **发布配置正好是文档说会退化 1.8 倍的那一档**。
3. 引擎读地址 `[2:0]` 只可能是 0 或 4（bias/weight/compute 三处的偏移都是 8 的倍数）
   ⇒ `rd_off ∈ {0,4}` 可以当**不变量**用。

## A.1 读路径为什么卡在 40 MHz

```
u_rd_addr → ① 26bit tag 比较 2 级
          → ② 32 路 OR 树 2 级
          → ③ 32 选 1 优先级编码 2~4 级
          → ④ rd_ent*9+slot（9bit 加法，非 2 的幂）2 级
          → ⑤ 288 深**异步** LUTRAM 读（5 bank + 5:1 mux）2~3 级
          → ⑥ 128bit barrel shifter 3 级
          → u_rd_data 触发器
```

$$\text{合计 } \mathbf{13}\ \text{ 级},\ \approx 6.5\ \text{ns} \Rightarrow \text{正好 40 MHz}$$

**关键洞察**：引擎的 `mem_rd` 契约本来就是"t 拍发地址、t+1 用数据"（等于 1 拍同步读），
所以 ①②③④⑤ 根本不必挤在同一拍——**只有 LUTRAM 的"异步读"逼你挤**。
换 BRAM 同步读后，问题从"13 级/1 拍"变成"6 级到 BRAM 地址 + 2 级到 u_ce"，两头都够。

## A.2 优化清单（按收益/风险比）

| # | 优先级 | 内容 | 收益 | 风险 |
|---|---|---|---|---|
| P2 | 高 | 128bit 桶形移位器 → 2:1 mux（`rd_off[2]` 只有 2 种）| −190 LUT，−3 级 | 极低 |
| P4 | 高 | `kk_c=r_k*r_k`、`wcap_c=ncg*kk`、`hw_c=H*W` 都是 **32×32 乘法** 且在启动闸门的组合路径上 | −300~900 LUT，去掉必挂路径 | 极低 |
| P1 | 高 | `USE_BUFGCE=1`（参数已存在，零逻辑改动）—— `u_clk = s_axi_aclk & u_ce` **没上全局时钟树** | 0 LUT，**150 MHz 前置条件** | 低 |
| P7 | 中 | `NSLOT=9` 非 2 的幂 ⇒ 三处 `×9` 加法器在关键路径；配 BRAM 时槽步长补到 16（512 深正好 1 个 RAMB36，存储免费涨）| −40 LUT，−2 级 | 低 |
| P5 | 中高 | `m_axi_wdata = bf_data[bf_rp]` 是 64bit 16:1 组合 mux 直连端口 | −290 LUT，−3 级 | 低 |
| P9 | 中 | 12 个配置寄存器全 32bit（真实 ≤9bit）+ `bmerge×12` | −250 FF，−200 LUT | 极低 |
| P13 | 中 | `dbg_addr[0:287]` = **9216 bit** 且带复位循环 ⇒ 9216 个 FF | **已用 `ifndef SYNTHESIS` 修掉** | 极低 |
| P3 | 中高 | 两份 288×64 异步 LUTRAM → **2× RAMB36 同步读**（代价只有"读变同步"，而引擎本来就是同步契约，**不需要额外周期**）| −900 LUT，−3~4 级 | 中（需回归 6 个 golden）|
| P8 | 中 | CAM 显式 one-hot→binary 编码（tag 唯一，安全）+ `cam_pf` 用 12bit 部分 tag（假阳性只掉性能不掉正确性）| −120 LUT，−2 级 | 低 |
| P6 | 中 | 写侧两个 64bit 8 粒度移位器 → 8 个字节组各自解码写使能 | −250 LUT，−2 级 | 中 |

## A.3 两个直接回答

**"可以移到 DSP 的运算"：本层没有。**
本层全部乘法都是小常数/小范围乘法，正确做法是**强度削减**（P4），搬 DSP 反而浪费 160 里宝贵的份额。
反向结论：**该往 DSP 搬的是 `conv_int8_uni` 的 MAC，不是这个 wrap**。

**"LUTRAM 该换 BRAM，而且免费"**：
现在两份 288×64 异步读 LUTRAM ≈ 5+2=7 LUT/bit ⇒ 450~500 LUT/份，两份 900~1000。
换成 512 深×64 宽 SDP（2 个 RAMB36 = 95 里的 2%），代价只有"读变同步"。
而且 miss 停钟期间地址不动，BRAM 输出自然一直有效；`ent_rdy` 是"整线到齐"，命中时 8 前瞻槽一定有效。

## A.4 建议路线

先用 **P1+P2+P4+P7+P13**（机械改动，几乎不可能改错）+ 回归，看能否从 40 上到 80~100 MHz；
再上 **P3+P5+P8**（BRAM + 端口寄存器化）冲 150。
`NLINES` 32→64 **只在 CAM 变便宜（P3+P8）之后才做**，否则 LUT 会顶到天花板。

# 附录 B：根因确认 —— LUT 占用导致布线延迟（有历史证据）

## B.1 旧设计从来没有真正收敛 150 MHz

```
pl/build/try125/timing_worst.rpt   (10/27，二值化之前，只有 k1+k3)
  Slack (VIOLATED): -1.505 ns      ← 150 MHz 下已经违例
pl/build/k1_opt/util.rpt
  LUT 38588 (83.52%)   BRAM 76 (80.00%)   DSP 137 (85.63%)
```

$$\Rightarrow \text{旧设计是"带病跑 150 MHz"（约 5\% 端点违例）}$$

$$\Rightarrow \text{加二值单元把 LUT 推到 88\%+ ⇒ 布线延迟吃掉余量 ⇒ 崩到 40 MHz}$$

$$\Rightarrow \textbf{根因 = LUT 占用，不是某几条长路径}$$

**收敛目标**：$\text{LUT} \le 30{,}000$（65%），给布线留出 35% 余量。

## B.2 实测的 LUT 黑洞（全部有综合日志证据）

| # | 位置 | 现象 | 代价 |

| **2** | `conv_int8_uni.v:704-715` 权重写口 | `8-6841 byte width(1)` / `8-6849 Infeasible ram_style` | BRAM **64 tile（67%）** + 2,048 LUTRAM |

## B.3 头号元凶的账

$$288\times64\times2 = 36{,}864\ \text{个位}\times 288{:}1\ \text{选择} \Rightarrow \approx 9{,}000\ \text{LUT6}$$

换成 **2 个 RAMB36 同步读**后：
- LUT −9,000
- FF −36,864
- 关键路径上 288:1 mux 消失
- 代价只有"组合读 → 同步 1 拍"，而**引擎契约本来就是 t 发地址 / t+1 用数据**，不需要额外周期

$$\Rightarrow \text{LUT } 40\text{k} \to 31\text{k} = 67\% \Rightarrow \text{150 MHz 有望}$$

# 附录 C：`bin_*` 三个单元（rprelu / sam / interp）

## C.0 重要前提

**当前 BD 里 `bin_unit_0` 的 UNIT=0 = 只有 `bin_conv_core`（5,845 LUT / 4,968 FF）**，
`rprelu/sam/interp` 只做过 xsim，**从未进过综合** ⇒ 40 MHz 不是它们造成的，
但加进去必须一次做对。

## C.1 除法可以整段删掉（已数值验证）

$$\text{26 个 interpolate 的 } \frac{H}{H_O}, \frac{W}{W_O} \in \left\{\frac14, \frac12, 2, 4\right\} \Rightarrow t_y, t_x \text{ 恒为 } \frac{den}{8} \text{ 的整数倍}$$

$$\Rightarrow \frac{N}{D} \equiv \frac{W}{64},\quad W = A_y A_x a + A_y B_x b + B_y A_x c + B_y B_x d,\quad |W| \le 8192\ (15\ \text{bit})$$

**验证**：4 个 manifest、**88,134 个像素**，`N/D` 与 `W/64` 整数精确对比，**0 差异**，
`round_half_even` 也一致。注意 640 网的 $D = 102400 = 2^{12}\cdot25$ **不是 2 的幂**，
所以"2 的幂就右移"不成立，而 $W/64$ 形式对 640 网同样成立。

**收益**：去掉 8 拍 48 位长除法 + 48 位 4 项加树 + 32 个 34×8 乘法
（DSP48E1 是 25×18，34 位要 2 个 DSP ⇒ 8 lane×4 = 最多 **64 DSP**）。

**不要做 PS 侧倒数乘法**：要精确需要 ≥53 位倒数，31×53 乘法 + 回乘验余数 ≈ 4~5 DSP/lane×8，比除法更差。

## C.2 8-bit 写口是吞吐天花板

wrapper 写打包器一拍只吞 1 字节 ⇒ 每组 8 通道要 8 拍。但 `C%8==0` 已被强制
（`bin_unit_axi_wrap.v:617 ERR_LAYOUT`），每组恰好是 8 字节对齐整字 ⇒ **一拍照写 64 bit**。

| 单元 | 现在 | 改后 @150 MHz |
|---|---|---|
| rprelu（227 层，93 M 元素）| 620 ms | **78 ms** |
| interp（30.7 M 元素）| **537 ms** | 67 ms |

## C.3 两个变移位器：约 6,400 LUT

- `bin_rprelu:236` `prod_r >>> sshift_r` —— wrapper 已在 `:650` 强制 `slope_shift==8`
  ⇒ **常量 8，纯布线**，省约 1,500 LUT
- `bin_rprelu:238` `r_c >>> oshift_r` —— 40 位×6 级 ≈ 240 LUT/lane（1,900）
- `bin_sam:273` `sx8(xg) <<< shift_r` —— **64 位**×6 级 ≈ 384 LUT/lane（**3,000**）

## C.4 地址路径的 6 个 32×32 乘法

`rprelu:147` `cg_r*hw_r`；`sam:197`；`interp:481/482` `cg_r*HW_r`、`y0c*W_r`×2；
`interp:506/507` `cg_r*HOWO_r`、`oy_r*WO_r`。
而 `cg*HW + pix` **总是连续的**（换组时 pix 归零，字号正好接上）
⇒ 改成 `wo <= wo + 1` 计数器，**6 个乘法全消**。

## C.5 interp 位宽核算（`HW_MAX` 是 wrapper 已有闸门，默认 4096）

| 量 | 契约上限 4096 | 定 HW_MAX=1024 后 | 现在 | 建议 |
|---|---:|---:|---:|---:|
| `den/tynum/vy` | 14 | 12 | 40 | **12** |
| 坐标 `y0/x0` | 13 | 13 | 40 | **13** |
| `kij, D` | 27 | 23 | 34 | **23** |
| `N, rem, dsh` | 35 | 31 | 48 | **31** |

⇒ 可省约 600 FF + 500 LUT。

## C.6 其它

- `sat8` 用 `or_reduce/and_reduce(v[W-1:8])` 取代两条 W 位比较器：8 lane 省约 600 LUT
- `bin_sam` 的 64 位加树（`acc_c` 3 个 64 位加法 ×8 lane ≈ 1,500 LUT）收窄到 32 位
  （$|acc| \le 128\cdot2^{15} + 3\cdot2^{15}\cdot128 \approx 2^{24}$）
- `bin_rprelu` 的 `dd` 用 16 bit 只在 $|zeta| \le 32512$ 时安全（`zeta` 是 int32 契约）
  ⇒ wrapper 加 ERR 检查
- FF 数组（`ob/nb/rem_r/q_r`）只有 8 项，**不该进 BRAM**（读出要 1 拍，延迟更差）
- **三个单元必须合并成一个 IP**：wrapper 本身约 2~2.5 kLUT，4 个 IP 就要 4 份，
  而 conv_uni 已占 24.4k/46.2k

## D.1 预期效果

$$\text{LUT}: 40\text{k} \xrightarrow{1} 30\text{k} \xrightarrow{2,3,5,7} \textbf{约 17k (37\%)}$$
