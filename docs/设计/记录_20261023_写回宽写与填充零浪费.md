## 1. 目标 1：写回 —— 先纠正一个前提

### 1.1 现状核对：三处写回循环**本来就已经 II=1**

按任务书的要求先查"达成 II"，答案是**没有 II=19 这回事**：

```
# 起点 csynth（proj/engine_v1/solution1/syn/report/，2026-10-23 08:33）
conv2d_engine_Pipeline_VITIS_LOOP_610_31_csynth.rpt   （k=1 快路径写回，源 :610）
 |- VITIS_LOOP_610_31 | 0 | 12 | 6 | achieved 1 | target 1 | 0 ~ 8 | Pipelined yes |
conv2d_engine_Pipeline_VITIS_LOOP_688_36_csynth.rpt   （k=3 快路径写回，源 :688）
 |- VITIS_LOOP_688_36 | 0 | 12 | 6 | achieved 1 | target 1 | 0 ~ 8 | Pipelined yes |
csynth.rpt 循环汇总                                  （通用路径写回，源 :705）
 |- VITIS_LOOP_705_37 | 16 | ? | 2 ~ ? | - | - | 8 | no |   ← 8 次 store、每次 2 拍
```

三处**都不是流水问题**。真正的证据在生成 RTL 里：

```
# 起点 proj/engine_v1/solution1/syn/verilog/
#   conv2d_engine_conv2d_engine_Pipeline_VITIS_LOOP_610_31.v
627: assign m_axi_gmem1_0_AWLEN = 32'd0;     // ← 每笔 AW 只有 1 拍
653: assign m_axi_gmem1_0_WSTRB = 1'd1;      // ← 只有最低字节
```

即：**每写 1 个字节就发一笔 AWLEN=0 的 1-beat AXI 写事务**，端口数据宽度也是 8 bit。
"19 拍/字节"是**每笔事务的往返延迟 ÷ 在途字节数**（16 笔 × 1 B），不是循环没流水。
所以"把循环改流水"不可能有效果——`#pragma HLS PIPELINE` 那三条早就在了。

> 附带纠正：`docs/设计/记录_20261023_DDR访问加宽4字节与上板.md` §5.2 里
> "HLS 早就把连续 8 次单字节写合成了一笔 burst"的说法**是错的**（当时只是推测，
> 没去读 RTL）。这也解释了上一轮"打包成 64-bit"为什么反而慢 5.6%：
> 它把 store 塞回了计算流水（8 个值攒齐才能打包），事务结构一点没变。

### 1.2 修法：行缓冲 + **独立**拷贝循环

```
计算（不变） → wbuf[8][448]（LUTRAM，8 个 oc 各一个 bank）
             → 本行块算完后再跑一条**纯拷贝循环**：8 bank 同址并行读 → 拼 64-bit → 连续写
```

```cpp
// C8 写回落到行缓冲（三条路径共用宏；CHW 仍是原样逐字节直写）
#define WB_STORE(i_, x2_) (wbuf[(i_)][(x2_)] = v8)

// 本 (y, ocb) 行块算完后一次性宽写出去
const int obase = (int)(OUT_ADDR(ocb, 0, y, x0));       // 恒 8 的倍数
w64_t *pw = reinterpret_cast<w64_t *>(out_fm + obase);
HLS_PRAGMA(HLS PIPELINE II=1)
for (int px = 0; px < xn; ++px) {
    w64_t w = (w64_t)(uint8_t)(wbuf[0][px]);            // 8 个常量移位拼字
    w |= (w64_t)(uint8_t)(wbuf[1][px]) << 8;
    ...                                                  // 2..6 同
    w |= (w64_t)(uint8_t)(wbuf[7][px]) << 56;
    pw[px] = w;
}
```

要点与代价：

* `wbuf` 的 dim1 **完全拆分**成 8 个 bank ⇒ 计算侧"第 i 个 oc 写第 i 个 bank"是
  **编译期常量偏移**，拷贝侧"一拍读 8 个 bank"也是常量 —— 没有违反
  "bank 号必须编译期常量"那条铁律。
* 端口宽度 8 → **64 bit**（`WSTRB = 8'd255`），事务数 ÷8、在途字节 16 B → 128 B。
  ⚠️ 但本轮 RTL 里 **`AWLEN` 仍然是 `32'd0`**（每像素一笔 1-beat 64-bit 事务）——
  HLS 对"局部数组 → m_axi"的拷贝**没有**给出长 burst。所以收益全部来自
  "每笔带 8 字节"，不是 burst；把 AWLEN>0 做出来还是下一步（§4）。
* 尾部通道：`cout%8 != 0` 时 8 字节整字会踩到补零通道，所以在 x2 循环前
  把 `wbuf[i≥ocbl][*]` 清 0（C8 下 PS 按 `ceil(cout/8)*8` 分配，期望那里是 0）。
* 串行代价：每 `(y, ocb)` 块多 `xn` 拍拷贝 ⇒ 全网络 `140.5 MB / 8 ≈ 17.6 M 拍 ≈ 0.12 s`。
* 资源：`wbuf` 8×448 放 LUTRAM = **+448 LUT**（报告里 `wbuf_*_RAM_2P_LUTRAM`，448 LUT/块 ×8）；
  64-bit 写端口让 AXI 写适配器多 **+3 BRAM18**；合计 +1,206 LUT、+3 BRAM18、+616 FF，DSP 不变。

### 1.3 写回实测成本

用 `swap_8_8` ↔ `swap_8_64`（只改 cout ⇒ 只改写回字节数与 MAC 数，可差分）标定：

| | 每字节写回成本 |
|---|---:|
| 旧 bit（逐字节 1-beat） | 116 ns/B ≈ **17.4 拍/B** |
| 新 bit（64-bit 宽写） | 55.5 ns/B ≈ **8.3 拍/B** |

带宽 2.1×。**没有到 8×**：事务数虽然 ÷8，但在途字节只有 16×8 = 128 B，
仍然被往返延迟卡；而且 HLS 没给长 burst（AWLEN 仍为 0），等于每 8 字节就要
一次完整的 AW/W/B 往返。这两件事就是 §4 的下一步。

### 1.4 试过但**无收益**的：`num_write_outstanding` 16 → 64

按"多 outstanding 生效"的思路把写事务在途数从 16 提到 64（csynth 里
`CH0_NUM_WRITE_OUTSTANDING 16→64`、`NUM_WRITE_OUTSTANDING 16→64`，资源逐项不变），
板上 13 个微基准**逐项一致到 0.01 ms**（`write_heavy_8_192` 1102.84 / 1102.84，
`k3_preconv1` 3816.28 / 3816.27，`runs/prof20261023/phase_split_r5_wr64.json`）。
而且 WNS 从 −0.229 恶化到 −0.695 ⇒ **已回退**，交付版停留在 outstanding=16。

原因：适配器的 AW 请求 FIFO（`USER_MAXREQS`）只有 **4** 深，写请求根本进不了
在途队列，加深响应 FIFO 没用。下一步要么把这个深度抬上去，要么让拷贝循环
产出**真正的长 burst**（AWLEN>0）——后者才是把 8.3 拍/B 压到底的办法。
（本轮没做：`pw[px]=w` 这种"局部数组 → m_axi"的拷贝，HLS 仍然只给 AWLEN=0。）

## 2. 目标 2：行填充 —— 3~5 s 的目标里，有 **4.2 s 是白写的零**

### 2.1 先把填充的账算清

填充循环（`C8_LAYOUT` 分支）对每个新载入行写三类字节，全部 **II=1（1 字节/拍）**
（csynth：`LOOP_279_10`/`LOOP_282_11` 补零、`LOOP_326_13` 数据，achieved II 均为 1）：

| 类别 | 全网络字节数 | 拍数 @150 MHz |
|---|---:|---:|
| 有效输入数据 | 52.4 MB | 0.35 s |
| **右补零（永不被读）** | **624.7 MB** | **4.17 s** |
| k=3/k=5 的行下移（BRAM 内 copy） | 238.0 MB | 1.59 s |
| **合计** | 924.8 MB | 6.17 s |

`k=1` 的"宽列块"（`K1_WIDE_COLS`）把 line_buf 的 7 个 row-bank 当 448 列用，
而 320 宽的层只填 `lb=320` 列，于是 **[320, 448) 这 128 列每行每通道都被写成 0**，
而计算只读到 `cb = x2 < xn == lb` —— 一次都不会读到它们。
`CHW` 分支早就有 `if (!wide1)` 跳过这段（注释还写着"wide1 时不需要尾部补零"），
**C8 分支漏了**。

### 2.2 改动：一行 `if`

```cpp
for (int ic = 0; ic < cin; ++ic) {
    for (int j = 0; j < la; ++j)            line_buf[ic][r][j] = 0;
    if (!wide1) {                           // ← 本轮新增
        for (int j = la + lb; j < bwcol; ++j) line_buf[ic][r][j] = 0;
    }
}
```

零资源代价，实测 `fill_heavy_192_8` 快 **49.9 ms**——与该形状白写的零字节数
（320 行 × 192 通道 × 128 列 = 7.86 MB ÷ 150 MHz = 52.4 ms）**吻合到 5%**，
证明"1 字节/拍"的模型是准的，也证明网络级 4.17 s 的估算可信。

### 2.3 为什么**没有**做"填充与计算重叠"

做完 §2.2 之后填充只剩 ≈2 s（数据 0.35 + 行下移 1.59），重叠的**收益上限就是这 2 s**。
再算预算：

* `line_buf[352][7][76]` 在 csynth 里被拆成 7 块 `line_buf_RAM_2P_BRAM_1R1W`，
  每块 16 个 BRAM18 ⇒ **112 块 BRAM18 = 56 个 BRAM tile**；
* 双缓冲要再来一份 ⇒ **+56 tile**，而 impl 只剩 **6.5 tile**（88.5/95）⇒ **超限 8 倍**；
* `DATAFLOW` 方案同样需要一份中间数组，量级相同；
* 且计算侧每拍都在读 line_buf（RAM_2P = 1R1W），填充要写同一批行（还没做行下移的话），
  真正重叠必须先解决"旋转行缓冲"，而旋转行的 bank 号是**运行期值** —— 直接撞上
  "bank 号必须编译期常量"那条铁律（见 `记录_20261023_k3权重装载宽读.md` §5.3 的教训）。

⇒ 按"LUT>85% / BRAM>95% 就放弃"的纪律：**放弃**，并把上面这 2 s 记为"不值得动"。
真正的下一步不是重叠，而是让 line_buf 的写口能**一拍写多字节**（28 bank），
但那是 +5.6k LUT 的老账（当前 LUT 78.8%，仍需另一次腾挪）。

## 4. 坑 / 结论

1. **"循环没流水"这个前提是错的，别再按它改。** 三处写回里两处 achieved II=1，
   第三处（通用路径）8 次 store 一共 16 拍。写回慢的原因是 **AXI 事务形态**
   （AWLEN=0 + 8 bit 端口），根因要看 `m_axi_*_AWLEN/WSTRB`，不是看 II。
2. **同一个"加宽写"动作，放的位置决定成败**：放进计算流水里（上一轮）= 慢 5.6%；
   放进独立拷贝循环（本轮）= 快 52%。区别是前者要求 8 个值攒齐、把 store 挤出流水，
   后者是纯数据搬运。**以后任何"宽写"都照后者做。**
3. **补零也会花真金白银**：C8 的宽列块给 k=1 每行每通道白写 128 个零，
   全网络 624.7 MB ≈ 4.2 s，比有效输入还多 12 倍。`CHW` 分支有 `if (!wide1)`，
   `C8` 分支漏了半年 —— **两个布局分支要逐行对照**。
4. **`num_write_outstanding` 在本设计里是空转的**：AW 请求 FIFO `USER_MAXREQS=4`
   才是真瓶颈；抬到 64 逐项 0 收益，还把 WNS 从 −0.229 拉到 −0.695。已回退。
5. **填充已经不再是 DDR 延迟问题**，而是 `line_buf` 写口 1 字节/拍的吞吐问题；
   重叠的收益上限（≈2 s）小于它的代价（+56 BRAM tile / 旋转行违反 bank 常量铁律）。
6. **bit 与包仍然成对**：本轮**没动**权重容器（PAD12/PAD28 一个字节没变），
   所以旧包 `ab33c237…` 直接沿用；只有 bit/hwh 换新。
