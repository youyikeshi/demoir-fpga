# pp 整网“成功但算错”的根因，以及 C8 层间算子的逐位一致加速

> 2026-10-23　|　范围：PS 侧（`pp_ops` / `ops_numpy` / `runner` / 一个新 C 内核）
> **未改 RTL、未重跑 HLS/Vivado、未 commit。**

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 黄金 bit 上 pp 为什么一直“没生效” | **那个 bit 里根本没有 pp IP**（`golden.hwh` 只有 `engine` 的 2 个 AXI-Lite）⇒ `PPEngine._discover` 抛异常，被 `run_network_on_board.py` 的 `try/except` 吞掉，`r.pp=None` ⇒ 全走 CPU。不是 `pp_ops` 的返回码问题。 |
| 新 bit 上 pp 为什么“成功但算错” | **不是地址、不是零拷贝、不是返回码**。SUM3W 用 Q16 int32 系数 + int32 累加，与整网参考的 float64 `w*(y*s)` 在 rint 的 .5 边界上必然分岔；整网对 1 LSB 中间差异**混沌放大**（翻 1 个像素 → 最终 58.7% 像素不同）。 |
| 修复 | sam_sum 不再走 pp（默认守卫）+ 逐位一致的快路径（numpy 分块 / ARM 上自动编译的 C 内核）；interp、eca 同样接 C 内核。整网从 **185.0 s → 144.89 s**，**0/1,228,800**。 |

## 1. 证据链

### 1.1 黄金 bit 没有 pp IP
```
golden.hwh:  /engine s_axi_control=0x40000000, s_axi_ctrl=0x40010000
             没有 /pp 模块
```
`PPEngine._discover()` 找不到 `pp` → `RuntimeError("overlay 里找不到 pp IP…")`
→ `run_network_on_board.py` 打印“不可用”，层间算子全部回落 numpy。

### 1.2 新 bit 的地址/寄存器/零拷贝都是对的（板上实测）
```
ip_dict: pp phys=0x40030000 type=xilinx.com:hls:interop_accel:1.0
写 ctrl(0x40020000)+0x18 = 0x5a5a0011 -> 读回 0x5a5a0011
写 base(0x40030000)+0x10 = 0x0badf00d -> 读回 0x0badf00d
交叉读: base+0x18=0x0  ctrl+0x10=0x0
```
生成头 `xinterop_accel_hw.h` 逐项核对：ctrl 块 0x00 ap_start / 0x10 ap_return /
0x18 op … 0x50 nsrc；control 块 src0 0x10、src1 0x1c、src2 0x28、src3 0x34、
dst 0x40、coef 0x4c（64 位，高半字 +4）。`pp_engine.py` 与之一致。

arena 零拷贝：5 个 sam_sum 张量的
`_dev().device_address - (pool.device_address + arena.offs)` **全部 Δ=0**；
`np.asarray(pool).ctypes.data == pool.virtual_address`（真零拷贝）。

### 1.3 在真实 arena 上单独跑算子，逐位全对
```
SUM3W  k=65536 单位系数（地址/步长）   0 / 4,915,200
SUM3W  真实系数（pp_ops 原样，不 flush）0 / 4,915,200
REDUCE_MEAN（arena scratch / 独立缓冲） 0 / 144
INTERP（arena 零拷贝）                 0 / 1,228,800
```

### 1.4 主机侧用 PPSim 复现出**完全一样**的 720,544
```
pps=interp,eca,sam_sum  PPSim  41.2s  与 ref_out 不一致 720544 / 1228800
pps=interp              0
pps=eca                 0
pps=sam_sum             720544
```
⇒ 与硬件无关，是 `sam_sum` 的**数值语义**。

### 1.5 逐层差异只有 ±1，但整网混沌放大
```
[0] encoder.encoder_1.sam_blocks.0.sum  C=48   302 / 4915200  max|d|=1
[1] encoder.encoder_2.sam_blocks.0.sum  C=96   274 / 2457600  max|d|=1
[2] encoder.encoder_3.sam_blocks.0.sum  C=192   73 / 1228800  max|d|=1
[3] decoder.decoder_3.sam_blocks.0.sum  C=64    55 /  409600  max|d|=1
[4] decoder.decoder_2.sam_blocks.0.sum  C=64   112 / 1638400  max|d|=1
[5] decoder.decoder_1.sam_blocks.0.sum  C=64   501 / 6553600  max|d|=1
```
把 sam_sum#0 输出**只翻一个像素**（+1）：
```
最终输出不一致 721,977 / 1,228,800 (58.7%)，幅值到 ±4
```
这与 C8 文档里“差一个 ulp 就雪崩到 59%”完全吻合。
⇒ **整网任何一处 1 LSB 差异都不可接受**，pp 的 Q16 在 sam_sum 上不可用。

## 2. 修复

### 2.1 `pp_ops.run_sam_sum` 默认关闭（`PP_SAM_SUM_ALLOW=1` 才放行）
原因写进 docstring：Q16 与 float64 无法逐位一致；放行仅供吞吐实验。

### 2.2 `ops_numpy.sam_sum_into`：逐元素同序的分块实现
与 runner 旧循环**逐元素同序**（IEEE 不可重排）：
```
yf  = w0*(y0*s0) + w1*(y2*s2) + w2*(y4*s4)     # 左结合，每个乘积先算
out = clip(rint((xf + yf) / s_out), -128, 127).astype(int8)
```
只把“16 通道 × 全图 float64 临时数组”换成“1 通道 × 8192 像素、两块复用缓冲”。
主机/板上逐位 0 差异。

### 2.3 `sam_sum_fast.c`（新）：ARM 上首次调用自动编译，自检不过静默回落
- `sam_sum_f64`（CHW）、`sam_sum_c8_f64`（C8 交错）、
  `chsum_c8`（ECA 的逐通道 int64 和）、`interp_c8`（C8 双线性，整数路径同序）；
- 编译参数 `-O2 -std=c99 -ffp-contract=off`（**绝不能** FMA 融合/重排）；
- ARMv7 没有 round-to-integral 指令，`rint()` 是 libm 调用（0.87 s/op）；
  改用 2^51 魔数 `(v+M)-M`（2 条 double 加法，等价于 half-even）；
- 加载后先用覆盖全部 int8 取值的样本对拍 numpy，一位不同就禁用 C。

### 2.4 **池内存是“非缓存”映射，必须整块暂存**
同一个 C 内核：私有数组 0.75 s/op，直接读 arena 池视图 **3.65 s/op**；
而 `np.copyto` 整块搬运有 260~570 MB/s。
⇒ C 内核一律 “池 → 私有 5 块缓冲 → 算 → 写回池”。sam_sum 6 个 op 24.8→3.3 s。

### 2.5 runner 接线
- CHW sam_sum → `ops.sam_sum_into`
- C8 sam_sum → `ops.sam_sum_c8_into`
- C8 eca（pp 在 C8 下被整段旁路）→ `ops.chsum_c8` + 与 pp 相同的均值公式
- C8 interp → `ops.interp_c8_into`（非 1/8 网格/布局不符自动回落）
- `run_network_on_board.py --pp-ops` 默认改为 `interp,eca`

## 4. 排除过的假设

| 假设 | 结论 |
|---|---|
| pp 的 ctrl/base 地址接反 | 否。hwh + 寄存器回读都证明 ctrl=0x40020000、base=0x40030000 |
| hwh 只报一个地址导致发现错 | 否。`_discover` 用固定 BD 地址，hwh 值只做校验 |
| arena 零拷贝偏移/itemsize 算错 | 否。全部 Δ=0，隔离算子 0 差异 |
| 系数 scratch 与张量重叠/未 flush | 否。真实 arena 上 SUM3W 真实系数 0 差异 |
| `_rc_of` 读错返回码 | 否。已正确解元组；pp 确实启动并完成 |
| pp 在新 bit 上没跑（超时/秒退） | 否。sam_sum 4.8 s 且与 PPSim 逐位一致 |
| ECA 均值/attn 分岔 | 否。`--pp-ops eca` 整网 0 |
| interp 分岔 | 否。`--pp-ops interp` 整网 0 |
| **sam_sum 的 Q16 定点** | **是**。唯一根因 |

## 5. 坑

1. **pp 在 C8 下被整段旁路**：`runner.py` 里 `ppen = set() if self.c8 else ...`。
   “新 bit + --c8 复现 pp 问题”不存在；C8 的层间算子根本没走 pp。
2. **arena 池的 CPU 字节访问极慢**（CMA 非缓存映射）：任何逐字节 numpy/C 循环
   直接读池都会慢 3~5 倍。要么整块暂存，要么让 PL 用 DMA 读。
3. **`np.ascontiguousarray(x).ctypes.data` 是悬垂指针**：临时数组取完指针就被回收。
   x86（intp=int64→int32 必新建）立刻出错；ARM（intp=int32，常原样返回）会“侥幸正确”，
   极难发现。必须先把数组绑定到局部变量。
4. **ARMv7 没有 `vrint`**：`rint()` 是 libm 调用；用 2^51 魔数等价替换。
5. **C 内核必须 `-ffp-contract=off`**：默认 FMA 融合会改末位。
6. **整网混沌**：任何“看起来只差 1”的中间量都会放大到 ~59% 像素。
   所有层间算子只有两条路：逐位一致，或不用。
7. `CmaFree=0` 在整网运行中是**正常**的（进程持有 arena）；收尾会回到 ~100 MB。
8. 后台 ssh 的 stdout 经 `tail` 会整段缓冲，别把“看不到输出”误判成卡死
   （看 `/proc/<pid>/stat` 的 utime 与 state=R 即可）。

## 7. 旁证：conv 的权重加载确实在 x 分块/行循环内被重复

`pl/src/conv2d_engine.cpp`：
```
for (x0 ... )            // 列块
  for (y ...)            // 输出行
    for (ocb ...)        // OC 块
      ... 权重从 DDR 读进 wgt3_buf ...   // ← 每个 (列块, 行, ocb) 都重装一次
      for (x2 ...) ...
```
权重与 (x0, y) 无关，却按 `Hout × ⌈Wout/bw⌉` 次重复装载；
这与你们测到的“权重加载 ~0.4 MB/s、随 cout 线性、大形状 6.1×”一致。
