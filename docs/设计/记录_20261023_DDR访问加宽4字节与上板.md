## 1. 改了什么（净改两处）

### 1.1 填充：`in_fm` 按 32-bit 读（`conv2d_engine.cpp` C8 分支）

C8 布局下连续 4 字节 = **同一像素的 4 个通道**。把内层循环从"每拍读 1 字节"
改成"**每 4 拍读一个 32-bit 字、其余 3 拍从循环携带寄存器 `hold` 里取字节**"：

```cpp
const w32_t *p32 = reinterpret_cast<const w32_t *>(in_fm + iob);
w32_t hold = 0;
for (int t = 0; t < nwide; ++t) {          // nwide = lb*8
    if ((t & 3) == 0) hold = p32[t >> 2];
    line_buf[cinb + (t & (C8_CH - 1))][r][la + (t >> 3)] =
        (data_t)(hold >> ((t & 3) << 3));
}
```

对齐前提（两条恒成立，已逐项核对）：
* `iob = io_row*8 + (cinb>>3)*H*W*8` ⇒ 恒为 **8** 的倍数；
* `lb*8` 恒为 4 的倍数（其实恒为 8 的倍数）。

### 1.2 权重装载（k=1 分支）：同样手法

`wgt1_buf[i][ic] = wgt[off1+ic]` → 每 4 拍读一个 32-bit 字。
k=1 时 `off_ocb` 每次加 `cin*8`（恒 8 对齐），块内 `off1 = off_ocb + i*cin`，
只有 **`cin%4==0`** 才保证 4 对齐，否则最后一个字会读到下一个 oc 的地界外 ⇒
`cin%4==0` 走宽路径、否则走原逐字节路径（运行期一次判断，不在循环里）。

### 1.3 没改的：写回（试过，实测无收益，已退回）

见 §5。

## 2. 硬判据：ARLEN 从"1 个字"变成变长 burst

`I_CH0_ARLEN` 的单位是**总线字**（gmem0 是 32-bit ⇒ 1 个字 = 4 字节），
不是字节。基线"每字节一笔"的真相是：**每笔请求 1 个字 = 抓回 4 字节、只用 1 个**。

**改前**（`/data/work/hls_c8_cosim/pure11/cosim1/sim/verilog/`）：

```

Pipeline_VITIS_LOOP_343_16_VITIS_LOOP_345_17.v:1016  assign m_axi_gmem0_0_ARLEN = 64'd1;   // k=1 权重重装
```

**改后**（`/data/work/hls_c8_csynth/c8_w4_final/solution1/syn/verilog/`）：

```

Pipeline_VITIS_LOOP_319_13 => assign m_axi_gmem0_0_ARLEN = 32'd0;      // 填充的分支已被拔到顶层 FSM（悬空）
（填充与 k=1 权重两条流水都**不再驱动** ARLEN）
$ grep 'gmem0_0_ARLEN =' conv2d_engine.v
        gmem0_0_ARLEN = 64'd1;                       // bias 读（4 字节，1 个字，未变）
        gmem0_0_ARLEN = zext_ln241_4_reg_9359;       // ★ 填充：**运行期变长 burst**
        ...
INFO: [HLS 214-115] Multiple burst reads of variable length and bit width 32
      has been inferred on bundle 'gmem0'  (src/conv2d_engine.cpp:314)   ← 填充
INFO: [HLS 214-115] Multiple burst reads of variable length and bit width 32
      has been inferred on bundle 'gmem0'  (src/conv2d_engine.cpp:409)   ← k=1 权重
```

即：HLS 把"填充循环里的全部读"推断成**一笔变长 burst**（长度 = `nwide/4` 个字 =
`lb*8` 字节，再按 `max_read_burst_length=256` 切），k=1 权重同理（每 oc 一段
`cin/4` 个字）。事务数从"字节数"降到"`lb*8/256` 或 `cin/4`"，**两到三个数量级**。

> 判据的教训：`ARLEN` 常数消失、被运行期信号取代，也是"变宽了"的合法证据；
> 不要死等 `ARLEN == 4` 这个字面值 —— HLS 一旦能证明连续，就直接给长 burst。

## 4. 为什么"填充只快了 3 倍"而不是 10 倍

填充循环本身是 **1 字节/拍**（line_buf 每拍只写得进 1 个字节：
7 个行 bank × 单写口，同一行内 8 个通道落在**同一个** bank 上）。
理论上界就是 3.36 s（504 MB ÷ 150 MHz），实测 `fill_heavy` 斜率约 3 拍/字节
⇒ 已经贴近"循环下界"，剩下的缺口是"等 burst 落地"没有和"写 line_buf"重叠
（HLS 把整段读推断成一笔 burst 后，循环要等它回来）。想要再快就得做
**双缓冲/数据流**（读下一段的同时写当前段），属于下一轮。

## 5. 试过但否决的两个方案（都有实测数据，别再试）

### 5.1 填充 II=1 并行写 4 个 bank（cosim 能到 301,500 拍，LUT 92%）

要让 32-bit 字的 4 个字节**同一拍**写进 4 个不同 channel，必须给 line_buf 的
通道维加 `cyclic factor=4`（28 个 bank）。功能完全正确、BRAM 一点不涨（仍 172），
但 csynth **LUT 35,361 → 42,920（76% → 92%）、FF +1,438**：28 个 bank 之后
每一处 line_buf 读写都要生成 28 份"地址 + 片选"，而 line_buf 的读写点在三条
计算路径里一共 40 来个 ⇒ 光 mux/译码就是 +5k LUT。当前 impl 已 80.66%，不能走。

**不写 pragma 的版本也一样**：HLS 看到"1 拍 4 写 + 1 读"会自动把 II 拍到 1，
然后**自己**把 line_buf 拆成 28 个 bank —— 同样 +5.6k LUT（LUT 40,996/88%）。
也就是说"宽读 + 一拍写 4 字节"这条路在现有 line_buf 形状下必然付 5k LUT，
只有"宽读 + 每拍仍写 1 字节"（本轮方案）才是零代价的。
（顺带：这个自动版本 cosim 是 **301,500 拍（−11.1%）**，如果将来 LUT 有余量，
这是现成的下一个台阶。）

### 5.2 写回 64-bit 打包（实测无收益，已退回）

C8 下同一像素 8 个 oc 是连续 8 字节，本想把 8 次单字节写攒成一个 64-bit 写
（`w64_t wpx` + `reinterpret_cast<w64_t*>(out_fm)[...] = wpx`，基址乘 8 恒对齐）。

板上实测**反而更慢**：`write_heavy_8_192` 2341 → **2472 ms（−5.6%）**、
`swap_8_64` 820.6 → 832.2 ms（−1.4%），而代价是 **+2.7k LUT、+3 BRAM、
gmem1 端口 8→64 bit、WNS −0.419 → −0.529 ns**。已整段退回。

结论：**HLS 早就把"连续地址上的 8 次单字节写"合成了一笔 burst**（写通道的
burst converter 自己会合），加宽只多付了打包的桶形移位和布线。写回真正的成本是
**每笔写事务的往返延迟、且写回循环没有流水**（≈19 拍/字节），不是事务宽度。
下一步要动写回，得让它和计算重叠（流水/多 outstanding 真正生效），不是改宽度。

### 5.3 k=3 权重加宽（拍平 wgt3_buf）：装载能宽读，但读侧垮了

把 `wgt3_buf[oc][ic][3][3]` 拍平成 `[oc][cin*9]` 后，装载确实能按 32-bit 读
（源连续、目的连续），但**读侧垮了**：计算时每个 ic 的 9 个抽头原来靠 (ky,kx)
各占一个 LUTRAM bank（8×3×3=72 个 bank，一个抽头一个读口），拍平后 9 个抽头
挤在同一个 bank 上，8 路 oc 展开 × 9 抽头 ⇒ 一个 bank 要 9 个读口。
csynth：DSP 111→119、FF 24,956→28,595、**LUT 38,056→42,464（82%→91%）**。
已放弃，正解见 §7。

## 7. 下一步（按收益排序）

时间账（本轮终值，逐层实测 + 相位模型）：conv 91.1 s ≈ **k=3 权重 ~40 s (44%)**
+ 计算 22.7 s (25%) + 填充 ~12 s (13%) + 写回 ~13 s (14%) + k=1 权重 ~4 s (4%)。


1. **k=3 权重装载（376 MB，仍 1 字节/笔，约 40 s，占 conv 的 44%）** ——
   这是现在唯一的大头。正解不是拍平 wgt3_buf，而是**改导出侧**：把 k=3 权重按
   "每 ic 补齐到 12 或 16 字节"重排（或按 (ky,kx) 拆成 9 个平面），
   这样"宽读"和"9 个抽头各占一个 bank"能同时成立。
   若不想动导出侧，次优是"每 ic 读 3 个字（覆盖 9 字节 + 相位）再按相位切片"，
   事务数 ÷3，但需要静态相位 ⇒ 把 ic 循环按 4 展开，代价是代码复杂。
2. **填充双缓冲**（§4）：把"等 burst 落地"和"写 line_buf"重叠，3 拍/字节 → 接近 1。
   预期 conv 再降 3~5 s。
3. **II=1 并行写 4 bank**（§5.1，cosim 301,500 拍）—— 只有 LUT 有余量才能上，
   需要先把别的模块的 LUT 腾出来（当前 79%，还差约 5k）。
4. 写回：要动就动"流水/重叠"（§5.2），不要再动宽度。

## 8. 坑（本轮新踩/复验）

1. **`I_CH0_ARLEN` 的单位是总线字，不是字节**。基线 `ARLEN=64'd1` 不是"1 字节"，
   而是"1 个字（4 字节）、只用其中 1 个"。判断"事务变宽"要看"每笔请求的有效字节数"，
   别只看常数。
2. **`#pragma HLS PIPELINE` 放在 `if` 块里的循环前面会被忽略**
   （`WARNING: [HLS 207-7042] pipeline pragma is ignored`，连夹一句变量声明也救不回来），
   HLS 会自己按 `pipeline_loops` 阈值拍到 II=1。基线里那条填充 pragma 一直是
   被忽略的，能 II=1 纯属自动拍。想强制 II，必须把循环移出 `if`。
3. **"宽读 + 一拍写多个不同 bank 的字节"在 line_buf 这种形状上必然 +5k LUT**
   （28 个 bank 的地址/片选复制）。宽读只能配"每拍仍写 1 字节"。
4. **HLS 会自动把"循环里全部连续读"推断成一笔变长 burst**，此时它会把这批读
   拔到顶层 FSM（流水模块的 ARLEN 端口变成悬空 `32'd0`）。看到"ARLEN 端口悬空"
   不要当成 bug —— 去看顶层 `gmem0_0_ARLEN = zext_lnXXX` 和 `214-115` 那条 INFO。
5. **写回 8 连写本来就已经是 burst**，加宽到 64-bit 只加资源不加速度（§5.2）。
6. **`cin%4 != 0` 的层不能走 k=1 权重宽读**：`off1 = off_ocb + i*cin` 会失去 4 对齐，
   末尾那个字会读到缓冲区外 3 字节。必须留逐字节回退路径。
7. 出 bit 后 WNS 是 **−0.529 ns**（上一交付版 −0.419），仍按 `ALLOW_NEGATIVE_WNS=1`
   收集，板上 150 MHz 与改前同一口径跑通（两版都跑 150 MHz 才有可比性）。
