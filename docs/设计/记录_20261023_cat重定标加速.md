## 1. 诊断：5.66 s 花在哪

### 1.1 逐层数据（`--profile-layers`，现有 bit，224 个 cat）

| 特征 | 观察 |
|---|---|
| 总量 | 535 MB（Σ 各段源字节），5.56 s ⇒ 96 MB/s 平均 |
| 分布 | **不是均匀的**：67 个"大 cat"（>2 MB）占 458 MB / 4.4 s；157 个"小 cat"占 0.95 s（6 ms/个） |
| 最贵的 | `decoder_1.sam.fuse_cat` 19.66 MB → 419 ms（47 MB/s）；`encoder_1.sam.fuse_cat` 14.75 MB → 317 ms；`decoder.cat1` 11.47 MB → 248 ms |
| **可疑规律** | 一大簇 cat 全部落在 **45~47 MB/s**（不管 3.28 MB 还是 19.66 MB），而另一些（纯拷贝段）能到 **197 MB/s** |

⇒ 时间不是在"搬运的字节数"上，而是在**某条固定速率的代码路径**上。

### 1.2 每个 cat 到底要干什么（按 manifest 算）

`compute_cat_alias` 已经把 cat 塌成"组缓冲 + 通道切片"，所以运行期每个 cat 只剩两种活：

| 活 | 字节 | 说明 |
|---|---:|---|
| direct 段、标度相同 | 262.7 MB | **零工作**（生产者直接写在目标位置） |
| direct 段、标度不同 | **185.2 MB** | 原地重定标 |
| copy 段（该输入之后还被别人用） | **86.0 MB** | 重定标 + 搬进切片 |

即：真正要碰的只有 **271 MB**，而 271 MB / 5.56 s ≈ **49 MB/s** —— 与 1.1 里那簇
45~47 MB/s 完全吻合。**问题定位到 `_req` 这条重定标路径**，不是 Python 开销，
也不是 cat 的段数。

### 1.3 这条路径有多慢（板上 CMA 缓冲实测，`ps/tools/cat_phase_diag.py`）

4.9 MB 的 `pynq.allocate` 缓冲（= 真实 arena 的映射），单位 MB/s：

| 路径 | 速率 | 备注 |
|---|---:|---|
| `np.copyto(dst, src)` | **183~192** | 内存带宽上限（同尺寸、异缓冲） |
| `i8_copy`（NEON 64 B/迭代） | 166~174 | 自写拷贝内核 |
| **现在的 `_req`：`tobytes()` + `bytes.translate` + 赋值** | **42.8** | ← 就是它 |
| ├ `tobytes()` | 145 | 多一遍读 + 一次 4.9 MB 临时分配 |
| ├ `bytes.translate(tbl)` | **69** | CPython 逐字节循环（10 拍/字节） |
| └ 赋值回 arena | 183 | 多一遍写 |
| 256 项 NEON 查表（16 B/迭代） | 62~65 | A9 的 NEON 是 64 位，256 项要 8 次 `vtbl`+选择 |

⇒ 三个结论：
1. **不是 Python 层开销**（224 次调用的固定开销只占 ~0.3 s）；
2. 也不是"arena 池带宽不够"（memcpy 有 183 MB/s）；
3. 是 `_req` 自己：**3 遍内存 + 69 MB/s 的标量查表**。

## 2. 解法

### 2.1 cat 的重定标：把"查表"换成**逐项验证过的整数仿射**

#### 关键观察

`_req` 的语义是 `y = clip(rint(x · s_from/s_to))`（`lut_util.rescale_lut_bytes`）。
与其在 256 项表里查，不如直接算 —— 但**必须逐位相同**，不能"差不多"。
做法不是猜参数，而是：

> 对每一对标度，找 `(m, A)` 使 `y = sat8(VQRDMULH(x << m, A))`（即
> `round(x·2^m·A / 2^15)`）**对全部 256 个 int8 取值都与查表结果逐项相同**；
> 只有 256/256 全对才采用，否则退回 `(A,S,C)` 仿射，再不行退回查表。

VQRDMULH.S16 是 ARMv7 的一条 NEON 指令，所以内核变成：

```
vld1q.s8 → vmovl.s8 ×2 → vshl.s16 ×2 → vqrdmulh.s16 ×2 → vqmovn.s16 ×2 → vst1q
```

约 11 条指令/16 字节（0.7 op/byte），算力不再是瓶颈。

**命中率（整网真实标度对，399 对）**：Q15 **389 对**，int32 仿射 **10 对**，
查表 **0 对**；再补 200 组随机标度对做压力测试，全部命中。

### 2.2 另一个关键：批量化 + 预热

第一版逐对标度拟合要 **4.2 ms/对**（板端 numpy 调用 ~0.3~0.5 ms/次），
整网 399 对 ⇒ **1.7 s 一次性开销** —— 实测第一版 cat 3.64 s，其中 1.7 s 就是这个。
`lut_util.warm_plans()` 把"求表 + 拟合 + 逐项验证"按 `(pair, m, x)` 三维一次算完：
**399 对 20 ms**（板上实测首次 4.2 ms → 预热后 0.02 ms/次），`Runner.__init__`
里预热一次。

### 2.3 三个调用点（都在 `runner.py`）

| 场景 | 新路径 | 内存遍数 |
|---|---|---|
| cat 的 **direct** 段重定标 | `_req_ip()` → 原地 Q15 内核 | **1 读 + 1 写**（原来是 3 遍 + 1 个临时数组） |
| cat 的 **copy** 段 | `_req_into()` → 直接写进组缓冲的通道切片 | 1 读 + 1 写 |
| 其它（add、非别名 cat…） | `_req()` → 同内核写进新数组 | 1 读 + 1 写 |

### 2.4 内核的"64 字节/迭代"

第一版内核按 16 字节/迭代，实测只有 71 MB/s（比 `bytes.translate` 好不了多少）。
原因：**非缓存的 CMA 内存上一次读会触发整条 cache line 的突发**，16 字节/迭代时
"读→算→写"串行，每条线只摊 16 字节的带宽。改成 64 字节/迭代（4 个 16 字节块，
先发 4 个 `vld1q` 再算再写）后：

| 内核 | 16 B/迭代 | **64 B/迭代** |
|---|---:|---:|
| Q15 重定标（异处） | 71 MB/s | **141 MB/s** |
| Q15 重定标（原地） | 78 MB/s | **163 MB/s** |

⇒ 从 `_req` 的 42.8 MB/s 提到 **163 MB/s**（3.8×，已接近 memcpy 的 183）。

### 2.5 interp：8 通道一次算（NEON int16 车道，无分支）

`ops_numpy.interp_c8_into` 的 C 内核是纯标量：每个输出像素过 8 个通道，每通道
4 次乘加 + 一段"半值取偶"的 `if/else`。实测 **≈1200 拍/像素**（A9 333 MHz），
26 次 interp 共 3.32 s。而 C8 视图里通道是**连续 8 字节**，天然可以一次装进
`int16x8`：

```
top = p00*(8-wx) + p01*wx     ∈ [-1024,1016]     （int16 绝不溢出）
bot = p10*(8-wx) + p11*wx
v   = top*(8-wy) + bot*wy     ∈ [-8192,8128]
q   = v >> 6 ;  r = v & 63
q  += (r > 32) | (r == 32 && (q & 1))      ← 两个 0/-1 掩码，无分支
out = sat8(q)                              ← vqmovn_s16
```

每像素 ~14 条 NEON 指令。**逐位相同**由 `i8_interp_selftest()` 保证：加载时用
标量版做 81 种 (wx,wy) 组合 × 4096 组像素（含 -128/-127/-1/0/1/63/127 等边界值）
的全量对拍，不一致就整块弃用。

### 2.6 add：一条 `VQADD.S8`

`ops.add` 原来是 numpy 的 `astype(int16)` + `+=` + `clip` + `astype(int8)`
（5 遍内存、两份 int16 临时）；饱和加法正好是 NEON 的 `VQADD.S8` 一条指令
（"加 + 饱和"同时完成），1 读 2 + 1 写。6 个 add：1.53 → **0.37 s**。

## 3. 正确性：为什么"换算法"不影响逐位结果

1. 三种实现（Q15 / int32 仿射 / 查表）在给出之前都**对 256 个 int8 逐项验证**过
   （见 `lut_util.fit_q15 / fit_affine / rescale_plan`）；
2. `i8_fast.py` 加载 `.so` 后立刻做一次**全值域自检**（每种 int8 值 64 次 + 随机
   4096 字节，5 组标度）与 `bytes.translate` 比对，一位不同就整个弃用并回落 numpy；
3. `ps/tools/check_i8_scaling.py`（新）：整网 399 对标度 + 200 组随机标度，
   逐项验证 Q15/仿射与查表一致；C 内核（NEON 或标量）与 `bytes.translate` 一致；
4. **整网**：主机 `check_pack_ref.py` 0/1,228,800；板上 0/1,228,800，输出 md5 不变。

## 5. 坑

1. **`cc` 默认不开 NEON**（板端 Cortex-A9/armv7l）：`i8_fast.c` 里 `HAVE_NEON=0`，
   于是走标量兜底——逐字节访问 CMA 只有 6.4 MB/s，**比改造前还慢 6 倍**
   （实测 cat 5.66 → 65.6 s）。现在编译时显式带 `-mfpu=neon -mfloat-abi=hard`，
   并在加载时打印 `i8_have_neon()`，ARM 上若为 0 会 WARNING。
2. **非缓存内存要按 cache line（64 B）成块处理**：16 B/迭代只有 71 MB/s，
   64 B/迭代 141~163 MB/s。任何"逐字节/16 字节"的内核在这块板上都要先看这一条。
3. **一次 numpy 调用在板端要 0.3~0.5 ms**：把 256 项验证写成"每对 8 次 numpy 调用"
   看似无害，399 对就是 1.7 s。批量/向量化到三维数组后只要 20 ms。
4. **`bytes.translate` 的表是按 uint8 位模式索引的**（`tab[b] = f(b if b<128 else b-256)`），
   不是按"数值顺序"。写验证脚本时按 `lut[x & 0xFF]` 取，否则对着表验证会得到
   "256/256 项都不同"的假象（本轮在这上面花了不少时间）。
5. **`-DK5_PAD28=0` 的对照构建不能拿新的权重包跑**（容器不匹配），
   cosim 会报 `weight.bin 是 16128 字节，期望 14400` —— 这是"包与 bit 成对"的又一次提醒。
