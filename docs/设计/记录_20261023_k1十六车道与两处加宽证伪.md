## 1. 任务 A 的否证：为什么"4→8 字节"必然回退

### 1.1 结论

`in_fm / wgt / bias` **共用 `bundle=gmem0`**。任一处改成 64-bit 读，HLS 就把**整条端口**加宽到
64 bit；而 k=3/k=5 的权重容器是 **12 / 28 字节**（`K3_PAD12` / `K5_PAD28`），
起点只保证 **4 字节对齐、不保证 8 字节对齐** ⇒ 端口一宽，HLS 再也合不成 burst。

### 1.2 硬证据：数 AR 笔数（RTL 插桩）

同一份 k=3 cosim 数据集（`tb_c8_k3_32x16`，2×320 cin=32 cout=16），在生成的 RTL 里插一段
`always @(posedge ap_clk) if (gmem0_0_ARVALID && gmem0_0_ARREADY) $display(...)`：

| 构建 | cosim `$TOTAL_EXECUTE_TIME` | AR 笔数 | AR 形态 |
|---|---:|---:|---|
| 交付基线（4 字节） | **217,907** | **201** | 40 笔填充长 burst（135 字）+ 160 笔 k=3 权重 burst（97 字）+ 1 笔 bias |
| 只改填充 → 8 字节 | 276,472（+26.9%） | 15,416 | **40 笔填充 burst 正常** + **15,376 笔"每字一笔"的 2-beat 事务**（地址在权重区 2560..3327 字反复出现 20 次 = 每个 (x0,y,ocb) 一遍） |
| 只改 k=1 权重 → 8 字节 | 284,546（+30.6%） | 同理退化 | k=1 权重扩容就把 k=3 的 burst 一起毁了 |

**填充本身是好的**：40 笔 burst，按 AR 时间戳算 **3,703 ns / 512 字节 = 555 拍 = 1.08 拍/字节**
（写侧 `line_buf` 每拍 1 字节是 1.0 的硬下界）。赔掉的是 k=3/k=5 的权重重装。

### 1.3 为什么"零资源增量"的前提不成立

任务书 §8.2 只算了"填充读变宽 ⇒ 事务数减半"，没算**同 bundle 的其它访问被绑架**。
这是一类通用陷阱，写进纪律：**动 `m_axi` 访问宽度前，先看这条 bundle 上还有谁**，
以及它们的地址步长是否与新宽度对齐。

### 1.4 真要做的唯一办法（未做）

把 `wgt` 或 `in_fm` 拆到独立 bundle（`bundle=gmem2`），要改 BD 加第三个 AXI master；
而收益只剩填充那约 −1.3 s（k=1 权重也跟着降约 −1 s，但 k=3/k=5 容器仍不能用 8 字节）。
**风险收益不划算，本轮不做。**

## 2. 任务 B：`BIND_OP mul=DSP` 生效，但**对拍数零影响**

### 2.1 改法与一个坑

```cpp
const int32_t t1 = p * (int32_t)wgt1_buf[i][ic];
HLS_PRAGMA(HLS BIND_OP variable=t1 op=mul impl=DSP)   // ← 必须在声明**之后**
```

⚠️ pragma 写在变量声明**之前**会报 `ERROR: [HLS 207-4637] use of undeclared identifier 't1'`
（伴随一条 `WARNING 207-7016 invalid variable expr`），csynth 直接失败。

### 2.2 csynth：资源与预测一字不差

| 项 | 交付基线 | +BIND_OP | Δ |
|---|---:|---:|---:|
| k=1 pipeline 的 8 条乘法 | `mul_8s_8s_16_1_1`，41 LUT/个、DSP=0 | 每条 **DSP=1、LUT=0** | — |
| LUT | 31,910 | **31,582** | **−328** |
| DSP | 100 | **108** | **+8** |
| FF / BRAM | 21,789 / 175 | 21,789 / 175 | 0 |
| Fmax（csynth） | 172.97 MHz | 172.97 MHz | 0 |
| k=1 流水 II / iteration latency | 1 / 5 | **1 / 5** | **0** |

### 2.3 cosim：**逐拍相同**

新建 k=1 的 C8 cosim 数据集（`/data/work/tb_c8_k1_64x64`，cin=64 cout=64 k=1 2×320，
40,960 输出全一致）：

| 构建 | `$TOTAL_EXECUTE_TIME` |
|---|---:|
| 基线（HEAD） | **531,437** |
| BIND_OP mul=DSP | **531,437（完全相同）** |

⇒ 搬 DSP 只换实现，不动调度。**它单做不提速**（报告里必须写清楚，别让后人误以为是提速项）。
它的价值是：① LUT −328；② **16 车道的前置条件**（16 个 LUT 乘法器要多占 656 LUT，混搭更省）；
③ 时序（见 §4）。

## 3. 顺带证伪的两条成本模型说法

### 3.1 "k=1 只有 5.96 MAC/拍，是 II=1.34"——**不是 II**

- RTL 里 k=1 流水**一个 stall 项都没有**：`ap_block_pp0_stage0_11001 = ~(1'b1==1'b1)`，II=1；
- 132 层 k=1 实测做最小二乘（RMS 2.7%）：
  `t = 1.2758·(MAC/8) + 1.880·fill_B + 3.171·wgt_B + 5.330·wr_B`
  ⇒ k=1 计算 = **1.276 × 理想**（6.27 MAC/拍）；
- cosim 直接量出块开销：cin=64 时每 (pixel, ocb) 块 = `68（cin+4）+ ~19 拍`；
- 所以"5.96"的来源是 **`0.21097 拍/(cin·cout)` 在"计算 / 权重重装"之间的切分偏了约 20%**
  （文档 §3 的 ±15% 交底低估了）。**合计量 0.211 是准的，切分不要拿来推结论。**

### 3.2 "车道填充率浪费"——**0.00%**

按 MAC 加权：`Σ⌈cout/8⌉·8 / Σcout = 1.0000`。k=1 层的 cout 分布（MAC 权重）
= cout 16(37.2%) / 64(30.0%) / 48(15.7%) / 96(10.0%) / 192(7.1%)，**全是 8 的倍数**，没有尾块。

### 3.3 "OC_BLOCK 8→16 能让权重重装 4.36 → 2.18 s"——**错的**

重装发生在 `(x0, y, ocb)` 每块，每块字节 = `cin*8`，块数 × 每块字节 = `cin·cout`
——**与块大小无关**。16 oc/块只是块数减半、每块字节加倍。
（已同步改掉 `记录_20261023_cin×cout二维网格与conv成本模型.md` §8.3 的这句话。）

## 4. 落地：k=1 车道 8 → 16（`K1_LANES=16`）

### 4.1 为什么 16 车道**不**撞 line_buf

16 个 oc 共用**同一个像素** `p`（`line_buf[ic][0][cb]` 每拍仍只读 1 次），
所以**存储器一行都不改**：不动 line_buf、不动填充、不动 k=3/k=5、不动 C8 地址公式、
不动 PS 侧、不动权重包。加倍的只有：

| 项 | 变化 | 代价（csynth） |
|---|---|---|
| `wgt1_buf` | 8 → 16 个 LUTRAM bank | +352 LUT（其中报 128 FF 是 LUTRAM 的读寄存器） |
| `wbuf` | 8 → 16 个 LUTRAM bank | +448 LUT |
| 累加器 | 16 oc × 2 条链 = 32 个 26 位 | +832 FF |
| 乘法器 | 8 → 16（前 `K1_DSP_LANES=8` 条 DSP、后 8 条留 LUT） | DSP +8、LUT +328 |

### 4.2 结构改动（**只碰 k=1 分支**）

1. `ocb` 循环仍按 `OC_BLOCK=8` 步进，但 **k=1 时跳过奇数块** ⇒ 一个 pass 算 `ocb..ocb+15`；
2. 三个权重基址递推（`off_ocb/off_ocb12/off_ocb28`）从循环体**尾部**提到**开头**
   （先取本块值、再无条件推进），否则 `continue` 会让递推错位；
3. 新增 `ocbl1 = min(cout-ocb, 2*OC_BLOCK)` 作为 k=1 的通道上界；
4. 写回：k=1 的第二个 8 字节字（`oc 8..15`）**再用一条同样形态的拷贝循环**写到
   `OUT_ADDR(ocb+8,…)` —— 每笔事务仍是 **8 字节 1-beat**，DDR 事务形态完全不变；
   仅当 `ocb+8 < ⌈cout/8⌉*8` 时写（`cout=8` 时不会越界写）；
5. 尾部补零改按 `ocbl1`（`cout=12` 时车道 12..15 补零，保证第二个字的高 4 字节是 0）。

**BIND_OP 的时间影响：0**（52.40 → 52.22/52.41，噪声内；conv 44.2 不变）。
它的三档价值必须分开写，别让后人误以为是提速项：
**① 资源 LUT −248（impl）/−328（csynth）；② 时序 WNS −0.184 → +0.005（唯一时序违例消掉）；③ 16 车道的前置条件。**

> **复现哪一档**：工作区当前源码是 **16 车道**（`K1_LANES=16` 默认）。
> 要重建 `88534456` 这一档（BIND_OP-only），加 `-DK1_LANES=8` 即可
> （`EXTRA_CFLAGS="-DC8_LAYOUT=1 -DK1_LANES=8"`）；`K1_LANES=8` 与原实现逐字等价。

时序为什么收正：phys_opt 阶段直接报
`WNS=0.224 … Design worst setup slack >= 0.000 ns. All physical synthesis setup optimizations will be skipped.`
—— **布局完就收正、没有靠 phys_opt 硬压**，正是"8×8 LUT 乘法 → 26 位加法 → 累加寄存器"这条组合链
从织物里消失的因果闭环。

`MAX_THREADS=4` + `setsid nohup`；被杀过的 `impl_1` 会停在 "Running"，

### 6.4 坑（本轮新增）

1. **`BIND_OP` 的 pragma 必须写在变量声明之后**，否则 `ERROR: [HLS 207-4637] use of undeclared identifier`
   （伴随 `WARNING 207-7016 invalid variable expr`），csynth 直接失败。
2. **`build_bd_engine.tcl` 会 invalidate IP 的 OOC 综合**（`design_1_engine_0_synth_1`），
   下一次 `launch_runs` 会先重跑 IP 综合 —— 这是内存高峰，**BD + impl 之间不要插别的重活**。
3. **同一个 `bundle` 上的访问宽度互相绑架**（§1）：判据要数 AR 笔数，不是只看拍数。
4. `K1_OC_UNROLL` 从本轮起**彻底没人引用**（被 `K1_LANES` 取代），改它一个数都不会变。
