## 1. "pp 可以删"的证据链

1. **runner 里 C8 一律清空 pp 白名单**：`board/board_bundle/runner.py:989`
   `ppen = set() if self.c8 else self.pp_ops_en`
   → C8 布局下**无论 `--pp-ops` 传什么**，`ppen` 都是空集；
   五个 pp 调用点（`run_interp` / `run_cat_rescale` / `run_add` / `run_eca_mean` / `run_sam_sum`）
   全部包在 `"xxx" in ppen and self.pp is not None` 里 ⇒ 一次都进不去。
   板上日志仍打印 `启用算子=['eca', 'interp']`，但那是**白名单字符串**，C8 下被丢弃。
2. **板上 A/B（同一份包、只换 `--no-pp`）**：
   默认（pp 已加载）52.39 s / `--no-pp` 52.22 s，两者 md5 都 = `ref_out.bin`（`97f5a094…`）
   ⇒ 差值在噪声内，pp **零贡献**。
3. `test_on_board.py` 全程不引用 pp（`grep -c pp_ops test_on_board.py` = 0）。
4. 删掉 pp 之后 PPEngine 构造会在 `run_network_on_board.py:149` 抛异常，被同一处的
   `try/except` 吞掉并打印"v2 层间算子加速器不可用" ⇒ **PS 侧不需要任何改动**。
5. 地址：`0x40020000` / `0x40030000` 两段消失，引擎的 `0x40000000`（offs）/ `0x40010000`（ctrl）
   **一个字都没变**，`check_regmap.py` 的口径不受影响。

BD 侧做成了开关：`PP_ENABLE=0` 出无 pp 的 BD，`PP_ENABLE=1` 原样回退（连接/地址/时钟全部条件化）。

## 2. 证伪一：`HAS_BURST=1` 不会让写变快

推论链原本是：HLS 的 `component.xml` 里 `m_axi_gmem*.HAS_BURST = 0`
→ SmartConnect 的 SI 转换器 `sc_si_converter.HAS_BURST = 0`
（`design_1_smc_0/bd_0/ip/*/bd_6c92_s01sic_0.xci`，实测值就是 0）
→ 每笔 burst 被拆成单拍 ⇒ 每 8 字节一次完整往返 ⇒ 6.4 拍/字节。

**改法**（已进 `build_bd_engine.tcl`，可用 `FORCE_HAS_BURST=0` 关掉）：export 后就地把
`BUSIFPARAM_VALUE.M_AXI_GMEM{0,1}.HAS_BURST` 改成 1，重跑 BD。验证：SI 转换器
`s00sic_0`/`s01sic_0` 的 `HAS_BURST` 由 0 → 1（pp 的 `s02..s04` 故意留 0，归因干净）。

**结果：零收益。**

| | 交付版 | HAS_BURST=1 |
|---|---|---|
| 整网（两次） | 52.41 / 52.82 s | 52.94 / 52.92 s |
| conv | 44.21 s | 44.30 s |
| `write_heavy_8_192` | 1102.8 ms | 1117.5 ms |
| `swap_8_64` | 375.4 ms | 380.2 ms |
| 资源 | LUT 36,414 / DSP 145 / BRAM 88.5 / WNS −0.229 | LUT 36,893 / DSP 145 / BRAM 88.5 / WNS −0.416 |

13 个微基准逐项 +0.3%~1.3%（= WNS 退化量），**事务粒度没变** ⇒ SmartConnect 的
`si_converter.HAS_BURST` 并不做"burst→单拍"转换，这条推断**错的**。
（bit 已归档 `c8_r5_hasburst_898bd37f.{bit,hwh}`，库里默认已回到 HAS_BURST=0。）

## 3. 证伪二：交付版**早就在发 64 拍真 burst**（AWLEN=63）

把交付版源码的 RTL cosim 工程拷一份，在 autotb 里加 AWLEN 监视器重跑
（`/data/work/wbexp/monsim`，日志 `/data/work/wbexp/mon_sim.log`）：

```
[MON-AW] #0 len=63 addr=0    cyc=14610
[MON-AW] #1 len=63 addr=1400 cyc=22022
[MON-AW] #2 len=63 addr=a00  cyc=36167        … 连续 15 笔全是 len=63
```

即每 (y, ocb) 行块一笔 64 拍（512 B）的 burst。上一轮 grep 到的
`…Pipeline_VITIS_LOOP_881_47.v:519 assign m_axi_gmem1_0_AWLEN = 32'd0` 是**流水模块的死输出**；
真正的 AW 由主状态机 `ap_CS_fsm_state149` 发（`conv2d_engine.v:8690
gmem1_0_AWLEN = sext_ln273_reg_7848`，长度以**字**为单位，store_unit 里
`wreq_len_byte = wreq_len << USER_ADDR_ALIGN` 换算成字节）。
连带纠正：`USER_MAXREQS` 确实只有 4（`conv2d_engine.v:6608`，HLS 硬写的 AW 请求 FIFO 深度），
但它不是瓶颈——内核每块只发 1 笔就等 B，`num_write_outstanding` 16→64 自然 0 收益。

## 4. k=1 只有 4.0 MAC/拍：不是"并行度不够"

用 13 个微基准拟合出的三项成本模型（RMS 6%，预测整网 44.81 s vs 实测 44.21 s）：

```
conv 44.21 s ≈ 计算 31.85 s(72%) + 填充/读 7.03 s(16%) + "写回" 5.93 s(13%)
k=1: a₁=1.69 ms/M-MAC（4.0 MAC/拍）   k=3: a₃=0.516（7.8 MAC/拍）
读 c=13.8 ms/MB（2.07 拍/B）          写 b=42.6 ms/MB（6.4 拍/B）
```

**k=1 的分解**（同一 cout=64、320²、只变 cin：57.5 / 375.4 / 676.1 / 1075.6 / 3077.6 ms）：

```
t(cin) = 275.4 ms + 12.5 ms × cin        ← 线性，四项残差 <0.1%
⇒ 每 (pixel, ocb) 块固定 50 拍 + 每个 ic 迭代 2.29 拍
```

**关键否证**：`K1_OC_UNROLL`（2→4→8）和 `K3_LANES`（4→8）**改了等于没改**：

| 构建 | LUT | DSP | FF | BRAM | Fmax |
|---|---:|---:|---:|---:|---:|
| 基线（K1=2） | 31,882 | 100 | 21,793 | 175 | 172.97 |
| `-DK1_OC_UNROLL=4` | 31,882 | 100 | 21,793 | 175 | 172.97 |
| `-DK1_OC_UNROLL=8` | 31,882 | 100 | 21,793 | 175 | 172.97 |
| `-DK3_LANES=8` | 31,882 | 100 | 21,793 | 175 | 172.97 |
| `-DK3_LANES=8 -DK3_PIPELINE_II=2` | 31,882 | 100 | 21,793 | 175 | 172.97 |

原因：k=1 快路径 `VITIS_LOOP_647_31` 本来就是 **8 个乘法器 + achieved II=1**
（`mul_8s_8s_16_1_1` ×8），`#pragma HLS UNROLL factor=K1_OC_UNROLL` 在外层 II=1 的约束下
被 HLS **完全展开**，factor 是空转；`K3_LANES/K3_PIPELINE_II/K3_FAST` 在 2026-10-22 的
k=3 重写之后**已经没有任何代码引用**（`grep -c` = 0），是死宏。
⇒ **"抬 k=1 并行度 / 删 pp 腾 DSP 换 2× k=1"这条路不存在**；头文件里
"DSP 131→约一半""8 车道 +51 DSP" 那些注释都是旧结构的账，已失效。

所以剩下的两个真问题（要动就得改循环结构，不是改宏）：

1. **每 (pixel, ocb) 固定 50 拍**（= 那 5.93 s "写回"，其实不是 DDR！）：
   和 DDR 无关的证据是 64×64 与 320² 两种形状的"每字节写成本"完全相同
   （512 B/块 vs 2560 B/块，per-block 成本却是 21.5 µs vs 108 µs ⇒ 不是按块计费）。
   要定位得看每个 pixel 的收尾序列（acc 合并 / bias / shift / relu / saturate / wbuf 存），
   目前是串行落在 FSM 里。
2. **k=1 的 ic 迭代实测 2.29 拍**，但 RTL 报 II=1 且有 8 个乘法器 ⇒ 差的 1.29 拍
   不在乘法器上。要定位只能拿一个 k=1 形状跑一次带监视器的 cosim（数每 ic 一拍）。

## 5. 坑

1. **别再用"grep 流水模块的 AWLEN"判断有没有 burst**。HLS 把"发 AW"放在主状态机里
   （`ap_CS_fsm_state149`），流水模块的 `AWLEN` 输出是恒 0 的死端口。
2. **`HAS_BURST` 是声明、不是开关**：改成 1 只多花 479 LUT、多掉 0.19 ns 时序，吞吐一点不动。
3. **`K1_OC_UNROLL` / `K3_LANES` / `K3_FAST` 现在都是空转宏**，改它们只会浪费一轮综合；
   连 csynth 报告都逐项相同（LUT/DSP/FF/BRAM 一个数都不差）——这是最快的判据。
4. **pp 的 `--no-pp` 与删 IP 不等价于"改了功能"**：C8 下 pp 白名单被强制清空，
   所以删 IP 是纯资源操作；但 **hwh 会变小**，`board_bundle/design_1.hwh` 要跟着重打包。
5. 删 pp 后 `run_network_on_board.py` 仍会打印"v2 层间算子加速器: 已启用（pp）"，
   因为 PPEngine 构造时只读 hwh 里找不到的偏移也不会报错——**看这行日志不能判断 pp 是否真在干活**。

### 7.3 这一轮学到的两件事（重要）

1. **cosim 拍数不能用来判定"内部调度类"改动。** 这个 TB 每 ~7.4k 拍才发一笔 AW，
   访存延迟绝对主导；收尾展开这种"少几拍算术"的改动在 cosim 里被完全掩盖。
   ⇒ 以后内部调度类改动一律**板上微基准**判定（`bench_phase_split.py --set main`）。
2. **黑盒拟合模型不能外推。** 三项模型对 13 个主用例 RMS 6%、整网误差 1.4%，
   但拿到 `phase_split2` 的讲外推就崩：
   `burst_W320`（cin=32 cout=8 320²）模型 123.7 ms vs 实测 385.2 ms（3.1×）；
   `burst_W32`（32 宽）模型 8.3 ms vs 实测 46.0 ms（5.5×）。
   原因：模型把"每 (y,x0) 行块一次、与 ocb 无关"的那部分成本摊进了"每 MAC / 每字节"，
   而主用例集里 ocb 恒为 8，共线，分不开。
   ⇒ 用 `phase_split2` 的 ocb 维度（cout=1/2/4/8/12/20，同一 ocb 内 cout 1→8 只涨 60.6 ms）
   可以单独把"每输出通道"的成本拎出来，这件事还没做完。
