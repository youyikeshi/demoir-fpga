## 2. 第 1 步：布局工具

### 2.1 定义与 numpy 表示

$$\text{addr}(c,y,x)=\lfloor c/8\rfloor HW8 + y\,W8 + x\,8 + (c\bmod 8)$$

用 numpy 形状直接表达（**C-contiguous 就是规范里的地址**）：

```
CHW : (C,  H, W)        C = Cb*8
C8  : (Cb, H, W, 8)     元素 [cb,y,x,ci] = CHW 的 [cb*8+ci, y, x]
```

于是「同一行、相邻 8 通道、同一列」= 连续 8 字节；「同一行 + 68 列 + 8 通道」= 连续 544 B。

API：

```python
to_c8(t, C8=8, pad=False)     # CHW -> C8；C%8!=0 时 pad=False 抛 ValueError，
                              # pad=True 补零并返回 (out, info)，
                              # info = {"orig_c","padded_c","n_pad","C8"}
from_c8(t, C8=8, orig_c=None) # C8 -> CHW；orig_c 用来切掉补零通道
c8_addr(c, y, x, C, H, W, C8=8)   # 解析地址（事务模型/校验用）
```

实现只用 `reshape/transpose/ascontiguousarray`，无 Python 逐元素循环。

### 2.2 正确性证据

| 检查 | 结果 |
|---|---|
| 随机往返 `from_c8(to_c8(x)) == x` | **160 组**：C ∈ {1,3,4,8,12,16,17,48,96,352} × H,W ∈ {1,5,16,320}，`np.array_equal` 全等 |
| 非 8 倍数通道 | `pad=False` 必抛；`pad=True` 往返后前 C 通道全等、尾部补零全 0 |
| 非连续输入（切片视图） | 通过 |
| dtype | float32 / int8 都原样保留 |
| 地址公式 | 对 4 组形状做**全量**校验：`addr(c,y,x)` 在 `[0,C·H·W)` 上是双射，且 `flat[addr] == x[c,y,x]` |
| 输出连续性 | `to_c8`/`from_c8` 返回的都是 C-contiguous |

### 2.3 性能（x86 本机，单线程；**板端 Cortex-A9 必须重测**）

| 形状 | 大小 | `to_c8` | `from_c8` |
|---|---|---|---|
| **48×320×320** | **4.92 MB** | **3.81 ms（1.29 GB/s）** | **1.52 ms** |
| 96×320×320 | 9.83 MB | 7.70 ms | 3.02 ms |
| 224×320×320（全网最大） | 22.94 MB | 18.27 ms | 7.35 ms |
| 48×640×640 | 19.66 MB | 15.72 ms | 6.55 ms |
| 3×640×640（例外，带 pad） | 1.23 MB | 2.69 ms | 0.93 ms |

另一种实现「8 次带步长写」在本机只要 **1.50 ms**（快 2.6×），但它是**逐字节带步长写**，
在 ARM Cortex-A9 上大概率更慢（无 SIMD gather），所以默认实现保留
`transpose + ascontiguousarray`（可移植性最好）。两者结果逐位相同（已 assert）。

## 3. 第 2 步：算子适配清单

原则：**正确性优先** —— 算子内部先 `from_c8` 转 CHW、调用原实现、再 `to_c8`；只有
"逐元素"和"结构对齐"的算子才直接在 C8 上算。适配层在 `ops_c8.py`，**没有改**
`ps/pynq/ops_numpy.py`。

`c8_runner` 实测的路径统计（517 个算子全覆盖，`paths_c8.json`）：

| 算子 | 个数 | 走的路径 | 做法 / 为什么 |
|---|---|---|---|
| `conv` | 247 | **246 @C8 + 1 @CHW** | 引擎前后 `from_c8`/`to_c8`（模拟 PL 直读 C8；`conv_first` 因 cin=12 回退 CHW） |
| `cat` | 224 | **224 块级 @C8** | 段通道数全是 8 的倍数 → **通道块级拼接**，零通道重排，逐段只做标度重定标 |
| `interp` | 26 | 26 转 CHW | 只有 H/W 变化，但 `ops.interp` 按 3-D 写死，先转 CHW 最稳 |
| `add` | 6 | **6 直接 @C8** | 纯逐元素 `sat16(a+b)`，与布局无关（已对拍） |
| `eca` | 6 | 6 转 CHW | **必须**：float32 空间均值对归约顺序敏感（见 §7 坑 1） |
| `sam_sum` | 6 | 6 转 CHW（默认） | 纯逐元素，理论上可直算 —— 变体 `C8_SAMSUM_DIRECT=1` 实测**同样 0 不一致**，已把它从"必须转"降级为"可直算" |
| `pixel_unshuffle` | 1 | 转 CHW | 通道重排（3→12），且 12 不是 8 的倍数 |
| `pixel_shuffle` | 1 | 转 CHW | 通道重排（12→3），同样是例外张量 |
| `slice` | 0 | — | manifest 里没有；适配器已实现并自测：**起止都对齐 8 → 块级切片**，否则回退 CHW |
| `rescale`（标度重定标） | 每段 cat | **布局无关** | 256 项 `bytes.translate` 是逐字节映射，C8 上同样成立（省掉一次转换） |
| `pool` | 0 | — | manifest 里没有；`ops_c8.pool(t, lay, fn, ...)` 给了通用壳（转 CHW 调 fn） |

## 4. 第 3 步：端到端逐位验证（核心验收）

### 4.1 方法

* 输入：`ps/manifest_640.json` + `pynq_specialized_code/deploy/weights_pack`（真实权重）
  + `input_q.bin`（真实量化输入），**517 个 needed 算子**；
* 卷积：**复用 `runner.RefEngine`**（它调用 `ref_numpy.conv_ref_numpy`），
  所以两边的卷积是**同一份代码**；C8 侧只在引擎出入口加 `from_c8`/`to_c8`
  （真硬件上 PL 直读直写 C8，这一步是模拟开销）；
* 其余算子：`ops_c8` 调 `ops_numpy` 原实现；`cat/add/eca/sam_sum` 的标度处理
  复用 `Runner._s/_lut/_req`（同一份 256 项 LUT），保证逐位可比；
* 因为没有修改 `Runner.run`（硬性约束），C8 侧是 `C8Runner.run`，**逐算子镜像**
  `Runner.run` 的分支与公式；正确性由"两路端到端 0 不一致"反证。

### 4.2 结果

```
C8 布局：508 个张量走 C8，14 个保留 CHW（8 个例外 + 6 个 fp32 attn）
c8: ops=517 conv=247 用时 38.6~39.2 s（不带对拍 hashlog）/ 43.0~45.5 s（带）
    out=(3,640,640) range=[-1,82]

最终输出: 不一致 0 / 1228800  (0.00%)  形状=(3, 640, 640) dtype=int8
算子输出 sha1 不一致: 0 / 517
  ✅ 全部 517 个算子的输出逐位相同
```

补充锚点：

| 对照 | 结果 |
|---|---|
| C8 输出 vs 部署包 `ref_out.bin`（官方导出参考） | **0 / 1,228,800** |
| 基线输出 vs `ref_out.bin` | 0 / 1,228,800 |
| C8 路径连跑两次 | 输出逐位一致（确定性） |
| **换输入**：随机 int8 全值域图（seed=1234） | **0 / 1,228,800** |
| **换输入**：随机 int8 全值域图（seed=7） | **0 / 1,228,800** |

### 4.3 负面对照（证明这套对拍不是空转）

把 ECA 的空间均值**不转 CHW**、直接在 C8 上 `mean(axis=(1,2))`：

```
最终输出: 不一致 725395 / 1228800  (59.03%)   最大绝对误差 6
算子输出 sha1 不一致: 433 / 517
  首个不一致: #84  encoder.encoder_1.sam_blocks.0.fusion  (eca)
按类型: eca 6, sam_sum 6, conv 206, cat 187, add 5, interp 22, pixel_shuffle 1
```

即：错误定位能精确落到**算子序号 + 名字 + 类型**，且一处 ECA 均值差 ulp
就雪崩到 59% 像素 ⇒ ① 对拍有效；② ECA 的 float32 均值**确实**对内存布局敏感。

### 4.4 PS 侧开销（x86 本机，关掉 hashlog 的纯净计时）

| | 墙钟（4 次） | 纯布局转换 |
|---|---|---|
| CHW 基线 | 40.8 / 42.1 / 43.1 / 43.7 s | — |
| C8 路径 | 38.6 / 38.9 / 39.2 / 43.0 s | `to_c8` 0.13 s + `from_c8` 0.20 s = **0.333 s（0.8%）** |

**两边的墙钟差在 −3 s … +2 s 之间跳，符号会翻转**（机器上还有别的重活在跑，
CPU 争用 + 页错误主导；差异全部落在 `conv` 一项，而两边卷积代码完全相同）。
所以不要引用"哪条路更快"——**唯一稳定可引用的是纯转换开销 0.333 s/张（0.8%）**，
且这还是**模拟开销**：真机上 PL 直读直写 C8，PS 根本不转换 conv 的输入输出。

真实部署里 PS **不需要**转换 conv 的输入/输出（PL 原生 C8）。按 manifest 统计：

| 转换量 | MB |
|---|---|
| conv 前后（**模拟开销，真机为 0**） | 638.8 |
| eca 输入 | 51.6 |
| interp 输入+输出 | 89.8 |
| sam_sum 输入+输出 | 86.0（变体 C 可再省 68.8） |
| pixel_* | 4.8 |
| **真机 PS 实际需要转换** | **≈ 165 MB（约 0.1 s @ x86；ARM 上待实测）** |

## 5. 第 4 步：事务数模型

### 5.1 方法（照抄 RTL 循环，不改 RTL）

模型直接复刻 `pl/src/conv2d_engine.cpp` 的 DDR 访问结构：

```c
for (x0 = 0; x0 < Wout; x0 += bw)          // 列块外层
  for (y = 0; y < Hout; ++y) {             // 输出行
    for (r = r_begin; r < span; ++r)       // 需要装载的输入行（宽>步长时只在 BRAM 内下移，DDR 只装 stride 行）
      if (iy 在图像内)                      // 补零行不读 DDR
        for (ic = 0; ic < cin; ++ic)        // 通道
          for (j = 0; j < lb; ++j) in_fm[io + j];   // 连续 lb 字节 ⇒ 1 笔
  }
```

* **CHW**：`io = iy*W + gc0+la + ic*H*W` ⇒ 一笔 burst = 一个 (通道, 行, 列块)；
* **C8**：同 (行, 列块) 的 8 个通道连续（`io_blk + j*8 + ic`）⇒ 8 个通道合成 1 笔，
  `bursts = ceil(cin/8)`；通道数不是 8 的倍数（例外张量）⇒ 该张量保持 CHW，笔数不变；
* 写侧同理：`out_fm[(oc*Hout+y)*Wout+x0+x2]` ⇒ 1 笔/(输出通道, 行, 列块)，
  C8 下 8 个通道连续 ⇒ 1 笔/(通道块, 行, 列块)。

### 5.2 口径校验（先证明模型可信）

| | 板端实测 | 模型（`wide1=0` + 行复用） | 差 |
|---|---|---|---|
| 填充事务数 | 8.76 M | **8.807 M** | **+0.5%** |
| 填充流量 | ~0.4 GB | 503 MB | — |
| B/事务 | 64.7 | 57.1 | −11.7% |

注意：当前 bit 里 `K1_WIDE_COLS=1`（k=1/s=1 走 448 列宽行），同一模型给出 3.592 M 笔。
**推断 8.76 M 是"宽读未开 + 行复用已开"那一版测的**（模型与该口径吻合到 0.5%），
所以下表把两个口径都给出来，结论（÷8）与口径无关。

### 5.3 新旧对比

| 口径 | 读（填充） | 写 | 读写合计 | 填充耗时 @10.3 µs |
|---|---|---|---|---|
| **标定口径**（与 8.76 M 吻合） | CHW **8.807 M** → C8 **1.118 M**（**÷7.88**） | 2.510 M → 0.331 M（÷7.59） | 11.317 M → 1.448 M（÷7.81） | **90.7 s → 11.5 s** |
| 当前 bit（wide1=1） | 3.592 M → 0.466 M（÷7.71） | 2.510 M → 0.331 M（÷7.59） | 6.102 M → 0.796 M（÷7.66） | 37.0 s → 4.8 s |

* 平均每笔字节：57.1 B → **450.2 B**（正是"544 B 长 burst"的量级）；
* 与设计预期「8.76 M → ~1.1 M、90 s → ~11 s」**完全对上**；
* 与验收判据「新 = 旧 ÷8（±5%）」：**÷7.88，即 −1.5%，通过**。达不到 8.00 的唯一原因是
  `conv_first` 的 `cin=12` 与 `decoder_1.out_conv` 的 `cout=12`（见 §6）。

单层视角：**246 个 conv 的读侧降幅全部恰好 8.0×**（cin 都是 8 的倍数；模型逐层核对，
读/写都只有 1 层是 1.0×），例如
`decoder_1.sam_blocks.0.conv_proj`（cin=224）358400 → 44800 笔/层。

## 6. 第 5 步：边界例外（8 个，保留 CHW）

| 张量 | C | H×W | 实际执行 | 生产者 | 消费者 | 原因 |
|---|---|---|---|---|---|---|
| `t0` | 3 | 640×640 | 是 | 网络输入 | `pre.unshuffle`(pixel_unshuffle) | RGB 3 通道 |
| `t1` | 12 | 320×320 | 是 | `pre.unshuffle` | `encoder.conv_first`(conv) | 12 = 3(rgb)×4(unshuffle 2×2) |
| `t520` | 12 | 320×320 | 是 | `decoder_1.out_conv`(conv) | `decoder_1.shuffle`(pixel_shuffle) | 同上 |
| `t521` | 3 | 640×640 | 是 | `decoder_1.shuffle` | —（网络输出 out1） | RGB 3 通道 |
| `t342` | 12 | 80×80 | **否** | `decoder_3.out_conv` | `decoder_3.shuffle` | 同上 |
| `t343` | 3 | 160×160 | **否** | `decoder_3.shuffle` | —（out3） | RGB 3 通道 |
| `t431` | 12 | 160×160 | **否** | `decoder_2.out_conv` | `decoder_2.shuffle` | 同上 |
| `t432` | 3 | 320×320 | **否** | `decoder_2.shuffle` | —（out2） | RGB 3 通道 |

（另有 6 个 fp32 的 `attn` 张量 `t85/t170/t255/t340/t429/t518`，(3C,1,1) 逐通道权重，
本来就不适用 int8 的 C8 布局。）

**处理方式**

1. **存储**：布局按张量决定 —— `int8 且 c%8==0` → C8，否则 CHW。
   实测 **508 C8 / 14 CHW**，运行时不需要任何标志位判断（布局表在 arena 里，一次性）。
2. **cat 完全不接触它们**：224 个 cat、**454 个段**的通道数**全部是 8 的倍数**，
   输出也全是 8 的倍数，且 `sum(段) == channels == out.c`（无 Ghost 截断），
   所以 C8 下就是"通道块级拼接"，**永远是快路径**。
   为保险仍实现了回退：任一段/输出不对齐 8 → 整段转 CHW 拼接（`ops_c8.cat` 已自测）。
3. **`cat` 若真遇到这 8 个例外**（本网络没有）：该段是 CHW → 走回退分支，
   段边界会"断块"，代价是一次整块 CHW 转换。已实现并自测，但本网络 224 个 cat
   一次都没用到 —— 这是"全部 8 字节对齐"这条可行性结论的直接后果。
4. **`pixel_shuffle`/`pixel_unshuffle`**：输入输出都是例外张量，本来就要转 CHW
   （通道重排），零额外成本。
5. **`conv_first`（cin=12）**：唯一"受损"的层，输入保持 CHW ⇒ 该层事务数不降
   （19200 笔，占全网读事务的 0.2%，可忽略）。
   `decoder_1.out_conv`（cout=12）写侧同样不降（19200 笔）。
6. **网络输出**（t521/t343/t432，3ch）：保持 CHW ⇒ 与现有 DMA/落盘路径完全兼容。

**顺带验证的一个好消息**：`cat` 的零拷贝 alias（`compute_cat_alias`/`plan_pool`）在 C8 下
**字节偏移公式完全不用改** —— 因为 `off_c*H*W == (off_c/8)*H*W*8` 恒等
（已用 20 个真实 cat 组验证）。只需把组缓冲的 **numpy 视图形状**换成
`(total/8, H, W, 8)`、成员视图换成 `buf[off_c/8 : (off_c+c)/8]`，
`plan_pool` 的 `offs[t] = o + off_c*H*W` 一行都不用动。本次为了"正确性优先"没有启用
alias，这条留给下一步优化。

## 7. 坑

1. **ECA 的 float32 空间均值对内存布局敏感 —— 必须转 CHW。**
   `np.mean(axis=(1,2), dtype=np.float32)` 在 C8 的 `(Cb,H,W,8)` 上走的是**带步长**归约，
   numpy 会退化成顺序累加；CHW 上是连续块 + pairwise 求和，尾数不同。
   实测（负面对照）：不转 CHW → 首个 eca（#84）就分叉，最终 **433/517 算子、59% 像素**错。
   与之对比，`add`/`sam_sum` 是纯逐元素（无归约），C8 直算**逐位相同**（已实测 0 不一致）。
2. **不要用 `t.shape[0]` 当通道数。** C8 是 4-D，`shape[0]` 是通道块数。
   `Runner` 里所有 `v[sl]`、`nc,hh,ww = v.shape`、`attn.reshape(3,C)` 都踩这个坑；
   适配层必须显式换算（`C = Cb*8`，切片 `[sl]` → `[sl/s8]`）。
3. **`bytes.translate` 重定标是逐字节的 ⇒ 布局无关**，这一点让 `cat`/`add` 的标度处理
   在 C8 上零成本复用。别画蛇添足去转 CHW 再重标（那是 535 MB 的白搬）。
4. **`cat` 的零拷贝 alias 不能照搬"视图即通道切片"的直觉**：偏移公式虽然不变（见 §6），
   但 4-D 视图的 `dst[...] = src` 必须落在 `(cb,h,w,8)` 的形状上；若要恢复 alias，
   建议 `put()` 支持"写进已存在的目标视图"而不是 `np.ascontiguousarray` 新分配。
5. **AXI 4 KB 边界**：C8 一笔逻辑 burst 是 544 B，可能跨 4 KB 边界被拆成 2 笔
   （概率 ~13%）。模型按"逻辑笔数"算，实际会比 ÷8 再打 ~7% 折扣（仍远好于现状）。
   AXI4 单 burst ≤256 拍：64 位位宽下 544 B 只占 68 拍，没问题；32 位位宽下 136 拍也没问题。
6. **写侧 8 字节连续写**：设计文档 §6 已警告 "写宽窄不等会让 HLS 复制存储器"。
   C8 下同一 (y,x) 的 8 个通道是连续 8 字节，**不要**诱使 HLS 做 64 位写/barrel shifter，
   照旧分 8 次单字节写（同一 bank 顺序写）。
7. **读循环必须重排才能拿到 544 B 长 burst**：C8 下 `in_fm[j*8 + ic]` 如果保持
   "ic 外层、j 内层"，就是 8 次跨步 8 的散读（更糟）。必须把 **ic 放内层**：
   `for j: for ic in 0..min(8,cin-cb*8): line_buf[ic][r][la+j] = in_fm[io_blk + j*8 + ic]`，
   HLS 才能把 544 B 折叠成一笔。这是 RTL 改造的**前置条件**（本次未改 RTL）。
8. **例外张量的 conv 不减事务**，且它们正好在网络的入口/出口 —— 不影响主体收益（0.2%）。
9. **`slice` 对齐**：按通道切片必须 `offset%8==0 && channels%8==0` 才能块级切；
   本网络没有 slice，但 Ghost 的 `[:oup]` 是通过 `cat` 的 `channels` 字段实现的
   （224 个 cat 全部 `channels == out.c`，没有真正的截断）。
10. **`conv_ref_numpy` 的输出尺寸由输入推**（`(H-1)//s+1`），`op["h"]/op["w"]` 是**输入**尺寸；
    C8 侧给引擎准备输出缓冲时要用 manifest 的 buffer 尺寸，不能用 `op["h"]/op["w"]`
    （`encoder_1.down` 等 2 个 stride=2 的层会错）。
11. **本机墙钟不能当性能结论**：两路之差在 −3…+2 s 之间来回跳、符号会翻转
    （机器上有别的重活在跑）。唯一稳的是纯转换 0.333 s/张（0.8%）。
    板端 ARM 的转换速度完全未知（1.29 GB/s 是 x86 数字，A9 上可能差 10×）；
    真机 PS 只需转换 ~165 MB/张，但**必须实测**。
12. **`hashlog` 会污染计时**：对拍用的逐算子 sha1 要把每个输出转回 CHW
    （多拷 1.2 GB），带 hashlog 的 C8 比不带慢 1~6 s（随内存压力波动）。
    比较性能时一律用 `run_nohash.py`。

## 8. 建议的下一步（未做）

1. **RTL**：`line_buf[8][SPAN][BWCOL]` + 通道块外层循环 + **ic 内层**的填充循环（坑 7），
   写侧保持 8 次单字节写（坑 6）。BRAM 从 183 KB 降到 ~21 KB。
2. **PS**：按 §6 恢复 cat 零拷贝 alias（偏移不变），并把 `sam_sum` 切到直算
   （变体 C 已验证 0 不一致），把真机 PS 转换量从 165 MB 降到 ~96 MB。
3. **manifest**：加一个 `layout` 标志位（`"c8"`/`"chw"`），让 PL 引擎按张量切换读模式；
   本报告的布局判据（`int8 && c%8==0`）已经够用。
4. **上板验证**：填充耗时应从 90 s 降到 ~11 s（标定口径）；`conv` 总时长按 130 s 估算到 ≤60 s。
5. `FUSE_OUT`/`FUSE_SUM` 与 C8 的交互本次未测（当前 bit 两个开关都是 0）。
