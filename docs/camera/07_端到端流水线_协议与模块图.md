# 端到端流水线：拍照 → 握手传输 → 去摩尔纹 → 拼图显示（协议与模块图）

> **基线**：板端去摩尔纹已定版 **accept-v57**（位流 `runs/ACCEPT_v57/03_BITSTREAM/design_1_150v57.bit`，
> PS 代码副本在 `runs/ACCEPT_v57/05_PS/`）。
> **摄像头**：MaixCAM Pro，走 **USB NCM 网卡直插板子 USB HOST 口**（方案 A，见 `maxicam/docs/maixcam-to-zynq-video.md`）。
> 摄像头开发环境：`/media/felix/892G/ai/maxicam`（用户口述的"570G"实为这块盘）。

> **相机 IP 与连接方式以 [`11_相机连接与IP_权威参考.md`](11_相机连接与IP_权威参考.md) 为准**

## 0. 一句话

- 相机取**原生 2K 的中心 ** 256 × 256 裁剪（像素子集，绝不缩放）
- 经 TCP 一次性发到板子（197 KB，带 md5）
- 板子跑 v57 去摩尔纹 ⇒ 左右拼接 + 上下黑边 ⇒ HDMI 720p30 显示

## 1. 拓扑与地址

| 端 | 地址 | 备注 |
|---|---|---|
| MaixCAM Pro | `10.13.148.1/24`（NCM 口） | 另一口 `10.13.149.1`（RNDIS），**两个都开** |
| AX7015B | `10.13.148.100/24` on **`usb1`（NCM）** | ⚠ 不是 `usb0`：本机内核把 NCM 注册成 `usb1`、RNDIS 才是 `usb0`（见 §12 实测） |
| 板子网口 | `192.168.7.2` | 与相机链路**互不影响**，可同时用 |

- 相机侧是 gadget（网卡） ⇒ 板子是 host ⇒ 一条 Type-C 线搞定，不需要额外网卡
- **风险**：USB2.0 HOST 只给 5 V/500 mA ⇒ 相机跑 AI 时可能欠压重启 ⇒ 必要时从 PMOD VBUS 补电

## 2. 数据格式（硬约束）

- **裁剪必须是像素级子集**（取原生帧的中心 256 × 256） ⇒ **绝不 resize**
- 理由：缩放会重采样，把摩尔纹的频率成分改掉 ⇒ 输入分布与训练集不一致，算法直接失效
- 这条在 `maxicam/apps/maixcam/main.py` 里已有先例注释（第 77 行） ⇒ **沿用**

| 项 | 值 |
|---|---|
| 像素格式 | **RGB888**（每像素 3 字节，行优先，左上原点，无行尾 padding） |
| 裁剪尺寸 | 默认 `256×256`（= v57 的输入尺寸），可参数化到 `128/512` |
| 原生帧 | `2560×1440`（GC4653 原生档）；裁剪前需保证该档可用 |
| 一帧字节数 | `256×256×3 = 196,608` |

- 灰度 vs 彩色：v57 按 RGB888 三通道设计 ⇒ 相机必须给 RGB888，不要 NV21/YUV

## 3. 握手协议（板子主动要图，一问一答）

**传输**：TCP，单连接，**单发一收**（不流水线）。相机侧监听端口 **`8660`**。

### 3.1 请求（板子 → 相机）：一行 JSON，以 `\n` 结尾
```json
{"v":1,"cmd":"shot","seq":123,"w":256,"h":256,"crop":"center","exp_us":400,"
gain":null,"timeout_ms":8000}
```
| 字段 | 含义 |
|---|---|
| `v` | 协议版本，固定 `1` |
| `cmd` | `shot`（其它值一律回 `err:"unknown_cmd"`） |
| `seq` | 单调递增，回包必须原样带回 |
| `w`/`h` | **裁剪尺寸（原生像素）** |
| `crop` | `"center"` 或 `{"x":..,"y":..}`（左上角，原生坐标） |
| `exp_us`/`gain` | 可空；空则不干预 |
| `timeout_ms` | 相机侧自身的采集超时 |

### 3.2 回包（相机 → 板子）：先一行 JSON，再紧跟原始字节
```json
{"v":1,"ok":true,"seq":123,"w":256,"h":256,"fmt":"RGB888","nbytes":196608,"
md5":"<32位小写hex>","native":"2560x1440","exp_us":400,"gain":312,""
t_cap_us":180000,"t_send_us":9000}
```
- **`ok:true` 时**：紧跟**恰好 `nbytes`** 字节载荷；不多不少。
- **`ok:false` 时**：`{"v":1,"ok":false,"seq":..,"err":"busy|timeout|bad_req|..."}`，**没有载荷**。
- `md5` 是**载荷**的 md5（不含 JSON 行）。

### 3.3 板子侧必须做的校验（缺一不可）
1. JSON 可解析且 `v==1`、`seq` 与请求一致
2. `nbytes == w*h*3` 且 `w,h` 与请求一致
3. **读取恰好 `nbytes` 字节**（`recv_until` 语义，处理短读）
4. **md5 校验** ⇒ 不符则丢弃 + 重试一次（重试仍失败则报错退出）
5. 单次 `shot` 的总超时（默认 8 s）

- 任何一条不满足 ⇒ **不许把半张图喂给算法** ⇒ 否则算出来的错图无法归因

### 3.4 错误与重试策略
| 情况 | 相机 | 板子 |
|---|---|---|
| 上一张还没采完 | 回 `err:"busy"`（**不排队**） | 等 200 ms 重试，最多 3 次 |
| 采集超时 | 回 `err:"timeout"` | 计数 + 重试一次 |
| md5 不符 | — | 丢弃 + 重发同 `seq` 一次 |
| 连接断 | — | 关连接、重连一次、重发 |

## 5. 时间预算（决定"看起来是不是实时的"）

### 3.5 ★ 三条实现口径（2026-11-03 相机侧实测后定稿）

#### ① `t_send_us` 报的是**上一张**的发送耗时（首张为 0）
- 原因：JSON 头必须先发，而本张的发送耗时在写头那一刻还不存在。
- ⇒ **不许为此编造字段或填假值**；文档与调用方都按"上一张"理解。
- ⇒ 板子侧若要算端到端时延，用 `t_cap_us`（本张采集）+ 自己计时，**不要**把 `t_send_us` 当本张。

#### ② `err` 取值集合（定版）
| 值 | 含义 | 板子侧动作 |
|---|---|---|
| `busy` | 上一张还没采完（**不排队**） | 等 200 ms 重试，≤3 次 |
| `timeout` | 相机侧采集超时 | 重试一次 |
| `bad_req` | 请求字段非法 | **不重试**，报错（这是程序 bug） |
| `unknown_cmd` | `cmd` 不认识 | **不重试** |
| `internal` | 必复现的内部错（如 grab 字节数不对） | **不重试**，报错并打印原因 |

- extbf关键区别： ext"每次都会失败"的错不许伪装成 exttttimeout
- ext否则板子会白重试、日志被噪声淹没 ⇒ ext真问题被掩盖

#### ③ 一条连接可连发多张（一问一答，**不流水线**）
- 同一 TCP 连接上可以连续 `shot`，但**同时只允许一个未完成请求**。
- `busy` 的判定边界 = **从受理请求到 `grab()` 结束**。

### 3.6 ★ 必须有的"裁剪未重采样"运行时守卫（真机唯一证据）
- ext主机侧只能证明"窗口计算 + 协议链路"无重采样
- extbf不能 ext证明 MaixPy extttimg.crop() ext内部没有插值 ⇒ ext那必须真机验
因此相机侧必须提供两样：
1. **运行时守卫**：`grab` 里断言 `img.width()==rect.w and img.height()==rect.h`，不符回 `internal`
2. **一次性自检**：设备上 `--check-crop` 开关 ⇒ 取一张全幅图，分别用 `img.crop()` 与"全幅切片"取中心块，**逐字节比较并打印 PASS/FAIL**
   ⇒ 这条是"MaixPy 没偷偷 resize"的唯一硬证据；上机第一件事就跑它

## 9. ★ v57 运行点（权威：`runs/ACCEPT_v57/06_REPRODUCE.md` §3.1~§3.5）

### 9.1 运行点开关（**9 条，逐条照抄**）
```
BIN_PACK=e1e2
BIN_LAZY_DEQ=1
BIN_LAZY_SLOTS=24
BIN_CAT_FUSION=1
BIN_BILINEAR_C=1
BIN_PRECOMP=1
Q8CACHE=1
BIN_F32DIRECT=1
BIN_CAT_ECA_FUSE=1
BIN_EPI_NOINV=1
```
- **`Q8CACHE=1`，不是 0**（`Q8CACHE=0` 是 v39 那一档的口径；用 0 会偏离冻结结果）
- 必须在 `import bin_net` **之前**设好（这些开关在导入时读取）
- pipeline 的日志行里要**打印实际生效的运行点** ⇒ 让每次测量自带出处

### 9.2 ★ 频率：v57 定版运行点是 **75 MHz**（不是 100）

**权威出处：`runs/ACCEPT_v57/README.md` + `runs/ACCEPT_v57/07_KNOWN_LIMITS.md`**

| 运行点 | 板端 sha1 | 结论 |
|---|---|---|
| 150 MHz | — | ❌ 10 ns 口径 WNS −3.07 ns，且新临界路径是**真实数据通路**（无"准静态"豁免） |
| 100 MHz | ❌ **0/7**（7 次 sha1 互不相同；另一实现 0/3 且越界写） | ❌ **不可用**（尽管 WNS +0.206 看着能过） |
| **75 MHz** | ✅ **3/3**（`9b1940c8`/`f86a7035`/`025757a8`；另一实现 4/4） | ✅ **最终交付运行点** |

- ext用户决定：按 75 extMHz 上板，慢一点无所谓 ⇒ extbf这就是最终版
- ext256² 墙钟： 6.198~6.234 exts @75 MHz（对比 5.25~5.32 exts @150 MHz）

- extbf写 extttClocks.fclk0\_mhz = 75
- extbf不要 ext把 HDMI 位流那个 1.5 倍口径套到 v57 的 BD 上
- ext两个 BD 的 extttIO\_PLL ext 不同（HDMI 1000 extMHz vs v57 1800 extMHz， extDIV0=4/DIV1=3）
- ext结论：写 75， ext打印目标与读回， ext并用独立手段确认； extbf不许按比例换算猜

- `06_REPRODUCE.md` §3.1 写的是"写 150 ⇒ 真实 100 MHz"，**已被 `README.md` / `07_KNOWN_LIMITS.md` 取代**
- 且那句 `assert abs(Clocks.fclk0_mhz - 100) < 1` 与板端实测（写 150 读回 150）**也不一致**
- ⇒ **凡"运行点"相关，一律以 `README.md` + `07_KNOWN_LIMITS.md` 为准**，`06_REPRODUCE.md` 的 §3.1 视为历史遗留

### 9.3 基址与「没有的东西」
| IP | 基址 |
|---|---|
| `conv_uni_0` | `0x40040000` |
| `bin_unit_0` | `0x40060000` |
| `fconv_0` | **不存在**（v57 没有这个 IP） |

- v57 基于 v39 ⇒ **没有 magic 寄存器**（`0x314` 读失败属正常，不要当故障）

### 9.4 输出与冻结校验（**关键：sha1 是算在 float32 原始张量上的**）
- `outs["out1"]` 形状 `(3, 256, 256)` float32
- 冻结判据：`sha1(np.ascontiguousarray(out1).tobytes())[:12]` 必须等于
  - 256²：`9b1940c8` / `f86a7035` / `025757a8`（分别对应 out1/out2/out3）
- **先比对 sha1，再转图**：
  - sha1 不符 ⇒ **抛异常**（说明运行点/频率/代码不对，此时转出来的图也是废的）
  - sha1 相符 ⇒ 再按既有口径转 uint8 显示：
    `clip(0,1).transpose(1,2,0) * 255 → round → astype(uint8)`
- ⇒ **顺序不能反**：先"证明算对了"，再"好看"

### 3.8 ★ "截断"的唯一定义（两侧联合定义，2026-11-03）

- ext两侧对"截断"这个词理解不同会造成误判 ⇒ ext现在定死：

| 相机侧实际行为 | 板子侧必须归为 | 理由 |

- extbf判据： ext"有没有收到 ``" ext是"断连"与"格式错"的分界线
- ext两侧的实测映射已对齐：相机 exttt--corrupt truncate ⇒ ext板子 extttdisconnected
- ext相机 exttt--corrupt short ⇒ ext板子 extttshort\_payload
