### 2.1 teacher 权重（50.83 MB）

落盘位置必须严格是（配置里 `T_load_path` 是相对路径，放对位置即无需改配置）：

### 2.2 UHDM 测试集（500 对 4K）

**不能用文档里的两条路**（本机实测）：

| 路径 | 实测结果 |
|---|---|
| Google Drive `test.tar.gz` | ❌ `drive.google.com` 直连超时（本机 hosts 只劫持了 `google.com` 裸域，未劫持 drive 子域，加速器不生效） |
| OpenDataLab `raw/UHDM.tar.gz` | ⚠️ 可用但是 **80GB 单文件整包**且需登录，为了 5.7GB 测试集不值得 |
| Kaggle `soumikrakshit/uhdm-dataset` | ❌ 该 slug 返回 404 |

**实际采用**：hf-mirror 上的 `leegwang/uhdm`（国内直连，实测 4.5~5.3 MB/s）。包里是**一个 44.78 GB 的 `uhdm.zip`**，内含 `test/test/`（1000 文件 / 5.71 GB）、`test_origin/`（3.97 GB）、`train/train/`（9000 文件 / 35.46 GB）。

新增脚本 `tools/fetch_uhdm_from_hf.py` 用 **HTTP Range 远程随机读取 ZIP**：
只读中央目录（4 次请求 / 1.12 MB）定位条目，再对每个需要的条目发一个精确 Range 请求，
**只取测试集那 5.55 GB，省掉整包 39 GB 流量**。多线程并发 + 逐文件 CRC32 校验。

```powershell
# 只列包内结构
python tools\fetch_uhdm_from_hf.py --list
# 抽取 500 对测试集到 uhdm_data/test
python tools\fetch_uhdm_from_hf.py --extract-test --path-filter "test/test/" --workers 12
# 划分 400/100（硬链接，不占额外空间）
python tools\make_split.py
```

> ⚠️ `--path-filter` 必须写 `test/test/`。写 `test` 会同时命中 `test_origin/test_origin/`，两者文件名相同会互相覆盖。

实测结果：1000 个文件、CRC32 全部通过、实际下载 5.55 GB、耗时 21 分钟；
**500 对全部为 3840×2160 RGB，无损坏，编号连续 0000–0499**；`split_train`=0000–0399、`split_eval`=0400–0499，`fsutil hardlink list` 确认是同一 inode（未重复占盘）。

## 3. 本机踩到的 5 个坑（都有实测证据）

### 3.1 ⚠️ 官方 PyTorch CDN 在国内会「假死」

`https://download.pytorch.org/whl/cu118/` 索引页能返回 200，但**实际的 .whl 请求会挂住**——
`pip install torch==2.7.0 torchvision==0.22.0 --index-url https://download.pytorch.org/whl/cu118`
（交付说明 4.1 的命令）在本机跑了 20 分钟无任何进展、进程几乎不占 CPU、TEMP 里没有下载中的文件。

**解法**：国内 `pytorch-wheels` 镜像只有 **aliyun** 与 **sjtu** 托管 cu118 的 Windows wheel（cernet/ustc/nju/bfsu 都是 404）。两者单连接都只有 0.2~0.3 MB/s，但多连接能叠加：

| 镜像 | 8 连接聚合 |
|---|---|
| `mirror.sjtu.edu.cn/pytorch-wheels/cu118/` | **5.26 MB/s** |
| `mirrors.aliyun.com/pytorch-wheels/cu118/` | 2.09 MB/s |

用 `tools/fetch_wheel_parallel.py` 并行下载 wheel 后**离线安装**（不走 pip 的网络）：

```powershell
python tools\fetch_wheel_parallel.py `
  "https://mirror.sjtu.edu.cn/pytorch-wheels/cu118/torch-2.7.0%2Bcu118-cp311-cp311-win_amd64.whl" `
  "E:\ai\demoir-fpga\wheels\torch-2.7.0+cu118-cp311-cp311-win_amd64.whl" --workers 16
# torchvision 同理（5.2 MB）
.venv-pdnet\Scripts\python.exe -m pip install --no-cache-dir --no-deps <两个 wheel>
```

### 3.2 ⚠️ A 机的 freeze 在 Python 3.11 上装不上

`tools/requirements_pdnet.txt` 是 A 机 **Python 3.12** 上的 `pip freeze`，其中：

```
numpy==2.5.2    →  镜像明确返回 "Requires-Python >=3.12"，3.11 最高只能装 2.4.6
```

**选择**：留在 Python 3.11（理由：本机已装好 cp311 的 torch，重下 cp313 的 2.9GB 不划算；且 **3.11 保留 `distutils`**，`thop` 能正常工作，而 3.12+ 已移除 distutils，只会走 `utils/common.py` 的降级分支拿不到 MACs 报告）。

实际可用的版本集已固化为 **`tools/requirements_pdnet_py311.txt`**（35 个包）。与 A 机 freeze 的差异：

| 包 | A 机 freeze | 本机实测 |
|---|---|---|
| numpy | 2.5.2 | **2.4.6**（≥2.5 要求 py≥3.12） |
| scipy | 1.18.1 | 1.17.1 |
| tifffile | 2026.9.9 | 2026.3.3 |
| filelock | 3.32.3 | 3.32.6 |
| tqdm | 4.70.0 | 4.70.1 |

其余（pillow 12.3.0、opencv-python 5.0.0.93、protobuf 7.36.1、PyYAML 6.0.3、scikit-image 0.26.0、tensorboardX 2.6.5、lpips 0.1.4、thop 0.1.1、gdown 6.2.0、certifi 2026.7.22 …）**与 A 机完全一致**。

### 3.3 ⚠️ pip 不要用默认缓存目录

本机 `C:\Users\<用户>\.cache\...` **不可写**（权限拒绝），pip 的 HTTP 缓存正好在那里，
表现为 `pip install --upgrade pip` 长时间无响应。**所有 pip 命令都要加 `--no-cache-dir`**：

```powershell
.venv-pdnet\Scripts\python.exe -m pip install --no-cache-dir -r tools\requirements_pdnet_py311.txt
```

### 3.4 ⚠️ torch 的权重缓存必须用 TORCH_HOME 指到可写位置

同样的原因：torch 默认把下载的权重写到 `C:\Users\<用户>\.cache\torch\hub\checkpoints\`（不可写）。
必须显式指定，且**建议放在仓库之外**——根 `.gitignore` 里并没有排除 `.torch_cache/`，
放在仓库内会让 760 MB 权重有机会被提交。

```powershell
$env:TORCH_HOME = 'E:\ai\demoir-fpga\.torch_cache'   # 仓库外
```

### 3.5 ⚠️ tensorboardX 需要命名管道

`train.py` 的 `init()` 会建 `SummaryWriter`，而 `tensorboardX` 的 `EventFileWriter` 用
`multiprocessing.Queue`，在 Windows 上要创建**命名管道**。受限执行环境下会直接抛：

```
File "...\multiprocessing\connection.py", line 575, in Pipe
    h2 = _winapi.CreateFile(...)
PermissionError: [WinError 5] 拒绝访问
```

这不是项目 bug。需要以更宽的权限运行 `train.py` 才能走**未经修改的原始代码路径**（保留 tfevents 日志，与 A 机产物可比）。

### 5.1 性能观察（⚠️ 曾一度判断错误，此处是修正后的结论）

**JPEG 解码不涉及任何 GPU 加速，是纯 CPU。** `dataset/load_data.py` 用 PIL 的 `Image.open`
整张解码 4032×3024 再裁块；本机 Pillow 12.3.0 确认启用了 `libjpeg_turbo`（带 SSE/AVX 的）
纯 CPU 路径，**Pillow 没有 GPU/iGPU 解码后端**，本项目也没有用到核显（Quick Sync / DirectML / OpenCL 均无）。

实测各路径解码速度（单进程，`E:\ai\demoir-fpga\_decode_bench.py`）：

| 路径 | 单张耗时 | 单进程吞吐 |
|---|---|---|
| PIL 解码 + 裁块（项目实际路径） | 116 ms | 8.64 张/s |
| `cv2.imread`（自带 libjpeg-turbo） | 121 ms | 8.25 张/s |
| `torchvision.io.decode_jpeg(device='cpu')` | 142 ms | 7.03 张/s |
| `torchvision.io.decode_jpeg(device='cuda')` | 173 ms | **5.78 张/s（反而更慢）** |

⚠️ **注意最后一行**：`torchvision.io.decode_jpeg` 虽然**支持 `device='cuda'`**（nvJPEG），
但在 4K 单张解码场景下**比 CPU 还慢**（单张逐个调用无法摊薄 H2D 与内核启动开销），
所以「改用 GPU 解码」并不是本项目的优化方向。

**关键推论**：4 个 worker 的解码能力约 34.6 张/s，而实际训练只消耗 4~6 张/s
——**解码能力有 6~8 倍富余，数据管线不是瓶颈**。

> 📌 修正说明：本文早期版本据「GPU 利用率 9%」的单次瞬时采样，判断「瓶颈在数据管线」。
> 该采样不可靠。改用**窗口采样**（每 2 秒一次、40 秒）后，GPU 平均利用率为 **28.7%**（区间 0~81%），
> 同期吞吐 3.18 it/s。即：**CPU 解码与 GPU 计算都没有跑满，限制来自两者之间的突发式串行**
> （worker 解码 → 主进程等待 → GPU 突发），并叠加上当时并发跑的 teacher 评测与 12 线程下载的争用。

**CPU 占用的真实量级**（30 秒窗口实测）：训练主进程约 20~26% 单核、每个 DataLoader worker 约 13% 单核，
即 Python 合计**不到 1 个核心**；本机 22 逻辑核，折合整机约 1~5%。
同期**整机最大 CPU 消费者是浏览器 msedge（约 22% 单核）**，而非训练。

**可调项**（供 B 机参考）：

- `WORKER` 提高仍可能有效（本机 22 核只用了 4 个），但收益上限受上面那条「串行」限制
- 显存有余（crop 512 + batch 2 实测 5965 MiB / 12282 MiB）：可提高 `BATCH_SIZE`
- ⚠️ 改 batch 会改变「每 epoch 步数」，就不再与文档的 6000 步协议可比了


### 5.2 ⚠️ 显存实测：官方协议的 crop 768 在 12 GB 上跑不了

交付说明 3.1 的显存表（256→501 MB、384→1094 MB、512→1911 MB）是 A 机用 `probe_vram.py` 测的
**「孤立单步」峰值，不含 VGG16 感知损失与 DWT 蒸馏**，因此**严重低估**真实训练占用。
本机用**真实 train.py 训练步**（student+teacher+VGG16+DWT+Adam）实测：

| 配置 | 实测吞吐 | **峰值显存** | 占 12282 MB | 150 epoch（全量 4500 对）总耗时 |
|---|---|---|---|---|
| crop 512 + batch 2 | ~2.6 it/s | 5965 MB | 49% | 约 36 小时（337,500 步） |
| **crop 640 + batch 2**（**采用**） | **2.62 it/s** | **8870 MB** | **72%** | **约 36 小时（337,500 步）** |
| **crop 768 + batch 2**（官方协议值） | **0.04 it/s** ❌ | **11830 MB** | **96%** | **不可行**（每步 25~30 秒） |
| crop 768 + batch 1 | 2.83 it/s | 6568 MB | 53% | 约 66 小时（675,000 步） |

三条重要结论：

1. **官方配置是按 3090（24 GB）写的**（`uhdm_config_distillation.yaml`: batch 2 / crop 768）。
   在 12 GB 上 batch 2 + crop 768 会用掉 96% 显存，PyTorch 分配器进入饥饿颠簸状态，
   吞吐从 ~2.6 it/s 崩到 **0.04 it/s（慢 65 倍）**。这不是"略慢"，是**不可用**。
   > 已排除桌面/浏览器占用：训练进程退出后整卡仅剩 291 MiB，11.5 GB 全是训练进程自己占的。

2. **crop 512 ↔ 640 的挂钟时间几乎相同（都是 ~2.6 it/s）**：GPU 有余量、瓶颈不在算力，
   所以 **640 相对 512 是"白送"的更大上下文**，且 `2250 步/epoch` 与官方协议一致。
   结合交付说明 §3.3 的结论（上下文收益在 512 处饱和、768 反而略降），**640 是本机的最优点**。

3. **不要拿 `probe_vram.py` 的数字规划训练**——它测出的 1911 MB 与真实训练步的 5965 MB 差 3 倍，
   若据此以为"12 GB 很宽裕"就会踩上面第 1 条的坑。


### 5.3 ⚠️ 为什么新建了 `real_30ep_local_config.yaml` 而不是改 `real_config.yaml`

`model/model.py` 的可视化文件名是 `visual_x{SAVE_ITER}_{序号}.jpg`，序号由 `iters//SAVE_ITER` 决定，
**与 EXP_NAME 无关、与是否新跑无关**。若沿用 `SAVE_PREFIX: ./out_dir/real` + `EXP_NAME: exp_real`，
重训会产生**完全相同的 60 个文件名**，把 A 机已提交的 `train_visual/visual_x0100_00001..00060` **原样覆盖**。

所以新配置改用独立的 `out_dir/local/exp_real_30ep`。**A 机的原始产物保持不动。**

### 5.4 ⚠️ 全图 fp32 推理会把显卡驱动撑到 TDR 蓝屏（已实测定位并复现）

**事件**：2026-09-16 23:11:46 本机蓝屏，BugCheck：

```
0x00000116  VIDEO_TDR_FAILURE   （显卡驱动超时，不是普通 OOM）
参数3: 0xffffffffc000009a = STATUS_INSUFFICIENT_RESOURCES（资源不足）
Minidump: C:\Windows\Minidump\091626-21843-01.dmp
```

同一时刻工作区里出现了一张待推理的图（`in/1.jpg`，23:01 放入，10 分钟后蓝屏）。

**根因链（每一环都有实测数据）**：

| 环节 | 实测值 |
|---|---|
| 该图尺寸 | **4080 × 3072 = 12.53 M 像素** |
| fp16 全图显存 | **5545 MB**（实测，约 443 字节/像素） |
| fp32 全图显存 | **约 10.9 GB**（按 2040×1536 实测 2777 MB ≈ 888 字节/像素线性外推） |
| 显卡总显存 | 12282 MB，扣掉桌面 / CUDA context 后可用约 11 GB → **不够** |
| `TdrDelay` 注册表 | **未设置 = 使用默认 2 秒** |

**为什么不是"干净报错"而是蓝屏**：Windows 的 **WDDM 允许显存超额分配**——显存不够时驱动
不会失败，而是把显存**换页到系统内存**。（交付说明 5.2 记录过 4K fp32 出现「约 22GB 内存
占用并假死」，就是同一机制。）一旦这个换页过程让驱动操作超过 **TDR 的 2 秒**上限，
Windows 无法恢复，直接 `VIDEO_TDR_FAILURE` 蓝屏。

> 附：本机 `C:\Windows\Minidump` 自 7 月以来已有 5 个 dump
> （07-06 / 07-13 / 08-08 / 08-28 / 09-16），说明这不是一次性偶发；长跑与推理都要按上面的显存预算来做。

**已做的防护**（`pdnet_smoke/infer_one.py`）：

1. **给 PyTorch 分配器设硬上限**（`set_per_process_memory_fraction`，默认总显存的 80%）
   —— 超限时抛的是可捕获的 `OutOfMemoryError`，**不会让驱动去超额分配**，把蓝屏变成干净报错
2. **按像素数预估显存**：超预算自动降 fp16；连 fp16 都不够就跳过该图并给出建议
3. 实测验证：同一张 4080×3072 的图自动选 fp16，**峰值 5545 MB / 上限 9825 MB，0.78 秒完成**

**使用结论**：

- 4K 级别图片**一律用 fp16**（`--half`，或直接不传参数让脚本自动选）
- fp32 全图只适合 **≤8 M 像素**（约 3300×2400 以内）
- 更大的图用**分块模式**（见 5.5），不要指望单卡整图吃下去

### 5.5 分块推理（`--tile`）：显存降 11 倍，但要接受"上下文变少"

为了从根本上避开 5.4 那个蓝屏风险，`infer_one.py` 增加了分块模式：**重叠 + 羽化融合**。
重叠默认 256，依据是交付说明 3.3 测出的**有效感受野约 512**（取一半）。

本机实测（同一张 4080×3072 图，student 模型，fp16）：

| 模式 | 峰值显存 | 耗时 | 与整图结果的 PSNR |
|---|---|---|---|
| 整图 fp32 | **约 10900 MB**（蓝屏风险） | — | 基准 |
| 整图 fp16 | 5545 MB | 0.78 s | 基准 |
| **分块 1024 / 重叠 256** | **489 MB**（↓11×） | 3.09 s | 22.78 dB |
| **分块 2048 / 重叠 512** | 约 1900 MB | 5.2 s | **33.31 dB** |

**两个必须说清楚的结论**：

1. **羽化融合是正确的，没有接缝**。沿块边界（x=768/1536/2304/3072、y=768/1536/2304）
   逐列/逐行统计差异，边界处与全图中位数的比值都在 **0.58x ~ 1.14x**，
   没有出现尖峰（若融合有 bug，边界会高出数倍）。

2. **但分块结果和整图结果差异很大，且这不是 bug，而是"网络看到的上下文变少"**。
   证据：块从 1024 放大到 2048，与整图的 PSNR 从 22.78 dB 升到 33.31 dB、平均绝对差
   从 13.34/255 降到 4.12/255 —— **块越大越接近整图**。
   这与交付说明 3.3 的结论一致（上下文有用，同一批像素多给周围信息可提升 1.27 dB），
   也和 `infer_demo.py` 当初选择"整图 fp16"而非分块的动机吻合。

**怎么选**：

| 场景 | 建议 |
|---|---|
| 显存够（4K 图 fp16 约 5.5 GB） | **整图**，质量最好 |
| 显存紧张 / 图特别大 / 要绝对安全 | **分块 2048/512**（质量接近整图，显存约 1.9 GB） |
| 拿不准 | 跑 `--compare` 同时出两份，直接对比 |
