# 分块推理：切割与拼接

> 面向：需要在**大图上**跑去摩尔纹、或显存吃紧时想看效果的人。
> 代码：`src/tiling.py`（切割/拼接库）+ `src/infer.py`（命令行入口）。
> 自检：`python src/tiling.py --selftest`（不需要显卡）。

---

## 1. 什么时候需要分块

两个**独立**的原因，任一个成立就该用：

### 1.1 显存：整图前向的显存线性于像素数

实测系数（`experiments/probe_image_vram.py` 可复现）：

| 模型 | fp16 | fp32 |
|---|---|---|
| student（1.562 M） | 469 字节/像素 | 936 字节/像素 |
| teacher（4.396 M） | 831 字节/像素 | 1657 字节/像素 |

于是同样一张 **4080×3072** 的图：

| 组合 | 需要显存 | 12 GB 卡 |
|---|---|---|
| student fp16 | 5.5 GB | ✅ |
| student fp32 | 10.9 GB | ⚠️ 贴边 |
| **teacher fp16** | **9.7 GB** | ❌ 超安全预算 |
| teacher fp32 | 19.3 GB | ❌ |

### 1.2 蓝屏：Windows 的显存超额分配会变成 TDR

这是本项目**真实踩过**的坑（2026-09-16 一次 `VIDEO_TDR_FAILURE (0x00000116)`）：

Windows 的 WDDM **允许显存超额分配** —— 显存不够时驱动**不报错**，而是把显存
**换页到系统内存**。一旦这个换页让驱动操作超过 TDR 默认的 **2 秒**上限，
Windows 无法恢复，直接蓝屏 —— **而不是抛一个可以捕获的 CUDA OOM**。

分块把单次需求压到几百 MB，从根上避开：

| 块边长 | student fp16 | teacher fp16 |
|---|---|---|
| 1024 | 约 0.5 GB | 约 0.9 GB |
| 2048 | 约 1.9 GB | 约 3.4 GB |

> 另外两道防护（即使不分块也有）：`src/infer.py` / `src/eval.py` 都用
> `set_per_process_memory_fraction()` 给分配器设了硬上限，超限时抛的是可捕获的 OOM。

## 2. 怎么切

### 2.1 两个参数

| 参数 | 默认 | 约束 |
|---|---|---|
| `--tile` 块边长 | 0（= 整图，不分块） | 必须是 **32 的倍数**（网络有 2 次 `pixel_unshuffle` + 4 级下采样，`infer.py` 会自动向上取整） |
| `--overlap` 重叠 | 256 | 必须 **< tile**；`infer.py` 会在越界时自动改成 `tile/4` |

### 2.2 为什么必须留重叠，且默认 256

网络的有效感受野约 **512** —— 这是本项目用受控实验测出来的
（`experiments/context_study.py`：固定同一批像素、只改变网络可见的上下文，
PSNR 提升 1.27 dB，在 512 处饱和、768 反而略降）。

**感受野之外的像素不影响该点的输出**，所以：

* **零重叠直接拼**：边界每个像素都缺一侧约 256 像素的上下文 → 边界出现**接缝**；
* **重叠 ≥ 256**（感受野一半）：重叠区内每个像素至少能被一块"完整看到"。

### 2.3 切法：最后一块贴边

`tiling.axis_positions()` 按 `step = tile - overlap` 铺开起点，然后**追加一个贴边位置**
（`length - tile`），保证：

* 全覆盖、不留缺角（不会在右边/下边剩下一条细缝）；
* 每块都是完整的 `tile × tile`，不会出现又窄又小的尾块。

```python
>>> axis_positions(5000, 2048, 256)
[0, 1792, 2952]
>>> tile_boxes(4080, 3072, 2048, 256)     # -> 6 块（3 列 × 2 行）
```

> ⚠️ "贴边补齐"的副作用：那一处与邻居的实际重叠可能**大于** `overlap`，
> 于是该区域有 3 块以上同时带全权重。这不影响正确性（见 3.3），但别假设"权重和恒为 1"。

## 3. 怎么拼

### 3.1 每块给一个线性斜坡权重

```text
块 A 的右侧： 1 ──────> 0
块 B 的左侧： 0 ──────> 1
```

**贴图像边界的那一侧不羽化**（外侧没有邻居可融合），权重保持 1。

### 3.2 融合就是加权平均

```
out(x,y) = Σᵢ wᵢ(x,y) · outᵢ(x,y)  /  Σᵢ wᵢ(x,y)
```

### 3.3 不留缝靠这三条（**不是**"权重和恒为 1"）

| 性质 | 作用 | 怎么验证 |
|---|---|---|
| **全覆盖** | 每个像素至少被一块覆盖，否则留黑洞 | `--selftest` 报告"未覆盖像素 = 0" |
| **权重连续** | 线性斜坡无突变 → 不会有可见台阶 | `--selftest` 检查最大梯度不超斜坡斜率 |
| **归一化** | 除以 `Σw`，某处权重和 > 1 也**不会变亮** | `--selftest` 的**纯色图往返偏差必须为 0** |

第 3 条最关键，也最好验证：把**纯色图**分块"推理"再拼回来，如果偏差为 0，
就说明拼接不会引入明暗带 —— 这是端到端的铁证，比看公式可靠。

## 4. 怎么用

### 4.1 命令行（推荐，`src/infer.py`）

```bash
# 大图：分块 2048，重叠 512
python src/infer.py --image big.jpg --tile 2048 --overlap 512

# 顺带对比：同一张图再跑一遍整图，看两种模式的差别
#   （--tile 与整图结果会有差异，这是算法层面的，见第 6 节）
python src/infer.py --image big.jpg --tile 2048

# 更保守的显存上限（例如同时开着浏览器/看片）
python src/infer.py --image big.jpg --tile 1024 --max-vram 6

# 整个目录
python src/infer.py --dir samples/phone --tile 2048
```

`infer.py` 会打印实际用了哪种模式：

```
本进程显存上限 = 9825 MB（超限干净报错，不让驱动超额分配 -> 避免 TDR 蓝屏）
1.jpg   4080 x 3072
  student  fp16 分块2048/重叠512
  [注意] 整图预估 9.7 GB > 上限 9.6 GB，自动改用分块 2048    <- teacher 时会出现
  teacher  fp16 分块2048/重叠256
```

可用的 API：

| 函数 | 作用 |
|---|---|
| `tile_boxes(w, h, tile, overlap)` | 返回 `[(x, y, w, h), ...]`，覆盖整图 |
| `axis_positions(length, tile, overlap)` | 一维切分起点（贴边、无缺角） |
| `feather_1d(n, overlap, ramp_start, ramp_end)` | 一维羽化权重 |

| `selftest(...)` | 纯 numpy 自检，不需要显卡 |

`keep_intermediates=True` 时额外返回权重和，便于自己检查覆盖情况。

## 5. 参数怎么选

| 情形 | 建议 |
|---|---|
| 显存够（4K 图 student fp16 约 5.5 GB） | **整图**（`--tile 0`），质量最好 |
| 显存紧张 / 图特别大 / 要绝对安全 | **`--tile 2048 --overlap 512`**，质量接近整图 |
| 显存非常紧（想同时开别的程序） | `--tile 1024 --overlap 256`，约 0.5 GB |
| 拿不准 | 先跑一次 `--tile 2048`，再跑一次整图，用 `experiments/make_compare_grid.py` 拼起来看 |

**不要**为了省显存把 `--tile` 降到 512 以下：块越小，每块看到的上下文越少，
结果偏离整图越多（见下一节），而且块数与重叠开销会迅速增加。

## 6. 实测：分块与整图差多少

同一张 4080×3072 的图，student，fp16，与**整图结果**逐像素比对：

| 分块配置 | 峰值显存 | 耗时 | 与整图的 PSNR | 平均绝对差 | 边界比值 |
|---|---|---|---|---|---|
| 整图 | 5545 MB | 0.78 s | 基准 | — | — |
| 1024 / 重叠 256 | 489 MB | 3.1 s | 22.78 dB | 13.34 / 255 | 0.58 ~ 1.14 倍 |
| **2048 / 重叠 512** | 约 1.9 GB | 4.5 s | **33.31 dB** | **4.12 / 255** | — |
| teacher 2048 / 512 | 3360 MB | 4.7 s | — | — | — |

### 6.1 怎么判断"有接缝"

**边界比值** = 块边界处的差异 ÷ 全图中位差异。

* 若拼接有 bug（权重不连续/覆盖不全），边界会高出**数倍**；
* 实测都在 **1 倍附近**（0.58 ~ 1.14）→ **融合正确、没有可见接缝**。

### 6.2 ⚠️ 分块 ≠ 整图，这是**算法层面**的差异，不是 bug

每块能看到的上下文只有块那么大，网络的行为会随之改变。
证据：**块越大越接近整图**（1024 → 2048 时，与整图的 PSNR 从 22.78 升到 33.31 dB）。

这与 `docs/训练/说明_交付_20260910.md` 3.3 的上下文结论一致，也解释了
`src/infer_demo.py` 当年为什么选"整图 fp16"而不是分块 ——
**它的顾虑（结果不同）是对的，只是原因不是接缝，而是上下文。**

## 7. 自检与验证

### 7.1 不需要显卡的自检

```bash
python src/tiling.py --selftest
```

会打印每种 `tile/overlap` 的块数、权重和范围、最大梯度，并做两件事：

* **纯色图往返**：偏差必须为 0（证明不会变亮/变暗）；
* **覆盖率**：未覆盖像素必须为 0。

也可以指定尺寸：

```bash
python src/tiling.py --selftest --width 1920 --height 1080
```

### 7.2 换了自己的模型后，怎么确认拼接没问题

1. 同一张图跑**整图**与**分块**两份结果；
2. 逐像素求差，取块边界附近的差异与全图中位差异的比值；
3. 比值接近 1 倍即正常（本项目实测 0.58~1.14）；
4. 想看得更清楚，用 `experiments/make_compare_grid.py` 拼成上下两行对比图。

## 8. 注意事项

1. **`tile` 必须是 32 的倍数**。`tiling.run_tiled()` 会直接抛错；`infer.py` 会自动向上取整。
2. **`overlap` 必须小于 `tile`**。等于或大于时 `infer.py` 自动改为 `tile/4`。
3. **不做任何缩放**。分块是在**原生分辨率**上裁的 —— 摩尔纹频率与采集分辨率绑定，
   resize 会把它混叠变形（`docs/训练/说明_交付_20260910.md` 3.4 有实测）。
4. **`Σw` 不恒为 1**（见 3.3 与 2.3）—— 别把"单位分解"当前提来推理。
5. **1:1 放大看边界**。分块与整图的差异平均只有几/255，缩览图上根本看不出来。
6. 分块的**块数与重叠开销**：`tile=1024/overlap=256` 时 4080×3072 要 20 块，
   而 `2048/512` 只要 6 块 —— 块开大反而更快（重叠重复计算更少）。

## 9. 与 FPGA 部署的关系

分块不是"退而求其次"，它**正是最终部署的形态**：

* Zynq-7000 的 BRAM 只有约 612 KB，**不可能**整帧驻留，必须按块/按行带流式处理；
* 因此"按块喂进去、按块出结果、再按羽化权重拼起来"这套逻辑，
  将来会**原样搬到 PL 侧**（块=行带，重叠=行缓冲的上下文，羽化=片上累加器）；
* 现在用 Python 版本验证的**块大小 / 重叠 / 画质折中**，就是硬件设计的输入参数。

> 换句话说：本文档第 5 节的选型表，同时也是 FPGA 侧的带宽/缓冲设计的参考。
