# FPGA / PYNQ 长期开发：编排、上板与取证

本技能是"多代理 + 真实硬件 + 长期迭代"这一类项目的**作业规程**。核心不是某个工具的用法，而是三条：
**① 机制 > 纪律；② 直接取证 > 间接推断；③ 等价性必须逐层证明到硬件。**

数字一律用 $\LaTeX$；结论必须带**运行点**（频率、槽数、位流版本、口径）。

---

## 0. 一页速查：最容易犯的 12 个错

| # | 错误 | 正确做法 |
|---|---|---|
| **0** | **主代理亲自编码/亲自上板**（元错误：会污染方向性判断） | 读证据、写判据、分派；需要写就开子代理（§1.2） |
| 1 | 用"WNS 更好 / TNS 更小"推出"能上板" | 看**违例性质**：准静态 CE 引脚 vs 真实数据通路。门槛见 §3 |
| 2 | xsim 逐拍等价 ⇒ 硬件一定对 | 仿真覆盖不到失效模式，必须硬件 A/B |
| 3 | 板子连不上就判"板子坏了" | 先查 `sshd MaxStartups`、先 `drop_caches`、先读 §8 决策树 |
| 4 | 金丝雀（canary）报警就当作噪声 | 金丝雀是 OOB 探测器，**一次都没误报** |
| 5 | 一次改两个变量（新位流 + 新 `.so`） | 一次只改一个，挂了才能归因 |
| 6 | 主机编好的 `.so` 直接上板 | 跨架构必须两边各验一次；加速开关默认关（opt-in） |
| 7 | 板端源码与主机不同步 | 每次上板前 `md5sum` 逐一对齐 |
| 8 | 计数器叫 `_bytes` 就按字节算 | 单位必须核；**精确整数倍数**通常是单位错 |
| 9 | 用轮询测事件耗时 | 用事件计数/总时间交叉验证，$\pm1\%$ 内必须自洽 |
| 10 | 报告代码跑在交付动作之后 | 产物先落盘，报告全包 `catch`（见 §7） |
| 11 | 子代理结束就 `send_message` 派新活 | 往往只总结旧任务；**新开一个自包含 brief 的子代理** |
| 12 | 硬断电 | `sync; sync; poweroff`，否则 ext4 走 journal recovery |

## 1. 分工：主代理不碰代码

分工不是"谁来干"，而是**谁能做什么、谁绝对不许做什么**。这条规矩的地位高于本技能其它所有技术章节——
因为长期项目里最常见的失败不是技术判断错，而是**主代理被实现细节淹没后丢失方向**。

### 1.1 主代理只有四项职责

| # | 职责 | 具体产出 |
|---|---|---|
| ① | **保持自身在长期任务下的稳定** | 上下文不被实现细节占满；关键状态外置到文档（§1.5 登记表） |
| ② | **制定与推进计划** | 计划分解、里程碑、依赖排序、**阈值/红线预先写死** |
| ③ | **分派任务与界定边界** | 每个子代理的自包含 brief（§1.4 六要素） |
| ④ | **存档与交付** | 产物归档、manifest、事故档案、基线冻结 |

主代理的核心产出是**判据**，不是代码。
"这件事算不算做完"由主代理定义；"怎么做完"由子代理负责。

### 1.2 ★ 硬规则：主代理不许亲自编码

**原因不是分工洁癖，是三种可观测的损害：**

1. **上下文被污染 ⇒ 方向性判断退化。**
   写完某个 tcl 的参数或某个 RTL 的赋值之后，脑子里装的是"这一行怎么写"，
   而全局约束（"LUT 才是墙，BRAM 不是""这个优化在多槽下不成立"）会被挤出去。
2. **边界模糊 ⇒ 责任无法归因。**
   主代理自己改了一处，子代理再改同一处，"谁引入的问题、谁该验证、谁该回滚"就说不清了。
3. **编排余量被吃掉 ⇒ 汇报到达时无力取舍。**
   子代理并行汇报时，主代理需要的是"能立刻判断的证据"，而不是"我刚写的那个函数"。

**真实教训（本项目）**：主代理亲自改 tcl、亲自写探针、亲自上板跑整网。
结果当子代理报"金丝雀（canary）被写坏 4096/4096"时，主代理已没有余量做冷静判断，
把它解释成"环境噪声"，随后**连续四次误判**（SD 写满 → 源码陈旧 → 卡坏 → 环境噪声），
把真正的结论（PL 越界写）推迟了将近一天。

### 1.3 主代理只允许做这四类"手上"的事（白名单）

| 允许 | 边界 |
|---|---|
| **读** | 读代码、读日志、读报告——**为了判断，不是为了实现** |
| **只读核查** | `md5sum`、`ls`、`grep`、看构建日志、看时序报告 |
| **单条诊断命令** | `ping` / `df` / `uptime` / 一次 `ssh`，**不写文件、不成环** |
| **紧急刹车** | 停任务、断资源、写事故记录（写文档是主代理职责，不是编码） |

> 一旦发现"需要写代码 / 改配置 / 跑长流程 / 迭代调试"——**立刻开子代理**。
> 判据很简单：**这条命令会不会产生需要别人复核的产物？** 会 ⇒ 不是主代理的活。

### 1.4 子代理的任务分派：六要素（缺一不可）

子代理**不共享主代理的上下文**，brief 必须自包含：

1. **拥有什么**：可写的精确路径（目录级，不是"相关文件"）；
2. **不许碰什么**：冻结资产清单 **+ md5**（"这些是硬资产，一个字节都不许动"）；
3. **要做什么**：按 ①②③ 编号，每步指向具体文件/函数；
4. **判据**：逐字节 / 拍数 parity / 资源上限 / sha1 三件套 / 门禁矩阵（**由主代理给，不由子代理定**）；
5. **边界与红线**：不许碰板子、不许起综合、不许 `pkill -f`、探针放 `/tmp/probe_<代理>_<任务>/`；
6. **汇报节奏**：先交方向性结论（静态分析/骨架/门禁 1~3），批准后再全量实现。

**界限原则：**
- **一个子代理只负责一个计划**；跨计划的改动必须由主代理重新拆分，不许它顺手改别的。
- 子代理**可以提出**判据建议，但**不能自行放宽容差**（"接近"不是"相同"）。
- 子代理**不许**决定架构取舍（几 lane、要不要搬 PL、要不要换算法）——那是主代理拿红线判的。
- 子代理**不许**动仓库里已冻结的算法文件；改动先落 `/tmp` 或 worktree，门禁过了再申请合入。

### 1.5 ★ 计划登记表：每个计划由谁负责，必须写进项目文档

**在主代理分派之前**就把计划写进文档（如 `docs/PLAN_TASKS.md`，或 `PLAN_*.md` 的固定章节）。
它是主代理的**外置记忆**：上下文被压缩、会话被续接、子代理换代之后，
读这张表就能恢复"全部在途工作 + 判据 + 负责人"。

最小列集（不要省列）：

| 编号 | 计划（一句话） | 负责子代理 | 判据（可复算） | 交付物与落点 | 状态 | 依赖 |
|---|---|---|---|---|---|---|
| T-07 | 把 PS 描述符组装开销降下来 | `d9bb1822` | 逐字节 + 6 个 sha1 + 三条失效门禁；`descviews ≤ 0.05 s` | `ps/pynq/bin_engine.py` diff + `runs/psdesc/` | 待复核 | T-03 |
| T-09 | floatconv 集成进 BD | `aa1dae08` | 门禁 ①~⑤ + LUT ≤ 18000（超则切 4 lane） | worktree + `bd_add_fconv.tcl` | 作废 | — |

状态机（只允许这五态）：
```
待分派 → 进行中 → 待复核 → 已归档
                    ↘ 作废（必须写原因）
```
规矩：
- **一计划一行**；编号一旦分配不复用。
- **"判据"列必须是可复算的**（含数字与命令），不能写"工作正常"。
- **"负责子代理"列必须有具体 id**，不能写"某代理"。
- 每次分派、每次收工、每次判据变化都更新；**它坏掉比代码坏掉更危险**（因为主代理会按它决策）。
- 与 `PLAN_*.md` 的技术章节**互相引用**：表格管"谁在做什么"，章节管"为什么这么做"。

### 1.6 复核：主代理读证据，必要时另开"对抗性复核"

- 子代理说"通过"时，主代理要能**只用它交的证据**复算一遍（读文件、看数字、对 md5），
  不允许"再跑一遍试试"式复核（那会重新污染上下文和时间窗）。
- 关键结论（会改架构、会换位流、会冻结基线）**另开一个复核子代理**做对抗性检查：
  brief 只给结论与证据，要求它**证伪**，不要求它赞同。
- 复核子代理与实现子代理**必须是不同会话**，且复核者不能看到实现者的自我评价。

### 1.7 跨会话/长期任务的稳定性

- 每轮结束把三件事落到磁盘：**计划登记表更新、PLAN 追加一节、产物归档 + manifest**。
- 会话续接后**第一件事是读登记表**，不是读对话历史。
- 关键数字只认文档里的（带日期与运行点），不认记忆里的。
- 上下文将满时的收尾顺序：**归档 > 更新登记表 > 写交接说明 > 再讨论新技术问题**。

### 1.8 已知的子代理失败模式

| 现象 | 原因 | 处置 |
|---|---|---|
| 刚结束的子代理收到 `send_message` 后**重述上一轮** | 竞态：它把新消息当成总结请求 | **新开子代理**，brief 只写当前任务 |
| 两个子代理同时用板子 | 无互斥 | 全部板端命令走 `boardlock.sh`（§2.1） |
| `/tmp` 同名脚本互相覆盖 | 都用 `/tmp/xxx.sh` | 探针放 `/tmp/probe_<代理>_<任务>/` |
| 两个构建同时跑把内存打死 | 无内存闸门 | 走 `memgate.sh`；`SwapTotal=0` 时尤其致命 |
| `pkill -f <模式>` 杀掉自己的 shell | 模式匹配到自身命令行 | 只用 `pkill -x` 或按 pid |
| 子代理"顺手"改了别的模块 | 边界没写清 | brief 里给冻结清单 + md5；一次只许一个计划 |

## 2. 板级安全：机制优先

### 2.1 一个租约 + 一个 load 令牌（`tools/boardlock.sh`）
```
如果一个项目只有一个开发板，就只允许一个"租约"：
  ping 前置 → 全局 flock → 唯一 download 令牌 → 执行 → 释放
```
必须实现的四条：
1. **ping 不通直接拒绝**（不要对已挂的板子发命令）；
2. **全局 `flock`**（跨代理互斥，`WAIT` 超时就拒绝而不是干等）；
3. **唯一 load 令牌**（首个 `download=True` 后写 token 文件，第二个直接 `exit`）；
4. **ssh 限速闸门**（见 §2.2）。

### 2.2 不许 ssh 重试风暴（真实事故）
`sshd` 默认 `MaxStartups 10:30:100`：**未认证**连接超过 10 个就开始丢弃。
症状极具欺骗性：
```
:22 TCP 能连上  →  但连 banner 都收不到  →  rc=124、stderr 全空
```
而板子其实一直好的。**自己写的"抢窗口"重试循环（每 6 s 一次 × 24 次）就能把名额打满**。
规程：60 s 内对板子最多 6 次连接；失败就**停下来看**，不要加密度。

### 2.3 板端命令的固定形状
```bash
# 每次实验前必须清 PYNQ 的残留状态，否则 Overlay 会认为已加载
sudo rm -f <pynq>/pl_server/global_pl_state_.json <pynq>/pl_server/_current_metadata.pkl

# sudo 会重置环境 ⇒ XRT 变量必须显式传（否则 "No Devices Found"）
sudo -S -p '' env XILINX_XRT=/usr /usr/share/pynq-venv/bin/python3 ...
```
- **不要用 `sudo -E`**：它保留用户 `PATH`，`cc` 可能解析到非本机编译器，编出错误架构的产物。
- **禁 core dump**：`ulimit -c 0`（板子只有几 GB SD，几百 MB 的 core 很致命）。
- 只看门狗：`nohup python3 wdt_arm.py &` 之类，**只 SIGTERM 不 SIGKILL**；PDB 的 magic-close 会顺手复位整板，杀它之前先想清楚。
- **断电前 `sync; sync; poweroff`**。硬断电会让 ext4 走 journal recovery。

### 2.4 CMA / 槽位
- `CmaTotal` 通常在启动时就预留好；`CmaFree` **在开机后几十秒内会从很低涨到高位**（初始化期占用）。
  ⇒ **不要在 uptime 90 s 时读 `CmaFree` 就下"永久不足"的结论**。
- 分配前先算账：`槽数 × (in + out) ≤ CmaFree`，并在日志里打印实际 `arena` 地址与大小。

## 3. ★ 时序结论的正确读法（本项目最贵的一课）

### 3.1 先确认约束是"诚实的"
```
BOARD 实际跑 150 MHz  →  create_clock -period 6.667
```
如果脚本里写 `10.000` 而 BD 跑 150 MHz，P&R 就在优化一个**松 1.5 倍**的目标，
报告出来的 WNS/TNS 全部没有意义（本项目曾因此把 P&R 结论整体作废重跑）。

### 3.2 违例**性质**远比数量重要
| | 位流 A | 位流 B |
|---|---|---|
| WNS | $-5.331$ | $-2.138$（好 3.19 ns） |
| TNS | $-47{,}312$ | $-818.7$（好 98.3%） |
| 违例端点 | 20,706 | 2,363 |
| **违例起点性质** | 三个**准静态**寄存器的 CE 引脚占 55.7% | **真实数据通路**：BRAM 输出 → 引擎数据输入，8.671 ns / 10 级 |
| 硬件 | **可跑、结果正确** | **跑 23 s 硬挂，卡死整板** |

解释：
- 准静态寄存器几乎不翻转，其 **CE 引脚**的 setup 违例在实际运行中不致命；
- 一旦把那些修掉、最差路径换成**真在搬数据的那一级**，违例直接变成**错数据** ⇒ 引擎算出越界地址 ⇒ 写出缓冲区 ⇒ 踩烂内核内存。

### 3.3 上板门槛（写进项目规则）
> **WNS $\ge 0$**，或者**逐端点证明所有违例都落在准静态寄存器的 CE 引脚上**。

检查方法：
```tcl
report_timing -max_paths 40000 -nworst 1 -setup -slack_lesser_than 0
# 读 END POINT PIN TYPE 与 STARTPOINT：CE 引脚 + 准静态 = 可容忍；D 引脚 + 活数据 = 不可上板
```

### 3.4 其它必查
- `report_utilization` 的 **`Register as Latch` 必须为 0**；同时用网表指纹 `REF_NAME == LDCE/LDPE` 复核。
- **指纹门禁**：改完 RTL 后，断言"新逻辑的 cell 存在（数目 $\ge$ N）"且"旧逻辑的 cell 数为 0"。
  例：`issue_en0_carry` 必须 0 才能证明旧的比较器真的消失。
- `(* max_fanout = N *)` **在 Vivado 综合里不一定落地** ⇒ 判据只能是"网表里数 replica 个数"，
  而且它给某些寄存器加会**引出 latch**（本项目中过一次）。

## 4. 仿真 ↔ 硬件等价性

### 4.1 等价性要逐层证明
```
RTL 行为等价（定向 TB，逐字节）
  → 综合后网表等价（synthcheck：多驱动 0 / 组合环 0 / latch 0）
  → 实现后时序"性质"合格（§3.3）
  → 硬件 A/B（同参数、同输入、比 sha1）
```
**任何一层缺失都不算"等价"。** 本项目出现"106 条命令逐拍等价、总拍数完全一致，但硬件崩"——
这一层靠仿真永远补不上，必须硬件 A/B。

### 4.2 测试设计的三条硬规矩
1. **随机测试对 $2^{-n}$ 边界结构性盲区**：如舍入进位导致指数丢 1（命中率 $2^{-23}$）。
   ⇒ 必须写**定向边界测试**，并证明"改前失败、改后通过"。
2. **换测试平台前先清状态**：`rm -rf xsim.dir`，否则会拿上次的成果得出结论（本项目"0 fail"曾是陈旧 work 库）。
3. **golden 必须来自目标平台**：主机结果不能当板端 golden（BLAS/舍入/指令集都可能不同）。

### 4.3 冻结式反压：要冻结**所有派生态**
若用"拉低全局 ce 冻结流水线"做反压，则凡是**每拍无条件赋值**的寄存器都必须显式加使能：
```verilog
// 错：地址被冻结，但读数据寄存器仍每拍刷新
tbuf_rdata <= tbuf[tbuf_raddr];
// 对：
if (ce) tbuf_rdata <= tbuf[tbuf_raddr];
```
只测"外部拉低 ce"永远测不出来——真正的触发条件是**冻结期间还有写入**。
⇒ 门禁必须包含：**冻结 + 同时写入** 的组合，以及"上游限速 N 拍 1 beat"的梯度测试。

### 4.4 用"错误的形状"反推故障机制
比逐信号打印有效得多。例：
- 错的是**一整段连续列**（`ox 8..15` = 某个 sub-group），而不是零散元素
  ⇒ 不是"丢一拍/重一拍"，而是**整段来源错位**（冷启动/映射错误）。
- 错数随某个控制量**单调增长** ⇒ 是确定性时序问题，不是偶发。
先问"错误的空间/时间形状是什么"，再决定查哪里。

## 5. 边界检查与"金丝雀"

在 PL 输出缓冲区的**尾部**放一段已知图案（canary），引擎每完成一次就校验：
```python
if canary != expected:  raise RuntimeError("引擎越界写，停机排查")
```
- 星星之火：本项目正是靠 4096/4096 全被改写这条线索，最终定位"PL 越界写踩烂内核内存"。
- **金丝雀报警时不许解释掉**。它的语义是"有人写到了缓冲区外"，先去查 OOB。

配套：`tools/board_memtest.py` 这类**三态对照**测量是分"硬件坏"与"软件坏"的最有力手段：
```
① 未加载 PL  →  RAM 图案校验 + 文件热读/冷读双校验
② PL 已加载但空闲 → 同上
③ PL 已加载并跑业务 → 同上
```
前两态零失败、第三态必挂 ⇒ 问题一定在 PL 的写通路，而不是 DDR/SD/系统。

## 6. PS 侧性能工作

### 6.1 先拆项，再改
把总时间拆成互不重叠的桶，并**把算子级计时只包住真正要算的那一段**
（本项目一度把"等 PL"的时间记进了"算子计算"桶，导致整个分解作废）。
口径要写进代码 docstring：**从哪一行到哪一行，含什么、不含什么**。

### 6.2 计数器纪律
- 名字带 `_bytes` 就**必须**是字节；单位错会造成 $4\times$ 带宽误判。
- 数值出现**精确整数倍数**（如恰好 $4.000\times$）时，先怀疑单位不一致，再谈物理。
- **测事件，不测轮询**：`while !done: sleep()` 测出来的是轮询周期。
  判据：同一件事用两种方法测，总时间必须自洽（$\pm1\%$）。
- 单点采样不足以下"永久/结构性"结论（本项目曾因开机 90 s 时的 `CmaFree` 误判"内存永久不足"）。

### 6.3 优化顺序：先找"每层固定开销"
$N$ 个 op 的框架里，"每 op 固定开销 $\times N$" 往往比某个大算子更值钱。
本项目：$227$ 层 $\times$ 约 $3\ \text{ms}$ 的调度/描述符/配置开销 $\approx 1.15\ \text{s}$，占总时间 13%。
识别方法：同一框架在不同输入尺寸下测，**不随数据量缩小而缩小的那部分**就是固定开销。

### 6.4 跨架构加速必须两道门
```
主机（x86）：逐字节等价 + 全形状覆盖
板端（ARM）：同样的逐字节，而且要用板端现场编译的产物
```
- **主机通过的 `.so` ≠ 板端能跑的 `.so`**（ABI、FPU 变体、`-mfloat-abi`）。
- 加速开关**默认关**（opt-in），任何异常静默回落原路径。
- 编译参数注意 `-ffp-contract=off`（否则 GCC 合成 FMA/VMLA，乘加之间不舍入，结果差 1 ulp）。
- 板端源码 md5 必须与主机一致，否则你验的是另一份代码。

### 6.5 分工原则
纯 CPU 的工作优先考虑"给 PS 写 C/NEON 内核"，而不是"搬进 PL"：
几十行 C 换回 $7.8\times$（$74.5\to9.5\ \text{ms}$），比新建一条 RTL 通路便宜一个数量级。
只有当 PS 已经贴着内存带宽上限、或需要减少 DDR 往返时才搬 PL。

## 7. 产物归档与取证

### 7.1 产物一落盘就归档
真实事故：构建**已布线完成**，但在最后的报告段报错（非法选项），而 `write_checkpoint` / `write_bitstream`
排在其后 ⇒ **整个实现被丢掉，白烧 22 分钟**。

规矩：
1. **`write_checkpoint` 提到所有报告之前**；
2. **每个报告项包 `catch`**，取不到就写 `N/A`，绝不让报告杀死构建；
3. 构建结束自动跑 `archive_build.sh`：bit / routed DCP / util / timing / manifest / `.hwh` / 日志 / RTL 快照 + `MD5SUMS` + `README`。

### 7.2 bit ↔ 源码 manifest（每次上板前必跑）
```bash
# 注意工作目录：manifest 里的相对路径以工程子目录为基准
cd <project>/pynq_code && md5sum -c ../runs/<ver>_archive/build_<ver>_manifest.txt
```
不一致 ⇒ **不许上板**：你验的是一个不存在于仓库里的设计。
另外必须确认 `util_<ver>.rpt` 里 `Register as Latch = 0`。

### 7.3 文档：单一事实源 + 事故档案
- 把"设计 + 决策 + 纪律 + 已推翻的判断"放**一个**不断追加的 `PLAN_*.md`，每节带日期与实测数字。
- 每条被推翻的旧结论要**留在原地并标注"已作废 + 为什么"**，否则后人和子代理会照着旧结论干活。
- 事故单独成文，且**必须写清自己的误判链**（判据、当时的证据、为什么错、正确做法）。
  这是最值钱的文档——它防止下一次用同样的间接推断得出同样的错结论。
- **计划登记表（§1.5）是项目文档的必备件**，不是主代理的私人笔记：
  它必须与代码一起进仓库、随 PLAN 一起更新，因为它记录了"每个计划由谁负责、判据是什么、现在在哪一步"。

## 8. 板子"死了"的 10 秒判定树

严格按顺序，**每步只做一次**，不许重试风暴：

```
1. ping 通吗？
   ├─ 不通 → 先查网线/供电；仍不通 → 断电重启（这是唯一合法结论）
   └─ 通 →
2. :22 TCP 能连上但拿不到 banner？
   ├─ 是 → 极可能 sshd MaxStartups 被自己打满 → 停手 1~2 分钟再试一次
   └─ 否 →
3. 能登录就立刻跑四项体检（不要先跑业务）：
   df -h /  |  df -i /  |  sudo -S -p '' true ; echo rc=$?  |  python3 -c "from pynq import Overlay"
   ├─ sudo 段错误 / find 段错误 / bad marshal data
   │    → 怀疑【内存被踩】：sync; echo 3 > /proc/sys/vm/drop_caches
   │      再 md5 同一文件；若 md5 变回正常 ⇒ 页缓存被改写 ⇒ 查 PL 越界写（§5）
   └─ 四项全过 → 才能做实验
4. 实验按下述梯度，一次只加一档：
   只 load 位流 + 读 IP 基址/频率  →  单次小尺寸整网  →  全尺寸 ×1  →  全尺寸 ×N
   任何一档失败即停，不连试。
```

判定要点：
- `ping` 通 + `:22` 开 + 无 banner ⇒ **连接层问题**（MaxStartups / 资源耗尽），不是"板子坏"。
- 文件 md5 变了但宿主机读同一文件正常 ⇒ **页缓存被踩**，磁盘是好的。**跨设备交叉取证**是关键一招。
- `sudo` / `find` 随机段错误 ⇒ 优先怀疑内存被改写，而不是"系统装坏了"。

## 9. 项目节奏（月级项目的实践形状）

1. **先建立冻结基线**：位流 md5 + `.hwh` + 一组 sha1 + 一个秒级数字 + 运行点（频率/槽数/开关）。
   之后所有改进都相对它报差值与相对值，**绝对时间只在同一运行点下可比**。
2. **一次只改一件事，改完立刻归档**；把"已实测"与"待实测"分开写在 PLAN 里。
3. **预留硬件时间窗**：编译（几十分钟级）与上板（分钟级）是两种资源，不要在同一条关键路径上串行等待。
   编译跑着的时候推进"不依赖硬件"的子任务（PS 侧拆项、RTL 静态审查、门禁脚本）。
4. **阈值预先写死**：例如"集成后 LUT $>18000$ 就切 4 lane""$c_{in}k^2>1024$ 直接报错"。
   预先写死才能在数据回来时**立刻决策**，而不是再开一轮讨论。
5. **每轮结束更新三样**：PLAN 追加一节、实验报告落 `runs/`、冻结资产打快照（含 md5）。
