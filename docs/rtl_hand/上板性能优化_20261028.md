# 上板性能优化记录（2026-10-27 ~ 28）

## 结果

$$\text{整网 247 个卷积 + 517 个算子，输出 0/1,228,800 逐字节等于金标准}$$

| 阶段 | 整网耗时 | 累计加速 |
|---|---:|---:|
| HLS 基线（已删除） | 43.55 s | 1.00× |
| 三引擎首版（k5 走 numpy） | 150.58 s | 0.29× |
| + 修 C 内核缺失（非卷积） | 106.71 s | 0.41× |
| + k1 wrapper 多笔在飞 | 71.09 s | 0.61× |
| + k5 走 C 加速 | **23.17 s** | **1.88×** |

当前分解：k1 8.16 s / 非卷积 7.4 s / k3 4.26 s / k5 2.46 s / 开销 0.88 s

## 四个根因（都靠"仿真加计数器"或"板端 profiler"一次定位）

### ① 板子卡死 5 次：k1 wrapper 漏驱动 `s_axi_bvalid`
端口声明为 `output logic` 却从未赋值 ⇒ 综合成常量 0 ⇒ PS 每笔写等不到 B 响应
⇒ CPU 停在 MMIO 写上一去不回（ARP 都不回）。
**为什么仿真没抓到**：TB 的写任务不等 bvalid；纯读的冒烟测试也过。
已加静态门禁 `tools/check_undriven_out.py`（端口表按逗号切开判方向 + 全文出现计数）。

### ② k3 大层误报"槽容量不足"：`k3_cfg_check.v` 的 ×1/×2 两分支写反
```verilog
// 错：d≠1 走 ×1、d=1 走 ×2
wire [13:0] need_cap = (cfg_dil != 1) ? {1'b0, ngrp_w} : {ngrp_w, 1'b0};
```
preconv_2（20×160=3200）被算成 6400 > 4608 ⇒ 错误码 8。已修。

### ③ 修好的 RTL 没进 bit：BD 里每个 IP 有独立 OOC 综合子 run
`REBUILD=1` 只重置 `synth_1/impl_1`，不碰 `design_1_k3_wrap_0_synth_1` 等
⇒ 顶层综合把旧 IP 网表合进去。**第二次踩**（上次 10-26）。
已写进构建脚本：REBUILD 时把所有 `design_1_*_synth_1` 一并 reset。

### ④ k1 只有 8~9% MAC 利用率
仿真加计数器（`[K1-DUTY]`）显示引擎 `issue` 占空比 **99%**（II=1，零浪费），
所以问题不在引擎。板端反推：额外周期恒为 `0.5 × cin`：
```
cin=48  → 6 笔 × 56 拍 = 336（实测额外 339）
cin=144 → 18 笔 × 56 拍 = 1008（实测额外 1014）
```
⇒ 每笔 8 字节单拍读付一次完整 AXI 往返。**根因：wrapper 的读仲裁器必须等
整笔 RLAST 握手完成才发下一个 AR**（k1 的读全是 arlen=0 单拍，C8 布局下
同一像素各通道组相隔 H·W·8 字节，连不成 burst）。

**修法**：三个通道本来就有独立 ARID（TAG_IN/TAG_B/TAG_W），改成多笔在飞 +
用 `m_axi_rd_rid` 分流；每通道记"在飞 beat 数"（同 ID 保序，无需 FIFO）。
$$\Rightarrow 8.1\times \to 1.5\times,\quad \textbf{43.5 s → 8.16 s}$$

实测 `MAXO`（在飞笔数上限）**12 与 24 完全等价** ⇒ 12 笔后限的是"总线接受
AR 的频率（约 1 次/4 拍）"，不是往返延迟。再快只能把多个像素合成一笔 burst。

## k5 的 2 列 bug（未修，暂用 C 兜底）

只有 x=3 与 x=259（= 3+256）两列错，全通道、约 70% 的行。已排除：地址混叠、
容量、随机竞争（同输入跑 3 次逐字节相同）、零/常数输入（0 不符）、行列映射
（单列脉冲支撑集恰好 [c-2,c+2]）。决定性证据：

$$\text{x=3 处 } \texttt{got} \equiv \text{窗口}[4..8]\ \text{的结果} \Rightarrow \text{与"列偏移+1"假设 } 48/48\ \text{通道吻合}$$

⇒ `shift_en` 在特定列多移了一拍。触发点随输入变化 ⇒ 与"组合地址
（`lb_raddr = x_cnt + 5`）直接喂同步 RAM"的时序相关。详见
`k5_上板bug定位_20261028.md`。

## k5 的 C 兜底（1 层 45 s → 2.46 s）

`conv_ref_fast.c`：逐像素收集抽头 + 每 4 个 oc 并行点积。**编译选项至关重要**：

| 选项 | 板上耗时 |
|---|---:|
| `-O2` / `-O3` | 7.5 s |
| `+ -funroll-loops` | 6.4 s |
| `+ -mcpu=cortex-a9 -mfpu=neon -ftree-vectorize` | **2.44 s** |
| 换成"分块+抽头主序+acc 常驻寄存器" | **4.29 s（更慢）** |

最后一行是踩过的坑：那样改会让 tap 被 48 个 oc 各重读一遍，代价超过省下的
acc 流量。**别凭直觉改，按实测走。**

## 补记（2026-10-28 上午）：一次失败的尝试与结论

**目标**：把 k1 的 1.5× 压到 1.25×（8.16 → 6.8 s），手段是"两个像素合成一笔 burst"
（C8 布局下相邻像素在同一通道组内连续、步长 8 字节，所以 `arlen=1` 合法）。

**做法**：把 fetch 的 AR 侧改成以"批"（2 像素）为单位推进，`arddr = base + pair*8 + g*hw8`，
`arlen = pair_n-1`；R 侧按 `(批基址 + 批内偏移, 组号)` 写 px_mem；批尾把两个像素一起置 ready。

**结果：仿真卡死在 `pix_cur=637/640`，回退。**

$$\text{态机观测：}\texttt{ar\_pair}=\texttt{rd\_pair}=640\ \text{（取数全完成）},\ \texttt{pix\_ready}[1]=1,\ \texttt{ob\_cnt}=0,\ \texttt{blk\_room}=1,\ \texttt{issue\_en}=0$$

⇒ 数据与缓冲都正常，是**状态机卡在非 `ST_PASS` 态**（`issue_en` 的第二项依赖 `state==ST_PASS`），
但我没能在有限时间内定位到底是哪个态、为什么进不去。

### 过程中踩到并已修复的两个真实陷阱（下次别再踩）

1. **不能为了"每拍只发一笔 AR"而用 `f_ar_busy` 去撤销 `arvalid`**。
   AXI 要求 `arvalid` 在握手前保持，撤销即丢事务（仿真里表现为 `pixwait` 吃满）。
   正确做法：AR 侧只靠"批/组计数器"推进，`arvalid` 由窗口条件直接给出。
2. **Verilog 不允许对括号表达式取位**（`(a+b)[1:0]` 是语法错），必须先声明中间 wire。

### 还值得试的下一步（按我的判断排序）

| 方向 | 预期 | 前置条件 |
|---|---|---|
| k1 多像素 burst（本次未成）| −1.4 s | **先在 TB 里打印 FSM 状态**定位卡在哪个态；建议给 `state` 加一个"卡死 N 拍报警"的断言，比人工看波形快 |
| k5 RTL 的"窗口+1" | −1.6 s | 需仿真定位 `shift_en` 多打一拍（见 `k5_上板bug定位_20261028.md`）|
| sam_sum 改定点 | −1.5 s | **不建议**：会破坏"逐字节等于金标准"，不值得 |
| 提高 FCLK | 0 | PYNQ 的可达频率只有固定几档，请求 111.1 仍给 107.1 |

**结论：23.0 s 是当前已验证的最优，回退点 `/tmp/keep_23s.bit`（md5 `770287c2`）。**

## 补记二（2026-10-28 上午）：burst 方案的**容量算术**结论（重要）

第二次尝试同样回退，但这次拿到了确定性的结论，不用再试第三次。

### 现象与定位

加了"状态机卡死检测"后一次就看清：

```
[K1-STUCK] state=2(=ST_PASS) 停 200000 拍 | pix_cur=637 pix_total=640
           ar_pair=640 rd_pair=640 ready=0100 ← 注意：Verilog %b 是 MSB 先打，
           ic_cur=0 issue_en=0 ob_cnt=0 blk_room=1   0100 是 bit2 置位
```

$$\texttt{cur\_buf}=637\bmod 4=1 \Rightarrow \text{需要 } \texttt{ready}[1],\ \text{实际只有 } \texttt{ready}[2]$$

再用 pix_ready 变化跟踪（只打 `pix_cur>=630`）看到真正的机理：

```
[READY] 0100 -> 0111 | rd_pair=638 pix_cur=633   ← 收下 pair(636,637)，写槽 0,1
[READY] 0111 -> 0101 | pix_cur=633→634           ← 算完 633，清掉槽 1
                                                   而槽 1 正是像素 637 的缓冲
```

$$\text{像素 } 633 \text{ 与 } 637 \text{ 相差 } 4 = \texttt{NBUF} \Rightarrow \textbf{共用同一个槽} \Rightarrow \text{637 的 ready 被 633 清掉}$$

### 结论：4 槽做不了 2 像素 burst（容量算术，不是逻辑 bug）

$$\text{像素槽需求} = \underbrace{2}_{\text{计算侧当前+下一像素}} + \underbrace{2 \times 2}_{\text{在飞 2 批}} = 6$$

$$\text{而 } \texttt{px\_mem} = 256 \times 64\text{bit} = 4\ \text{像素} \times 64\ \text{组} \Rightarrow \textbf{只有 4 槽}$$

$$\Rightarrow\ \textbf{4 槽恰好是"1 像素粒度"双缓冲的上限；要做 2 像素 burst 必须先把 px\_mem 扩到 512 项（8 槽）}$$

### 如果以后要做（改动清单，避免再摸一遍）

1. `px_mem` 从 256×64 → **512×64**（+1 块 RAMB36，当前 BRAM 76/95 有余量）
2. 像素槽索引 `pix[1:0]` → `pix[2:0]`（`cur_buf` / `nxt_buf` / `pix_ready` 都从 4 位变 8 位）
3. 窗口条件改成 `f_ar_pair - pix_cur <= 6`，`f_ar_pair - f_rd_pair <= 4`
4. 其余（AR 以批推进、R 侧按 `(批基址+批内偏移, 组号)` 写、批尾一起置 ready）本次已验证逻辑正确，可直接复用

### 另外两个已验证的踩坑点

- **不能用"本拍已发"的门去撤销 `arvalid`**：AXI 要求 valid 在握手前保持，撤销即丢事务
- **Verilog 不允许对括号表达式取位**（`(a+b)[1:0]` 语法错），必须先声明中间 wire

### 当前状态

源码树与板上 bit 一致（engine v4 + wrapper MAXO=24），**整网 23.0 s，逐字节 0/1,228,800**。
回退点 `/tmp/keep_23s.bit`（md5 `770287c2`）。TB 里新增的两个诊断（issue 占空比 + 状态机卡死检测）保留，后续调 RTL 直接用。

## 补记三：burst 方案的**真正拦路虎 = AXI 4 KB 边界**（2026-10-28 上午）

### 第三次尝试：8 槽扩容后仿真通过、硬件挂死

按补记二的改动清单做了 8 槽（`px_mem` 512×64、槽索引 3 位、`NBUF=8`、窗口 6/4）：

$$\text{仿真：}\textbf{PASS}\ (0/40960\ \text{字节不一致}，\texttt{issue}\ \text{占空比 } 99\%)$$

$$\text{硬件：}\textbf{超时}\ (\texttt{busy}=1\ \text{永不完成，120 s 后驱动超时返回})$$

### 根因：一笔 burst 跨越了 4 KB 边界

$$\text{addr} = base + pair \times 8 + group \times H{\cdot}W{\cdot}8,\qquad H{\cdot}W{\cdot}8 = 819200 = 200 \times 4096$$

$$\text{组内按 8 字节递增} \Rightarrow \text{2 像素 burst} = 16\ \text{字节}$$

$$\text{当 } pair \times 8 \bmod 4096 = 4088 \ \Leftrightarrow\ pair \equiv 511 \ (\mathrm{mod}\ 512) \Rightarrow [4088, 4104) \ \textbf{跨过 4 KB 边界}$$

$$\text{320} \times \text{320} = 102400\ \text{像素} \Rightarrow \text{每层每通道组有 } 200\ \text{处越界}$$

**AXI4 明确禁止 burst 跨 4 KB 边界**（从机行为未定义）。TB 的从机模型不检查这一条 ⇒ 仿真通过；真实 smc 遇到违规 burst ⇒ 行为未定义、`busy` 永不落下。

### 修复只要 4 行（下次直接用）

让"成对"跳过越界点——**两侧各自从自己的批基址推导，天然保持同步**：

```verilog
// 位于 4 KB 边界前一个像素（512 个一批）时不配对，退化成单拍
wire p_cross_a = (f_ar_pair[8:0] == 9'h1FF);
wire p_cross_r = (f_rd_pair[8:0] == 9'h1FF);
wire [1:0] ar_pair_n = (((f_ar_pair + 32'd1) < pix_total_r) && !p_cross_a) ? 2'd2 : 2'd1;
wire [1:0] rd_pair_n = (((f_rd_pair + 32'd1) < pix_total_r) && !p_cross_r) ? 2'd2 : 2'd1;
```

$$\text{只损失 } 200/102400 = 0.2\% \text{ 的配对机会，几乎不影响收益}$$

### 为什么这次没继续做完

第三次尝试的时间成本 = 一次 25 分钟构建 + 一次板测；而收益只有 1.4 s（23.0 → 21.6 s，6%）。
**已连续三次尝试同一处**，边际收益不足以再烧一轮，故记录在此留给后续。

$$\textbf{整网 22.99 s，0/1,228,800 逐字节一致}$$

TB 里保留了 issue 占空比 + 状态机卡死检测两个诊断（后续调 RTL 必用）。
