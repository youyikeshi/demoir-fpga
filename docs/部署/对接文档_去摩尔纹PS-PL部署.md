# AX7015B 去摩尔纹模型 PS–PL 部署对接文档

> 版本：2026-09-30（板卡软件链路完成后修订）· 状态：**M−1 的软件侧（板卡镜像构建）已完成并逐项验证，待上板实测**；量化、硬件实现、板上推理尚未开始  
> 目标板：ALINX AX7015B，XC7Z015（Zynq-7000，双核 Cortex-A9 + FPGA）  
> 当前模型：`weights.yaml` 中的 `student/uhdm4k_s640_ep150.tar`，`my_model(48, 32, 64, 32, 1)`  
> 首次验收：SD 卡读取一张图片，在开发板上运行完整 student 推理并保存结果。相机连续采集是后续阶段。

## 1. 先统一“部署”到底指什么

现有 `nets_student.py` 是 PyTorch 网络定义，`.tar` 是训练权重。两者不能直接变成 FPGA 电路。**PYNQ 完全可以负责 PS–PL 联动**：它让 ARM 上的 Python 程序调用 PL 加速器，不要求首先把调度程序改写成 C/C++。这里需要形成三种可分别验证的产物：

1. **电脑端模型参考**：继续使用现有 Python/PyTorch，生成逐层和最终输出，作为唯一数值基准；在电脑上完成量化和权重整理。
2. **PL 推理 IP**：用可综合的 Vitis HLS C++（必要处可用 RTL）实现计算单元，经综合、布局布线成为 bitstream。HLS C++ 是电路描述，不能把 PyTorch 调用直接粘进去。
3. **PS 控制程序**：首版优先使用 PYNQ 上的 Python/NumPy。它负责输入图片、内存、逐层调度、硬件状态、错误处理和输出。PYNQ 的 Python 是**控制加速器**，不是把现有 PyTorch 网络原样搬到 Cortex-A9 上执行。若板上实测发现逐层 Python 调度成为瓶颈，再减少控制调用、让 PL 批量执行任务，必要时将 PS 控制层改为 C/C++。

**板卡软件是新增的前置关口**：PYNQ 官方提供 Zynq-7000 架构支持及可供定制板使用的 ARM rootfs，但官方预编译镜像列表没有 AX7015B。不能把 PYNQ-Z2 的 SD 镜像或 PS 配置直接用于 AX7015B；需依据本板 DDR、SD、串口、网口和启动配置制作或移植板卡镜像。官方 PYNQ v3.1 镜像构建说明以 Vivado/Vitis/PetaLinux **2024.1** 为版本组合，而本工程用 **2025.2**。**2026-09-30：这条路线已在 2025.2 上跑通并逐项验证** —— 做法是在现有 2025.2 PetaLinux 工程里移植 PYNQ 组件（zocl + 设备树节点 + AMD 的板卡无关 rootfs），完整步骤见 [`全链路构建/README.md`](全链路构建/README.md)。板上启动、overlay 加载和缓冲区分配仍需**实测**确认。板上只加载推理权重，不需要训练数据、teacher、优化器或 PyTorch 训练环境。

## 2. 系统结构与职责

```text
SD 卡图片 / 后续相机帧
        │
        ▼
  PS：PYNQ Python 应用 ────AXI4-Lite────▶  PL：可复用推理 IP
        │              参数 / 启动 / 状态        │
        │                                        │ AXI4 master
        ▼                                        │ 经 PS HP 口读写
  PS DDR：输入、权重、中间特征、输出  ◀──────────┘
        ▲
        └── 完成 / 错误中断 ── PL
        │
        ▼
SD 卡结果 / 后续显示
```text

- **PS 做控制**：PYNQ Python 负责文件或帧接入、RGB 解码、边界补齐、模型执行顺序、缓冲区复用、异常恢复、结果写出、耗时统计。ARM 不承担大量卷积乘加。
- **PL 做密集计算**：卷积为优先项；后续将插值、全局平均池化、ECA、小型逐元素运算纳入，以减少 PS/PL 来回搬运。测试初期可在 PS 实现个别算子作功能对照，但每次回退都要记录耗时和数据传输量。
- **DDR 存大数据**：权重、跳连特征、多尺度分支和输出放在 DDR；BRAM 用于当前层的行缓冲、局部权重缓存和累加。AX7015B 手册给出 160 个 DSP、3.3 Mb BRAM（约 0.41 MB）。156 万个 INT8 权重约 1.56 MB，仅权重已超过全部 BRAM；以 512×512 输入为例，单张 `64×256×256` 的 INT8 特征图就占 4 MiB。因此不能设计成“整网权重或中间特征常驻片上”。

**首版接口选择**：HLS IP 用 AXI4 主接口（`m_axi`）直接访问 DDR，用 AXI4-Lite（`s_axilite`）接受任务参数。这样先用一个可复用 IP 跑逐层计算，暂不依赖独立 AXI DMA IP。已有的 AXI DMA 环回教程仍可用于熟悉 HP 口和 Linux 数据通路；只有当实测表明流式接口更合适时，再评估 AXI DMA + AXI4-Stream。`m_axi` 访问 DDR 也属于硬件直接存取，不等于由 ARM 逐字搬运。

在 PYNQ 中，上述接口对应 `Overlay` 加载同名 `.bit` 与 `.hwh`、通过 IP 的寄存器映射设置 AXI-Lite 控制字、通过 `pynq.allocate()` 获取 PL 可访问的连续缓冲区，并把缓冲区的 `device_address` 交给 `m_axi` IP。返回的缓冲区可像 NumPy 数组一样读写，但必须通过 `pynq.allocate()` 分配；PS 写入后与 PL 写出后都要按 PYNQ 缓冲区 API 完成相应的缓存同步。若以后改用“DDR ↔ AXI4-Stream”数据路径，可以在 overlay 中加入 AXI DMA，并用 PYNQ 的 DMA 类发送和接收数据。PYNQ 是**控制与共享内存框架**，不会自动把 `nets_student.py` 合成为硬件。

## 3. 当前 student 的精确推理契约

源文件：`vendor/PDNet/model/nets_student.py`；权重与结构参数以 `weights/weights.yaml` 为准。网络是三层编码器、三层解码器。以 **512×512 原生裁块**作为首轮联调样例，主要特征尺寸如下（仅表示逻辑张量，实际硬件排列可调整）：

```text
RGB 3×512×512
  → pixel_unshuffle：12×256×256
  → 5×5 conv：48×256×256
  → 编码 1：48×256×256 ────────────────────────┐
  → 下采样 / 编码 2：96×128×128 ───────────┐    │
  → 下采样 / 编码 3：192×64×64           │    │
  → 解码 3：64×64×64 → 上采样特征 64×128×128
  → 解码 2：64×128×128 → 上采样特征 64×256×256
  → 解码 1：64×256×256 → 最终 RGB 3×512×512
```

该图省略了各级内部的 GhostModule 和 SAM；不得据此直接估算计算量。实际清单必须从 `forward()` 顺序展开，并记录：

- `5×5` 首层卷积；`3×3` 普通/步幅为 2 的卷积；`1×1` 卷积；`3×3` 空洞卷积（dilation 1、2、3）；ReLU 与残差加法。
- Ghost 模块的逐层拼接。拼接虽无乘加，也会影响地址、缓存和 DDR 流量。
- SAM 的 1×、1/2×、1/4× 分支、双线性缩放、分支加权求和；ECA 的全局平均池化、两个 `Conv1d(k=9)`、通道重排、ReLU 与 sigmoid。全局平均需要等整幅当前特征完成，不能假设整网可单次无停顿流过。
- `pixel_unshuffle`、`pixel_shuffle`、decoder 跳连，以及图像输入输出格式。

最终只需 `out_1`。`out_2`、`out_3` 的**最终图像输出头**可以在推理图优化时移除；它们所在 decoder 级产生的 `feat_2`、`feat_3` 仍是下一层输入，不能删掉。

输入输出要与 `src/infer.py` 保持一致：RGB、`uint8 → [0,1]`、先补边到网络可接受尺寸、推理后裁回原大小、输出截断到 `[0,1]`。当前 `img_pad()` 用 RGB 三个不同的常数 **0.3827 / 0.4141 / 0.3912** 补边；不能随手改成零填充或镜像填充后再拿现有浮点结果对比。首轮选 512×512，是为了减少补边与尾块变量，**不是最终相机分辨率的决定**。

## 4. 模型准备与量化

### 4.1 固定一个可追溯版本

记录模型文件版本、权重文件校验值、结构参数、输入预处理及评估图片清单。保留 5–10 张固定图片，至少覆盖强摩尔纹、细字/细线、低纹理区域和原本较干净的区域。保存浮点模型的最终输出及关键层输出。现有 UHDM 评估的平均 `ΔPSNR +4.70 dB / SSIM 0.7735` 只适用于记录中的 **400 个原生裁块**，不能当作相机画面的承诺。

### 4.2 先做离线量化验证

先尝试权重 INT8（可按输出通道设比例系数）、激活 INT8、偏置及乘加采用足够宽的整数累加；具体累加位宽需用各层通道数和数值范围核算。对每层固定缩放、舍入与饱和规则，并验证溢出。ECA 的池化、sigmoid 和加权乘法可先用较高精度参考，再按误差与资源报告选择定点格式。

量化顺序：浮点参考 → 量化仿真 → 同图逐层比较 → 整图画质评估。若后几层误差明显累积，再做量化感知训练（QAT）或只提高敏感算子的精度。**量化后的权重文件不是原 `.tar` 直接拷贝**：需要另附层顺序、张量尺寸、权重布局、比例系数和格式版本。ONNX 可作为检查计算图的辅助产物，但不会自行生成适合 XC7Z015 的完整加速器。

量化阶段的验收门槛应由项目组根据相机画质目标定下；在相机数据尚未建立前，至少要求固定 UHDM 集上的数值和视觉结果可复核，不能仅凭一张样例图通过。

## 5. PL 计算单元如何组织

### 5.1 首版采用“按层复用”

建立一个支持可配置输入输出通道、尺寸、核大小、stride、dilation、padding 和激活方式的卷积计算单元。先实现一个卷积层的精确推理，再接 GhostBlock、一个 Encoder_Level、一个 SAM，最后拼成整网。每次扩展后保留前一阶段的数值对照和综合报告。

卷积单元内部按资源报告选定并行通道数，使用行缓冲和局部权重块以减少重复 DDR 读取。多尺度插值、重排、池化、ECA 与逐元素运算可以是同一 IP 内的不同模式，或者少量专用 IP；最终以 DDR 往返次数和综合资源为决策依据。**不要**同时实例化网络中所有卷积层；资源与布线大概率不允许。

### 5.2 内存与调度契约

每个硬件任务至少指定：操作类型、输入/输出/权重的 DMA 地址、H/W/C、布局与步长、卷积参数、量化比例、缓存长度及超时。PS 维护一个静态计算计划，按依赖顺序发任务；输出和中间张量占用同一块 DDR 的不同区域。只有确认某张量后续不再使用，才可复用其内存。编码器跳连、SAM 三个分支及 ECA 加权前的特征需要保留，不能简单只用两个全局 ping-pong 缓冲。

建议首版硬件张量统一为**通道连续的 NHWC 排列**，通道数按选定并行宽度补齐；权重按同一并行宽度分块存放。这样可规划连续突发读写，但实际块宽由 M2 的综合和板上测量决定。电脑端 PyTorch 的 NCHW 输出要在对照前按约定转换。层描述中必须写明排列、补齐、比例系数、版本和文件校验值；不能只传一段没有格式说明的 `weights.bin`。

实施前要从**实际推理图**测得：总 MAC、各层最大存活张量、峰值 DDR 占用、每层理论读写字节、在估计时钟与并行度下的计算下界。然后用 Vivado 的综合、实现和板上测量替换估算。Python/GPU 的峰值显存含框架开销，不能直接当成 FPGA DDR 用量。

### 5.3 PYNQ 内存与控制

首版在 PYNQ 上用 `Overlay` 管理 PL 设计、用 `pynq.allocate()` 分配输入/权重/中间结果缓冲区、通过 `device_address` 给 IP 传地址，再通过寄存器启动和读取状态。应用应在 PS 修改缓冲区后 `flush()`，在 PL 写入后 `invalidate()`；若 PYNQ 报告该缓冲区为 coherent，相关同步由 API 自行处理。缓冲区应显式释放。启动时尽量分配并复用长期缓冲区，同时核对镜像中可分配的连续内存（CMA）是否足够；1 GB DDR 容量不等于都能被 `pynq.allocate()` 一次性分配。不能把普通 Python/NumPy 对象地址写进硬件寄存器，也不能默认 CPU 与 PL 的缓存始终同步。

Vivado Block Design 至少包含 PS7、PL 时钟/复位、PS GP 到 IP 的 AXI-Lite 控制路径、IP 到 PS HP 的 DDR 数据路径、必要的 AXI 互连与中断。每次改变硬件都重新生成匹配的 `.bit`、`.hwh`；PS 外设、内存映射或中断的变化还要核对板卡镜像和设备树。PYNQ 解析 `.hwh` 才能把实际 IP 和寄存器暴露给 Python，两个文件的基名应一致。

首版应用的一次调用顺序应固定为：启动 PYNQ 并加载 overlay → 核对硬件与权重格式版本 → 分配并登记 DDR 缓冲区 → 读入图片并完成 RGB/补边/量化 → 按静态计划下发逐层任务 → 每层等待完成或超时、必要时记录中间输出 → 反量化与裁边 → 保存图片及各阶段耗时。权重可以在启动时从 SD 卡载入 DDR，后续多张图片复用，避免每张图重复读卡。发生超时或数值错误时记录层编号、参数与缓冲区范围，停止后续层，防止把错误结果当成画质问题。

## 6. 实施顺序与每一步的交付物

### M−1：AX7015B 的 PYNQ 启动验收

- **工作**：为本板选定 PYNQ 版本和匹配工具链，准备 AX7015B 的 PS 配置/板卡镜像，核对 FPGA manager 与连续内存配置；确认从 SD 卡启动、串口/网口工作、可从 Python 加载测试 `.bit`/`.hwh`、`pynq.allocate()` 可分配并同步缓冲区。
- **交付**：可复现的板卡镜像构建记录、测试 overlay 和最小 PS–PL 内存往返结果。
- **通过条件**：在**本块 AX7015B** 上实测成功，而不只是在 PYNQ-Z1/Z2 上运行示例。如果现有 2025.2 工程集成 PYNQ 不通，就按官方支持的版本组合另建 PYNQ 板卡镜像；保持模型/HLS 设计目标不变。若板卡适配成本过高，再使用现有 PetaLinux 路线和受控 Linux 驱动作为后备方案。

### M0：模型与预算冻结

- **工作**：列出完整推理算子、张量生命周期、尺寸、MAC、权重大小、DDR 流量；固定黄金图片和逐层输出。
- **交付**：推理图、模型/权重版本记录、测试集、资源与延迟预算。
- **通过条件**：所有算子都有落点；XC7Z015 资源下的第一版并行规模可以说明依据。若估算已明显达不到目标，先考虑缩小输入块或模型，而不是先写整套 HLS。

### M1：量化参考通过

- **工作**：完成 INT8 或混合定点方案，导出权重和机器可读的层描述。
- **交付**：量化参考输出、逐层误差、画质对照、权重格式说明。
- **通过条件**：误差可定位，固定样例与评估集达到预先约定的画质门槛。

### M2：单层硬件闭环

- **工作**：实现一个真实模型卷积层；先仿真，再综合成 IP，与 PS、DDR 连通。
- **交付**：HLS/Vivado 工程、匹配的 `.bit`/`.hwh`、资源及时序报告、PYNQ 调用路径、板上逐元素对照。
- **通过条件**：输入输出正确；没有缓存不同步、地址越界或超时；实现后的资源仍允许后续算子。

### M3：整网图片推理

- **工作**：按 GhostBlock → Encoder → SAM/ECA → Decoder 的顺序扩展；SD 卡图片输入，保存结果。
- **交付**：可启动的 AX7015B PYNQ 镜像、overlay 的 `.bit`/`.hwh`、PS 端 Python 应用、模型权重与格式说明、端到端结果。只有选用自定义驱动路线时才额外交付驱动。
- **通过条件**：固定测试图与电脑量化参考一致到约定误差；异常能报告所在层；连续处理多张图稳定。

### M4：测量并优化

- **工作**：分别测读图/预处理、权重加载、每层 PL 计算、DDR 传输、**PYNQ 逐层调度开销**、后处理耗时；记录 LUT/FF/DSP/BRAM、时钟和功耗。
- **优化顺序**：先定位最慢层及 DDR 流量，再调整并行度、通道块、数据布局、相邻算子融合和缓冲复用。如果 Python 的逐层控制开销明显，先减少 PS 发任务的次数或在 PL 加任务序列控制；仍不够时再考虑把 PS 控制层改为 C/C++。每次优化都复跑数值与画质对照。
- **通过条件**：提供可重复的单图延迟；是否具备实时可行性由目标相机分辨率及帧率决定。

### M5：接入相机

在 M3/M4 稳定后，选择相机接口、格式、采集分辨率及目标帧率。采集模块把帧送入 DDR，后续调用与 SD 图片模式相同的推理接口；随后才考虑采集、推理、显示的双缓冲或流水并行。相机输出可能是 Bayer、YUV 或 RGB，色彩转换必须纳入预处理契约。**不能把 4K 图缩小后的摩尔纹效果当成原生低分辨率采集效果**；需要用目标相机采集的画面重新评估，必要时微调训练或量化数据。

## 7. 当前最容易走偏的四件事

1. **把“PYNQ 上写 Python”理解为原样运行 PyTorch 模型**：PYNQ 可以用 Python 调用 overlay，但现有 `nets_student.py` 的运算不会自动落到 PL。必须另做加速 IP 和推理调度。
2. **把整个网络“转成 C”后让 ARM 算**：可能得到 CPU 软件基线，但不会利用 FPGA 的并行乘加。第一版的 PS 控制程序可以用 PYNQ Python；HLS C++ 描述的是另一份 PL 计算实现。
3. **把所有权重或特征放 BRAM**：权重约 1.56 MB，而总 BRAM 约 0.41 MB；还要为行缓冲留空间。数据驻留 DDR、局部缓存 BRAM 是基础约束。
4. **先追求相机实时视频**：当前尚无目标帧率、相机原生分辨率、板上耗时和完整硬件资源报告。先验收 SD 卡单图整网，再用测量决定相机方案和是否需要缩模。

## 8. 对接时必须明确的开放参数

- 目标相机型号、输出接口、像素格式、原生分辨率、期望帧率和允许延迟。
- 首版 SD 卡图片的尺寸上限；超过时是拒绝、裁块，还是重叠分块。分块须复用现有 `src/tiling.py` 的位置与羽化规则，并重新量化板上耗时。
- 可接受的画质下降阈值、指标测试集及对无真值实拍图的人工审查方式。
- PYNQ 板卡镜像采用官方匹配工具链重新构建，还是试验向现有 2025.2 PetaLinux 工程加入 PYNQ 组件；在 M−1 实测前不能假设任一路线已经可用。首版优先 PYNQ Python；自定义驱动与 ARM C/C++ 是板卡适配或性能需要时的后备选择。

## 10. AX7015B 的 PYNQ 移植入口

> **2026-09-30 更新：本节写于 2026-09-28，记录的是当时的核查结论。**
> 下面提到的阻塞（XSA 缺 SD/网口、`MANUAL_SELECT`）都已修复，移植路线也已选定并跑通，
> 完整现状与操作步骤见 [`全链路构建/README.md`](全链路构建/README.md)。
> 本节保留作为"当时为什么判断它还不是合格基础"的记录。

AX7015B 不在 PYNQ 官方预编译镜像列表中。官方“其他 Zynq 板卡”入口指向 [自定义 SD 镜像构建指南](https://pynq.readthedocs.io/en/v3.1/pynq_sd_card.html)，其中的 **Retargeting to a Different Board** 才是本板应读的部分；它要求板卡目录、板卡规格文件及匹配版本的 PetaLinux BSP，Zynq-7000 的架构为 `arm`，可复用 PYNQ 的 ARM 通用 rootfs。

本工作区已有的 `xilinx_project/moro_v1/design_1_wrapper.xsa` 是 **Vivado 2025.2** 生成的。**当时**（2026-09-28 之前）其 `.hwh` 中 `PCW_EN_SDIO0=0`、`PCW_EN_ENET0=0`、`PCW_EN_USB0=0`，只启用了 UART1；PetaLinux 工程配置也将网口、Flash、主 SD 标为 `MANUAL_SELECT`。所以它当时还不是 PYNQ 板卡 BSP 的合格硬件基础，更不能直接拿 PYNQ-Z2 镜像替代。这些外设已于 2026-09-28 补全（见 [`全链路构建/流程_前置条件.md`](全链路构建/流程_前置条件.md) 第 2.2 节）。

对这块板的最短核查顺序是：

1. **固定版本组合**：官方 PYNQ v3.1 文档使用 Vivado/Vitis/PetaLinux 2024.1。若按官方流程移植，单独准备匹配版本的构建环境与 XSA/BSP；现有 2025.2 工程保留供对照。向 2025.2 工程移植 PYNQ 组件可研究，但属于未验证路线。
2. **先做能启动的板卡 PS 设计**：按本地 `../../../AX7015B_LINUX教程_2025.2版/PetaLinux_创建流程_XSA到上板.md` 的板级信息核对 DDR、SD0、UART1、PS 网口及 PHY、USB、时钟和启动方式；相应工程必须在选定的匹配版 Vivado 中生成。后续 overlay 所需的 GP/HP 接口也要在设计中核对。
3. **生成同版本的 PetaLinux BSP**：检查设备树、SD 启动、串口、网口、FPGA manager 和连续内存配置。板卡 BSP 是自定义 PYNQ 镜像的输入，不等于把当前已构建的 `BOOT.BIN` 复制到 PYNQ-Z2 镜像。
4. **建立 PYNQ 板卡目录**：按官方指南准备 `AX7015B.spec`、BSP、可选启动 bitstream 与板卡补丁，选择 `arm` 通用 rootfs 和匹配的 PYNQ 源码发行包，然后生成专属 SD 镜像。（**本仓库最终没走这条 sdbuild 路线**，因此不附 `.spec`/BSP；实际做法见 [`全链路构建/README.md`](全链路构建/README.md)。）
5. **先验收 PYNQ 基础功能**：SD 启动、串口登录、网口或其他远程连接、Python 导入 PYNQ、加载同名 `.bit`/`.hwh`、分配与同步缓冲区、运行一个简单的 PL 内存往返。此时再进入去摩尔纹算子开发。

本节是 2026-09-28 的移植路线核查记录，**不是当前做法**；当前做法与现状见 [`全链路构建/README.md`](全链路构建/README.md)。
