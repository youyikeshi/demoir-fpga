## 附录 H：术语速查（白话版）

> 按主题分组。每条格式：**术语** —— 白话解释 ｜ 它在本项目里出现在哪。
> 想追根究底的话，每组末尾给了权威文档的去处。

### H.1 板子与芯片

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **PS / PL** | PS = 芯片里那个 ARM 处理器（跑 Linux 的部分）；PL = 同一块芯片里的 FPGA 可编程逻辑。本项目先把 PS 跑起来（M−1），模型进 PL 是后面的事（M0–M5） |
| **XC7Z015 / Zynq-7000** | 芯片型号。Zynq-7000 = ARM Cortex-A9 + FPGA 的组合芯片；XC7Z015 是其中一个具体型号（ARM32，不是 64 位） |
| **ARM32 / armv7l / armhf** | 32 位 ARM 架构。`uname -m` 返回 `armv7l` 就对了。**所有给板子的软件包必须是 32 位 ARM 版**，拿 aarch64（64 位）的会跑不起来 |
| **XSA** | Vivado 导出的一份"PS 配置说明书"（里面是 `.hwh` + 一堆文本）。PetaLinux 靠它生成设备树；**PS 里没使能的外设，设备树里连节点都不会有** ｜ §2.2 |
| **PS7 / PCW_EN_xxx** | PS7 = Zynq-7000 里的 PS 配置模块。`PCW_EN_SDIO0`、`PCW_EN_ENET0` 这种是"某外设使能了没有"的开关 ｜ §2.2 的自检就在数这些开关 |
| **MIO** | PS 引脚的编号（MIO0～MIO53）。UART1、SD、网口、USB 都是通过这些引脚接出去的 ｜ 附录 E #2 讨论过 MIO7 |
| **eMMC vs SD** | 板上有两处存储：SD 卡座（`mmcblk0`）和焊在板上的 eMMC（`mmcblk1`）。本项目**从 SD 卡启动** ｜ §10.6 第 1 项 |
| **拨码 SW1** | 核心板上的两位开关，决定从哪儿启动。**OFF/OFF = SD 卡**，ON/ON = JTAG，OFF/ON = QSPI ｜ §10.2 |
| **FSBL** | First Stage Boot Loader，芯片上电后执行的第一段程序，负责初始化 DDR 等。它和 DDR 参数一起被打包进 `BOOT.BIN` ｜ 附录 C.5 |
| **BOOT.BIN** | 上电后板子读的第一个文件（含 FSBL + U-Boot + 一个环境块）。**里面的 `bootargs` 会覆盖设备树里的** ｜ §7.2 |
| **U-Boot** | 第二段引导程序，负责加载内核。串口上先刷出来的就是它 ｜ §10.4 |
| **bootargs** | 传给 Linux 内核的一串启动参数，比如"根文件系统在哪"（`root=/dev/mmcblk0p2`）｜ §7.2、§12 |
| **image.ub** | 打包好的内核（+ 设备树）。**从 20 MB 变成约 5 MB 说明 ramdisk 去掉了**，这是最好用的判据 ｜ §7.3 |
| **ramdisk / initramfs** | 临时塞进内核的小型内存文件系统。本项目不用它（根文件系统在 SD 卡上），所以要把它关掉 ｜ §4、§7.3 |
| **vermagic** | 内核模块的"指纹"，记录它是对着哪个内核版本编的。**对不上就 `insmod` 报 `invalid module format`** ｜ 附录 C.3 耦合点 1 |
| **内核模块 / `.ko`** | 可以运行时插进内核的驱动文件。`zocl.ko` 就是我们的那个 ｜ §6–§7 |
| **insmod / modprobe / lsmod / depmod** | 分别是：插模块 / 智能插模块（会先处理依赖）/ 列出已插的 / 生成模块依赖索引 |

### H.2 设备树

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **设备树 / dts / dtsi / dtb** | 一份"这块板子上有什么硬件、怎么接的"的说明书。`.dts`/`.dtsi` 是人写的源码，`.dtb` 是编译后的二进制（内核读它）。**`system-user.dtsi` 是我们在本项目的权威修改处** ｜ §5 |
| **节点 / 属性** | 设备树里的一个硬件就是一个"节点"，节点里的一条设置就是一个"属性" ｜ §5 |
| **compatible** | 节点上写的"我是哪种设备"，驱动靠它认领。zocl 节点写的是 `compatible = "xlnx,zocl"` ｜ §5.2 |
| **`chosen/pynq_board`** | 设备树里一个专门放"这块板叫什么名字"的节点。PYNQ 靠它认板卡，验收第 ③ 项检查它 ｜ §5、附录 C.3 |
| **`status = "okay"`** | 把某个节点打开。写 `disabled` 就是把那个硬件关掉 ｜ §5 |
| **PHY / MDIO / RGMII** | PHY = 网口那个负责电气信号的芯片；MDIO = 处理器跟 PHY 对话的"管理通道"（用来看 PHY 的 ID、能力、链路状态）；RGMII = 处理器和 PHY 之间传数据的接口方式 ｜ §5、附录 C/E |
| **`phy-mode` / `rgmii-id`** | 告诉驱动 RGMII 的时序怎么接。`-id` 表示"延迟由 PHY 自己加"。**这块板上它是不是选对了，附录 E #3 仍在追** ｜ §5 |
| **pad skew** | 芯片引脚上的信号延迟微调。千兆速率对时序特别敏感，靠它对齐 ｜ 附录 E #3 |

### H.3 启动之后：链路与网口

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **carrier** | 网口"物理链路通没通"的开关：`1` = 线插对了且两端谈好了；`0` = 没通。**跟有没有 IP 完全是两件事** ｜ §10.5 |
| **自动协商 / autoneg / advertise** | 网线两端正式传数据前要先"商量"用多快、谁当主。`advertise` = 只对外声明自己支持哪些速度。`0x00f` = 只声明 10M/100M，把千兆排除掉 ｜ §10.5.1 |
| **ethtool** | 看/改网卡底层设置的工具（速率、双工、链路）。板上带，宿主机默认没装 ｜ 附录 E #8 |
| **双工 / Full / Half** | 能不能同时收发。`Full` 才是正常状态 ｜ 验收第 ② 项 |
| **静态 IP vs DHCP** | 静态 = 手工写死地址（本项目：板子 `192.168.7.2`、电脑 `192.168.7.1`）；DHCP = 向服务器要地址（直连没有服务器，所以要手工） ｜ §10.3、§10.5 |
| **网关 / 默认路由** | 网关 = "出这个网段找谁"；默认路由 = 没有更具体规则时的兜底出口。**直连场景没有网关，所以验收会报一条 WARN，属于正常** ｜ §11 |
| **NetworkManager / nmcli** | 宿主机上管网络的守护进程 / 它的命令行。`Wired connection 1` 是它给 USB 网口自动建的那条连接 ｜ §10.3 |
| **ufw** | 宿主机防火墙。本项目它开着也不影响（我们只是从电脑连板子） ｜ §10.3 |
| **by-id 路径** | `/dev/serial/by-id/...` 这种长名字由芯片型号 + 序列号生成，**跟着设备走**，换 USB 口也不变；`/dev/ttyUSB0` 则会变号 ｜ §10.4 |
| **dialout 组 / brltty** | 串口设备属于 `dialout` 组，用户不在组里就打不开（`sudo usermod -aG dialout $USER` 后重登）；`brltty` 是盲文终端服务，Ubuntu 22.04 上会抢串口 ｜ §10.4 |
| **console / 串口 console** | 通过串口线看到的板子文本界面（本项目 115200 8N1）。板子没网时它是唯一通道 ｜ §10.4 |

### H.4 XRT 与 PYNQ

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **PYNQ** | AMD 的一套 Python 框架，让 Python 能配置 FPGA 并跟它交换数据。本项目的目标环境是 PYNQ 3.1 ｜ 第 8 册全册 |
| **XRT** | AMD 的"运行时"，负责管理 FPGA 设备、给 PL 分配内存、加载 xclbin。分**内核态**（`zocl.ko`）和**用户态**（`pyxrt.so`）两部分，**两者必须同一版本** ｜ 附录 C.3 耦合点 3 |
| **zocl** | XRT 的 Zynq 版内核驱动。它提供 `/dev/dri/renderD*` 节点和缓冲区管理。**2025.2 自带的配方不含 zynq，所以我们自己编** ｜ §6 |
| **pyxrt** | XRT 用户态的 Python 绑定（`/usr/lib/python3.10/pyxrt.so`）。AMD 的 Ubuntu 包里已预装 ｜ §11 第 6 项 |
| **DRM / `/dev/dri/renderD128`** | DRM = Linux 的图形设备子系统；zocl 借它暴露一个设备节点。**PYNQ 就是靠"能不能打开这个节点"来判断设备在不在** ｜ §11 第 5 项 |
| **fops / `FOP_UNSIGNED_OFFSET`** | fops = 驱动给每个设备节点登记的一张"别人来操作我时该调哪个函数"的表。`FOP_UNSIGNED_OFFSET` 是内核 6.12 新增的一个标志位，**不声明它 → 所有打开这个节点的尝试都返回 `EINVAL`**。这是本项目最隐蔽的一个坑 ｜ 附录 C.3 耦合点 2、补丁 `0003` |
| **`XILINX_XRT` 环境变量** | PYNQ 3.1 用它判断"要不要去找 XRT 设备"。**缺了它 `Device.devices` 恒为空**，症状是 `No Devices Found`。由我们加进 rootfs 的 `/etc/profile.d/xrt_setup.sh` 提供 ｜ 附录 C.3 耦合点 4 |
| **overlay / bitstream / `.bit` / `.hwh`** | bitstream = 要烧进 FPGA 的配置数据（`.bit`）；`.hwh` = 硬件设计信息（寄存器地址等）；overlay = PYNQ 里"一份 bitstream + 它的描述"的封装对象 ｜ §11 第 ⑩ 项 |
| **xclbin / xclbinutil** | xclbin = XRT 认的二进制格式；PYNQ 加载 `.bit` 时会用 `xclbinutil` 临时生成一个只含内存信息的 xclbin ｜ §11 第 ⑨ 项 |
| **`pynq.allocate()` / 连续内存 / CMA** | 给 PL 用的内存必须是**物理连续**的（普通内存是散落的）。CMA = 内核预留的一块专门用来分配连续内存的区域（本项目预留 16 MB）｜ §11 第 ⑧ 项 |
| **`Overlay is not downloaded`** | `allocate()` 的报错：它要先从已加载的 xclbin 里读出"内存分几个 bank、各多大"才知道能分多少。**PL 里还没有逻辑时必然报这个，不是故障** ｜ §11 第 ⑧ 项 |
| **venv / pydantic** | venv = Python 虚拟环境（PYNQ 装在 `/usr/local/share/pynq-venv`）；pydantic 是 PYNQ 依赖的一个 Python 库。**`sudo` 会重置 PATH 从而丢掉 venv**，表现成"pydantic 找不到" ｜ §11 的环境陷阱 |

### H.5 分区与文件系统

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **分区表** | 磁盘开头那张"目录"，只记录每个分区从第几个扇区开始、到第几个扇区结束、是什么类型。**它和里面的数据是两回事** ｜ §12 那两行救砖记录 |
| **扇区 sector** | 磁盘最小的读写单位，512 字节。本项目 p2 的起点是**扇区 1048584**（= 512 MiB + 8 扇区）｜ §9 的警示 |
| **1 MiB 对齐** | 分区起点取 2048 的整数倍（= 1 MiB 的整数倍）。**本镜像的 p2 故意不对齐**，而 `fdisk` 新建分区时默认往上对齐 → 这就是"第二次开机 panic"的成因 ｜ §12、附录 E #3 |
| **超级块 superblock / ext4 魔数 `53 ef`** | 超级块 = 文件系统自己的"身份证"，位于文件系统开头偏移 **1024** 字节处；它的 magic 字段在超级块内偏移 56，即**文件系统内偏移 1080**，值 `0x53EF`。我们用"1080 处是不是 `53 ef`"来判断分区表有没有对错位置 ｜ 修正版 `resizefs.sh` 的安全闸 |
| **挂载 mount** | 把某个分区"接"到目录树上（本项目把 p2 接到 `/`）。挂载中不能对它做 `fsck`/`resize2fs` ｜ §10.1、§12 |
| **rootfs / 根文件系统** | 挂在 `/` 上的那个文件系统，装的是整份 Ubuntu ｜ §8 |
| **orphan_file** | ext4 的一个新特性（"孤儿文件表"）。**`mke2fs` 1.47 默认打开它，而 1.46.5 的老工具不认识 → `resize2fs` 直接罢工**。这是"根分区只有 8 GiB"的根因 ｜ 附录 E #6 |
| **e2fsprogs / mke2fs / resize2fs / tune2fs / dumpe2fs / e2fsck / blkid** | 一套 ext 文件系统工具：`mke2fs` 造文件系统 / `resize2fs` 改大小 / `tune2fs` 查改参数 / `dumpe2fs` 查详情 / `e2fsck` 体检修复 / `blkid` 认分区里是什么文件系统。**版本必须 ≥ 制卡用的版本**，否则认不出新特性 ｜ 附录 E #6 |
| **fsck / `-n` / `-y`** | 文件系统体检。`-n` = 只回答"不"（纯只读，安全）；`-y` = 全部回答"是"（真修）｜ §12 |
| **`lost+found`** | 文件系统修复时"捡回来的孤儿文件"放这儿。**它空着 = 修复过程没丢文件** ｜ 排查文件为何消失时先看它 |
| **journal / 日志** | ext4 的"操作预告本"，突然断电后靠它把没写完的操作补完 ｜ §12 的 panic 之后 |
| **`/etc/fstab`** | 开机自动挂载/启用哪些东西的清单（本项目往里加了 swap）｜ 修正版 `resizefs.sh` 第 6 步 |
| **swap** | 当内存不够时拿来顶替的磁盘空间。本项目在卡上划了 512 MB ｜ §11 第 0 节 |
| **LABEL / PARTUUID / UUID** | 给分区/文件系统起的名字或编号。本项目根分区 `LABEL="root"`、`UUID=809c2aa9-…`。**bootargs 用的是设备名 `/dev/mmcblk0p2`，不是 PARTUUID**，所以分区表重写不影响启动 ｜ §10.1 |
| **`.wic` / `.wks`** | `.wks` 是 wic 的分区配方（本项目的 `rootfs.wks` 写的是"512M FAT32 + 8G ext4"）；`.wic` 是它产出的整盘镜像 ｜ §9 |

### H.6 构建系统

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **PetaLinux** | AMD 的嵌入式 Linux 构建工具（Vivado 的配套）。`petalinux-create` 建工程、`petalinux-config` 改配置、`petalinux-build` 构建、`petalinux-package` 打包 ｜ §3–§9 |
| **bitbake** | PetaLinux 底下的构建引擎（来自 Yocto）。它按"配方"去取源码、打补丁、编译 ｜ §7 |
| **recipe / `.bb`** | 配方 = 告诉 bitbake"这个软件从哪来、怎么编、装到哪"的文件。`zocl_git.bb` 就是 zocl 的配方 ｜ §6 |
| **SRC_URI / PV / PREFERRED_VERSION** | 配方里的字段：源码去哪取 / 版本号 / "优先用哪个版本"。本项目用 `PREFERRED_VERSION_zocl` 钉住 2024.1 那一版 ｜ §6 |
| **补丁 / patch / `SRC_URI += file://…`** | 补丁 = 一个描述"改了哪几行"的文本文件，构建时自动套到源码上。本项目有 3 个（`0001`/`0002`/`0003`） ｜ §6、`deploy/pynq/zocl-kernel-6.12/` |
| **patch fuzz** | 补丁套用时的"模糊匹配"。**上下文对不上还得靠猜，质量检查会直接判失败**。踩过的坑：源码里留下旧补丁的副本 → 生成补丁时务必用真文件 `diff -u` ｜ `zocl-kernel-6.12/README.md` |
| **sstate / downloads / 离线缓存** | sstate = 编译结果的缓存（命中就不用重编）；downloads = 下载源码的仓库。两者合起来就是我们说的"离线缓存"（约 18 GB） ｜ §2.4 |
| **fakeroot / pseudo / setuid** | ubuntu 压缩包里有 root 属主、setuid 位和设备节点，普通用户解压会丢失。`fakeroot` 让进程"以为"自己是 root，**解压和重打包必须在同一个会话里** ｜ §8.1 |
| **Kconfig / CONFIG_xxx** | 内核编译时的功能开关。`CONFIG_MICREL_PHY` 没开，就是本项目千兆没跑起来的一个嫌疑 ｜ 附录 E #3 |
| **modpost** | 编内核模块的最后一步，会检查"用到的符号有没有人提供"。**zocl 的 AIE 符号问题就是在这步暴露的** ｜ 附录 C.2 |
| **device tree 编译 / `petalinux-build -c device-tree`** | 单独重建设备树。改完 `.dtsi` 只跑这一条能省时间 ｜ §13.2 |
| **`petalinux-package boot --u-boot --force`** | 重打 `BOOT.BIN`。**改了 bootargs 必须重打**，因为 `petalinux-build` 不会自动做 ｜ §7.2 |

### H.7 排查时会遇到的其它词

| 术语 | 白话解释 ｜ 在本项目里的位置 |
|---|---|
| **`Waiting for root device`** | 内核说"我找不到根文件系统在哪"。常见原因是根设备名写错，或卡被枚举成别的名字 ｜ §12 |
| **`Kernel panic - not syncing: VFS: Unable to mount root fs`** | 内核找到了设备但上面没有可识别的文件系统 → 直接停机。本项目踩过两次，原因完全不同（一次是 bootargs 指向 `ram0`，一次是分区表被平移）｜ §12、附录 E #3 |
| **`root=` / `rootwait` / `rootfstype=`** | bootargs 里的三个参数：根在哪 / 等一下设备出现再找 / 文件系统是什么类型 ｜ §7.2 |
| **`uEnv.txt`** | U-Boot 会读的一个小配置文件，**可以覆盖 `BOOT.BIN` 里的 bootargs**。作为救急手段（不用重编镜像）｜ §12 |
| **`PermitRootLogin prohibit-password`** | sshd 的默认设置：root 只能凭密钥登录，密码被拒。**所以本项目用 `xilinx` 登录再 `sudo`** ｜ §11 |
| **`dmesg`** | 内核的日志缓冲区。排查驱动问题时第一眼看它 ｜ §11 多处 |
| **`df -h /` / `findmnt /`** | 看根分区还剩多少空间 / 看根分区到底挂的是哪个设备、什么文件系统 ｜ §10.6、§11 |
| **`--fixed-size` / `--align`** | `.wks` 里那两个参数：分区固定多大 / 起点怎么对齐。**`--align 4` 是 KiB 单位，所以 p2 落在 512 MiB + 8 扇区上** ｜ §9 的警示 |
