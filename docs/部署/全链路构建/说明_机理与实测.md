## 附录 C：为什么这样配（机制）

这一节解释"为什么"；操作步骤在上面各节。更深的论证分别在各工具自己的 README 里。

### C.1 XSA 为什么必须先补全 PS7

PS 里没使能的外设，PetaLinux 生成设备树时**连节点都不会有**。只配 DDR + UART 的 XSA
做出来的系统没有网口、没有 SD 卡、没有 QSPI，**镜像根本起不来**（U-Boot 拿不到 MMC）。

完整记录（26 个属性、两个顺序坑、逐节点证据）：[`deploy/xsa/README.md`](../../../deploy/xsa/README.md)。

### C.2 zocl 的 AIE 符号问题（自建路线唯一的实质风险）

XRT 2024.1 的 zocl 是针对内核 6.6 写的。打完 API 兼容补丁后全部 `.c` 能编译，
但 modpost 链接时报 **10 个 `aie_*` 符号未定义**。

**根因**：这些符号由内核 AI Engine 驱动导出，而 AIE 是 Versal 专属硬件，其 Kconfig 是
`depends on ARM64 || COMPILE_TEST` + `depends on ZYNQMP_FIRMWARE` —— Zynq-7000 是 **ARM32**，
两条都不满足。**6.6 的 Kconfig 限制完全相同，这不是 2025.2 引入的问题。**

**解法**：用 XRT 上游自己为非 PetaLinux 构建预留的 `__NONE_PETALINUX__` 开关，它让
`zocl_aie.c` 改用 `include/zocl_aie.h` 里的 `static inline` 空桩（内联进 `zocl.ko`，
不产生外部符号）。上游空桩清单漏了 2 个函数，补丁 `0002` 补齐；配方加一行
`EXTRA_OEMAKE += "cflags_zocl=-D__NONE_PETALINUX__"`。

完整记录（含验证命令、回退方法）：[`deploy/pynq/zocl-kernel-6.12/README.md`](../../../deploy/pynq/zocl-kernel-6.12/README.md)。

> **教训**：遇到"符号未定义"先找上游有没有预留开关，再考虑改代码。改代码之前把源码里
> 所有 `#ifdef` 和构建脚本读一遍。

### C.3 PYNQ 在 Zynq-7000 上靠什么跑（四个耦合点）

PYNQ v3.x 在 Zynq-7000 上是**混合方案**：**FPGA manager 配置器件 + `/dev/mem` 访问 PL 寄存器 +
XRT 分配内存**（`pynq.allocate()` → `pyxrt.bo()`）。**v2.7 起已无 CMA/xlnk 路径。**

四样东西必须同时对齐（**2026-10-06 首次上板实测后校正，第 2、4 条是那次才发现的**）：

| # | 耦合点 | 我们怎么满足 | 缺了的症状 |
|---|---|---|---|
| 1 | `zocl.ko`（绑内核 vermagic） | 第 6/7 节：用本工程的内核编 | `insmod` 报 `invalid module format` |
| 2 | **zocl 的 DRM fops 必须带 `FOP_UNSIGNED_OFFSET`（内核 ≥ 6.12）** | [`../../deploy/pynq/zocl-kernel-6.12/`](../../../deploy/pynq/zocl-kernel-6.12/README.md) 补丁 `0003` | 所有 `/dev/dri/*` 的 `open()` 返回 `EINVAL` → `xbutil examine` 显示 `0 devices found` → `pyxrt.device(0)` 报 `Could not open device with index '0'` → `pynq.allocate()` 报 `No Devices Found`。**四个报错看起来毫无关联，根因却是同一个标志位** |
| 3 | `pyxrt.so` / XRT 用户态（要同 XRT 版本） | AMD 包里预装的 2.17.0，与 zocl 同版本 | `import pyxrt` 失败 |
| 4 | **`XILINX_XRT` 环境变量**（**不是** `pynq_board`！） | [`../../deploy/pynq/build_pynq_rootfs.sh`](../../../deploy/pynq/build_pynq_rootfs.sh) 往 rootfs 里写 `/etc/profile.d/xrt_setup.sh` | `pl_server/__init__.py` 里那句 `if os.environ.get("XILINX_XRT", False)` 不成立 → `EmbeddedDevice` 压根不导入 → `Device.devices` 恒为 `[]` → allocate 警告 `No devices found, is the XRT environment sourced?` |

> **订正一处老说法**：本文早先写过"`pynq/ps.py` 用 `ON_TARGET` 判断是否在真板子上，
> 缺 `chosen/pynq_board` 会导致 `pyxrt` 不被 import"。**这在 PYNQ 3.1 里不成立** ——
> 整个 `pynq/` 包 grep `ON_TARGET` 零结果，那是更老版本 PYNQ 的机制。
> 3.1 的真正开关是第 4 条的 `XILINX_XRT`（见 `pl_server/__init__.py` 第 17 行）。
> `chosen/pynq_board` 仍然要补（PYNQ 靠它认板卡名、`AX7015B` 也是验收项 ③），
> 但它**不是** `import pyxrt` 的开关。

### C.4 宿主机不需要装 pynq / pyxrt

PetaLinux 构建用的是它**自带的 Python 3.12**，与系统 Python 3.10 完全隔离：

| | 系统 Python | PetaLinux 构建用 |
|---|---|---|
| 路径 | `/usr/bin/python3` | `/opt/pkg/petalinux/sysroots/x86_64-petalinux-linux/usr/bin/python3.12` |
| site-packages | `/usr/lib/python3/dist-packages` | `/opt/pkg/petalinux/sysroots/.../python3.12/site-packages` |

实测反证：完整跑过含内核、u-boot、zocl、wic 的构建，宿主机 `~/.local/lib/python3.10/site-packages/`
**一个文件都没变**。`pynq` / `pyxrt` 是给板子（ARM）用的。

### C.5 不要用 PYNQ-Z2 的官方镜像

镜像里的 `BOOT.BIN` 含 FSBL 的 **PS DDR 初始化参数**，按目标板 DDR 芯片写死。
PYNQ-Z2 是 512 MB/16-bit，AX7015B 是 **1 GB/32-bit** → DDR 初始化错误 → **连 U-Boot 都进不去**。
社区实证：一位 AX7020 用户"因为 SoC 相同"烧了 Z2 镜像，原话
**"my board doesn't even boot from it"**。

同理，**PYNQ v3.1 官方文档只声明在 2024.1 上测试过** —— 那是"他们测过的组合"，不是机制上的
硬要求。真正的限制写在 Kconfig 里（见 C.2），应该直接去读。

| 5 | SD 卡到底是 `mmcblk0` 还是 `mmcblk1`？ | 实测是 `mmcblk0`（eMMC 是 `mmcblk1`） | [第 4 节](流程_构建镜像.md#4-改工程配置)的 `SDROOT_DEV` **不用改**，[第 12 节](说明_故障排查.md#12-故障排查)的 `uEnv.txt` 兜底也用不上 |

| 7 | 验收第 6/7/8 项**同时**报红（`ModuleNotFoundError: No module named 'pydantic'`），看着像 pynq 装坏了 | **`sudo` 重置 PATH，把 PYNQ 的环境弄丢了**：PYNQ 的 python 和依赖都在虚拟环境 `/usr/local/share/pynq-venv`（靠 `/etc/profile.d/pynq_venv.sh` 激活），`XILINX_XRT` 靠 `/etc/profile.d/xrt_setup.sh` —— **这两样都只在登录 shell 生效** | 验收脚本已自带环境自愈（自己从这两个路径找回来）；详见[第 11 节](说明_板上验收.md#11-板上验收)那个警示框。⚠️ 别把它当成板子故障去修 rootfs |

### E.2 还没解决的问题

| # | 问题 | 影响 | 怎么解 |
|---|---|---|---|
| 1 | ~~SD 卡是 `mmcblk0` 还是 `mmcblk1`？~~ **2026-10-06 实测：`mmcblk0`** | ~~决定 `SDROOT_DEV` 要不要改~~ **不用改** | 根就是 `/dev/mmcblk0p2`，eMMC 是 `mmcblk1` |
| 2 | ~~PHY 复位 MIO7 的实际电平行为~~ **实测：不是复位问题** | — | 板子能正常读到 PHY 的 ID（`0x00221622`，KSZ9031 族）和完整能力（10/100/1000），说明 PHY 没被按在复位里。**但内核确实从不驱动这根线**（`enet-reset` 内核不认），属于"能跑、但没有兜底手段" |
| 3 | ~~`phy-mode` 该用 `rgmii-id` 还是 `rgmii`~~ **实测：千兆握不上手，降到 100M 就通** | ⚠️ **目前链路只能跑 100M** | 现象：板子 `carrier=0`、宿主机也 `carrier=0`；在板上执行 `ethtool -s eth0 autoneg on advertise 0x00f`（只广告 10/100）后**两边立刻 `carrier=1`，100Mb/s Full**（操作步骤见 10.5.1）。千兆失败的原因：这颗 KSZ9031 族 PHY 的 RGMII 时序参数（pad skew）需要专用驱动来配，而内核里 `CONFIG_MICREL_PHY` **没编**，现在用的是通用驱动 → **待查**。M−1 阶段先跑 100M，不影响验收。⚠️ **2026-10-06 复测补充（推翻了一部分）**：板子冷启动时，宿主机**一度真的看到了 `carrier=1` + `speed=1000Mb/s Full`**，随后才被板上那条"只广告 10/100"的 `ethtool` 配置降成 100M。也就是说"千兆完全握不上手"这个结论**不牢靠** —— 那次失败可能是线材/对端网卡/USB 网卡当时的接口状态导致的。需要单独复现：把板上的 `advertise 0x00f` 去掉，在两端都确认 `1000Mb/s Full` 的情况下做实测（大包 + 校验比对），才能给这颗 PHY 的 RGMII 时序下定论 |
| 4 | 赛事口径：预编译的 Ubuntu 根文件系统算不算合规 | 影响交付方式 | 问组织方 |
| 5 | XC7Z015 只有 160 DSP / 3.3 Mb BRAM | PYNQ 基础 overlay 可能资源不够 | M−1 用最小测试 overlay，不用 base overlay（而"第一个 overlay"正是 ⑧⑩ 两项转绿的前提） |
| 6 | **根文件系统只有 8 GiB，20 GB 用不上** | 影响板上可用磁盘空间（Jupyter notebook 与中间文件都落在根分区） | 根因：制卡用的 `mke2fs` 1.47.0 默认打开 `orphan_file`，板上 `e2fsprogs` 1.46.5 不认识 → `resize2fs` 在特性检查那步罢工。**临时（已生效）**：用构建产物里同版本的 1.47.0 工具在电脑上扩（[第 12 节](说明_故障排查.md#12-故障排查)对应那一行）—— 2026-10-06 已把那张卡扩到 28.6 GiB。**根治（待做）**：改 `.wks` 让 `mke2fs` 不开这个特性 —— 需先确认 wic 的 `part` 是否支持传 mkfs 参数；不做的话**每张新卡都得手工补这一步** |

| 8 | 宿主机上没有 `ethtool`（板子上有） | 排查千兆/百兆协商时看不到速率细节 | 需要一个就 `sudo apt install -y ethtool`；不装也能用 `/sys/class/net/<网口名>/carrier` 判断通断 |

## 附录 F：为什么走"2025.2 自建"这条路线

赛事要求工具链 **≥ 2025.2**，这一条直接废掉了"退回 2024.1 走 PYNQ 官方 sdbuild"的路线。
所以路线收敛成了一条：**在现有 2025.2 PetaLinux 工程里移植 PYNQ 需要的组件**。

| # | 路线 | 可行性 | 说明 |
|---|---|---|---|
| **A** | **2025.2 + 移植 PYNQ 组件**（本文） | ✅ **已跑通** | zocl 自己编、pyxrt 用 AMD 包里的、设备树自己补。唯一有实质风险的一环（AIE 符号）已解决，见附录 C.2 |
| B | 官方 sdbuild + 装 2024.1 工具链 | ❌ 违反赛事约束 | 官方唯一"声明支持"的路径，但版本不合规，且要额外装 100+ GB |
| C | 换 BOOT.BIN 保留 PYNQ-Z2 rootfs | ❌ 不推荐 | v2.7/v3.x 无成功先例；且 Z2 镜像是 2024.1 编的，口径也不合规。DDR 参数还会让板子起不来（附录 C.5） |
| D | 用 meta-xilinx 自带的 zocl/xrt recipe | ❌ 不可行 | `COMPATIBLE_MACHINE` 不含 `zynq`（202310/202320/202410/202420/202510/202520 逐版本核对），必然被跳过 |
| E | 直接烧 ALINX 给的现成镜像 | ⚠️ 仅作参考 | ALINX 生态做过 Zynq-7000 的 PYNQ（AX7020），但**没有 AX7015B**；且现成镜像未必是 ≥2025.2 编的。**向 ALINX 要板级源文件（设备树、`.spec`、tcl）比自己烧镜像有价值** |
