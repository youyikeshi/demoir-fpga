# 板端"系统被写坏"的真相：PL 越界写踩烂了内核内存

> **性质**：事故定案与移交说明（2026-11-01 定稿）
> **一句话结论**：**SD 卡没坏、文件系统没坏、DDR 没坏、系统镜像没坏。是 PL 引擎的越界写把内核内存踩了——金丝雀从头到尾都是对的，我先后四次误判。**
> **板卡**：ALINX AX7015B（XC7Z015，ARM32）
> **配套工具**：`tools/board_memtest.py`、`tools/board_memtest.sh`、`tools/boardlock.sh`、`tools/archive_build.sh`、`tools/board_bootstrap.sh`

---

## 0. 一页看懂：所有症状与唯一原因

| 观察到的现象 | 真实原因 | 我曾误判为 |
|---|---|---|
| `sudo -S -p "" true` → **段错误 rc=139** | sudo 的**代码页**被踩烂 | "SD 卡写满" |
| `find`、`python3` 随机段错误 | 同上 | "板端源码陈旧" |
| `ValueError: bad marshal data` | `.pyc` 的**页缓存**被改写 | 同上 |
| `inspect.py` 第 1577 行出现 `0xf2` 垃圾字节 | 源文件的**页缓存**被改写 | "SD 卡坏块" |
| 同一文件两次 md5 不同，`drop_caches` 后又变对 | **页缓存被改写**（磁盘内容一直是对的） | "磁盘坏了" |
| `bin_unit OUT: 金丝雀被写坏 4096/4096` | **引擎真的写出缓冲区之外** | "环境坏了导致的误报" |
| 跑整网 **23 秒后失联、ping 100% 丢包** | 越界写踩到内核关键结构 ⇒ 硬挂 | "并发调度把板子打挂" |
| 重启后"依旧" | 被踩坏的页缓存在**同一个 boot 内**不会自愈 | "持久性磁盘损坏" |

**一条原因解释全部现象：PL 的 DMA 写到了不该写的物理地址。**

## 1. 决定性实验：三态对照

用 `tools/board_memtest.sh`，在**同一块板、同一个 boot**里测三种状态。每态 8 轮，每轮 256 MB RAM 图案校验 + 10 个文件热读/冷读双校验。

| 状态 | RAM 图案 | 文件热读/冷读 | 整网 | 板子 |
|---|---|---|---|---|
| **未加载 PL**（`fpga0=unknown`） | 8×256 MB 全过 | 全一致 | — | 正常 |
| **PL 已加载、空闲**（`fpga0=operating`，不跑网络） | 8×256 MB 全过 | 全一致 | — | 正常 |
| **PL 已加载 → 跑整网** | 来不及 | 来不及 | 第 23 秒失联 | **硬挂** |

- 前两态各 8 轮、**零失败** ⇒ DDR 与 SD 卡都是好的。
- 只有当"引擎真的搬数据"时才出事 ⇒ 问题在 PL 的写通路。

**这是整晚最有力的一次测量**：它把"硬件坏"与"软件坏"一次分开。

## 2. 判决实验：v39 与 v40 的 A/B

板子重启到干净状态后，同一个 `board_v39_verify.py`、同一套参数（150 MHz / 16 槽 / reps 1）：

| 位流 | 结果 | sha1 |
|---|---|---|
| **v39** | **RC=0，板子活着** | `net256`：`9b1940c8/f86a7035/025757a8` **OK/3**<br>`net64`：`bfa246d3/226bd39e/762d84b9` **OK/3** |
| **v40** | **23 秒后硬挂**（`ping` 100% 丢包） | 跑不完，无输出 |

- **v39 可用；v40 是真实的功能回归。**
- v40 相对 v39 只差三样：刀7（`rem` / `sw_act_q`）、诚实时钟约束（`10.000` → `6.667` ns）、以及**零效果**的 `max_fanout`。
- 而 xsim 上 106 条命令逐拍等价、总拍数 $7{,}244{,}033$ 不变 ⇒ **仿真没覆盖到硬件上的失效模式**。

## 3. 为什么"仿真等价"却"硬件崩"——最该带走的一条

两者用同一份 6.667 ns 约束：

| 指标 | v39 | v40 |
|---|---|---|
| WNS | $-5.331$ | $-2.138$（好 3.19 ns） |
| TNS | $-47{,}312$ | $-818.7$（好 98.3%） |
| setup 违例端点 | 20,706 | 2,363 |
| **违例起点的性质** | 使能锥（三个准静态寄存器占 55.7%） | **真实数据通路**：`linecache win_q/CLKBWRCLK → u_eng/s1_pc_q/D`，8.671 ns / 10 级 |
| 硬件表现 | 可跑 | **崩** |

解释：

- v39 的违例集中在**几乎不翻转的寄存器的 CE 引脚**上，是"准静态"违例，实际不致死。
- v40 把那些修掉了，但最差路径换成了**真在搬数据的一级**，违例直接变成错数据 ⇒ 引擎算出越界地址 ⇒ 写出缓冲区。

**新判定准则（比任何一次优化都重要）：**

> "WNS 更好 / TNS 更小 / 违例更少"**不能**推出"能上板"。
> 上板门槛应是 **WNS ≥ 0**，或**逐端点证明所有违例都落在准静态寄存器的 CE 引脚上**。
> 检查方法：`report_timing -max_paths N`，看 `END POINT PIN TYPE` 与起点是否准静态。

## 4. 我犯的四个错误（含判据，供后来者对照）

| # | 错误结论 | 当时的"证据" | 为什么错 | 正确做法 |
|---|---|---|---|---|
| 1 | "SD 卡被 core dump 写满" | 会话挂住、`scp` 报成功但文件不在 | 从未在板上读过一次 `df` | 先 `df -h /` 与 `df -i /` 再谈磁盘 |
| 2 | "板端源码陈旧导致 segfault" | md5 与主机不一致 | 源码确实旧，但那是**页缓存被踩之后**的表现 | 先 `drop_caches` 再比 md5 |
| 3 | "SD 卡坏块" | 板上读到 `fe 7f 10 00 …` 重复图案 | 我把卡插到宿主机读，ELF 头全是对的 | 跨设备交叉取证 |
| 4 | "金丝雀失败是环境噪声" | 同一失败在"坏环境"里出现过 | **金丝雀就是越界写探测器，它一次都没误报** | 金丝雀报警 ⇒ 立刻停手查 OOB，不许解释掉 |

四次误判的共同毛病：**用间接症状推断，没有直接取证。**
而唯一一次正确的判断（"`tbuf_rdata` 缺 `ce` 门控"）之所以对，是因为它来自**读代码 + 定向实验**。

## 5. 澄清：不是"我写的脚本把板子搞坏"

| 被怀疑的对象 | 真相 |
|---|---|
| `tools/boardlock.sh` 的 ssh 限速闸门 | 它是**防止**重试风暴的闸门，不是原因 |
| 我写的重试循环（3 / 10 / 24 次） | 确实会打满 sshd 的 `MaxStartups 10:30:100`，表现成"连上但拿不到 banner"——**这是真实操作失误**，但它只造成"连不上"，不会改变文件内容 |
| `tools/board_memtest.py` | 它只是测量工具；三态对照正是靠它做的 |
| 镜像构建的三个脚本 | 与板端故障无关（那是另一个独立问题：构建根放在 NTFS 上） |

唯一真实的"我搞坏板子"的一次是：**两次硬断电发生在系统写盘时**，让 ext4 走了 journal recovery。
但即使那一次，盘上文件内容也没坏（见 §4 第 3 条）。

## 7. 板端操作纪律（新增，必须遵守）

### 7.1 每次上板前先做四条（十秒，能分清"我代码错"还是"系统坏"）

```
df -h /                                 # 空间
df -i /                                 # inode
sudo true                               # rc 必须为 0
python3 -c "from pynq import Overlay"    # PYNQ 能否导入
```

### 7.2 判定"文件内容异常"的唯一正确姿势

```
sync; echo 3 > /proc/sys/vm/drop_caches
md5sum <文件>
```

- 清缓存后**变对** ⇒ 页缓存被改写，是**内存被踩**（查 PL / 驱动）。
- 清缓存后**仍错** ⇒ 磁盘内容真的坏（换卡 / 重刷）。

### 7.3 跑网络的铁律

- **金丝雀不能关**：它是唯一能抓住越界写的机制。
- 任何新位流第一次跑网络，**先跑 64²**（小批次，踩坏范围小）。
- 跑之前记下 3~4 个关键文件的 md5，跑完复比。
- 一旦挂机：**立刻断电重启**，不要在挂掉的状态上继续测。

### 7.4 不许做的事

- 不许对板子做 **ssh 重试风暴**：`MaxStartups 10:30:100` 会被打满，症状是"`ping` 通但 `ssh` 无 banner"。
- 不许 `pkill -f`：今晚它三次匹配到我自己的命令行，自杀三次。
- 不许 `kill -9` PYNQ；不许 `kill` 看门狗。
- 断电前必须 `sync; sync`。

## 9. 下一步（按优先级）

1. **保底**：继续用 **v39**（8.096 s @150 MHz，sha1 已验证），把已验证的优化（interp C 内核，整网 −1.75 s）落到它上面。
2. **修 v40**：给 `linecache win_q` 加 BRAM 输出寄存器，打断那条 8.671 ns / 10 级的路径。代价是读路径多一拍，**必须验拍数 parity**；该模块已有 `desc_rd_q` 的先例（v38 的 Fix A），手法可复用。
3. **目标**：WNS ≥ 0，或"全部违例落在准静态 CE 引脚"，才允许上板。
4. **板端**：任何新位流先跑 64² + 金丝雀 + md5 前后对比。

> **给下一个人一句话**：别信"时序数字变好了"，也别解释掉金丝雀。
> 先 `drop_caches` 再比文件，先三态对照再谈硬件，先 64² 再跑整网。
