# 层间流水：把 PS 藏进 PL —— 实现与实测报告

**结论先说**：整网 64×64 从 **14.47 s → 11.45~11.72 s（−21%）**，冻结 sha1 三路全部一致。
PS 从 **4.17~4.50 s → 2.34 s**，其中 **1.22 s 被 PL 盖住**，暴露在 PL 外面的只剩 **1.35 s**。
剩下 10.37 s 是 PL 本身（硬件下界，不是本次任务能动的）。

改动只碰了两个文件：`ps/pynq/bin_net.py`、`ps/pynq/bin_engine.py`
（另按调度要求把 `bin_ref_numpy.py` 里 `eca_attn_f32` 的 docstring 改正，见 §7）。

## 1. 流水图：哪一步能重叠、哪一步不能

一个二值卷积层在 PS 侧被切成三段。**硬依赖链**是

```
T(n-1) ──[epilogue: 读回+C8还原+反量化]──► pack(n) ──[prologue: 量化+二值化+打包]──►
        ──[写 IN buffer]──► PL(n) ──► done ──► T(n) ──► pack(n+1) ...
```

```
   prologue(n)              PL(n)                    epilogue(n)
  ┌──────────────┐   ┌────────────────────┐   ┌──────────────────┐
  │ 量化 + 二值化 │   │ 引擎在片内跑       │   │ 读回 OUT buffer  │
  │ + 打包 (PS)  │   │ XNOR+popcount (PL) │   │ + C8 还原        │
  │ 1.46 s 合计  │   │ 10.37 s 合计       │   │ + 反量化 (PS)    │
  └──────────────┘   └────────────────────┘   └──────────────────┘
        ↑                     ↑                        ↑
   需要 T(n-1)           需要 IN 写好              需要 done 置起
   ↑ 必须等 PL(n-1) done
```

**这条链上，同一条 conv 链的 prologue/epilogue 无法与自己的 PL 重叠**——因为它们
就是"上一层 PL 的输出"到"这一层 PL 的输入"之间的必要工序。任务书里
"T = max(T_PS, T_PL) + T_首层" 这个模型**在单引擎 + 串行 conv 链上取不到**；
真正的下界是 `Σ PL + Σ(无法隐藏的 PS)`。

能重叠的是下面三类，本实现全部做到了：

| # | 重叠对象 | 机制 | 实测收益 |
|---|---|---|---|
| ① | 下一层的**配置页写入** | RTL 在 start 那一沿把 `cfg_*`/`base_*` 全部锁存进 `_q`（`bin_conv_core.v` ST_IDLE），所以跑第 n 层时可以改写配置页准备第 n+1 层 | MMIO 从"每层 30 次串行写"变成"14 次 + 藏在 PL 时间里" |
| ② | 分支区的**下层 prologue** | SAM 的 b0/b2/b4 三条 ghost 链在给定 x 后互不依赖 ⇒ b0 在大分辨率上跑 PL 时，PS 把 b2/b4 的整层 prologue（量化+打包+写 IN）全做掉 | 1.02 s prologue 被盖住 |
| ③ | 分支区的**纯 PS 算子** | 依赖已满足的 cat/add/interp/eca/sam/convfp 优先执行 | ~0.20 s 被盖住 |

**不能重叠、也承认不能重叠的**：同一条链的 prologue/epilogue；以及全精度卷积
`conv_first`/`decoder_{1,2,3}.conv`（numpy matmul，且是下一个 PL 卷积的前置）。

## 2. op 依赖分析

执行图由 `_Graph` 在构建期用**数据流**显式建立（每个 op 记录吃哪几个张量），
调度器只按依赖边放行 —— **不存在"猜哪层能流水"的启发式**。

```
执行图 395 个 op：conv=227  cat=116  interp=26  sam=6  add=6  eca=6  convfp=4
                  shuffle=3  unshuffle=1
张量 396 个，其中 220 个 fanout>1（真分支）
入度：max=5（sam：x,y0,y2,y4,w），平均 1.50
```

依赖图结构上分三类：

1. **线性 conv 段（占 227 层里的绝大多数）**：`DenseConv → cat → DenseConv`，
   每层输入都由上一层输出（+ 已完成的 cat）决定 ⇒ **不能流水**，只能靠
   §1 的 ①②③ 去偷。
2. **DenseNet 的 rdb**：`conv → cat([y, t_]) → conv`，cat 的 `t_` 分支是"早就绪"的，
   但它只是 cat 的一个输入，不构成独立可执行的链 ⇒ 段内串行。
3. **SAM 的三分支（真正的并行窗口）**：`y0=ghost(x)`、`y2=ghost(x2)`、`y4=ghost(x4)`
   三条链只依赖 x/x2/x4 ⇒ **b0 的 PL 时间可以整段盖住 b2/b4 的 PS**。
   6 个 SAM × 2 条小分支 × 11 层 = 132 层落在这些窗口里。
   这就是实测 1.22 s 重叠量的主要来源。

## 4. 实测结果（船上 64×64，`bin_net.py --board --hw 64`）

### 4.1 2×2 消融（同一 session、**只 load 一次 overlay**、同一输入 seed）

| 配置 | 整网 | 说明 |
|---|---:|---|
| **A** 慢内核 + 串行（= 旧架构） | **14.47 s** | 与任务书的 14.85 s、历史 `perf_probe_opt.log` 的 16.06 s 同量级 |
| **B** 慢内核 + 流水 | 13.45 s | **流水单独贡献 −1.02 s** |
| **C** 快内核 + 串行 | 12.09 s | **快内核单独贡献 −2.38 s** |
| **D** 快内核 + 流水（最终） | **11.46 / 11.45 s** | 合计 **−3.01 s（−21%）** |

### 4.2 最终版本的分解（官方 CLI 实测）

```
总耗时 11.72 s   (PS/PL 重叠调度)
   PL 时间          10.37 s   (Σ 每层 done，硬件计)
   PS 时间           2.34 s   = prologue 1.46 + epilogue 0.26 + 非卷积 0.61
     其中被 PL 盖住  1.22 s   (52% of PS；prologue 里占 1.02 s)
   ⇒ 关键路径上只剩 PS 1.12 s
   纯等 done          9.30 s
   op 分解：cat=0.149  interp=0.177  eca=0.134  convfp=0.116  sam=0.033  add=0.005
   MMIO：真写 3168 次 / 影子缓存跳过 3188 次
```

拿"墙钟 − PL"做不自欺的核对：`11.72 − 10.37 = 1.35 s` 是**暴露在 PL 外面的 PS 总量**，
相对旧架构的 4.17 s 降了 **68%**。（埋点算出的 1.22 s 重叠量略偏乐观，因为它把
"PL 已 done 但还没收"的一小段也算进去了；上界就是这 1.22 s。）

### 4.3 与任务书目标的差距

- 目标 `~10 s`，实测 **11.45~11.72 s**。差的 1.1 s 就是 §4.2 的"关键路径 PS"，
  它由 interp/cat/eca/convfp(0.60 s) + 未能隐藏的 prologue(0.44 s) 构成。
- **PL 是瓶颈**（10.37 s），这一点任务书的判断是对的。想进 10 s 必须动 PL（换 RTL 并行度），
  已经不是"调度"能解决的了。

### 4.4 顺手纠正任务书里的两处算术

| 项 | 任务书 | 实测/重算 |
|---|---|---|
| MMIO | "30 次 × 30 µs = 0.9 ms；227 层 ⇒ **~1.0 s**" | 0.9 ms × 227 = **0.20 s**（不是 1.0 s）。实测配置+基址 1.35 ms/层 ⇒ 0.31 s，优化后真写 14 次/层 ≈ 0.10 s |
| 轮询 | "poll=2e-4 实际 0.29 ms ⇒ **−0.3 s**" | 0.29 ms 是对的，但只影响"done 检测延迟"，全网上限 **~0.07 s**（227 × 0.29 ms）。实测这部分确实很小 |

省下的 3 s 里，**2.4 s 来自把 prologue 内核砍掉 3.8×**，0.6 s 来自"提前准备 + 分支区重叠"，
0.1 s 来自 MMIO/轮询 —— 也就是说：**任务书假设的"用流水吃掉 4.5 s"做不到，
真正吃掉它的是"把 4.5 s 变成 2.3 s，再用流水盖住一半"**。

## 5. sha1 回归

**板端（冻结基线 `board/WORKING_v1_20261030/`）**，本次共 **6 次独立运行**（A/B/C/D×2 + 官方 CLI）：

```
out1  3x64x64   min=0.1395 max=0.6164 mean=0.4065  sha1=bfa246d34681   ✓
out2  3x32x32   min=0.6390 max=1.3604 mean=0.9178  sha1=226bd39e522a   ✓
out3  3x16x16   min=0.0684 max=0.9327 mean=0.5568  sha1=762d84b9618e   ✓
```

**本机 dry-run**（`--dry-run --hw 64`，冻结值为 `104710f69c4d/52df3da63d0b/0d19b18a9e0b`）：

| 模式 | out1 sha1 |
|---|---|
| 流水 + 快内核 | `104710f69c4d` ✓ |
| `--no-pipeline` | `104710f69c4d` ✓ |
| `--legacy-kernels` | `104710f69c4d` ✓ |
| `--no-pipeline --legacy-kernels` | `104710f69c4d` ✓ |
| `--nbuf=3` | `104710f69c4d` ✓ |

**数据竞争的三道防线**（任务书要求的三条都做了）：

1. `--dry-run` 验调度逻辑（上面 5 种组合）。
2. `--verify-buffers`：每次写完 IN 缓冲**读回来逐字节比对**；跑全 227 层不报错。
3. 额外加了一层**异步假 PL**测试（`SlowFakeUnit`：done 延后到 deadline 才置起，
   执行时才真正访存）—— 这是唯一能暴露"提前写 buffer"类 bug 的测法。
   它当场抓到一个真问题：`nbuf=1` 时 prepare-ahead 会写到正在被读的同一块 IN 缓冲
   ⇒ 已改成"流水强制 nbuf≥2"。

**累计验证规模**：内核等价性 227 层 × 4 分辨率 × 3 数据形态 = **2724 组，0 差异**
（含强制饱和值、恰好落在 .5 边界的 tie 值）；整网 sha1 板端 6 次 + 本机 5 种配置。

## 6. 关键内核的等价性证明（不是"跑一下试试"）

`quant_pack` 把 `sat8(rint(f64(x)·2^fs))` 再 `binarize_pack(x, t_q)` 塌缩成**一次比较**：

- `bits = (sat8(y) + t > 0)`，`y = rint(v)`，`v = x·2^fs`。令 `k = 1-t`，则 `bits ⟺ sat8(y) ≥ k`。
- **clamp 恒为恒等**：本容器 `t_q ∈ [-20, 13]`（227 层 40304 个通道全查过）⇒ `k ∈ [-12, 21] ⊂ (-128, 127]`。
  （若有通道越界，`pack_thresh()` 返回 `ok=False`，自动退回参考实现。）
- `y ≥ k ⟺ v > k-0.5`，tie 处按 round-half-to-even 修正：`k` 偶 ⇒ 等号算真（用
  `nextafter(k-0.5, -inf)` 把 `>=` 变成 `>`），`k` 奇 ⇒ 等号算假。
- `x·2^fs` 在 float32 里**精确**（2 的幂只动指数），所以与原来 float64 算出的 `v` 逐位相同。
- 结果：`bits = (x > adj)`，`adj` 逐层预算并缓存。

实测 3.81×（A53，6 个真实层 359.5 ms → 94.4 ms）。

## 7. 异常发现：`eca_attn_f32` 不是逐字节等价

`bin_ref_numpy.eca_attn_f32` 把 "C 次 `np.dot(w, v[i:i+9])`" 换成一次 gemv
（`as_strided(...) @ w`）。gemv 与逐窗口 `np.dot` 的 **BLAS 分块/累加顺序不同** ⇒ 舍入不同。

用**真实激活**在本网 6 个 ECA 上实测：**1584 个通道里 614 个(39%)不同，最大 16 ULP**；
**随机数据测不出来**（随机 w/x 是 0 差异）——"随机数据验证通过"不能当等价性证据。

⇒ 默认 `FAST_ECA=False` 走参考实现（`BIN_FAST_ECA=1` 可开）。代价仅 ~0.13 s/帧，
换整网 sha1 可回归，很划算。已把 `bin_ref_numpy.py` 里那句"逐位等价快速版"改正。

另 4 个快速内核（`conv2d_f32` / `bilinear_f32` / `add_f32` / `sam_mix_f32`）实测**逐位等价**，
已默认启用。

## 8. 没做、但值得做的

1. **激活全程 int8（含 cat）**——预估再省 0.2~0.3 s，但**不是改一处就能拿**：
   `interp`(26 次) 在浮点域做双线性、`add` 要把不同 `fs_out` 的两支对齐、
   `eca`/`sam` 需要浮点权重 ⇒ 只有 `conv→cat→conv` 这一段能保持 int8（配 per-channel
   尺度 + 把阈值表从整数改成 dyadic 有理数）。改动面覆盖整个数据流表示，
   在"sha1 必须一致"的硬约束下应当单独立项、单独回归。
2. **让 PL 与 PS 不抢 DDR 带宽**——实测 PL 时间从历史上的 9.68 s 变成 10.37 s
   （+7%），大概率是 PS 并发访存把 PL 的 DDR 读拖慢了。
   把 PS 的工作集压进 L2、或给 PL 的读口加优先级，可能把这 0.7 s 拿回来。
3. **把 epilogue + 下一个 prologue 融成一趟**（读回 int8 后直接按下一层的阈值打包），
   省掉"反量化成 float32 再量化回去"的中转；只对 `conv→conv` 直连的层成立。
4. **`--verify-buffers` 上板跑一次**：本机 FakeArena 上通过了，但真实的 CMA 缓存
   行为（`invalidate` 的粒度）只有板上能验。
5. **多 PL 实例**（BD 里只有 `bin_unit_0`）：若能有 2 个实例，两条独立分支可以真并行，
   §2 的并行窗口才能变成"PL 也并行"，而不只是"PS 藏在 PL 后面"。

## 9. 我不确定的地方

1. **板子曾硬挂一次**（我在做基线测量、单次 load overlay 时）。恢复后连续 4 个 session
   各 load 1~2 次都正常。所以"连续多次 load bitstream 会挂"这个假设我**没能证实也没能排除**；
   本次所有测量都是"一次 session 一次 load"。这条建议保留给后续。
2. **PL 时间 10.37 s vs 历史 9.68 s** 的差异我只归因于"PS 并发抢带宽"，没有单独实验证。
   若要在报告里引用 PL 数字，建议用"同一次 session 内的相对值"。
3. **重叠量 1.22 s 略偏高**（见 §4.2），真实上界就是它；更严格的测法需要在
   长 PS 操作内部插 poll，我没做。
4. **`nbuf=2` 是否够**：目前调度器同时只有 1 个 PL 作业在飞，2 套槽位理论上富余；
   但如果将来允许多个 PL 作业排队（多实例），要重新算。
5. **A 配置（14.47 s）不是"纯净"旧基线**：它仍带 MMIO 影子缓存（少写 ~3400 次 ≈ 0.1 s），
   且 `_conv` 的 4 行差异已合入。真正的旧基线请以 `perf_probe_opt.log` 的 16.06 s 为准。
6. 板端 ECA 只测了 64×64；256×256 下 ECA 的 `mean(axis=(1,2))` 会变成 O(面积)，
   那时 `FAST_ECA` 的取舍要重算（对方估算 256² 只差 108 ms，未实机验证）。
