# bin_catpack 上板报告（PS 驱动 + 功能 + 读带宽）

日期：2026-10-31　板卡：Pynq-Z2（xc7z015）　比特流：`design_1_150v33.bit`（**未重新 load**）
fclk0：100 MHz　看门狗：已 arm（未触发）　驱动：`ps/pynq/catpack.py`（新增）

---

## 0. 一句话结论

**catpack 能跑、逐字节全对，但它不是 1 GB/s，也不是 305 MB/s：**

| 规模 | PL 读带宽（f32 有用字节） | 拍/字 |
|---|---|---|
| H×W ≤ 576（本网 64² 的层） | **285–366 MB/s**（≈ E1E2 的 305 MB/s） | 83–84 |
| H×W ≥ 1024（本网 256² 的层） | **90–142 MB/s**（比 E1E2 慢 2–3×） | 252–269 |

- 305 MB/s 与 1 GB/s 的差别**没有出现**：catpack 在"小层"与 E1E2 同档（0.38 读拍/拍），
  在"大层"反而掉 3 倍 —— **平面 f32 布局对共享线缓存不友好**（机理见 §6，不是噪声）。
- 端到端也不赚：64² 把 PS 路径换成 catpack 后 **2.69 s → 3.07 s（+0.38 s，
  池命中 227/227 的最好情况也一样）**；256² **15.94 s → 16.34 s（+0.4 s）**。
  函数正确（sha1 完全相同），但本版本**不该开**。
- 真正吃掉 72 s 的是 **E1E2 的 PS `quantize_int8`**，不是"PL 读得慢"。
  正确的下一步是**让 E1E2 直接读 conv 的 int8 C8 输出**，而不是让 catpack 读 f32。

## 2. 交付物

### 2.1 `ps/pynq/catpack.py`（新）

```python
from catpack import CatPackEngine
cp = CatPackEngine(engine, fclk_mhz=100)   # engine = BinConvEngine
cp.probe()                                  # 写 R_RUN_UNIT=5 读回 5，写 0 读回 0

# 单源（= 取代 E1E2 的用法：f32 → 1bit，不需要 PS 量化）
res = cp.pack_tensor(x_f32, adj)            # (u8, cin, H, W, cb) 或 None
# 多源（cat 的各段）
res = cp.pack_tensors([x0, x1, x2], adj)    # 任何一段拿不到 pa ⇒ 返回 None
# 底层的 [(pa, C, H, W)] 形式
res = cp.pack_segments(segs, adj)
```

- `config(c,h,w,base_desc,base_out)` → 0x18/0x20/0x28/0x204/0x208/0x210
- `start()` / `wait_done()`；**每次 start 前先 `_wait_idle()`**（RTL 在 `run_active`
  期间丢弃 AP_CTRL 写，不排队）；同一 job 内后续组复用"上一组已 done"的前提省掉这次读。
- 描述符：`build_desc()` 逐通道展开 `{adj[63:32], src_pa[31:0]}`，段边界任意、不限段数，
  表按 64 通道补齐（RTL 不会读越界项）。
- **拿不到 pa ⇒ 返回 None**（宿主内存 / 不连续 / 非 f32），绝不伪造输出。
- 源 flush：`pack_tensors()` 对每个叶子调 `f32_flush()`（只 flush 它那个槽）。
- `stats()`：优先用 DBG 拍数，否则用墙钟；本比特流走墙钟（见 §3.3）。
- `dbg_reads=False`（默认）：v33 的 DBG 不统计 catpack，5 次 MMIO 读 = 0.16 ms/组，白花。

### 2.2 接入开关（默认关）

- `bin_engine.BinConvEngine.pack_input()`：`CATPACK=1` 时**先试** catpack（f32 直读），
  拿不到 pa 再走 E1E2 / 原 PS 路径。`enable_catpack()/disable_catpack()` 显式挂/摘。
- `bin_net`：`CATPACK=1` 时 cat 变**惰性**（`_CatLazy`，只记叶子，不 `np.concatenate`），
  由下一层 conv 的 `prepare()` 直接建描述符交给 PL；任何一段没有 pa 就当场物化回落。
- 未设 `CATPACK` ⇒ 一个字节都不多走。回归：
  - `bin_engine.py --selftest`：全过
  - `catpack.py --selftest`：全过（含 64/544 通道、尾块、1–11 段、宿主回落、护栏）
  - `bin_net.py --dry-run --hw 256`：`392d1ae02761 / 7f68fb00d2b5 / aa03751a2d1c` **不变**
  - `bin_net.py --dry-run --hw 64`：`104710f69c4d / 2ac6efec2325 / 8ab595fcf7cd` **不变**

## 3. RTL 契约核对：三个**新发现**（都会影响别的驱动/后续 RTL）

### 3.1 ⚠ `H*W` 必须是偶数，否则逐字节全错（已在驱动里硬拒）

读口是 **64-bit 整字**：wrapper 用 `u_rd_addr[31:3]` 取字，**低 3 位直接丢弃**。
逐通道源地址 = `pa + c*H*W*4`，只有 `H*W` 偶数时全部 8 字节对齐。

板上实测（cin=64/544）：

| 形状 | hw | 差异 |
|---|---|---|
| 5×7 | 35（奇） | **全部字都不同**（每次读偏 4 B） |
| 5×8 / 4×9 / 7×8 | 40/36/56 | 0 |
| 24×24 | 576 | 0 |

⇒ `build_desc()` 对奇数 `H*W` 直接 `ValueError`。本网所有层 8²…256² 都满足，但
**"段边界任意"只在 H*W 偶数时成立**（每个段的 pa 仍需 8 B 对齐）。

### 3.2 尾 tile 会**多写**最多 15 个输出字（内容恒 0）

`bin_catpack.v` 的 `ST_FLUSH` 固定 `wp=0..15`：最后一个 tile 即使只有 3 个像素，
也会写满 16 个字 ⇒ 每个 group 的输出块后最多多写 15 字（120 B），值恒 0。
中间 group 的这段会被下一组覆盖；**最后一组**会写到输出区之后。

⇒ 驱动在 out 区后固定留 **128 B slack**（再往后才是金丝雀），并把 slack 预填 `0x5A`、
跑完检查"被写到的部分是否全 0"。板上 `tail_zeroed=True`，与 RTL 推断一致。

### 3.3 ⚠ 本比特流的 DBG_E（0x230..0x240）**不统计 catpack**

同一比特流上 E1E2 的 DBG 有数（`e1e2_bench.json`：rd_words/cyc 非 0），
catpack 跑完读 0x230..0x240 **全 0** ⇒ v33 的 `cnt_e_rd` 接的是 E1E2 的读使能
（`pl/rtl_hand/modules/bin_unit_axi_wrap.v` 当前 master 已改成 `u_rd_en`，但 v33 不是）。
所以**读带宽全部用时间反推**（下一节），驱动也不默认读 DBG。

## 5. 读带宽（cin=544，单源，f32 有用字节 / PL 时间）

### 5.1 任务要求的四档

| 档 | bytes | PL 时间 | **MB/s** | 拍/字 | job 墙钟 | job MB/s |
|---|---|---|---|---|---|---|
| 128 KB（8×8） | 0.14 MB | 0.724 ms | **192.4** | 125.7 | 7.00 ms | 20.0 |
| 512 KB（16×16） | 0.56 MB | 1.934 ms | **288.0** | 83.9 | 7.98 ms | 69.6 |
| 1.25 MB（24×24） | 1.25 MB | 4.302 ms | **291.3** | 83.0 | 10.45 ms | 119.8 |
| 5 MB（48×48） | 5.01 MB | 35.096 ms | **142.9** | 169.3 | 41.5 ms | 120.7 |

> 5 MB 档比 1.25 MB 档"慢一半"不是噪声：48×48 的通道跨距 9216 B 让 8 通道工作集
> （73.7 KB）越过线缓存（64 KB），每 tile 的 128 B 线只用一半 ⇒ 2× 放大。

### 5.2 控制变量（cin=544 固定，扫 H*W）—— 这是关键

| H*W | 通道跨距 | MB/s | 拍/字 |
|---|---|---|---|
| 256 | 1 KB | 292.7 | 82.6 |
| 576 | 2304 B | 289.3 | 83.6 |
| 1024（32²） | 4096 B | **91.4** | 264.7 |
| 1536（32×48） | 6144 B | 96.1 | 251.7 |
| 2048（32×64） | 8192 B | 90.3 | 267.8 |
| 2304（48²） | 9216 B | 142.4 | 169.8 |
| 4096（64²） | 16384 B | 89.9 | 268.9 |
| 16384（128²） | 65536 B | 94.4 | 256.2 |

**悬崖在 hw≈768 附近**：工作集 `8 × hw × 4 B` 一旦超过有效容量，带宽掉到
~1/3，并在 power-of-2 跨距（4K/8K/16K/64K）上最差。
本网 256² 的 cat 层 hw ∈ {1024, 4096, 16384} ⇒ **全部落在 90 MB/s 区间**。

### 5.3 控制变量（H*W=576 固定，扫 cin）

| cin | bytes | MB/s | 拍/字 |
|---|---|---|---|
| 64 | 0.15 MB | 365.5 | 70.0 |
| 160 | 0.37 MB | 320.1 | 66.6 |
| 288 | 0.66 MB | 285.5 | 80.7 |
| 544 | 1.25 MB | 299.0 | 80.9 |

⇒ 在缓存装得下的区间，带宽与"读多少"无关（≈300 MB/s 平台），不是规模效应。

### 5.4 多源（1.25 MB，544ch）

| 段数 | PL 时间 | MB/s | 拍/字 |
|---|---|---|---|
| 1 | 4.20 ms | 298 | 81 |
| 3 | 4.50 ms | 279 | 87 |
| 9 | 3.59 ms | 350 | 69 |
| 11 | 3.62 ms | 346 | 70 |

描述符只与**通道数**有关（每组 544 条 = 4352 B），与段数无关；多源不额外收费
（差异在 ±8% 抖动内）。描述符构建 `build_desc` 板上实测 **~1.1 ms/次**（544 通道）。

## 6. 为什么会掉到 90 MB/s（机理，不是测量问题）

- wrapper 的读线 = `RD_WIN_WORDS=16 × 8 B = 128 B`（= 32 像素），`LC_N=512` ⇒ 64 KB。
- catpack 每个通道每个 tile 只读 **64 B**（16 像素），**半条线**；另一半要等
  "同一通道的下一个 tile"才用得上 —— 而中间要跨越另外 7 个通道。
  ⇒ 8 通道工作集 `8×hw×4 B`：
  - hw ≤ 576：18 KB，装得下 ⇒ 半条线的另一半还能命中，≈300 MB/s；
  - hw ≥ 1024：≥33 KB，加上组相联/跨距别名 ⇒ 每次访问都是**依赖型 miss**
    （先描述符、再数据，下一通道的线要等当前通道 8 拍跑完才发）⇒ 单元被 CE 冻结 ~2/3，
    实测 ≈1.1 B/拍。
- 与 RTL 的"compute-bound 峰值" 672 MB/s（6.7 B/拍）差 7 倍，正是这些冻结拍。

> 这与 E1E2 的差别不是"读口速度"，而是**布局**：E1E2 读 int8 C8（8 通道交织），
> 一个 tile 只有 8×128 B=1 KB 工作集，任何 hw 都命中 ⇒ 305 MB/s 全尺寸稳定。

## 7. 与 PS 路径的对比（同一层、同一数据）

| 用例 | PS `np.concatenate` | PS `quant_pack`（C 内核） | 合计 | catpack（job 墙钟） |
|---|---|---|---|---|
| 544×24²（1.25 MB） | 4.28 ms | 9.64 ms | **13.9 ms** | **10.45 ms** |
| 544×48²（5 MB） | 17.3 ms | 37.0 ms | **53.6 ms** | **41.8 ms** |
| 3 段 544×24² | 4.17 ms | 9.55 ms | 13.8 ms | 10.5 ms |
| 9 段 544×24² | 3.97 ms | 9.61 ms | 14.1 ms | 10.0 ms |
| 544×64×64（8.9 MB） | — | — | — | 106 ms（≈84 MB/s） |

- 单看"大层"：catpack 比 `concat+pack` 快 **1.3×**（省的是 concat）。
- 但 catpack 的 job 里 **PL 只占 4.3/10.4 ms**，其余 6.1 ms 是驱动开销
  （描述符构建 1.1 + 拷贝/flush 0.5 + 9 组 MMIO/轮询 2.8 + invalidate/金丝雀 1.1）。
  层越小，这部分越致命（128 KB 档：PL 0.72 ms，job 7.0 ms）。
- f32 槽 flush（1.25 MB）：**0.15 ms**（`BIN_F32POOL` 每槽独立 CMA 的收益）。

## 8. 端到端（整网）

| 配置 | 64² | 256² |
|---|---|---|
| A 基线（今天） | 3.633 s | 15.939 s |
| B 仅 `BIN_F32POOL=1`（12 槽 / 24 槽） | **2.690 s** / 2.703 s | — |
| C `BIN_F32POOL=1 + CATPACK=1`（12 槽） | 3.074 s | 16.339 s |
| C（24 槽，池命中 227/227） | 3.072 s | — |
| sha1 A==B==C | ✅ | ✅ |

- B 的 −0.76 s 来自 **f32 池**（epilogue 不再 mmap/缺页），与 catpack 无关。
- 把池加到 24 槽（64² 下 9.4 MB）让 `hits=227/227`、catpack 真正跑了 164 组
  （8.38 MB @115.6 MB/s），**总时间仍然更差**（3.072 s）：
  - 每次 catpack 调用有 **~1.2 ms 固定开销**（`build_desc` 1.1 ms + invalidate/
    金丝雀 1.1 ms + 每组 MMIO 0.25 ms）。64² 的层只有 0.2–1 MB，PS 的 C 内核
    `quant_pack` 只要 0.3–2 ms/层 ⇒ **catpack 赢不了小层**；
  - 256² 的大层 PL 读只有 87–94 MB/s，也不比 C 内核（~130 MB/s）快。
- 只有"**大层 + concat 占比高 + hw 仍在缓存友好区**"这一窄带才有赚：
  5 MB（hw=2304）PS `concat+pack` 53.6 ms vs catpack job 41.8 ms（**1.28×**）。
  本网 256² 的 cat 层 hw ∈ {1024, 4096, 16384}，都不在这个窄带里。
  另外：惰性 cat 会**钉住**叶子所在的 f32 槽。256² 上不加上限（`CATPACK_LAZY_MB`，
  默认 6 MB）时会钉住 16.8 MB 的大张量 ⇒ 池全 miss + 反复大拼接，端到端反而
  慢 **6.7 s**（实测 22.48 s）；加上限后回到 +0.4 s。这个坑已写进代码注释。

⇒ **结论：CATPACK 保持默认关。** 开关、回落、逐字节等价都已完成并验证；
     它现在是一个"正确的工具"，但这一版 RTL 的访问模式让它没有用武之地。

## 9. 不确定项 / 没做的

1. **PL 时间用 start→done 墙钟**（本比特流 DBG 不统计 catpack）。轮询粒度 33 µs，
   小层（<1 ms）绝对误差 ~5%，大层 <1%。趋势（300→90 MB/s）远超误差。
2. 板上同时有 `nice -n 19` 的 OpenBLAS 编译（loadavg 2.5）。已用 min-of-7 与
   中位数交叉核对；PS 侧数字（concat/quant_pack）受 CPU 争用影响可能偏高 5–10%。
3. E1E2 的 305 MB/s 是在 hw=576 测的；其 C8 布局在任意 hw 都命中缓存，
   但**没有在 hw=1024+ 复测**（需要 E1E2 描述符重排，超本次范围）。
4. 整网 A/B 只做了 64²/256²，且 256² 的池受 CMA 限制（6 槽）。
   更大的池（如 12 槽 × 16.8 MB = 200 MB）在 1 GB 板上有 OOM 风险，没试。
5. 没做 RTL 修改（硬约束）。§6 的机理推论（依赖型 miss）没有 xsim/DBG 直接证据
   （DBG 不统计 catpack）；但 hw 扫描的拐点与"8×hw×4 vs 64 KB"预测一致。
6. `build_desc` 1.1 ms/次仍偏慢（544 通道），如果以后要按层用，值得再优化。

## 10. 建议（按收益排序）

1. **不要开 catpack 跑整网**（实测更慢，见 §8）。保留为"f32 源 + 小层"的专用通道。
2. **要救 72 s 的 E1E2 回归**：让 E1E2 直接读 **conv 的 int8 C8 OUT 缓冲**，
   彻底删掉 PS 的 `quantize_int8`（板端 140 ms/层）。这才是"正确架构"。
   catpack 读 f32 是 4× 的字节量，且在大 hw 上还要再吃 3× 的缓存惩罚。
3. 如果一定要用 catpack：
   - **RTL v2**：TILE 加到 32（一次读满 128 B 线）或在当前通道的 8 拍里预取下一通道的线；
     两者都能把大 hw 的 90 MB/s 拉回 300 MB/s 量级（RTL 改动，本次未做）。
   - 源改成 C8/交织的 f32 布局，工作集会小 8×。
4. 驱动侧（若启用）：把描述符/输出 arena 常驻、按层缓存描述符表、
   关掉重复的 invalidate/金丝雀，可把每 job 的 6 ms PS 开销压到 1–2 ms。
5. **f32 池本身是赚的**（64² −0.88 s），可以单独保留；但要把槽数/尺寸按
   CMA 与层尺寸重新规划（256² 目前只命中一半）。
