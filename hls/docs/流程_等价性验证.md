# 流程 —— 等价性怎么验证

> "把 Python 算法改成 C/C++ 再丢给 HLS"这件事，最大的风险不是写不出来，
> 而是**写出来了、跑起来了、结果悄悄不对**。定点化、循环重排、算子融合、
> 布局转换，每一步都可能引入一个只在特定输入下才暴露的偏差。
>
> 这份文档说明三段证据链各自证明什么、怎么跑、判据是什么。

---

## 1. 为什么要三段，而不是"跟 PyTorch 比一下"

```text
  PyTorch (nets_student.py)
      │
      │  ① tests/test_ops_numpy_vs_torch.py    逐算子、逐参数组合
      │  ① tests/test_graph_numpy_vs_torch.py  整网、真实权重
      ▼
  NumPy (ps/ops_ref.py)          ← 不依赖 torch，板上能跑
      │
      │  ② tests/run_equiv.py                  逐算子、NHWC 布局
      ▼
  C++/HLS (pl/src/*.cpp)         ← 要综合成 PL 的那一份
```

**为什么不让 C++ 直接跟 PyTorch 比**：PYNQ 上装不了 torch；而且真出偏差时，
"整网差了 3 dB" 定位不到是哪一层、哪个算子、哪个参数组合。

**为什么每段都要分"逐算子"和"整网"两个粒度**：

| 粒度 | 能发现 | 发现不了 |
|---|---|---|
| 逐算子 | 公式错、参数记错、顺序反了、边界条件 | 图的拓扑错（`cat` 顺序、漏了一条 SAM 分支、dilation 记错） |
| 整网 | 图的拓扑错、误差累积 | **定位不到是哪一条**；而且可能互相抵消 |

两个粒度都做，才有定位能力。实际发生过：`mul_channel` 的 `chunk` 用了尺度标签
0/2/4 而不是序号 0/1/2（见 `切分契约.md` K2）—— 逐算子测试一跑就点名到具体用例，
整网测试只会告诉你"差了 0.03"。

**为什么 NumPy 那一层不能省**：它是板上的兜底路径（某个算子没上 PL 时 ARM 顶上），
也是"不需要 torch 就能复现等价性"的唯一方式。省掉它，板上就没法自查。

## 2. 三段各跑什么

### ① NumPy ↔ PyTorch

```bash
.venv-hls/bin/python hls/tests/test_ops_numpy_vs_torch.py
.venv-hls/bin/python hls/tests/test_graph_numpy_vs_torch.py --size 256
```

| | 逐算子 | 整网 |
|---|---|---|
| **覆盖** | 12 类算子、39 个用例。**包含网络里没有的组合**：奇数边长、非 2 的幂缩放、偶数卷积核、stride>k | 真实照片 → 补边 → 整网 → 与 `my_model.forward()` 逐像素比；**再走一遍"补边→整网→裁回原尺寸"** |
| **判据** | 卷积 `atol = 4e-5·C_in·k²/100 + 1e-5`（fp32 累加顺序差）；其余 `1e-5` | `max|Δ| ≤ 3e-4`，同时报未 clamp / clamp 后 / 端到端三种口径 |
| **实测** | 全部通过；卷积最大 **2.5e-5** | 256×256：未 clamp `1.31e-6`（132.4 dB）；**全分辨率 1728×1280：`1.97e-6`（135.3 dB）** |
| **端到端实测** | — | 249×243 → 补边 (3,6,4,7) → 裁回：`1.55e-6`（133.4 dB） |

> **为什么还要单独测"端到端"**：`src/infer.py` 的补边是**非对称**的
> （左补 `w_pad`、右补 `w_pad + (w%2)`，三个通道还是三个不同的常数）。
> 这类 off-by-one 只影响图像最外几行像素，在整网 PSNR（132 dB）里完全看不出来。
> 所以 `test_graph_numpy_vs_torch.py` 会在整网比对之外，再跑一遍
> `pad_amounts → pad_image → 整网 → 裁回`，与 `ps/run_ref.infer_image` 逐像素比，
> 而且**故意把输入裁成 249×243 这种不整除 32 的尺寸** —— 用 256×256 的话补边量全是 0，
> 那一段就等于没测（这个坑第一次写这个测试时就踩了：端到端数字与整网数字一模一样）。

> **为什么整网要报"未 clamp"**：`src/infer.py` 最后会 `clamp(0,1)`。
> 如果只比 clamp 后的结果，网络输出在 [-0.03, 0] 和 [0, 0.03] 两种情况的差异
> 会被 clamp 抹平成 0 或放大成 0.03，看不出真实精度。
> 本项目第一次跑就是这么被骗过去的（`max|Δ|=2.97e-2`），分开报之后真相是 1.3e-6。

> **容差为什么不能更紧**：PyTorch 的 CPU 卷积走 im2col+GEMM，NumPy 这份走
> `tensordot` 逐 (kh,kw) 累加。**累加顺序不同，float32 下必然有 1e-6~1e-5 的差**。
> 公式写错的话误差是 O(1) 量级，这个容差仍然分得开。

> **别拿 `src/infer.py` 的输出当参照**：它在 CPU 上会强制走 **fp16**
> （`src/infer.py: half = a.half or device.type == 'cpu'`）。
> 拿它跟我们的 fp32 NumPy 比，端到端只有 **51 dB**（`max|Δ| = 0.0039`）——
> 这个差全部来自 fp16 与 fp32，不是实现问题。要对照就用同精度的 fp32，
> 也就是上面这条测试。

### ② C++ ↔ NumPy

```bash
make -C hls/pl csim                                   # 用 g++ 建 op_runner
.venv-hls/bin/python hls/tests/run_equiv.py --source graph  --size 256
.venv-hls/bin/python hls/tests/run_equiv.py --source random --size 256
```

它做的事：把每个用例的输入写成 `.npy`（**转成 NHWC**）→ 写一份清单 `manifest.txt`
→ 调 `pl/build/op_runner` 执行 → 读回输出、跟 NumPy 参考比。

| 参数 | 含义 |
|---|---|
| `--source graph` | 输入是**真实网络在该层的真实激活** + 真实训练权重 |
| `--source random` | 随机输入（权重仍是真的），覆盖网络里没出现的边界 |
| `--size` | 生成 graph 用例的输入边长 |

| | 结果 |
|---|---|
| 覆盖 | 12 类算子、64 条用例（按"形状签名"去重，优先挑最大的几组） |
| 判据 | `atol + rtol·max|expected|`，默认 `2e-5 + 2e-5·max` |
| 实测 256×256 | 全部通过。`conv2d` 最大 **2.4e-6**，`add`/`concat`/`mul_channel`/`pixel_*`/`channel_*` **恰好为 0** |

> `--source graph` 比随机数苛刻：随机数不会触发 ReLU 全负、不会让 ECA 的 sigmoid
> 饱和、也不会碰到某层输入恰好是零的边界。所以它是默认值。
>
> 但**随机模式不能省**：它才覆盖"网络里没出现过的形状"。两者互补。

### ③ HLS 综合能不能过

```bash
source /home/zheyang/AMD/2025.2/Vitis/settings64.sh
make -C hls csynth
```

| | 结果 |
|---|---|
| 器件 | `xc7z015-clg485-1`（AX7015B 的 XC7Z015），时钟约束 10 ns |
| 综合 | **通过**，14 秒。`vitis_hls` 可执行文件在 2025.2 已并入统一 Vitis，只能用 `vitis-run --mode hls` |
| 资源 | 34 DSP (21%) / 9258 LUT (20%) / 10518 FF (11%) / 6 BRAM_18K (3%) |
| 时序 | 估算 **136.99 MHz**（目标 100 MHz，余量充足） |

⚠️ **这不是"整网能跑"的证据**。综合的是一个**通用卷积器**（维度全是运行期标量），
所以报告里的 Latency 是 `?`。它的价值只有两条：
证明工具链能用、证明算子写法能被综合。真正的加速器架构是 M2 的事。

## 3. 一条命令跑完

```bash
make -C hls check SIZE=256        # ① + ② + 算子清单；需要 torch
make -C hls check-quick SIZE=256  # 只有 ②；任何有 g++ + NumPy 的机器都能跑
```

`check-quick` 是**板上也能跑**的那条：板上不需要 torch，装不了也不需要。

一条用例失败时怎么定位：

```bash
# 用例数据留在 hls/build/equiv/data/，文件名带 tid 和算子名
ls hls/build/equiv/data/ | grep t017
# 想看某个用例的输入长什么样
.venv-hls/bin/python -c "import numpy as np; a=np.load('hls/build/equiv/data/t017_conv2d_in0.npy'); print(a.shape, a.min(), a.max())"
# 报告（按算子汇总 + 最接近容差的用例）
cat hls/build/equiv/report.md
```

## 4. 要加一个新算子，必须同步改哪些地方

**顺序不能乱**，前一步通过再进下一步 —— 否则出错时说不清是公式错还是接口错。

| # | 改哪 | 改什么 |
|---|---|---|
| 1 | `vendor/PDNet/model/nets_student.py` | **不改**。它是上游快照，动它等于失去对照基准 |
| 2 | `ps/graph_spec.py` | 在对应模块的展开函数里 `b.add('<kind>', ...)`；形状由 builder 推导（形状不对会立刻抛） |
| 3 | `ps/ops_ref.py` | 写 NumPy 参考实现 |
| 4 | `ps/run_ref.py: DISPATCH` | 注册分派。**漏了这里 `run_ref.misses()` 会在对拍前就报出来** |
| 5 | `tests/test_ops_numpy_vs_torch.py` | 加一个跟 PyTorch 原算子比对的用例（含网络里没出现的参数组合） |
| 6 | `pl/include/demoir_ops.h` | 声明 C 接口。**注释里写清 NHWC 还是 OIHW、有没有广播、是不是屏障算子** |
| 7 | `pl/src/*.cpp` | 实现。放哪个文件按主题：搬运/卷积/缩放/逐元素 |
| 8 | `pl/tb/op_runner.cpp` | 加一个 `if (kind == "...")` 分支：读输入 → 定形状 → 调算子 → 写出 |
| 9 | `tests/run_equiv.py: MAX_CASES` | 加该算子的用例条数 |
| 10 | `tools/op_inventory.py: OWNER` | 加归属（PL 还是 PS）；不加的话清单里会显示 `?` |
| 11 | `make -C hls check` | 跑通。**三段全绿才算加完** |

> 第 2 步和第 4 步是最容易漏的：`graph_spec` 加了但 `DISPATCH` 没加，
> 报错信息会是"未实现的算子：xxx"，很明确；反过来 `DISPATCH` 加了但图里没有，
> 那个实现会永远不被执行 —— **没有人会发现**。所以 `run_equiv.py` 里
> 按图遍历用例，而不是按 `DISPATCH` 遍历。

## 5. 这套验证证明不了什么

诚实列出来，免得被误当成"已经对了"：

| 证明不了 | 为什么 | 什么时候解决 |
|---|---|---|
| **定点/量化后的正确性** | 现在全是 fp32 | M1：量化参考 + 逐层误差表 |
| **硬件上跑出来一致** | 综合报告里的 Latency 是 `?`，没有 cosim | M2：`csim` → `cosim` → 板上逐元素对照 |
| **整网拼接后的正确性** | ② 是逐算子的，没有"把 PL 的 577 个任务串起来"的对照 | M3 |
| **分块推理的边界** | `src/tiling.py` 的羽化拼接没有进这条链 | M5 |
| **性能** | 没有任何耗时/带宽的真实数字 | M4 |
