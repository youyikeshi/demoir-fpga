# 说明 —— 程序流的前后对比

> 这份文档回答一个具体问题：**这个网络原来是"一次 `model(x)`"，
> 现在拆成 PS 和 PL 两段之后，程序流和数据流到底变成了什么样。**
>
> 切分**判据**和两边的**契约**在 [`切分契约.md`](切分契约.md)；
> 本文只讲流程本身的变化。图一律纯文本，便于在终端和 `git diff` 里看。

---

## 1. 原来是什么样：一次 `model(x)`，里面是一棵递归的调用树

`src/infer.py` 里最核心的动作就是这一句（`pad_forward` 里，`src/infer.py:130`）：

```python
out = model(img_pad(x, w_pad, h_pad, w_odd, h_odd))[0]
```

**这一行调用下面是一棵 5 层深的函数调用树。** 以编码器第一级的一条支路为例：

```text
my_model.forward                      nets_student.py:26
├─ Encoder.forward                                    :86
│  ├─ F.pixel_unshuffle(x, 2)                         :87   ← 3×512×512 → 12×256×256
│  ├─ self.conv_first(x)          (nn.Sequential)     :88   ← Conv2d(12,48,5) + ReLU
│  └─ Encoder_Level.forward                           :114
│     ├─ self.rdb(x)              GhostModule         :115
│     │  └─ GhostModule.forward                       :182
│     │     ├─ for ghost_conv in self.ghost_layers:   :184   ← 3 次，通道数 Python 里累加
│     │     │  └─ GhostBlock.forward                  :165
│     │     │     ├─ primary_conv(x)   Conv2d 1×1     :166
│     │     │     ├─ cheap_operation   Conv2d 3×3 dil :167
│     │     │     └─ torch.cat([x1, x2], dim=1)       :168   ← 物化一块新内存
│     │     ├─ self.conv(t)            Conv2d 1×1     :187
│     │     └─ return t + x            ← 残差        :188
│     ├─ sam_block(out_feature)       SAM             :117
│     │  └─ SAM.forward                               :240
│     │     ├─ F.interpolate(×0.5) / (×0.25)          :242-243
│     │     ├─ 三个 GhostModule1 分支                  :245-247
│     │     ├─ F.interpolate(×2) / (×4)               :249-250
│     │     ├─ torch.cat / ECA / torch.chunk          :252-254
│     │     └─ w0*y_0 + w2*y_2 + w4*y_4               :255
│     └─ self.down(out_feature)                       :119
└─ Decoder.forward                                    :59
   ├─ preconv_3 → Decoder_Level                      :61-62
   ├─ torch.cat([y_2, feat_3], dim=1)                :64
   ├─ preconv_2 → Decoder_Level                      :65-66
   ├─ torch.cat([y_1, feat_2], dim=1)                :68
   └─ preconv_1 → Decoder_Level                      :69-70
```

这棵树有三个性质，全都跟 FPGA 不兼容：

| # | 性质 | 具体表现 | 为什么 FPGA 受不了 |
|---|---|---|---|
| O1 | **顺序是"跑出来"的，不是"写出来"的** | 通道数在 Python 里累加（`c = c + inter`，`:179`）；`for` 循环的次数取决于 `d_list`；`if self.level < 3` 决定有没有 `down`（`:118`） | PL 侧没有 Python 解释器。每个任务的地址、尺寸、参数必须在**下发之前**就是确定的数 |
| O2 | **内存是隐式的、自动回收的** | 每个 `torch.cat`（`:168/:186/:252/:64/:68`）、每次 `Conv2d`、每次 `interpolate` 都分配一块新内存；PyTorch 的 caching allocator 在引用计数归零时回收 | `pynq.allocate()` 要**一次性**把连续内存要下来；PL 只认 `device_address`，不认 Python 对象 |
| O3 | **"在哪算"是隐式的** | 算子跟着 tensor 的 `device` 走，dispatch 由框架决定 | 需要显式回答："这一步谁执行、数据从哪来、到哪去" |

**但注意 O1/O2/O3 全是"形式"上的问题，不是"数学"上的问题。**
运算本身（哪几次乘加、什么顺序的依赖）是确定的 —— 这正是后面能做等价性验证的前提。

## 2. 分离思路：把这个网络"编译"一遍

一句话：**把调用栈里的隐式顺序，编译成一份平坦的、带显式地址的任务表。**

这跟编译器做的事逐条对应，不是类比：

```text
            原始（PyTorch）              等价于编译器的             产物
  ┌────────────────────────────┐   ┌──────────────────┐   ┌──────────────────────┐
  │ 递归的 forward() 调用树     │──▶│  前端 / lowering  │──▶│ 577 条算子的 DAG     │
  │ 通道数运行时累加            │   │  展开、定型       │   │ graph_spec.py        │
  └────────────────────────────┘   └──────────────────┘   └──────────────────────┘
                                                                      │
  ┌────────────────────────────┐   ┌──────────────────┐   ┌──────────────────────┐
  │ torch 的临时张量            │──▶│  寄存器分配 /      │──▶│ 578 块缓冲，带偏移   │
  │ 引用计数自动回收            │   │  内存规划          │   │ 和生命周期           │
  └────────────────────────────┘   └──────────────────┘   │ schedule.py          │
                                                          └──────────────────────┘
                                                                      │
  ┌────────────────────────────┐   ┌──────────────────┐   ┌──────────────────────┐
  │ 解释器逐 op 派发            │──▶│  后端 / codegen   │──▶│ HLS 电路 + AXI 接口  │
  │ Python 循环                 │   │                   │   │ pl/src/*.cpp         │
  └────────────────────────────┘   └──────────────────┘   └──────────────────────┘
```

### 2.1 第一步：结构摊平 —— 递归调用 → 平坦 DAG

`hls/ps/graph_spec.py` 里的 `_Builder.add()`（`:87`）是唯一的生产口。
每个模块的展开函数（`_conv2d` / `_ghost_block` / `_sam` / `_encoder_level` …）
照着 `nets_student.py` 的嵌套顺序"走"一遍，但**不执行任何计算**，只登记：

```python
Op(name, kind, inputs, attrs, shape)
```

举三条例子里长什么样（512×512 输入，实际打印）：

```text
enc.conv_first         conv2d       in=(enc.unshuffle,)         out=(48,256,256)
  attrs={k:5, stride:1, pad:2, dilation:1, bias:True, relu:True,
         w:'encoder.conv_first.0.weight', b:'encoder.conv_first.0.bias'}

enc1.rdb.g0.merge      concat_c     in=(enc1.rdb.g0.cat, enc.conv_first)  out=(80,256,256)

dec1.sam0.attn2        mul_channel  in=(decoder.decoder_1.sam_blocks.0.fusion.sigmoid,
                                      dec1.sam0.up2)          out=(64,256,256)
  attrs={chunk:1, chunks:3}
```

三点值得注意：

* **形状是推导出来的**，不是手填的。`add()` 从输入形状按 `k/stride/pad/dilation`
  现算输出形状，不自洽就当场抛错（比如 SAM 的 1/4 分支上采样回来对不上原尺寸）。
  这是对 O1 的直接回答：**把"运行时才知道"变成"展开时就算出来"**。
* **权重键直接就是 `state_dict` 的键**（`w` / `b` 字段），所以权重导出不需要另写映射表。
* **`torch.cat` 在树上是一条独立算子**（`concat_c`）。它 MAC 为 0，但占全图
  41% 的访存 —— 保留成一条独立的算子，正是为了 M4 有机会把它融合掉。

### 2.2 第二步：内存摊平 —— 临时对象 → 带生命周期的缓冲

`hls/ps/schedule.py:161` 的 `build_plan()` 走同一张图，但做的事完全不同：
它**只做地址**，不算数值。

规则只有一条（`:186-189`）：

> 一个张量在它的**最后一个消费者**执行完之后，就可以被回收。

```python
for n in op.inputs:
    left[n] -= 1
    if left[n] == 0 and n != graph.input_name:
        pool.free(bid_of[n])          # 交还给一个线性 arena
```

分配器是"线性 arena + first-fit + 相邻空闲块合并"（`_Pool` 类）。实测：

```text
任务 577 条 / 缓冲 578 块
不复用合计       2069.08 MB
实际要分配        210.00 MB   ← 9.9× 的复用收益
权重常驻            5.90 MB
合计占 DDR        215.90 MB
```

这一步是对 O2 的直接回答：**把"引用计数自动回收"变成"一张预先算好的分配表"**。

> 生命周期那 10 行，`run_ref.py:79-91` 和 `schedule.py:168-189` 是**镜像**的两份：
> 一份回收 Python 对象，一份回收缓冲 id。这是刻意的 ——
> 它保证"张量什么时候可以复用"这条规则在两处是同一个语义，可以互相对照。
> 代价是同一段逻辑写了两次；如果再加第三个消费者，就该抽成一个
> `liveness.py` 了。

### 2.3 第三步：执行摊平 —— 递归下降 → 一个 for 循环

原来"解释器一边走调用树一边派发"，现在变成：

```python
for task in plan.tasks:          # 577 次，顺序在计划表里写死
    下发(task) ; 等待完成(task)
```

**递归没了。** 调用树早在第一步就被展平成了 `plan.tasks` 这个数组。
这就是 M2 要在 PYNQ 上写的那个循环 —— 它现在还没有，因为还没有 bitstream。

## 3. 分离之后：两个域，一条数据通路

```text
┌─────────────────────── PS（ARM Cortex-A9，跑 Python）────────────────────────┐
│                                                                             │
│  ① 读图/SD  ② RGB  ③ 补边32  ④ 量化  ⑧ 反量化  ⑨ 裁边  ⑩ 写盘  ⑪ 计时/报错   │
│                    ┌──────────────────────────────────────────┐             │
│                    │  ⑤ for task in plan.tasks:               │             │
│                    │       写 AXI-Lite 寄存器                  │             │
│                    │       ⑥ 等中断 / 轮询 ap_done             │             │
│                    └───────────────┬──────────────────────────┘             │
└────────────────────────────────────┼────────────────────────────────────────┘
                                     │  AXI4-Lite（控制）
                                     │  任务类型 + 地址 + C/H/W + k/s/p/d + scale
                                     ▼
┌──────────────────────── PL（FPGA）──────────────────────────────────────────┐
│   ⑦ demoir_conv2d_top 被拉起 → 收参数                                       │
│       │                                                                     │
│       │  AXI4 master (m_axi)  ─┬─ gmem0 读输入                              │
│       │                          ├─ gmem1 读权重                              │
│       │                          ├─ gmem2 读 bias                             │
│       │                          └─ gmem3 写输出                              │
│       ▼                                                                     │
│   置 ap_done ──────────────────────────────────────────────▶ 回到 ⑥          │
└─────────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
                    PS DDR：输入 / 权重 / 中间张量 / 输出
                    （全部由 ps/schedule.py 预先分配好偏移）
```

对照 `pl/src/demoir_top.cpp`（`:23` 是顶层函数）：`:27-30` 是四个 `m_axi`（`gmem0~3`），
`:31-44` 是 AXI-Lite（张量基址 + 所有标量参数 + `return`）。**这就是 O3 的答案**：
"在哪算"从隐式 dispatch 变成了"这 18 个寄存器里写了什么"。

## 4. 跑一个任务：完整时序

拿 `enc.conv_first` 举例（5×5、12→48、256×256、pad=2、ReLU）。

**原来（PyTorch）**，就一行：

```python
x = self.conv_first(x)      # nets_student.py:88
```

**现在**，同样一次卷积要经过：

```text
  PS 侧（Python，读 plan.tasks[N]）
  ├─ 从 task 里取出：in_buf=3, out_buf=4, k=5, stride=1, pad=2, dilation=1, relu=1
  ├─ 查缓冲表：buf[3].offset → 基址 A；buf[4].offset → 基址 B
  ├─ 查权重表：encoder.conv_first.0.weight 的 DDR 基址 W（启动时载入，常驻）
  ├─ 写 AXI-Lite 寄存器：in=A  w=W  b=Bb  out=B
  │                       C_in=12  H=256  W=256  C_out=48
  │                       k=5  stride=1  dilation=1  pad=2  relu=1
  ├─ 写 ap_start
  │
  ├─ 等 ap_done（轮询或中断）
  │        │
  │        └──▶ PL 侧：demoir_conv2d_top 被拉起
  │               ├─ 通过 gmem0 从 DDR 读 12×256×256 的输入
  │               ├─ 通过 gmem1 读 48×12×5×5 的权重、gmem2 读 48 个 bias
  │               ├─ 算 48×256×256 个输出点
  │               ├─ 通过 gmem3 写回 DDR
  │               └─ 置 ap_done
  │
  └─ 收到完成 → 下一个 task
```

**关键差别**：原来这一行的"上下文"（张量的物理地址、通道数、补边量）
全部藏在 Python 对象和框架里；现在**全部被显式地写进了寄存器**。

⚠️ 上面这段是**设计**，不是实测 —— M2 才实现，现在还没有 bitstream。
现在能跑的只有 `ps/run_ref.py`（在 ARM 上用 NumPy 算同一件事）和
`pl/tb/op_runner.cpp`（在 x86 上算同一件事并跟 NumPy 对拍）。

## 5. 数据流：一张图走过哪些形态

```text
  SD 卡 JPEG
      │  PS: PIL/cv2 解码
      ▼
  numpy (H,W,3) uint8 → float32 /255
      │  PS: pad_amounts + pad_image（三个通道三个不同的常数补边）
      ▼
  NCHW (3, 1280, 1728) float32        ← 图输入
      │  PS: to_hw()  ── 布局转换（也可以做成 PL 的一个模式）
      ▼
  NHWC (1280, 1728, 3) float32
      │
      │  ┌──────────── 这中间是 577 条任务，全部在 PL 上 ────────────┐
      │  │  每个中间张量都住在 PS DDR 的某一段偏移上，               │
      │  │  由 ps/schedule.py 预先算好；用完即被下一个任务覆盖        │
      │  └──────────────────────────────────────────────────────────┘
      ▼
  NHWC (1280, 1728, 3) float32        ← 图输出
      │  PS: from_hw()
      ▼
  NCHW (3, 1280, 1728) → clamp(0,1) → 裁回 (1279, 1706)
      │  PS: ×255 → uint8
      ▼
  结果 PNG
```

三处"形态"变化值得单独记住，因为它们各自是一个 bug 来源：

| 变化 | 在哪发生 | 踩过的坑 |
|---|---|---|
| NCHW → NHWC | `ops_ref.to_hw` / 每个 PL 算子的地址计算 | 硬件侧通道最内层才能并行；对拍时写 `.npy` 前统一转，所以布局约定本身也被测到了 |
| 补边常数 0.3827/0.4141/0.3912（**不是 0**） | `run_ref.PAD_VALUE` | 改成零填充，首尾几行就对不上 golden，且整网 PSNR 看不出来 |
| 补边量**非对称**（左 `w_pad`、右 `w_pad + w%2`） | `run_ref.pad_amounts` | 用 256×256 测的话补边量全是 0，等于没测（写测试时踩过） |

## 6. 什么变了，什么没变

**没变（这是整个方案能成立的前提）：**

* **数学**：同样的 577 次运算、同样的权重、同样的结果。所以三段等价性测试才有意义 ——
  它证明的不是"差不多"，而是 `max|Δ| = 1.3e-6`（fp32 累加顺序差）。
* **数据依赖 DAG**：拓扑序完全一样，一条边都不多不少。

**变了：**

| 维度 | 原来 | 现在 |
|---|---|---|
| 执行顺序 | Python 解释器边走调用树边决定 | `plan.tasks` 数组里写死（静态） |
| 内存 | caching allocator + 引用计数 | 预分配 578 块缓冲，偏移与生命周期在计划表里 |
| 计算 | 逐元素 Python/C 循环 | PL 上的并行乘加流水 |
| 布局 | NCHW | NHWC |
| 数值 | fp32 | fp32（M1 之后转定点，只改 `demoir_t` 一处） |
| "在哪算" | tensor.device 隐式决定 | 18 个 AXI-Lite 寄存器 |

## 7. 为什么三个模块长得几乎一样

`run_ref.execute()`、`schedule.build_plan()`、以及将来的 PS 执行循环，
**遍历的是同一张图、同一个顺序**。这不是重复劳动，是同一份 IR 的三种解释：

| 消费者 | 它对每个 op 回答的问题 | 需要什么 |
|---|---|---|
| `run_ref.execute` | "输出数值是多少？" | NumPy + 权重 |
| `schedule.build_plan` | "输入输出放在哪块 DDR？" | 只要形状 |
| PS 执行循环（M2） | "往哪几个寄存器写什么？" | 只要 `plan.tasks` |

**好处**：改一次 `graph_spec.py`，三个消费者自动跟上；形状、权重键、MAC 预算、
缓冲表、任务表全部从同一处派生，**不可能互相不一致**。

**代价**：多了一层"展开"。但这一层只在开发机/PS 上跑一次，PL 侧拿到的
已经是扁平数组了。

## 8. 这套拆法已知的简化

诚实列出来，免得被当成最终形态：

| 简化 | 现在 | 该变成什么 |
|---|---|---|
| 一次任务算一层 | `plan.tasks` 577 条，PS 发 577 次 | M4 实测 Python 调度开销后，考虑 PL 内串多层 |
| 每条任务一次 `ap_start`/`ap_done` | 严格串行，没有流水 | 乒乓缓冲让"算第 N 层"和"传第 N+1 层"重叠 |
| 中间张量都落 DDR | 朴素流量 3.95 GB | 融合（尤其那 224 条 `concat_c`）+ 行缓冲 |
| 生命周期规则写了两遍 | `run_ref.py:79-91`、`schedule.py:168-189` | 抽成 `liveness.py`（等第三个消费者出现时） |
| `concat` 是显式算子 | 物化 1.28 GB | 融合成写偏移 / 多缓冲读 |
