# 切分契约 —— PS 控制 / PL 算子怎么分、按什么分

> 这份文档回答一个问题：把 `vendor/PDNet/model/nets_student.py` 那个 PyTorch 网络
> 拆成"ARM 上跑的 Python"和"PL 上的 HLS 算子"时，**边界画在哪、两边各自要守什么约定**。
>
> 可执行的版本在 `hls/ps/graph_spec.py`（图）和 `hls/tools/op_inventory.py`
> 的 `OWNER` 表（归属）。**本文解释为什么，代码是唯一真相源**；两者不一致时以代码为准，
> 并回来改本文。

---

## 1. 先看清一件事：这个网络是**访存受限**的，不是算力受限

这是整个切分和后续优化的出发点。512×512 单张图实测：

| 量 | 值 | 来源 |
|---|---|---|
| 乘加总数 | **21.28 G MAC** | `docs/算子清单.md`，遍历图实测 |
| 朴素实现的 DDR 读 | 1.93 GB | 同上 |
| 朴素实现的 DDR 写 | 2.02 GB | 同上 |
| 张量峰值驻留 | 131 MB | 同上 |
| 权重 | 5.90 MB (fp32) / 1.48 MB (INT8) | 同上 |

拿 XC7Z015 的账面能力对一下：

```text
计算下界   21.28 GMAC ÷ (160 DSP × 137 MHz)  ≈ 0.97 s   ← 100% DSP 占用，理想情况
访存下界   3.95 GB  ÷ 1~2 GB/s（PL 经 HP 口实测经验值）≈ 2.1 ~ 4.2 s
```

**访存是计算的两到四倍。** 所以：

* 把算子做成"一个接一个、每个都把输入重读一遍、输出重写一遍"是**结构性的错误**，
  哪怕每个算子内部优化到最优；
* M4 的第一优先级不是加 DSP，而是**让中间张量不要落到 DDR**（融合、行缓冲、缓冲复用）；
* 切分时要问的第一个问题不是"这个算子好不好算"，而是
  **"值不值得为它付一次完整张量往返"**。

参考点：同一张 1706×1279 的图（补边后 1728×1280），**x86 CPU** 上
PyTorch fp32 跑 5.0 s、我们的 NumPy 参考跑 33 s。换成 AX7015B 的双核 Cortex-A9
还会再慢一个数量级 —— 这就是"必须把算子挪到 PL"的全部理由，
也是为什么板上首版只跑单图而不是视频。

> 「朴素实现 DDR 流量」是这么算的：每个算子把它的每个输入完整读一次、输出完整写一次。
> 其中 conv 的 `k²` 次窗口重读**没有**算进去（那是 M2 行缓冲要解决的）；
> 权重也按"每次重读"算，所以 5.90 MB 的权重在表里被算了 247 遍。
> 也就是说 3.95 GB 是**乐观的**下界，实际会更差。

## 2. 切分判据

### 2.1 进 PL 的三条（全部满足才进）

| # | 判据 | 反例（不进） |
|---|---|---|
| P1 | **计算密度足够**：每个输出元素要 k×k×C_in 次乘加，或每字节数据要被复用多次 | `concat`（0 次乘加）单独看不够格 |
| P2 | **局部性成立**：一个输出只依赖一个有界的输入邻域 | 全局平均池化依赖整幅图 → 但它仍有 C×HW 次加法，且**必须**进 PL，见下 |
| P3 | **调用次数够多或单次够大**：摊得平"一次任务下发 + 一次 DDR 往返"的固定成本 | 只调用一次的 3×3 卷积可以留 PS |

### 2.2 留 PS 的三条（满足任一条就留）

| # | 判据 | 例子 |
|---|---|---|
| S1 | **和像素数无关**：代价只随通道数/层数增长 | 下发任务、读寄存器、设置 DMA 地址 |
| S2 | **有全局串行依赖**：必须等整张图/整条流水完成 | 权重加载顺序、错误恢复、耗时统计 |
| S3 | **不变量多、调用少**：写一次能复用很久，或本来就只跑一次 | 权重从 SD 卡载入 DDR、图像前后处理 |

### 2.3 归属结论

**12 类算子全部进 PL，PS 侧一个算子都不留。** 这不是"能加速的都加速"的直觉结论，
而是上面判据跑出来的：

| 算子 | 条数 | MAC | 判据 | 为什么必须进 PL |
|---|---:|---:|---|---|
| `conv2d` | 247 | 21.07 G (99.05%) | P1 P2 P3 | 唯一真正吃算力的 |
| `resize_bilinear` | 26 | 92.1 M | P1 P2 | 每输出 3 次乘加；26 次调用，摊得平固定成本 |
| `add` | 24 | 44.0 M | P3 | 单条太便宜，但**24 条 × 每次几百 MB 往返**，留 PS 就是 336 MB 的纯搬运 |
| `global_avg_pool` | 6 | 33.0 M | **P2 反面** | 依赖整幅图 —— 但它的输入必须有地方产生；留 PS 意味着把 126 MB 特征搬回 ARM 再算 33 M 次加法 |
| `mul_channel` | 18 | 33.0 M | P3 | 同上，126 MB |
| `conv1d_c` | 12 | 28.5 K | P3 | 只在 (1,1,C) 上算，数据量极小，但和 ECA 一起做能省 6 次同步 |
| `sigmoid` | 6 | 1.6 K | P3 | 同上 |
| `concat_c` | **224** | **0** | P1 反面 | **MAC 是 0，却占 361 MB 读 + 1.28 GB 写 —— 全图最大的访存来源。** 它进 PL 的理由不是"要算"，而是"要能改地址"：见 §2.4 |
| `channel_shuffle/unshuffle` | 12 | 0 | P3 | 纯置换，留在 PL 可以和 ECA 合成一次调用 |
| `pixel_unshuffle/shuffle` | 2 | 0 | P2 | 纯搬运，PL 上就是改地址；PS 做要 3 MB 往返 |

### 2.4 `concat` 这个反直觉的结论值得单独说

它是这张表里唯一"MAC 为 0 却必须进 PL"的算子，而且**它才是 M4 最大的优化目标**：

* 224 条 `concat`，读 361 MB、写 1.28 GB —— 占了整网访存的 **41%**；
* 在 PyTorch 里它是 `torch.cat`，必须物化一块新内存；
* 在硬件上它**可以完全消失**：把输出写成"基址 + 通道偏移"，或者让下游的卷积
  从两段不连续的地址读。都是地址计算，零搬运。

所以正确表述是：**`concat` 进 PL 不是为了加速它，而是为了有机会消灭它。**
首版仍然实现成显式算子（`pl/src/rearrange.cpp: demoir_concat_c`），
把等价性钉死；融合留到 M4，并且融合时 `concat` 的语义已经有一份可对照的实现。

## 3. 张量契约

### 3.1 布局：硬件侧一律 NHWC

```text
PyTorch / NumPy (NCHW)          硬件 (NHWC)
  (C, H, W)          ──to_hw()──▶   (H, W, C)
  (C, H, W)          ◀─from_hw()─   (H, W, C)
```

理由三条，按重要性排：

1. **通道并行 = 最内层向量化**。HLS 里要同时开 D_k 个乘法器，最自然的写法是
   内层循环遍历通道。NCHW 下这个循环的步长是 H×W，没法向量化。
2. **`m_axi` 突发连续**。NHWC 里同一行的相邻像素地址连续，一次突发能取回
   多个像素的同一批通道。
3. **`concat` 退化成写偏移**（§2.4）。NCHW 下拼接是"大块 memcpy"，
   NHWC 下也还是 memcpy，但**下游按偏移读**就完全不用搬。

转换本身在 `ps/ops_ref.py: to_hw/from_hw`，对拍时显式调用，所以"布局约定"这一步
也被等价性测试覆盖了（`tests/run_equiv.py` 写 .npy 前统一 `to_hw`）。

### 3.2 数据类型：`demoir_t` 一个 typedef

```c
typedef float demoir_t;     /* pl/include/demoir_ops.h */
```

现在 = float。**M1 量化时只改这一处**，所有算子自动跟着变。
定点的累加器位宽要单独看：`global_avg_pool` 要在 HW 最大 65536 个值上累加，
float 尚可，int8 直接溢出 —— 这类"累加器深度"是量化时必须逐算子核的。

### 3.3 权重：保持 PyTorch 的 OIHW

`w[((co*C_in + ci)*k + kh)*k + kw]`，不做重排。理由：权重导出（`tools/export_weights.py`）
就不需要再写一份布局映射，少一处会不一致的地方。硬件上的分块排布（按并行通道宽度切）
是 M2 打包阶段的事，那时再引入一个显式的"权重打包器"，**不要**让算子同时支持两种布局。

### 3.4 形状与边界

* 输入必须是 **32 的倍数**（补边后）。`graph_spec.build_graph` 会直接拒绝其它尺寸 ——
  32 来自：encoder 三级下采样 ×8，decoder 的 pixel_shuffle ×2，SAM 的 ×4 分支，
  合起来最小公倍数是 32。
* 补边常数是 **0.3827 / 0.4141 / 0.3912**（RGB 三个通道各一个值），
  来自 FHDMi 训练集均值。**不是零填充、不是镜像填充**，
  改了就跟 golden 对不上（`ps/run_ref.py: PAD_VALUE`）。
* 补边量是**非对称**的：`w_pad` 在左、`w_odd` 在右，且 `w_odd = w_pad + (w%2)`。
  见 `src/infer.py: pad_forward` 与 `ps/run_ref.py: pad_amounts`。

## 4. 任务接口契约

每个 PL 任务至少带这些字段（首版还没全实现，但接口要按这个留）：

| 字段 | 谁填 | 说明 |
|---|---|---|
| 操作类型 | PS | 对应哪个算子（`pl/include/demoir_ops.h` 里的函数） |
| 输入/输出/权重地址 | PS | `pynq.allocate()` 拿到的 `device_address`，**不是 Python 对象的 `id()`** |
| 形状 C/H/W | PS | 逻辑形状；硬件按 NHWC 解释 |
| 卷积参数 | PS | k / stride / dilation / pad / 是否 ReLU |
| 量化比例 | M1 之后 | 每层的输入/权重/输出 scale（首版为 1.0） |
| 激活/超时 | PS | 完成中断或轮询，以及超时阈值 |

**统一走 `m_axi` 直访 DDR + `s_axilite` 收参数**，首版不用 AXI DMA、不用 AXI-Stream。
理由：先用一个可复用 IP 跑通逐层计算，DMA/Stream 是"实测表明流式更合适时"才引入的优化。
参考 `pl/src/demoir_top.cpp`（目前只有一个 `demoir_conv2d_top`）。

这张表里的"地址"怎么变成 PL 能用的东西、AXI 互连由谁建、PYNQ 在这一环做什么，
以及从这些源码到能上板还差哪几步，见 [`说明_从HLS到上板.md`](说明_从HLS到上板.md)。

## 5. 缓冲与生命周期

这张契约有**两份可执行版本**：

* `ps/run_ref.py: execute()` —— 引用计数释放，用来验证算法；
* `ps/schedule.py` —— **板上真正要用的那份**：静态任务表 + DDR 缓冲分配表。

`python3 ps/schedule.py --size 512` 的实测结果：

```text
任务 577 条 / 缓冲 578 块
峰值同时存活      131.00 MB   ← 理论下界（假设可完美装箱）
不复用合计       2069.08 MB
实际要分配        210.00 MB   ← 9.9× 的复用收益
权重常驻            5.90 MB
合计占 DDR        215.90 MB   ← 1 GB DDR 装得下（fp32！INT8 后约 60 MB）
```

注意 210 MB 与 131 MB 的差：**理论下界假设内存可以完美装箱搬移，实际不行**。
线性 arena + first-fit 的 210 MB 才是"打几个 `pynq.allocate()`"的真实数字。

```text
DDR 里同时活着的张量，由"还有几个消费者没跑"决定：

  enc1 ─────────────────────────────┐   ← 跳连：要留到 dec1 才用
  enc2 ──────────────┐              │
  enc3 ──▶ dec3 ──▶ feat_3 ─┐       │
                    dec2 ──▶ feat_2 ┴──▶ dec1 ──▶ out
                                          ▲
  张量峰值驻留 131 MB（512×512）——————─┘
```

三条硬约束：

1. **不是两个 ping-pong 缓冲就能了事。** 编码器三级跳连、SAM 的三条尺度分支、
   ECA 加权前的 `y_0/y_2/y_4` 都必须同时活着。峰值是 131 MB（fp32）/ 33 MB（INT8 后）。
2. **屏障算子会打断流水。** `global_avg_pool` 必须等整幅特征写完才能出结果，
   所以"整网无停顿流水"的假设在这里失效。整网流水线要在 ECA 处分段 ——
   这也是 `SAM` 里最不该被忽略的结构特征。
3. **只有确认某个张量后续不再使用，才能复用它的内存。** 首版直接按
   `left[n] == 0` 释放；`ps/schedule.py` 把它变成了显式的静态分配表。

## 6. 与 PyTorch 刻意不同的三处（都必须先证明等价）

| # | 差异 | 为什么 | 影响 |
|---|---|---|---|
| D1 | `conv2d` 把紧随的 ReLU 吃掉（`relu=True`） | 原网络里**所有** conv 后面都紧跟 `nn.ReLU(inplace=True)`，融合是恒等变换，省一次 DDR 往返 | MAC 不变；写流量省掉一遍 conv 输出 |
| D2 | 剪掉 `out_2`/`out_3` 的图像输出头 | 最终只用 `out_1`；但 `dec2`/`dec3` **decoder 主体仍要保留**，因为 `feat_2`/`feat_3` 是下一级的输入 | 去掉 2 个 3×3(64→12) 卷积 + 2 个 `pixel_shuffle`：21.4166 G → **21.2751 G MAC**，少物化 2 张 RGB 图 |
| D3 | `concat_c` / `channel_shuffle` 等在图上仍是独立算子 | 为了逐算子对拍能定位；融合是 M4 的优化，不是现在的正确性目标 | 访存表里那 1.28 GB 就来自这里 |

D1/D2 由 `ps/graph_spec.py` 实现，D3 是显式的取舍。
**三处都通过了整网对照**（`max|Δ| = 1.3e-6`），所以在数值上没有引入偏差 ——
这正是为什么差异必须写在这里，而不是散在代码注释里。

## 7. 实测踩到的坑（都是真的差过，不是"可能的"风险）

| # | 坑 | 症状 | 处理 |
|---|---|---|---|
| K1 | **双线性缩放的步长是 `1/scale_factor`，不是 `in/out`** | 奇数尺寸下采样（如 67→33）误差 0.37，肉眼可见 | `ops_ref._bilinear_taps` 照抄 ATen 顺序；`_bilinear_taps` 的 docstring 里写明 |
| K2 | `mul_channel` 的 `chunk` 是**段序号 0/1/2**，不是尺度标签 0/2/4 | chunk=2 时切到空数组，`(0,1,1)` 广播失败 | `graph_spec._sam` 用 `enumerate`；C++ 侧 `chunk` 作参数传，切片 = 指针偏移 |
| K3 | `channel_shuffle` 是"先 view(g,cpg) 再 transpose"，**不是**先 view(cpg,g) | 形状对、数值错，而且只在 H>1 时暴露 | `ops_ref.channel_shuffle` 的 reshape 顺序 + `tests` 里补了 4D 用例 |
| K4 | ECA 里 **`conv2` 先作用**（名字与执行顺序相反） | 按名字顺序实现会得到完全不同的权重对 | `pl/src/channel_ops.cpp: demoir_eca_fused` 的参数名直接叫 `w_conv2`/`w_conv1`，注释里点名 |
| K5 | `GhostBlock` 的 `out[:, :oup]` 切片**恰好是恒等**（`ceil(oup/2)*2 == oup`） | 现在无所谓，改 `ratio` 或让 `inter` 变奇数就静默错 | `graph_spec._ghost_block` 里直接断言，不满足就抛 |
| K6 | 补边常数是三个不同的值，不是 0 | 首尾几行像素对不上 golden | `ps/run_ref.py: PAD_VALUE` + 文件头说明 |

> K1 在当前网络里**恰好不触发**（全是 32 的倍数 + 2 的幂缩放，两种约定重合）。
> 它是在"故意用奇数尺寸"的测试里被揪出来的。K3/K5 也一样。
> 这三条说明：**只测真实网络是不够的**，`tests/test_ops_numpy_vs_torch.py`
> 里那些"网络里没出现过的组合"才是真正值钱的部分。
